SECTION 1 — EXECUTIVE SUMMARY
================================================================================

This document is the complete frontend engineering blueprint for VoiceGuard.
It converts the approved UX specification (Batch 02) into a scalable,
maintainable frontend architecture that a senior engineering team can
implement immediately without architectural clarification.

Batch 01 defined WHAT the product does and WHY.
Batch 02 defined HOW it looks and HOW users interact with it.
Batch 03 defines HOW the frontend is engineered.

SCOPE
─────
  • Complete project folder structure with module boundaries
  • Routing architecture for all 22 screens with guards and lazy loading
  • Component architecture — every component, its props contract, and
    its relationship to parent/child components
  • State management strategy — global, feature, and local state
  • Data flow diagrams for every major user action
  • API integration layer — request, response, caching, retry
  • Theme architecture — token system, dark/light switching, persistence
  • Performance strategy — code splitting, memoization, virtualization
  • Accessibility architecture — focus management, ARIA, keyboard nav
  • Error handling strategy — boundaries, recovery, crash reporting
  • Engineering standards — naming, testing, documentation, imports
  • Self-audit with resolved issues
  • Risks and mitigations

SECTION 2 — FRONTEND VISION
================================================================================

GUIDING STATEMENT
─────────────────
The VoiceGuard frontend must feel like a product built at Stripe or Linear —
not because of visual polish alone, but because every interaction is deliberate,
every state is handled, every edge case is accounted for, and the code
architecture supports rapid, confident iteration for years to come.

TECHNOLOGY STACK RATIONALE
───────────────────────────

Framework: React (with Next.js App Router)
  Why: Server-side rendering for S01 (landing) and S20 (shared result) — both
  are public, SEO-relevant pages that benefit from SSR. The App Router's
  layouts, loading.tsx, and error.tsx conventions map directly to this
  architecture's layout and error boundary strategy.

Styling: CSS Custom Properties (design tokens) + CSS Modules
  Why: Batch 02 mandates a design token system implemented as CSS custom
  properties. CSS Modules provide component-level scoping without a
  runtime CSS-in-JS performance penalty. This combination gives:
    — Zero-cost dark/light theme switching (swap the token values at :root)
    — No style injection overhead at runtime
    — Full tree-shaking (dead styles are never shipped)

State: Zustand (global) + React Query (server state) + React Hook Form (forms)
  Why: Zustand for lightweight global UI state (auth, theme, notifications,
  upload state). React Query for all server-fetched data (scan history,
  user profile) — it handles caching, deduplication, background refetch,
  and optimistic updates natively. React Hook Form for all forms — no
  re-renders on every keystroke, built-in validation, integrates with Zod.

Routing: Next.js App Router
  Why: File-system routing maps cleanly to the 22-screen sitemap. Parallel
  routes handle the scan processing overlay. Route groups separate public
  from authenticated layouts.

ARCHITECTURE PRINCIPLES
────────────────────────

  P1 — Feature-first, not file-type-first
     Code is organized by product feature (auth, detection, history),
     not by type (components/, hooks/, utils/). This ensures the entire
     code for a feature lives together and can be deleted or extracted
     as a unit.

  P2 — Every module has an explicit public API
     Each feature module exports only what other modules need. Internal
     components, hooks, and utilities are not exported from the module
     barrel. Cross-module coupling is always explicit and reviewable.

  P3 — Design tokens are infrastructure, not styling
     The token system is established before the first component is written.
     All values flow from tokens to components. No raw values in component
     files.

  P4 — Components are stateless by default
     A component receives data via props and fires events via callbacks.
     It does not own server state. Server state lives in React Query.
     UI state that is local lives in useState. Global UI state lives in
     Zustand. This distinction is enforced at the architectural level.

  P5 — Performance is designed, not optimized after the fact
     Code splitting, lazy loading, skeleton loaders, and memoization
     strategies are defined here, not discovered during a post-launch
     performance audit.

  P6 — The shell renders first
     The AppShell (top bar + sidebar) is always server-rendered and
     visible within 500ms. Content areas load independently. Users
     never see a full-page blank state.

  P7 — Every error has a recovery path
     Error boundaries exist at module level. Every API failure has a
     defined fallback UI. No component renders into an unhandled error
     state.

  P8 — Accessibility is structural, not cosmetic
     Focus management, ARIA roles, keyboard navigation, and
     reduced-motion preferences are implemented in the component
     architecture, not added after QA feedback.

SECTION 4 — MODULE ARCHITECTURE
================================================================================

Each module is a self-contained vertical slice of the application. A module
owns its routes, components, hooks, API calls, and local state. Modules
communicate only through their public index.ts API — never through direct
internal imports.

MODULE DEPENDENCY RULES
────────────────────────
  ALLOWED:    module → shared/components
  ALLOWED:    module → shared/hooks
  ALLOWED:    module → shared/utils
  ALLOWED:    module → config/*
  ALLOWED:    module → types/*
  FORBIDDEN:  module → another module's internal files
  FORBIDDEN:  shared/ → any module (shared never imports from features)

If module A needs a component from module B, that component belongs in
shared/components, not in module B's internal directory.

SECTION 5 — ROUTING ARCHITECTURE
================================================================================

ROUTING STRATEGY
─────────────────
Next.js App Router. Route groups create layout boundaries without
affecting URL paths. All routes with authentication requirements
use a guard component (AuthGuard, GuestGuard) rendered at layout level.

URL CONVENTIONS
────────────────
  - Lowercase, hyphen-separated slugs
  - No trailing slashes
  - Dynamic segments: [paramName]
  - No query params in URLs for navigation state (use Zustand for filter state)
  - Exception: /scan/[scanId] where scanId is a UUID for direct deep links

COMPLETE ROUTE TABLE
─────────────────────

  Screen  URL                          Auth     Layout        Guard
  ──────────────────────────────────────────────────────────────────────────────
  S01     /                            none     PublicLayout   none
  S02     /signup                      guest    PublicLayout   GuestGuard
  S03     /login                       guest    PublicLayout   GuestGuard
  S04     /verify-email                partial  MinimalLayout  none
  S05     /forgot-password             guest    PublicLayout   GuestGuard
  S06     /onboarding                  auth     MinimalLayout  AuthGuard +
                                                               OnboardingGuard
  S07     /dashboard                   auth     AppShell       AuthGuard
  S08     /scan/new                    semi     AppShell       SemiAuthGuard
  S09     /scan/processing             auth     AppShell       AuthGuard
  S10     /scan/[scanId]               semi     AppShell       SemiAuthGuard
  S11     /history                     auth     AppShell       AuthGuard
  S12     /history/[scanId]            auth     AppShell       AuthGuard
  S13     /notifications               auth     AppShell       AuthGuard
  S14     /help                        none     AppShell       none
  S15     /help/[articleSlug]          none     AppShell       none
  S16     /feedback                    auth     AppShell       AuthGuard
  S17     /settings/profile            auth     AppShell       AuthGuard
  S18     /settings/account            auth     AppShell       AuthGuard
  S19     /settings/appearance         auth     AppShell       AuthGuard
  S20     /r/[scanId]                  none     PublicLayout   none (SSR)
  S21     * (not-found.tsx)            none     MinimalLayout  none
  S22     error.tsx                    none     MinimalLayout  none

GUARD DEFINITIONS
──────────────────

  AuthGuard
    Behavior: If user is not authenticated, redirect to /login
              with returnUrl param: /login?return=/dashboard
    Position: Rendered inside (app)/layout.tsx — applies to ALL app routes
    Exception: /help routes skip AuthGuard (public content)

  GuestGuard
    Behavior: If user IS authenticated, redirect to /dashboard
              (prevents logged-in user from seeing /login or /signup)
    Position: Rendered inside specific page components where applicable

  SemiAuthGuard (New Scan / Scan Result)
    Behavior: Allows guest sessions. Initializes guest session token if
              no auth token is present. Does NOT redirect to login.
              Tracks scan in anonymous session for later migration.
    Position: /scan/new and /scan/[scanId] page.tsx components

  OnboardingGuard
    Behavior: After auth, if hasCompletedOnboarding === false, redirect
              to /onboarding before allowing access to /dashboard
    Chain:    AuthGuard runs first, then OnboardingGuard
    Exception: After completing onboarding, redirect to /dashboard and
               set hasCompletedOnboarding = true in user record

REDIRECT FLOWS
───────────────

  Unauthenticated user accesses /dashboard:
    → AuthGuard triggers
    → Redirect: /login?return=%2Fdashboard
    → After login: /dashboard (consuming return param)

  Authenticated user accesses /login:
    → GuestGuard triggers
    → Redirect: /dashboard

  New user (post-verification), no onboarding:
    → AuthGuard: passes
    → OnboardingGuard: hasCompletedOnboarding === false
    → Redirect: /onboarding
    → After onboarding: /dashboard

  Guest user submits scan:
    → SemiAuthGuard: creates guest session
    → /scan/new → /scan/processing → /scan/[scanId]
    → Post-result CTA: "Save result" → /signup?migrateScan=[scanId]
    → After sign-up: scan migrated, redirect to /dashboard

  404 catch-all:
    → app/not-found.tsx renders S21
    → Expired shared link (/r/[scanId] returns 404 from API):
      → Renders expired-link state within S20 page, not redirecting to 404

BREADCRUMB ROUTING
───────────────────
Breadcrumbs are data-driven, not URL-parsed. Each page defines its
own breadcrumb trail by exporting a generateMetadata function and
a useBreadcrumbs hook that returns the trail for that page.

  S12 /history/[scanId]:
    Trail: [{ label: "Dashboard", href: "/dashboard" },
            { label: "History",   href: "/history" },
            { label: filename,    href: null }]  ← last item is not a link

  S15 /help/[articleSlug]:
    Trail: [{ label: "Dashboard", href: "/dashboard" },
            { label: "Help",      href: "/help" },
            { label: article.title, href: null }]

  S19 /settings/appearance:
    Trail: [{ label: "Settings", href: "/settings/account" },
            { label: "Appearance", href: null }]

LAZY LOADING STRATEGY
──────────────────────
All (app)/ routes are lazy-loaded. The (public)/ routes that are
accessed before any code splitting (S01 landing, S20 shared result)
are statically rendered and ship minimal JS.

  Eagerly loaded (in initial bundle):
    - ThemeProvider
    - QueryProvider
    - ToastProvider
    - AuthProvider
    - AppShell shell (TopBar, Sidebar, BottomTabBar)
    - shared/ui/Button, Card, Spinner (used everywhere)

  Lazy loaded (per-route):
    - Every module's page-level components
    - GradCAMPanel (large component, only on S10/S12/S20)
    - AudioPreviewPlayer (depends on Web Audio API)
    - MicrophoneRecorder (depends on MediaRecorder API)
    - ActivityChart (depends on charting library)
    - DateRangePicker (large component, only on S11)
    - PDFExport utilities (only triggered on button click)
    - MicrophoneRecorder is also dynamically imported with ssr: false
      (Web API not available in SSR context)

CODE SPLITTING BOUNDARIES
───────────────────────────

  Bundle 1 — Critical (always loaded):
    Providers, AppShell, design system tokens, shared UI primitives
    Target size: < 80KB gzipped

  Bundle 2 — Landing (S01):
    PublicNavbar, PublicFooter, landing page sections
    Target size: < 60KB gzipped

  Bundle 3 — Auth bundle (S02, S03, S04, S05):
    All auth module components and forms
    Shared between these routes, not split further
    Target size: < 40KB gzipped

  Bundle 4 — Detection bundle (S08, S09, S10):
    FileDropzone, MicrophoneRecorder, ProcessingCard, VerdictCard,
    ConfidenceBar, GradCAMPanel, LimitationsCard
    Target size: < 100KB gzipped (Grad-CAM panel is complex)

  Bundle 5 — History bundle (S11, S12):
    ScanTable, FilterBar, DateRangePicker, pagination
    Target size: < 50KB gzipped

  Bundle 6 — Settings bundle (S17, S18, S19):
    All settings forms and components
    Target size: < 40KB gzipped

  Bundle 7 — Help bundle (S14, S15):
    Markdown renderer, TOC, search
    Target size: < 60KB gzipped (includes markdown parser)

  Charting library:
    Loaded only when ActivityChart is rendered (S07 Dashboard, after 5+ scans)
    Must not be included in Bundle 1

ROUTE TRANSITIONS
──────────────────
All route transitions use Next.js's built-in navigation with:
  - Loading states: loading.tsx files at each route segment level
  - Stale-while-revalidate: React Query serves cached data instantly,
    refetches in background
  - Optimistic navigation: For S08→S09→S10, state is pre-loaded into
    detectionStore before navigation, so S10 renders immediately

SECTION 7 — COMPONENT ARCHITECTURE
================================================================================

Components are organized into three tiers:
  Tier 1 — Primitives:   Atomic design system elements (Button, Card, Badge)
  Tier 2 — Composites:   Combinations of primitives (FormField, ScanRow)
  Tier 3 — Features:     Full feature blocks (VerdictCard, GradCAMPanel)

PROP CONTRACT CONVENTIONS
──────────────────────────
  - Required props have no default
  - Optional props use ? and document their default in comments
  - Event handlers are named onEventName (not handleEventName)
  - Boolean props default to false; never required to be false
  - variant, size, and state are string literal unions, not booleans
  - Children follow the ReactNode pattern for composable components
  - Components never read directly from any store — they receive data via props
    (exception: layout components like TopBar read global store values)

TIER 1 — PRIMITIVE COMPONENTS
───────────────────────────────

BUTTON
  Props:
    variant:   'primary' | 'secondary' | 'ghost' | 'danger' | 'accent'
    size:      'sm' | 'md' | 'lg'
    loading?:  boolean (replaces label with spinner + loading text)
    loadingText?: string (shown during loading state; defaults to label + "...")
    disabled?: boolean
    leftIcon?: ReactNode
    rightIcon?: ReactNode
    fullWidth?: boolean
    type?:     'button' | 'submit' | 'reset'
    onClick?:  () => void
    children:  ReactNode

  States: default | hover | active/pressed | focused | disabled | loading
  Accessibility:
    - aria-disabled on disabled state (not HTML disabled — allows focus)
    - aria-busy on loading state
    - role="button" if rendered as non-button element (avoid this)
    - Minimum 44x44px touch target on mobile

CARD
  Props:
    variant?: 'default' | 'elevated' | 'interactive' | 'verdict' | 'danger'
    padding?:  'none' | 'sm' | 'md' | 'lg'
    as?:       'div' | 'article' | 'section'
    onClick?:  () => void  (makes card interactive if provided)
    children:  ReactNode
  Note: Verdict variant is never used directly — VerdictCard uses it
        internally with the appropriate verdict-specific styling

BADGE
  Props:
    variant: 'human' | 'ai' | 'uncertain' | 'info' | 'new' | 'default'
    size?:   'sm' | 'md'
    children: ReactNode
  Rendering: Always pill-shaped (radius-full). Color is semantic,
             mapped from variant using design tokens.

MODAL
  Props:
    isOpen:         boolean
    onClose:        () => void
    title:          string
    description?:   string
    size?:          'sm' | 'md' | 'lg'
    hideCloseButton?: boolean
    children:       ReactNode
    footer?:        ReactNode
  Behavior:
    - Renders via portal into document.body
    - Traps focus within modal while open (useFocusTrap)
    - Returns focus to trigger element on close
    - Closes on Escape key
    - Overlay click closes (unless closeOnOverlayClick=false)
    - Body scroll locked while open (useScrollLock)
    - aria-modal="true", role="dialog", aria-labelledby=title id

CONFIRM DIALOG
  Extends Modal with opinionated structure for destructive confirmations.
  Props:
    isOpen:         boolean
    onClose:        () => void
    onConfirm:      () => void | Promise<void>
    title:          string
    description:    string
    confirmLabel?:  string  (default: "Confirm")
    cancelLabel?:   string  (default: "Cancel")
    variant?:       'default' | 'danger'
    isLoading?:     boolean
    confirmationText?: string  (if provided, renders a text input that must
                               match this string before confirm button enables)
  Used by: Delete scan, Delete account, Cancel processing

TOAST
  Props:
    id:       string           (generated by ToastStack)
    variant:  'success' | 'error' | 'info' | 'warning'
    title:    string
    message?: string
    action?:  { label: string; onClick: () => void }  ← for "Undo" actions
    duration?: number  (ms before auto-dismiss; default 4000; 0 = no auto-dismiss)
  Behavior:
    - Slides in from right (desktop) or bottom (mobile)
    - Auto-dismisses after duration
    - Hover pauses auto-dismiss timer
    - Manual dismiss via × button
    - aria-live="assertive" for errors; "polite" for success/info

SKELETON LOADER
  Props:
    variant: 'text' | 'rect' | 'circle' | 'row' | 'card'
    width?:  number | string
    height?: number | string
    count?:  number  (renders N instances for row lists)
  Behavior: Animated shimmer (left-to-right sweep)
            Respects prefers-reduced-motion (shimmer disabled, static color)

TIER 2 — COMPOSITE COMPONENTS
───────────────────────────────

FORM FIELD
  Props:
    label:        string
    name:         string           (maps to form control)
    error?:       string           (inline error below input)
    hint?:        string           (helper text below input)
    required?:    boolean
    children:     ReactNode        (Input, Select, etc.)
  Renders: label (uppercase, 11px) → children → hint/error
  Accessibility:
    - label htmlFor={name}
    - error div has id={name}-error, linked via aria-describedby on child input
    - required: aria-required="true" on input

SCAN ROW (History table row)
  Props:
    scan:      ScanSummary         (see types/models.ts)
    selected?: boolean
    onSelect?: (id: string) => void
    onView:    (id: string) => void
    onDelete:  (id: string) => void
    onCopyLink?: (id: string) => void
  Variants:
    Table row (desktop): checkbox | icon | filename | verdict badge |
                         confidence % | duration | date | actions menu
    Card (mobile): filename + verdict badge | confidence | date | chevron
  States: default | hover | selected | focused

STAT CARD (Dashboard stats)
  Props:
    label:     string           ← "Total Scans", "Human Detected"
    value:     number | string
    delta?:    number           ← change from last period (+ or -)
    icon?:     ReactNode
    color?:    'default' | 'success' | 'alert' | 'warning' | 'accent'
  Animation: value count-up on first render (1200ms ease-out)
             Respects prefers-reduced-motion (shows final value immediately)

BREADCRUMB TRAIL
  Props:
    items: Array<{ label: string; href: string | null }>
  Rendering:
    [Item1 label] / [Item2 label] / Current (no link)
    Last item: not a link, aria-current="page"
    Truncation: middle items truncated with ellipsis on mobile

PROGRESS STEPS
  Props:
    steps:        Array<{ label: string; description?: string }>
    currentStep:  number            (0-indexed)
    completedSteps: number[]
    variant?:     'horizontal' | 'vertical'
  Used in: S04 Email Verification, S06 Onboarding, S09 Processing

TIER 3 — FEATURE COMPONENTS
─────────────────────────────

VERDICT CARD
  Props:
    verdict:     'bonafide' | 'spoof' | 'uncertain'
    confidence:  number               (0–1, e.g., 0.973)
    summary:     string               (plain-language explanation)
    isLoading?:  boolean              (skeleton mode)
    animated?:   boolean              (confidence bar animates on mount; default true)
  Internal structure:
    - VerdictIcon (shield-check / shield-x / shield-question, 40px)
    - VerdictLabel ("HUMAN VOICE" / "AI-GENERATED VOICE" / "UNCERTAIN")
    - ConfidenceDisplay (confidence % in mono-lg font)
    - ConfidenceBar (animated fill)
    - VerdictSummary (plain-language text)

    bonafide  → success token set (border, background, text)

SECTION 8 — STATE MANAGEMENT ARCHITECTURE
================================================================================

STATE TAXONOMY
───────────────
  Server State:    Data that lives on the server and is fetched
                   (scan history, user profile, notifications, help articles)
                   Owner: React Query
                   Never duplicated in Zustand

  Global UI State: Application-wide UI decisions that persist across routes
                   (auth session, theme, notification count, upload state)
                   Owner: Zustand stores

  Feature State:   State that lives for the duration of a feature flow
                   (current scan being processed, history filters)
                   Owner: Zustand feature slices or React Query (if server-backed)

  Local State:     State that lives in a single component or its children
                   (form input values, modal open/closed, hover state)
                   Owner: useState or React Hook Form

ZUSTAND STORES — COMPLETE DEFINITION
──────────────────────────────────────

Cache Times:
  user profile:         5 minutes stale, 10 minutes cache

  scan detail:          5 minutes stale, 10 minutes cache

  dashboard stats:      2 minutes stale, 5 minutes cache
  notifications:        30 seconds stale, 2 minutes cache

Optimistic Updates (React Query mutation + historyStore):
  Delete scan:
    1. Add ID to historyStore.pendingDeleteIds (immediately hidden from UI)

SECTION 10 — API INTEGRATION STRATEGY
================================================================================

This section defines the API layer architecture. It does NOT implement
specific endpoints — those are defined in Batch 01.

API LAYER STRUCTURE
────────────────────

  src/modules/[module]/api/[module]Api.ts
    ↓ calls
  src/shared/utils/apiClient.ts          ← Single HTTP client instance
    ↓ built on
  fetch (native) OR axios                ← Recommendation: native fetch
                                            (no bundle overhead; adequate features)

API CLIENT (shared/utils/apiClient.ts)
  Responsibilities:
    - Base URL injection from config/api.ts
    - Auth token injection (reads from session cookie automatically — HttpOnly,
      so no manual header injection needed for same-origin requests)
    - Content-Type: application/json for all JSON requests
    - Content-Type: multipart/form-data for file uploads (omit to auto-set boundary)
    - Response parsing (JSON.parse all responses)
    - HTTP status code mapping to typed error objects
    - Request timeout (default: 30s; scan endpoint: 120s)
    - Request cancellation (AbortController, passed down for component unmounts)

REQUEST LAYER
──────────────
Each module's api/*.ts file contains functions that:
  1. Accept typed request parameters
  2. Call apiClient with the correct endpoint, method, and body
  3. Return typed response objects
  4. Never handle errors — errors propagate as thrown exceptions to React Query

Function signature convention:
  [verb][Resource](params: RequestType): Promise<ResponseType>

  Examples:
    detectionApi.uploadScan(file: File, guestToken?: string): Promise<{scanId: string}>
    historyApi.getScans(filters: ScanFilters, page: number): Promise<ScanListResponse>
    authApi.login(email: string, password: string): Promise<{user: User}>
    settingsApi.updatePrefs(prefs: Partial<UserPreferences>): Promise<UserPreferences>

RESPONSE LAYER
───────────────
All API responses follow this envelope format (assumed from Batch 01):
  Success: { data: T, meta?: PaginationMeta }
  Error:   { error: { code: string, message: string, field?: string } }

The API client unwraps this envelope:
  - Success: returns response.data directly
  - Error: throws ApiError(code, message, field)

ApiError class (shared/utils/errorUtils.ts):
  code:    string     (e.g., "FILE_TOO_LARGE", "INVALID_TOKEN")
  message: string     (user-readable message from server)
  field?:  string     (form field name for field-level errors)
  status:  number     (HTTP status code)

ERROR CODE → UI MESSAGE MAPPING (errorUtils.ts)
  Server error codes are mapped to user-facing messages in the frontend.
  The server never sends raw error messages directly to users.
  "FILE_TOO_LARGE"       → "File exceeds 10MB limit. Try a shorter clip."
  "UNSUPPORTED_FORMAT"   → "Format not supported. Use WAV, FLAC, MP3, or AIFF."
  "PROCESSING_FAILED"    → "Analysis failed. Please try again."
  "RATE_LIMIT_EXCEEDED"  → "Too many requests. Please wait a moment."
  "UNAUTHORIZED"         → triggers logout() + redirect to /login
  "NOT_FOUND"            → triggers navigation to not-found.tsx
  "SERVER_ERROR"         → "Something went wrong on our end. [Try again]"

CACHING STRATEGY
─────────────────
React Query is the only cache layer for server data.
  No custom caching logic in api/*.ts files.
  Cache configuration lives in config/queryKeys.ts (stale times defined there).

  Strategies by data type:
    User profile:         Cache with 5min stale — changes are rare
    Scan history list:    Cache with 2min stale — new scans are frequent
    Single scan detail:   Cache with 5min stale — scan results are immutable
    Notifications:        Cache with 30s stale — must be fresh for badge count
    Help articles:        Cache with 30min stale — content rarely changes
    Dashboard stats:      Cache with 2min stale — frequently updated

RETRY STRATEGY
───────────────
React Query default retry: 3 attempts with exponential backoff (1s, 2s, 4s).
Custom retry policy per query type:
  Scan upload:            Retry: 0 (user must re-trigger; don't auto-retry uploads)
  Scan status poll:       Retry: infinite (poll until result or timeout)
  GET queries:            Retry: 2 (default 3 is excessive)
  Mutation (delete, save): Retry: 1 (retry once on network error)

HTTP 401 handling:
  apiClient detects 401 responses globally.
  Action: authStore.logout() → router.push('/login?session=expired')
  Toast: "Session expired. Please log in again."
  This is the ONLY place logout is called for auth failures.

OFFLINE BEHAVIOR
─────────────────
  Detection: OfflineBanner (shared/components/feedback) renders when
             navigator.onLine = false (useEffect event listener).
  Offline during scan upload: Upload fails immediately with error:
    "You appear to be offline. Check your connection and try again."
  Offline during result view: React Query serves cached data — result
    page renders from cache with no network required.
  Offline during history browse: Cached pages render; filter changes
    that require a new request show SkeletonLoader briefly, then error:
    "Can't load history — no connection."

TIMEOUT HANDLING
─────────────────
  Standard endpoints:    30 second timeout
  Scan upload endpoint:  120 second timeout (large file + processing)
  Polling endpoint:      10 second timeout per poll (short — polling resumes)

  On timeout: ApiError thrown with code "REQUEST_TIMEOUT"
  UI: Component receives error from React Query, renders retry CTA.

PDF EXPORT (client-side generation)
─────────────────────────────────────
  PDF is generated client-side using a PDF library (jsPDF or pdfmake).
  The API provides the raw data (verdict, scores, image URLs).
  The frontend renders the PDF from that data — no server-side PDF endpoint.
  This avoids server load and enables offline PDF generation from cached results.

  Flow:
    1. User clicks "Download PDF Report"
    2. Button shows loading state: "Generating..."
    3. usePDFExport hook:

DESIGN TOKEN IMPLEMENTATION
─────────────────────────────
All design tokens from Batch 02 Section 5 are implemented as CSS custom
properties. The token files in src/styles/tokens/ define all values.

Token file structure (src/styles/tokens/colors.css):
  :root[data-theme="dark"],
  :root {                       ← dark is default
    --color-bg:           #0A0A0A;
    --color-surface:      #111111;
    --color-surface-2:    #161616;
    /* ... all dark tokens ... */
  }

  :root[data-theme="light"] {
    --color-bg:           #FAFAFA;
    --color-surface:      #FFFFFF;
    --color-surface-2:    #F5F5F7;
    /* ... all light tokens ... */
  }

  :root[data-theme="system"] {
    /* Handled via JavaScript — see ThemeProvider */
  }

System theme handling (ThemeProvider.tsx):
  When theme = 'system':
    window.matchMedia('(prefers-color-scheme: dark)').matches
      → true:  document.documentElement.setAttribute('data-theme', 'dark')
      → false: document.documentElement.setAttribute('data-theme', 'light')
    addEventListener for 'change' event on matchMedia query
    → Re-applies when OS theme changes (no page reload needed)

Components reference tokens via CSS Modules:
  .verdictCard {
    background: var(--color-surface);
    border: 1px solid var(--color-border);
  }

  NOT this (banned):
  .verdictCard {
    background: #111111;   ← RAW HEX BANNED
    border: 1px solid #1F1F1F;
  }

THEME PERSISTENCE CHAIN
────────────────────────

  1. User selects theme in S19 Appearance
  2. settingsStore.setTheme(value) — updates store + DOM + localStorage
  3. Background API call saves to user record
  4. On next visit:
       Server-side (Next.js middleware): reads theme cookie
       → Adds data-theme attribute to <html> in SSR render
       → Prevents flash of wrong theme (FOUT)
       → ThemeProvider hydrates with same value

  Theme cookie: 'vg-theme', expires 1 year, SameSite=Lax, Secure
  This cookie is set server-side on login and client-side on theme change.

PREVENTING FLASH OF WRONG THEME (FOUT)
────────────────────────────────────────
  Problem: React hydration happens after HTML is painted. If theme is
  applied via JS in useEffect, users see a flash of the default theme.

  Solution: Next.js middleware reads the vg-theme cookie before SSR
  and adds data-theme to the <html> element in the server response.
  The correct theme is applied before any JavaScript runs.

  SSR fallback (no cookie): defaults to 'dark' (Batch 02 primary theme).

ANIMATION TOKENS
─────────────────
  All animation durations and easing functions are also CSS custom properties.
  Components reference --motion-duration-fast, --motion-ease-spring, etc.

  prefers-reduced-motion handling:
    @media (prefers-reduced-motion: reduce) {
      :root {
        --motion-duration-fast:    0ms;
        --motion-duration-normal:  0ms;
        --motion-duration-enter:   0ms;
        --motion-duration-reveal:  0ms;
      }
    }
  This disables ALL transitions and animations globally when the user
  prefers reduced motion. No component needs individual motion logic.
  Components that have non-motion purposes (confidence bar fill as
  data communication) show their final value immediately.

PERFORMANCE BUDGET
───────────────────
  Metric                                  Target          Priority
  ──────────────────────────────────────────────────────────────────────────
  First Contentful Paint (FCP)            < 1.0s  (3G)    Critical

  Total page weight (landing, S01)        < 300KB          High

CODE SPLITTING — IMPLEMENTATION DETAILS
────────────────────────────────────────
Next.js App Router implements automatic code splitting per route.
Additional manual splits for heavy components:

  GradCAMPanel:
    Dynamic import with ssr: false

  MicrophoneRecorder + WaveformVisualizer:

LAZY LOADING — IMAGES
──────────────────────
  All images use native loading="lazy" attribute.
  Exceptions (load eagerly):

    - User avatar in TopBar (used in initial render of every page)

      2. Image component renders blurred placeholder immediately

  Next.js Image component (<Image>) used for all images:
    - Automatic WebP conversion
    - Responsive srcset generation
    - CLS prevention (explicit width/height required)

MEMOIZATION STRATEGY
─────────────────────
Memoize only when there is a documented, measurable performance problem.
Premature memoization adds complexity without measurable benefit.

  Memoize (React.memo):
    ScanRow: re-renders on every history list refresh; 20+ items per page
    StatCard: re-renders on every dashboard refresh; value is always same
    NotificationItem: list of 20+ items
    Badge: rendered inside every ScanRow; pure render based on variant
    ConfidenceBar: animation runs on mount; should not re-animate on re-renders

  Memoize (useMemo):
    Filter query key construction in useScanHistory:
      const queryKey = useMemo(() => queryKeys.scanHistory(filters), [filters])
    Chart data transformation in ActivityChart:
      const chartData = useMemo(() => transformScansToChartData(scans), [scans])

  Memoize (useCallback):
    onFileAccepted handler in FileDropzone usage sites
    onDelete handler passed to ScanRow (changes on every render otherwise)

  Do NOT memoize:
    Simple components that render cheap JSX
    Components that rarely re-render
    Context consumers (use Zustand selectors instead)

VIRTUALIZATION
───────────────
  S11 History list: virtualize when > 100 scans
    Use TanStack Virtual (tanstack/virtual) for row virtualization
    Implementation: only activated when total scan count > 100
    Below 100: standard non-virtualized list (simpler, less overhead)

  S13 Notifications: no virtualization needed (max reasonable: 50 items)
  S14 Help search results: no virtualization needed (max 20 results)

FONT LOADING
─────────────
  Self-hosted fonts in public/fonts/ (no Google Fonts CDN — GDPR + performance)
  Preconnect + preload in <head> for Inter and Inter Tight (woff2, Latin subset)
  JetBrains Mono loaded on-demand (only when monospace content is shown)
  font-display: swap for all fonts (prevent invisible text during load)

PREFETCHING STRATEGY

SECTION 15 — ERROR HANDLING STRATEGY
================================================================================

ERROR BOUNDARY HIERARCHY
─────────────────────────

  Level 1 — Global (app/error.tsx):
    Catches: Any unhandled JS error at the top level
    Shows: S22 Service Error page
    Includes: "Something went wrong on our end" + Retry button + Error ID
    Reports: Error details logged to error reporting service (Sentry or similar)

  Level 2 — Module boundary (inside AppShell <main>):
    Each route group has an error.tsx that catches module-level failures.
    Shows: ModuleErrorFallback — a contained error card within the page shell,
           not a full-page takeover.
    Copy: "This section couldn't load. [Try again] [Go to Dashboard]"
    Benefit: If S11 History crashes, the TopBar and Sidebar remain functional.

  Level 3 — Section boundary (ErrorBoundary component):
    Used within individual page sections that load independently.
    Shows: SectionErrorFallback — small card with icon + retry link.
    Example: If ActivityChart crashes on S07, the rest of Dashboard renders.
    Copy: "Chart couldn't load. [Retry]"

  Level 4 — React Query error state:
    Every useSomething hook that fetches data has isError state.
    Components render their own error state from this (not a boundary).
    Example: ScanTable in S11 renders "Couldn't load scans. [Try again]"
             when query.isError === true

ERROR FALLBACK COMPONENTS
──────────────────────────

  ErrorFallback (shared/components/feedback/ErrorFallback.tsx)
    Props: error, resetErrorBoundary, size ('page' | 'section' | 'inline')
    Variants:
      page:    Full-height centered card (S22 style, within page shell)
      section: Card within the page content area
      inline:  Single line with error icon + message + retry link

  OfflineBanner (shared/components/feedback/OfflineBanner.tsx)
    Renders as sticky top banner (below TopBar)
    Text: "You appear to be offline. Some features may be unavailable."
    Auto-dismisses when connection restored (online event)
    aria-live="assertive" (offline is important — announce immediately)

API ERROR FLOW
───────────────

  API call fails
      ↓
  apiClient throws ApiError(code, message, status, field?)
      ↓
  React Query mutation/query catches error
      ↓
  isError = true + error = ApiError
      ↓
  Component receives error from hook
      ↓
  if (error.code === 'UNAUTHORIZED')
    → authStore.logout()
    → router.push('/login?session=expired')
    → Toast: "Session expired..."
  else if (error.code === 'NOT_FOUND')
    → router.push('/not-found')
  else if (error.status >= 500)
    → if within ErrorBoundary: boundary catches
    → else: component renders inline error state
  else
    → Component renders specific error message via errorUtils.getMessageForCode()

FORM ERROR HANDLING
────────────────────
  Client-side validation (Zod) runs on blur for each field.
  Server-side errors (from API response) are mapped to fields:
    If error.field is set: setError(error.field, {message: error.message})
    If error.field is not set: setError('root', {message: error.message})
  Root form errors render above the submit button as an Alert component.

CRASH REPORTING
────────────────
  Error boundaries capture: error message, stack trace, component tree,
  current URL, user ID (hashed), browser/OS info.
  Reported to: error tracking service (architecture supports Sentry integration)
  Error ID: generated UUID shown to user ("Error ID: abc123") for support
  PII: User email NEVER included in error reports. User ID is hashed.

SCAN PROCESSING ERROR STATES
──────────────────────────────
  These are the most critical error states — user has submitted work and
  expects a result. Each has a specific recovery path.

  processing-timeout (> 15s no response):
    Show: "Taking longer than usual..."
    Action: [Keep waiting] [Cancel] [Contact support]

  processing-error (server returns error):
    Show: "Analysis failed. This sometimes happens with unusual audio formats."
    Actions: [Try again with same file] [Upload different file] [Report issue →]
    Note: "Try again with same file" re-uses the file still in detectionStore.
          User does not have to re-upload.

  processing-unsupported (model rejects the audio):
    Show: "This audio format couldn't be analyzed."
    Sub: "Try converting to WAV or FLAC and uploading again."
    Actions: [Upload different file]

  network-error during upload:
    Show: inline error below dropzone
    Text: "Upload failed. Check your connection and try again."
    Action: [Try again] — re-submits the same file from detectionStore

───────────────────

  Import order (enforced by ESLint):
    1. React and React-related libraries
    2. Third-party libraries (alphabetical)
    3. Internal imports — absolute paths (aliased via tsconfig paths)
    4. Relative imports (for same-module internal files)
    5. CSS module imports (always last)

  Path aliases (tsconfig.json paths):
    @/modules/*      → src/modules/*
    @/shared/*       → src/shared/*
    @/styles/*       → src/styles/*
    @/config/*       → src/config/*
    @/types/*        → src/types/*

  Barrel (index.ts) imports:
    Every module exposes a barrel file that defines its public API.
    Other code imports from the barrel, never from internal paths.
    Correct:    import { VerdictCard } from '@/modules/detection'
    Forbidden:  import { VerdictCard } from '@/modules/detection/components/VerdictCard'

COMPONENT CONVENTIONS
──────────────────────

  File structure within a component file:
    1. Imports
    2. Type definitions (Props interface)
    3. Component function (named export, not default)
    4. Helper components (small, used only in this file)
    5. Exports

  Props interface:
    Always named [ComponentName]Props
    Defined in the same file as the component
    Exported if other components extend it; otherwise not exported

  Component function signature:
    export function VerdictCard({ verdict, confidence, ... }: VerdictCardProps) {
    No default exports from component files (named exports only)
    Reason: Named exports make refactoring and tree-shaking explicit

  State in components:
    Local UI state (hover, open, selected): useState
    Form state: React Hook Form
    Server data: React Query (via custom hook)
    Global state: Zustand selector (useAuthStore, useDetectionStore)
    Never: useContext for mutable state (use Zustand)

  Conditional rendering:
    Prefer ternary for simple cases, early return for complex logic
    Avoid nested ternaries (extract to named variables)
    Avoid && for rendering JSX when left side could be 0 or '' (use ternary)

HOOK CONVENTIONS
─────────────────

  Custom hooks must:
    - Return a typed object (not arbitrary tuples)
    - Handle loading, error, and success states explicitly
    - Never contain JSX
    - Never contain routing logic (hooks are not page-level concerns)

  React Query hooks pattern:
    function useScanHistory() {
      const filters = useHistoryStore(s => s.filters)
      const page    = useHistoryStore(s => s.page)
      return useQuery({
        queryKey: queryKeys.scanHistory({ filters, page }),
        queryFn:  () => historyApi.getScans(filters, page),
        staleTime: 2 * 60 * 1000,
      })
    }

  Mutation pattern:
    function useDeleteScan() {
      const queryClient = useQueryClient()
      return useMutation({
        mutationFn: (scanId: string) => historyApi.deleteScan(scanId),
        onSuccess: () => {
          queryClient.invalidateQueries({ queryKey: queryKeys.scanHistory() })
        }
      })
    }

TESTING CONVENTIONS
────────────────────

  What to test:
    Unit tests:       Utility functions, Zod schemas, store actions
    Component tests:  Component rendering in all states (using Testing Library)
    Integration tests: User flows through multiple components
    E2E tests:        Critical paths (sign up, upload + result, delete scan)

  What NOT to unit test:
    CSS / visual appearance (snapshot tests for this are brittle)
    Third-party library internals
    Simple getters/setters

  Testing priorities (in order):
    1. useScanProcessing hook (most complex async flow)
    2. useFileUpload hook (validation logic is critical)
    3. VerdictCard (most important component; tested in all 3 verdict states)
    4. FileDropzone (drag-and-drop, file validation, error states)
    5. AuthGuard (route protection)
    6. All form validation flows (sign up, login, settings)
    7. E2E: Guest upload → result → sign up → dashboard
    8. E2E: Authenticated user search and filter history

  Test file location: co-located with source (VerdictCard.test.tsx beside
                      VerdictCard.tsx) for features; tests/e2e/ for E2E

  Testing Library conventions:
    Query by: role > label > text > testId (testId is last resort)
    Avoid: querySelector, className queries (implementation detail)
    userEvent over fireEvent (userEvent simulates real browser interaction)

ISSUE LOG
──────────────────────────────────────────────────────────────────────────────

AUDIT-01: Tight Coupling — Detection Components in S12 Scan Detail
STATUS: RESOLVED IN THIS DOCUMENT

Issue: S12 Scan Detail needs VerdictCard, ConfidenceBar, GradCAMPanel,
       LimitationsCard — the same components as S10 Scan Result.
       Naively, the history module might duplicate these.

Resolution: Detection module exports these components in detection/index.ts.
            History module imports from detection/index.ts.
            S20 Shared Scan Result also imports from detection/index.ts.
            Single source of truth, three consumers.

──────────────────────────────────────────────────────────────────────────────

AUDIT-02: State Duplication — React Query vs Zustand for Scan Result
STATUS: RESOLVED IN THIS DOCUMENT

Issue: detectionStore.currentResult and React Query both hold the scan result.
       This risks stale state if one is updated but not the other.

Resolution: detectionStore holds currentResult for the duration of the
            active scan session only (for immediate S10 render).
            After navigating away and back, S10/S12 reads from React Query
            exclusively. detectionStore.reset() is called when user starts
            a new scan. The two never diverge because React Query is always
            the authoritative source; the store is a short-lived read cache.

──────────────────────────────────────────────────────────────────────────────

AUDIT-03: Guest Session Management Complexity
STATUS: ACCEPTABLE — DOCUMENTED

Issue: Guest users can create scans, and those scans must be migrated to
       their account after sign-up. This creates a coordination requirement
       between auth, detection, and onboarding modules.

Resolution: authStore.guestScanId holds the scanId created in guest session.
            After sign-up → verification → auth:
              authApi.migrateScan(guestScanId, userId) is called once.
            This migration call is made in AuthProvider after the first
            authenticated session is established.
            The migration endpoint is idempotent (safe to call twice).
            If migration fails: non-critical — scan is lost. User sees
            notification: "Your guest scan couldn't be migrated. Please
            re-upload the file."

──────────────────────────────────────────────────────────────────────────────

AUDIT-04: Performance — Charting Library in Dashboard Bundle
STATUS: RESOLVED IN THIS DOCUMENT

Issue: Including a charting library (e.g., Recharts ~100KB gzipped) in
       the dashboard bundle would bloat the initial page load.

Resolution: ActivityChart is dynamically imported with next/dynamic.
            It only renders when scan count > 5 (empty state below that).
            The charting library is in its own code split chunk and never
            part of the critical path.

──────────────────────────────────────────────────────────────────────────────

AUDIT-05: Settings Sidebar — Mobile Usability
STATUS: RESOLVED IN THIS DOCUMENT

Issue: The settings layout uses a sidebar tab list (S17/S18/S19). On mobile,
       a vertical sidebar becomes unusable (too narrow).

Resolution: SettingsSidebar renders as:
            Desktop (> 900px): vertical tab list on left, content on right
            Mobile (< 900px):  horizontal scrollable tab bar at top,
                               content below

──────────────────────────────────────────────────────────────────────────────

AUDIT-06: Accessibility — MicrophoneRecorder Permission Denied State
STATUS: RESOLVED IN THIS DOCUMENT

Issue: When microphone permission is denied, the browser shows a native
       dialog. After dismissal, the app's state machine must handle this
       correctly for keyboard and screen reader users.

Resolution: useMicrophoneRecorder tracks permission state explicitly.
            On permission denied: state = 'permission-denied'
            MicrophoneRecorder renders a Card with:
              - aria-live="assertive" announcement: "Microphone access denied"
              - Browser-specific instructions (detected from userAgent)
              - "Try uploading a file instead" link (keyboard accessible)
            Focus moves to the first instruction link.

──────────────────────────────────────────────────────────────────────────────

AUDIT-07: Security — File Upload XSS via Filename
STATUS: RESOLVED IN THIS DOCUMENT

Issue: Filenames are displayed in multiple places (FilePreviewCard, ScanRow,
       VerdictCard footer, PDF). A crafted filename could contain HTML/JS.

Resolution: All filename rendering uses textContent, not innerHTML.
            React's default JSX rendering escapes all string values.
            PDF generation sanitizes filenames before insertion.
            Filenames are truncated at 80 characters for display.

──────────────────────────────────────────────────────────────────────────────

AUDIT-08: DX — Module Barrel Files May Cause Circular Imports
STATUS: ADDRESSED — CONVENTION ESTABLISHED

Issue: Barrel files (index.ts) in modules create risk of circular imports
       if modules start importing from each other's barrels.

Resolution: The rule is enforced: modules may ONLY import from shared/*.
            If two modules need to share a component, it belongs in shared/.
            No module imports from another module's barrel.
            ESLint rule: import/no-cycle enforces this at lint time.

──────────────────────────────────────────────────────────────────────────────

AUDIT-09: Performance — Multiple Zustand Selectors Causing Re-renders
STATUS: ADDRESSED — PATTERN DEFINED

Issue: If a component selects multiple values from a Zustand store in
       separate useStore calls, each store update triggers a separate
       re-render, even if the component uses both values together.

Resolution: Use object selector with shallow equality:
  const { verdict, confidence } = useDetectionStore(
    useShallow(s => ({ verdict: s.currentResult?.verdict,
                       confidence: s.currentResult?.confidence }))
  )
  useShallow from zustand/react/shallow prevents re-renders when the
  selected values haven't changed.

──────────────────────────────────────────────────────────────────────────────

AUDIT-10: Future Maintenance — Error Code Mapping Duplication
STATUS: RESOLVED IN THIS DOCUMENT

Issue: Error messages for API codes are mapped in errorUtils.ts. If the
       backend adds new error codes, the frontend silently falls back to
       a generic message. This fallback must be graceful.

Resolution: errorUtils.getMessageForCode(code) returns a generic
            "Something went wrong. [Try again]" for any unmapped code.
            Additionally, unknown error codes are logged to the error
            reporting service so they surface during development/monitoring.
            The mapping function is the single place where this logic lives.

SECTION 19 — RISKS & MITIGATIONS
================================================================================

RISK 01 — Next.js App Router Complexity
Probability: Medium | Impact: High
Description: The App Router's caching, parallel routes, and server component
             model introduces complexity that can cause subtle bugs — especially
             for teams unfamiliar with the paradigm.
Mitigation:
  - Use Client Components for all interactive UI (components with state,
    events, and hooks). Server Components only for static/SEO pages.
  - Establish team convention: mark all interactive components with
    'use client' immediately, not after debugging a hydration error.
  - Create a decision doc: "Server Component vs Client Component" checklist.
  - Use Pages Router as fallback if App Router issues prove blocking
    (all routing patterns defined here work in both routers with minor changes)

RISK 02 — Web Audio API Cross-Browser Compatibility
Probability: Medium | Impact: Medium
Description: MediaRecorder API and AudioContext have inconsistent support
             across browsers and iOS Safari has known limitations.
Mitigation:
  - Detect MediaRecorder support on component mount
  - If unsupported: disable "Record" tab, show "Recording not supported
    in your browser. Please upload a file instead."
  - Test explicitly on iOS Safari 15+ and Firefox 115+
  - Fallback is always available (file upload mode works everywhere)

RISK 03 — Grad-CAM Images Taking Longer Than Expected to Load
Probability: Medium | Impact: High (S10 is the most important screen)
Description: Grad-CAM images are generated server-side. If generation is
             slow, S10 renders the verdict but not the visual evidence,
             undermining the professional use case.
Mitigation:
  - GradCAMPanel renders a spectrogram-shaped SkeletonLoader immediately
  - Images use blur-up: low-res placeholder available instantly from API
  - Backend caches Grad-CAM images for the scan's lifetime
  - If both images fail to load: LimitationsCard explains why (fallback copy)
  - SLO: Grad-CAM images available within 1s of scan complete (from Batch 01)

RISK 04 — Mobile Microphone Recording Quality
Probability: High | Impact: Medium
Description: Mobile browser microphone recordings may have lower quality,
             background noise, or different sample rates that affect model
             accuracy. Users may receive unexpected results and blame the tool.
Mitigation:
  - Display explicit notice before recording on mobile:
    "Recording on mobile may produce different results than uploading a file.
    For forensic analysis, upload the original file."
  - This notice is part of the "About audio requirements" collapsible
    section on S08 (defined in Batch 02)
  - No technical change needed — this is a content/UX mitigation

RISK 05 — React Query Cache Stale Data on Result Pages
Probability: Low | Impact: High
Description: If a scan result is modified (e.g., admin correction), a cached
             React Query result would show stale data.
Mitigation:
  - Scan results are immutable once created (by design, from Batch 01)
  - React Query's 5min stale time is appropriate — results never change
  - If server ever sends updated data: React Query refetches in background
    and updates the UI without disrupting the user's reading

RISK 06 — Zustand Store Size Growing Over Time
Probability: Medium | Impact: Medium (maintenance)
Description: As features are added, Zustand stores accumulate state
             properties. Bloated stores become hard to reason about.
Mitigation:
  - Each module has its own store file (no single global store)
  - State review in ADR when adding > 3 properties to any store
  - Server-fetched data goes in React Query, not stores (this constraint
    prevents the most common cause of store bloat)
  - Quarterly code review: evaluate whether any store property can be
    replaced with React Query or local state

RISK 07 — PDF Export Library Bundle Size
Probability: Medium | Impact: Medium
Description: PDF generation libraries (jsPDF, pdfmake) are typically
             100–200KB gzipped. Loading on button click creates a delay.
Mitigation:
  - Dynamic import: library loads only when user clicks "Download PDF"
  - Loading state: button shows "Loading..." during library download (~1s)
  - This 1-second delay is acceptable for an on-demand action
  - Alternative if unacceptable: server-side PDF generation endpoint
    (trades bundle size for API latency — acceptable tradeoff in v2)

RISK 08 — Authentication State Flash on Hard Refresh
Probability: High | Impact: Low (cosmetic)
Description: On hard refresh, AuthProvider reads the session cookie and
             hydrates authStore. During this async operation, the page
             briefly renders the unauthenticated state before the auth
             check completes, causing a layout flash.
Mitigation:
  - AppShell layout.tsx renders a full-height skeleton (not the actual
    sidebar navigation) until sessionStatus !== 'loading'
  - AuthGuard shows a full-page spinner while sessionStatus = 'loading'
  - This prevents flash of wrong navigation state
  - Target: AuthProvider hydration completes within 100ms (reads cookie;
    no network request needed for initial auth state check)

RISK 09 — Content Security Policy (CSP) Blocking Inline Styles
Probability: Medium | Impact: Medium
Description: Strict CSP policies block inline styles. CSS-in-JS libraries
             (if ever used) inject inline styles and require 'unsafe-inline'.
Mitigation:
  - Current architecture uses CSS Modules only — no inline styles
  - CSS custom properties (design tokens) are defined in .css files, not JS
  - Next.js with CSS Modules is fully CSP-compatible
  - Rule: never add CSS-in-JS libraries (styled-components, Emotion) as
    they would require relaxing CSP

RISK 10 — Testing Coverage Gaps in Complex Async Flows
Probability: High | Impact: Medium
Description: The scan upload → poll → result flow involves async state
             transitions that are easy to under-test, leading to regressions
             in the core product loop.
Mitigation:
  - useScanProcessing hook has dedicated unit tests covering every state
    transition (idle → uploading → processing step 0/1/2 → complete → error)
  - E2E test covers the full guest upload → result flow (highest priority test)
  - Mock Service Worker (msw) used for API mocking in component tests
    (not jest.mock — avoids brittle implementation mocks)

REC 02 — IMPLEMENT DESIGN TOKENS BEFORE WRITING ANY COMPONENT STYLES
───────────────────────────────────────────────────────────────────────
The single most important implementation decision in this document.
Every shortcut taken here (hardcoding a color "just this once") will
compound. Dark mode retrofitting costs 3–5× what implementing tokens first
costs. The payoff is not just theme switching — it is brand-wide consistency
that is never broken by a single component making an independent color choice.

REC 03 — DO NOT USE CONTEXT API FOR MUTABLE GLOBAL STATE
──────────────────────────────────────────────────────────
React Context triggers re-renders for every consumer when the context
value changes. For high-frequency state updates (upload progress, scan
processing steps), this causes significant performance problems. Zustand
with granular selectors solves this cleanly. This architecture uses:
  - Zustand for all mutable global/feature state
  - Context ONLY for dependency injection (QueryClient, theme value)
    where the value changes rarely or never

REC 04 — ENFORCE MODULE BOUNDARIES WITH ESLint IMPORT RULES
──────────────────────────────────────────────────────────────
The module architecture defined in this document only holds if engineers
can't accidentally violate it. Configure eslint-plugin-import with:
  import/no-cycle: error
  boundaries/element-types: module cannot import from another module
  This makes violations a CI failure, not a code review discussion.

REC 05 — THE LIMITATIONS CARD IS NON-NEGOTIABLE IN THE COMPONENT TREE
────────────────────────────────────────────────────────────────────────
Following Batch 02 Principle 2: LimitationsCard is always rendered on
S10, S12, and S20. Never conditional. Never behind a feature flag.
It must be treated as a first-class component in the component tree,
not a "nice to have" detail section.

REC 06 — MINIMUM PROCESSING DISPLAY TIME IS AN ARCHITECTURAL CONSTANT
────────────────────────────────────────────────────────────────────────
The 1500ms minimum display time on S09 Processing is a user trust
mechanism, not a bug. It is implemented in useScanProcessing as:

  const elapsed = Date.now() - processingStartedAt
  const remaining = Math.max(0, MIN_DISPLAY_MS - elapsed)
  setTimeout(() => navigateToResult(), remaining)

This constant (MIN_DISPLAY_MS = 1500) must NOT be removed in
performance optimization passes. It is intentional behavior.

REC 07 — SHA-256 IS COMPUTED CLIENT-SIDE, NOT SERVER-SIDE
───────────────────────────────────────────────────────────
The SHA-256 hash in LimitationsCard must be the hash of the ORIGINAL
file — the file before upload. If it is computed server-side after
receive, any transmission modification would not be detected.

useFileHash hook uses the Web Crypto API (SubtleCrypto.digest) to compute
SHA-256 in the browser immediately after file selection.
This computation is async and runs in the background while the user
reviews the file preview, completing before the Analyze button is pressed.

REC 08 — MOBILE IS NOT A SIMPLIFIED DESKTOP
─────────────────────────────────────────────
Following Batch 02 Principle (Section 8): the mobile layout is explicitly
designed. Key mobile-specific implementations required:
  - BottomTabBar replaces Sidebar entirely (not a collapsed sidebar)
  - GradCAM panels stack vertically (not side-by-side)
  - History table becomes a card list (not a compact table)
  - User menu becomes a full-screen bottom drawer (not a popover)
  - FileDropzone shows full-width "Browse" button (no dashed zone — mobile
    doesn't support drag-and-drop in practice)

REC 09 — REACT QUERY IS THE ONLY SERVER CACHE
───────────────────────────────────────────────
Do not build a secondary caching layer. Do not store fetched data in
Zustand for caching purposes. React Query is the server cache.
Zustand is the UI state store. When in doubt: if the data comes from
an API, it belongs in React Query. If it's a UI decision (sidebar open,
filter state, current theme), it belongs in Zustand.

REC 10 — ACCESSIBILITY TESTING BEFORE LAUNCH, NOT AFTER
─────────────────────────────────────────────────────────
The accessibility architecture defined in Section 14 must be validated
before launch with actual screen readers, not just automated tools.
Automated tools (axe-core, Lighthouse accessibility audit) catch ~40%
of accessibility issues. The remaining 60% — focus management behavior,
live region announcements, keyboard navigation flows — require manual
testing with NVDA on Windows and VoiceOver on macOS.

Schedule one dedicated accessibility testing session per phase:
  Phase 2 (after S10 is built): test the result announcement flow
  Phase 3 (after auth): test form error navigation
  Phase 4 (after history): test table keyboard navigation
  Final (pre-launch): full regression across all 22 screens
