SECTION 1 — EXECUTIVE SUMMARY
================================================================================

This document converts the VoiceGuard Product Architecture (Batch 01) into a
complete, implementation-ready UX specification. Every screen, interaction,
component, state, and content decision is defined here at the level of detail
a frontend engineer needs to build the full interface without additional
design clarification.

Batch 01 defined WHAT the product does and WHY. Batch 02 defines HOW it
looks, HOW users interact with it, HOW every component behaves in every state,
and HOW the system communicates with users at every moment.

This document extends Batch 01 without contradicting it. Every decision here
is grounded in the architecture decisions made in Batch 01.

SECTION 2 — UX PRINCIPLES
================================================================================

These 10 principles govern every design decision in this document. When any
ambiguity arises during implementation, resolve it by returning to these
principles in order.

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 1 — THE RESULT IS THE PRODUCT
──────────────────────────────────────────────────────────────────────────────
Every screen exists to bring the user to S10 (Scan Result) or to let them
return to a past result. The verdict card is the moment VoiceGuard either
earns or loses user trust. When in doubt about any design decision, ask:
"Does this help the user get to or understand a result?" If no, reconsider.

Application: The confidence bar animation is not decoration — it is the
product's single most important interaction. The Grad-CAM visualization is
not a technical feature — it is the evidence layer that makes the verdict
defensible. Design both as primary, not secondary, content.

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 2 — TRUST IS EARNED THROUGH HONESTY
──────────────────────────────────────────────────────────────────────────────
VoiceGuard's target professional users (journalists, forensic analysts,
cybersecurity professionals) have been burned by opaque AI tools before.
They will test the model against known recordings. They will read the
limitations section. They will look for signs of overconfidence.

The Limitations Notice on S10 is not a disclaimer — it is a trust signal.
Never hide, minimize, or make it harder to access. The product earns the most
trust when it says clearly: "Here is what I found, here is why, and here is
where I might be wrong."

Application: Model confidence thresholds must map to language precisely.
A 97% score says "strong indicators." A 72% score says "some patterns suggest."
A 55% score says "inconclusive." Never let a low-confidence result generate
high-confidence language.

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 3 — ONE PRIMARY ACTION PER SCREEN
──────────────────────────────────────────────────────────────────────────────
Every screen has exactly one primary action. That action has the highest
visual weight on the page. All other actions are secondary or tertiary in
visual hierarchy. Users should never feel uncertain about what to do next.

Screen → Primary Action:
  S01 Landing        → "Get Started Free"
  S02 Sign Up        → Submit Registration
  S03 Login          → Submit Login
  S08 New Scan       → "Analyze"
  S09 Processing     → (system action — user waits)
  S10 Result         → "Analyze Another File"
  S11 History        → Click a scan row
  S07 Dashboard      → Embedded upload dropzone

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 4 — FRICTION IS THE ENEMY OF FIRST VALUE
──────────────────────────────────────────────────────────────────────────────
A user who lands on VoiceGuard should be able to complete their first scan
in under 90 seconds without creating an account. Every click, every form
field, every redirect that exists between landing and first result is a
friction point that reduces conversion.

Application:
  - Guest mode is mandatory, not optional
  - Email verification is not required to view a scan result
  - The dropzone on Dashboard removes the need to navigate to New Scan
  - File preview plays inline — users never leave the page to verify their file

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 5 — COMMUNICATE SYSTEM STATE AT ALL TIMES
──────────────────────────────────────────────────────────────────────────────
A user should never be unsure whether the system is working, waiting, or
has failed. Every action that has a system consequence has a visible system
response. The response appears within 100ms of the user action.

Timeline of acceptable response speeds:
  < 100ms : Immediate feedback (button press state, hover state)
  < 500ms : Visual loading indicator if action is not complete
  < 3s    : Progress steps with description if operation is complex
  > 3s    : Time estimate shown; user can cancel

Application: The Analyze button transitions from idle → loading spinner
(100ms) → navigates to S09 Processing (500ms). The user always knows the
system received their action.

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 6 — DESIGN FOR THE PROFESSIONAL FIRST, THE CASUAL USER SECOND
──────────────────────────────────────────────────────────────────────────────
The casual user tolerates some roughness and forgives unclear UI. The
journalist filing a story under deadline, the HR professional reviewing
personnel audio, or the forensic analyst preparing court evidence will leave
and never return the moment the tool fails them.

This means: the technical details layer (Grad-CAM, raw scores, file hash,
model version) must always be complete and accurate. It may be collapsed by
default for casual users, but it must be immediately accessible and
unambiguous for professionals who expand it.

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 7 — DESIGN TOKENS BEFORE COMPONENTS
──────────────────────────────────────────────────────────────────────────────
No component is built before the design token system is established. Every
color, spacing value, radius, shadow, and typography value is a token.
Components reference tokens, never raw values. This ensures:
  - Perfect visual consistency across the entire application
  - Dark/light mode switching with zero component changes
  - Brand updates that propagate everywhere automatically

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 8 — EVERY COMPONENT IS DESIGNED IN ALL STATES
──────────────────────────────────────────────────────────────────────────────
A component is not done until all of the following states are designed:
default, hover, focused, active/pressed, disabled, loading, error, success,
empty. A button with only a default state is an unfinished component.

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 9 — ACCESSIBILITY IS NOT A FEATURE, IT IS A REQUIREMENT
──────────────────────────────────────────────────────────────────────────────
WCAG 2.1 AA compliance is the minimum, not the goal. All primary result
display (verdict text, confidence numbers) must meet AAA contrast ratios.
Keyboard navigation covers every interaction. Screen readers get equivalent
information to visual users — including textual descriptions of Grad-CAM
visualizations.

──────────────────────────────────────────────────────────────────────────────
PRINCIPLE 10 — ANIMATIONS COMMUNICATE, THEY DO NOT DECORATE
──────────────────────────────────────────────────────────────────────────────
Every animation tells the user something: what just happened, what is
happening, or what is about to happen. Animations that exist purely for
aesthetics are removed. Animations that slow down information delivery are
removed. The confidence bar fills from 0 to value — this communicates that
the number was just calculated, not that it was pre-set. That is the reason
for the animation. Every animation has a reason that can be stated in one
sentence.

────────────────────────────────────────────────────────────────────────────────
S01 — LANDING PAGE
────────────────────────────────────────────────────────────────────────────────

SCREEN NAME:     Landing Page
PURPOSE:         Convert visitors to users. Answer "What is this? Who is it
                 for? Can I try it now?" within 5 seconds of arrival.
BUSINESS GOAL:   Maximize conversion to first scan (guest or registered).
                 Secondary: email sign-up conversion. Tertiary: build brand
                 credibility with professional users.
USER GOAL:       Understand what VoiceGuard does and decide whether to try it.

ENTRY POINTS:
  - Direct URL / root path
  - Google / Bing organic search result
  - Social media shared link
  - Referral from blog post or news article
  - Shared scan result (S20) "Create Account" CTA carries UTM parameter

EXIT POINTS:
  - S02 Sign Up (primary CTA "Get Started Free")
  - S08 New Scan (CTA "Try without an account")
  - S03 Login (nav link for returning users)
  - S14 Help Center (footer link)
  - S20 Shared Result (if user arrived from shared link, may go back)

SECTION BREAKDOWN:
  [NAV]       Public navbar — transparent on load, solid background on scroll
  [HERO]      Full-width hero: headline, sub-headline, dual CTAs, hero visual
  [HOW]       "How It Works" — 3-step horizontal card row
  [SOCIAL]    Stats bar — scan count, EER benchmark, free forever
  [USECASES]  Use case grid — 4 cards: Journalists, HR, Security, Researchers
  [TECH]      Technology credibility section — model name, benchmark, methodology
  [DEMO]      Embedded scan result preview (static screenshot or animated demo)
  [TRUST]     Testimonials placeholder (v1: "join X users who have analyzed Y
              files" — real number if > 1000, placeholder until then)
  [FOOTER]    Full public footer with links

COMPONENT PLACEMENT:
  Navbar:
    Left:   VoiceGuard logo (SVG, 28px height)
    Center: [About] [How It Works] — ghost links, 14px
    Right:  [Login] (ghost) + [Get Started Free →] (primary button, accent)

  Hero Section (min-height: 100vh, centered content):
    Headline:     "Is this voice real?"
                  Font: Inter Tight, 56px, weight 700, line-height 1.0
                  Max-width: 700px, centered
    Sub-headline: "AI-powered audio deepfake detection. Upload any recording.
                  Get a verdict in seconds. Free forever."
                  Font: Inter, 18px, weight 400, color text-secondary
                  Max-width: 580px, centered, margin-top: 20px
    CTA Row:      Two buttons, centered, gap 16px, margin-top 40px
                  Primary:   "Get Started Free"  — primary button, lg size
                  Secondary: "Try it now — no account needed" — ghost button, lg
    Hero Visual:  Right-aligned on desktop (50% width), full-width below hero
                  text on mobile. Shows a real scan result screenshot with:
                  verdict card (green "Human Voice 97.3%") + Grad-CAM panel.
                  Has a subtle animated shimmer on load to draw attention.
                  Alt text: "VoiceGuard scan result showing Human Voice verdict
                  with 97.3% confidence and frequency analysis heatmap"

  How It Works (3 columns, 24px gap, max-width 900px, centered):
    Each card:    Icon (48px, accent color) + Step number + Title + Description
    Step 1:       Upload icon    | "Upload Audio"    | "Drop any audio file..."
    Step 2:       CPU/AI icon    | "AI Analysis"     | "LCNN model analyzes..."
    Step 3:       Shield icon    | "Get Your Verdict"| "Clear Human or AI..."
    Connector:    Subtle arrow between cards on desktop (hidden on mobile)

  Stats Bar (full-width, surface background, 64px height):
    3 stats, separated by vertical dividers:
    "[N] scans completed"  |  "7.07% EER — beats academic baseline"  |  "Free forever"
    All stats: mono-lg font, white text, label in muted below

  Use Cases Grid (2×2 grid, desktop; 1×4 on mobile):
    Each card: icon + persona name + 2-line description + link "See how →"
    Journalist:   📰 "Verify leaked audio before publishing"
    HR/Recruiter: 👥 "Screen voice submissions for authenticity"
    Security:     🔐 "Detect vishing attacks in recorded calls"
    Researcher:   🔬 "Benchmark deepfake detection with Grad-CAM evidence"

  Technology Section (2-column: text left, specs right):
    Left:  "Built on real research" headline + paragraph about LCNN, ASVspoof
    Right: Spec cards:
           Model: LCNN (Light CNN) | EER: 7.07% | Dataset: ASVspoof 2019 LA
           Params: 699,938 | Baseline comparison: LFCC-GMM 8.09% EER
           "View methodology →" link (opens Help article)

  Demo Section:
    Title: "See it in action"
    Shows static image of full result page on a laptop mockup frame
    Below: "Your result will look like this" caption
    CTA: "Try it yourself →" → S08 guest

  Footer: (see Section 7.6 from Batch 01 for link structure)

USER ACTIONS:
  1. Click "Get Started Free" → navigate to S02
  2. Click "Try it now — no account needed" → navigate to S08 (guest mode)
  3. Click "Login" → navigate to S03
  4. Scroll page → navbar transitions from transparent to solid (border appears)
  5. Click any use case "See how →" → scroll to relevant section or help article
  6. Click footer links → navigate to respective pages

SYSTEM RESPONSES:
  - On scroll past hero: navbar background transitions to surface color
    (200ms ease-in-out transition)
  - On scroll to How It Works: step cards animate in from below (staggered,
    100ms delay each, translateY(20px) → 0, opacity 0 → 1, 400ms ease-out)
  - Live scan counter increments (if WebSocket connected) — animated count-up

VALIDATION RULES:
  None — this is a public marketing page with no form inputs.

ACCESSIBILITY REQUIREMENTS:
  - Skip-to-content link as first focusable element (visually hidden until
    focused): "Skip to main content" → targets main content area
  - Navbar: role="navigation" aria-label="Main navigation"
  - Hero: role="main" (wraps the primary content area)
  - CTA buttons: descriptive labels ("Get Started Free", not "Click here")
  - Hero visual: aria-hidden="true" for decorative animation elements;
    actual screenshot has full alt text
  - How It Works: role="list" with each step as role="listitem"
  - Stats bar numbers: aria-label="[number] scans completed" for screen readers
  - All links have descriptive text — no "click here" or "read more" alone
  - Contrast: headline text on dark background must meet 7:1 (AAA)
  - Motion: the shimmer animation on hero visual must respect
    prefers-reduced-motion (disable animation if set)

RESPONSIVE BEHAVIOR:
  Desktop (1200px+):
    - Full layout as described above
    - Hero: headline left-aligned at 600px, visual right-aligned at 50% width
    - How It Works: 3 columns horizontal
    - Use Cases: 2×2 grid

  Laptop (900–1199px):
    - Hero: headline centered, visual below headline text
    - How It Works: 3 columns still, reduced padding
    - Use Cases: 2×2 grid

  Tablet (600–899px):
    - Navbar: hamburger menu; full links in slide-down drawer
    - Hero: single column, visual hidden or shown as small thumbnail
    - How It Works: 3 columns compressed, descriptions hidden
    - Use Cases: 1×4 column

  Mobile (< 600px):
    - Navbar: hamburger; drawer
    - Hero: single column, sub-headline shortened to 2 lines max
    - CTAs: stacked vertically, full-width buttons
    - How It Works: 1 column stacked cards
    - Stats bar: stacked 3 rows
    - Use Cases: 1 column
    - Technology section: stacked
    - Demo: hidden (too small to be useful)

EMPTY STATE: N/A (static marketing page)

LOADING STATE:
  - Page renders progressively: text content first, images lazy-loaded
  - Hero visual: shows a blurred placeholder (same dimensions) that
    sharpens when image loads (blur-up technique)
  - Stats counter: shows "—" until API returns live count (if applicable)

SUCCESS STATE: N/A

ERROR STATE:
  - If live scan counter API fails: shows static fallback number
    ("10,000+ scans completed") — never shows an error to the user for
    a marketing vanity metric
  - If page itself fails to load: browser default error (out of scope)

EDGE CASES:
  - User is already authenticated and visits landing page:
    Navbar shows "Go to Dashboard →" instead of "Get Started Free"
    and replaces "Login" with "Dashboard" link
  - Shared scan link user (arrived from S20):
    Hero sub-headline variant: "Analyze the voice recording shared with you"
    Primary CTA: "Analyze Your Own Audio"
  - User visits from unsupported browser (IE):
    Banner at top: "VoiceGuard requires a modern browser. Download Chrome or
    Firefox for the best experience." [Download Chrome] [Download Firefox]

FUTURE IMPROVEMENTS (v2):
  - Live scan counter with WebSocket real-time update
  - Video demo (15-second autoplay, muted, loop) replacing static screenshot
  - Testimonial carousel with real quotes (after beta user collection)
  - "As seen in" press logos (after launch coverage)
  - A/B test: "Is this voice real?" vs "Detect AI-generated audio instantly"

S02 — SIGN UP
────────────────────────────────────────────────────────────────────────────────

SCREEN NAME:     Sign Up
PURPOSE:         Collect minimum registration data to create an account.
BUSINESS GOAL:   Convert landing page visitors to registered users.
                 Minimize drop-off during registration.
USER GOAL:       Create an account quickly to save scan results.

ENTRY POINTS:
  - S01 Landing Page primary CTA "Get Started Free"
  - S10 Scan Result post-guest-scan CTA "Save this result"
  - S03 Login "Don't have an account? Sign up" link
  - Email invitation links (future team feature)

EXIT POINTS:
  - S04 Email Verification (successful form submit)
  - S03 Login ("Already have an account?" link)
  - S08 New Scan (back to guest — "Continue without account" link)

SECTION BREAKDOWN:
  [PROGRESS]  3-step progress indicator: "Create account → Verify email → Start"
  [FORM]      Registration form: email, password, confirm password
  [OAUTH]     OAuth alternatives: Google button (primary), GitHub (secondary)
  [DIVIDER]   "or" divider between OAuth and form
  [LEGAL]     Terms of Service + Privacy Policy consent checkbox
  [FOOTER]    "Already have an account? Sign in"

COMPONENT PLACEMENT:
  Page layout: centered card (max-width 440px) on surface-2 background
  Card padding: 40px desktop, 24px mobile

  Progress Indicator (above card, or inside at top):
    Step 1 (active): ① Create account
    Step 2 (inactive): ② Verify email
    Step 3 (inactive): ③ Start using VoiceGuard
    Visual: numbered circles connected by a line
    Active: accent-colored filled circle, bold text
    Inactive: muted border circle, muted text

  OAuth Buttons (above divider):
    Google:  [Google icon] "Continue with Google" — secondary button, full-width
    GitHub:  [GitHub icon] "Continue with GitHub" — secondary button, full-width
    Gap: 12px between buttons

  Divider: full-width horizontal line with "or" centered in white space

  Form Fields (below divider):
    Email:
      Label: "EMAIL ADDRESS" (uppercase, 11px, label style)
      Input: type="email", placeholder "you@example.com"
      Inline validation: valid format check on blur
      Error: "Enter a valid email address" / "An account with this email exists"
      Helper: none

    Password:
      Label: "PASSWORD"
      Input: type="password" with show/hide toggle (eye icon, right side)
      Password strength meter (below input):
        1 bar (red):    "Weak — add more characters"
        2 bars (amber): "Fair — add uppercase or numbers"
        3 bars (green): "Strong"
      Requirements tooltip (? icon): "8+ characters, 1 uppercase, 1 number"
      Validation: on blur AND live update of strength meter on keystroke

    Confirm Password:
      Label: "CONFIRM PASSWORD"
      Input: type="password" with show/hide toggle
      Validation: checks match live AFTER first keystroke in this field
      (not before — don't show error before user has had a chance to type)
      Error: "Passwords do not match"
      Success: green check icon when matching

  Consent Checkbox:
    Checkbox + "I agree to the Terms of Service and Privacy Policy"
    "Terms of Service" and "Privacy Policy" are underlined links
    (open in new tab — legal pages should not disrupt the flow)
    Required: true (Submit disabled until checked)
    Error on submit without check: "Please accept the terms to continue"

  Submit Button:
    Label: "Create Account"
    Style: primary button, full-width, lg size
    Disabled state: when any field has an error OR required fields empty
    Loading state: "Creating account..." + spinner (replaces label)
    Error state: see Error States below

  Footer link:
    "Already have an account? Sign in →" — centered, below card

USER ACTIONS:
  1. Type email → blur → inline validation fires
  2. Type password → live strength meter updates
  3. Type confirm password → live match check after first keystroke
  4. Click show/hide password icon → toggles visibility
  5. Click Terms / Privacy links → open in new tab
  6. Check consent checkbox → enables submit button
  7. Click "Create Account" → form validates, submits, navigates to S04
  8. Click "Continue with Google" → OAuth popup opens
  9. Click "Continue with GitHub" → OAuth popup opens
  10. Click "Sign in →" → navigate to S03

SYSTEM RESPONSES:
  - Email blur: if email format invalid → inline error immediately
  - Email blur: if email already registered → "Account exists. Sign in →"
    (the link in the error goes to S03 pre-filled with the email)
  - Password keystroke: strength meter updates in real-time
  - Password blur: if requirements not met → show specific missing requirement
  - Confirm password keystroke (after user has started typing here):
    match check live; error disappears as soon as strings match
  - Submit click with errors: all errors show simultaneously, scroll to first
  - Successful submit: loading state → navigate to S04 (500ms loading max)
  - OAuth click: browser popup for provider; on success → S06 Onboarding
    (OAuth skips email verification step)
  - OAuth failure: popup-level error, page shows alert:
    "Sign-in failed. Try again or use email and password."

VALIDATION RULES:
  Email:
    - Required
    - Valid email format (RFC 5322 simplified)
    - Not already registered (server-side, on blur via debounced API call)
    - Validate on: blur, revalidate on submit

  Password:
    - Required
    - Minimum 8 characters
    - At least 1 uppercase letter
    - At least 1 number
    - Strength meter: weak (<8 chars), fair (8+ chars, missing 1 req),
      strong (all requirements met)
    - Validate on: blur for requirements; live for strength meter

  Confirm Password:
    - Must match password field exactly
    - Validate on: first keystroke in this field (after user starts typing)

  Consent:
    - Required (boolean true)
    - Validate on: submit only

ACCESSIBILITY REQUIREMENTS:
  - Form: role="form" aria-label="Create account"
  - All inputs: associated labels via for/id (not placeholder as label)
  - Password requirements: aria-describedby pointing to requirements tooltip
  - Strength meter: role="meter" aria-valuenow={strength} aria-valuemin=0
    aria-valuemax=3 aria-label="Password strength"
  - Error messages: aria-live="polite" region; associated with input via
    aria-describedby
  - OTP/confirmation: auto-complete="email" on email field,
    auto-complete="new-password" on password fields
  - Submit button: aria-disabled="true" when disabled (not disabled attr,
    to keep it focusable for screen reader users who need the error message)
  - OAuth buttons: clear labels "Continue with Google" not just logo
  - Focus order: OAuth Google → OAuth GitHub → Email → Password →
    Confirm → Checkbox → Submit

RESPONSIVE BEHAVIOR:
  Desktop/Laptop: centered card with max-width 440px, surrounded by
    surface-2 background. Padding: 40px.
  Tablet: same card, reduced outer padding
  Mobile: card fills full width (16px horizontal margin), padding 24px.
    Keyboard appearance: sticky submit button above keyboard (position fixed
    bottom on iOS to avoid scroll issues with soft keyboard)

EMPTY STATE: N/A (form page)

LOADING STATE:
  - Page load: form card fades in (opacity 0→1, 300ms)
  - OAuth button click: spinner in button, button disabled, "Connecting..."
  - Form submit: button transitions to loading (spinner + "Creating account...")

SUCCESS STATE:
  - Brief (200ms) green check on button before navigation to S04

ERROR STATE:
  Generic server error: Alert banner at top of form (inside card):
    Type: error alert
    Icon: warning icon
    Message: "Something went wrong. Please try again."
    [Dismiss ×]

  Rate limit: "Too many sign-up attempts. Please wait 15 minutes."

  Server validation failure (e.g., email already exists despite client
  check passing): the server error message appears inline under email field

EDGE CASES:
  - User navigates back from S04 to S02: form is cleared (do not re-submit)
  - User with OAuth account tries email sign-up with same email:
    Error: "You signed in with Google previously. [Sign in with Google]"
  - Browser autofill fills all fields instantly: re-run validation on
    input event to ensure strength meter and match check reflect autofill
  - Clipboard paste into password: triggers live strength update
  - Very long email: input truncates with ellipsis, full value in tooltip

FUTURE IMPROVEMENTS:
  - Magic link sign-up (email only, no password)
  - Phone number as alternative identifier
  - "Invite code" field for private beta gating

BUSINESS GOAL:   Return users to the product quickly. Prevent abandonment.
USER GOAL:       Get back into the product fast.

ENTRY POINTS:
  - S01 Landing Page navbar "Login" link
  - Session expiry redirect (with return URL parameter preserved)
  - Deep links from notification emails (include return URL)
  - S02 Sign Up "Already have an account?" link
  - S05 Forgot Password success state redirect

EXIT POINTS:
  - S07 Dashboard (successful authentication)
  - S05 Forgot Password
  - S02 Sign Up

SECTION BREAKDOWN:
  [OAUTH]    Google + GitHub OAuth buttons
  [DIVIDER]  "or" divider
  [FORM]     Email + Password inputs
  [REMEMBER] "Remember me" checkbox
  [SUBMIT]   Login button
  [FORGOT]   Forgot password link
  [SIGNUP]   "No account? Create one" link

COMPONENT PLACEMENT:
  Same centered card layout as S02 (440px max-width, 40px padding)
  No progress indicator (returning users don't need it)

  OAuth: identical to S02
  Form:
    Email: type="email", placeholder "you@example.com", autofocus on load

    Checkbox: "Keep me signed in for 30 days"
    Behavior: if checked, refresh token TTL extends to 30 days
    Default: unchecked

  Forgot Password:
    Positioned: below password input, right-aligned

    Label: "Sign In"
    Style: primary, full-width, lg

  Footer:
    "New to VoiceGuard? Create a free account →"

USER ACTIONS:

  Primary UI:    Inter (Variable font, weight 100–900)

  mono-sm       13px   400     1.4       0px    SHA-256 hash, UUIDs, IDs
  mono-xs       11px   400     1.4       0px    Dense technical metadata

TYPOGRAPHIC RULES:
  - Never use weight < 400 for body text (readability on screens)
  - Maximum 80 characters per line for body text (line length)
  - Maximum 60 characters per line for narrow content columns
  - Avoid more than 3 type sizes on a single screen section
  - Technical text (hashes, IDs, scores) always uses JetBrains Mono
  - Button labels: 14px (md) weight 500, 16px (lg) weight 500
  - All input labels: uppercase, 11px, letter-spacing 0.8px
  - Error messages: 12px, body-sm, never bold (emphasis via color, not weight)
  - Empty state headings: heading-md (not xl — empty states are not heroic)
  - Verdict label: heading-xl minimum — it is the most important text on page

SECTION 7 — INTERACTION DESIGN
================================================================================

────────────────────────────────────────────────────────────────────────────────
7.1 STATE DEFINITIONS FOR ALL INTERACTIVE ELEMENTS
────────────────────────────────────────────────────────────────────────────────

Every interactive element has FIVE baseline states. All five must be designed.

DEFAULT:    Element at rest, no user interaction
HOVER:      Mouse cursor is over the element (desktop only)
FOCUSED:    Element has keyboard focus (Tab / click)
ACTIVE:     Element is being pressed (mousedown / touchstart)
DISABLED:   Element is not interactive (no user action possible)

Additional states (context-dependent):
LOADING:    Element triggered an async action (button submitting)
ERROR:      Element validation failed or action failed
SUCCESS:    Element action completed successfully
SELECTED:   Element is in a selected state (tabs, filter chips, nav items)
EXPANDED:   Element reveals content on expansion (accordion, collapsible)

STATE TRANSITION RULES:
  hover → focused: allowed simultaneously (mouse users can hover + focus)
  focused + active: pressed while focused (keyboard + mouse)
  disabled: overrides all other states — no hover, no focus, no active
  loading → default: on action complete (navigates, or shows success then reset)
  error: can coexist with focused (user correcting a field)

────────────────────────────────────────────────────────────────────────────────
7.2 HOVER STATES
────────────────────────────────────────────────────────────────────────────────

BUTTONS:
  All variants: opacity 0.85 on background color, 150ms ease transition
  Exception: link variant shows underline, no bg change

CARDS (interactive):
  Background shifts from surface to surface-3 (subtle lightening in dark mode)
  Border shifts from border to border-hover

7.4 FOCUS STATES
────────────────────────────────────────────────────────────────────────────────

FOCUS RING (universal):
  Outline: 2px solid border-focus (accent in dark, Apple-blue in light)
  Outline-offset: 2px
  Shadow: shadow-focus (0 0 0 3px rgba(accent, 0.3))
  Radius: matches element's own border-radius
  Applied to: ALL interactive elements (buttons, inputs, links, checkboxes,
              select, tabs, accordion triggers, icon buttons)

NEVER remove outline without providing an alternative focus indicator.

FOCUS MANAGEMENT RULES:
  1. On modal open: focus moves to first focusable element inside modal
  2. On modal close: focus returns to the element that triggered it
  3. On page navigation: focus moves to main heading of new page
  4. On dialog confirm: focus returns to trigger or next logical element
  5. On toast appear: do NOT move focus to toast (disruptive)
  6. On scan result load: focus moves to verdict card heading
  7. On accordion expand: focus stays on trigger (content is below, accessible
     by continuing to Tab)
  8. Skip link: "Skip to main content" as first focusable on every page

7.5 DISABLED STATES
────────────────────────────────────────────────────────────────────────────────

VISUAL: opacity 0.4 on the element (background, text, icon all dim together)
CURSOR: not-allowed
POINTER EVENTS: none (no hover effects)
ACCESSIBILITY: use aria-disabled="true" instead of the disabled HTML attribute
  on buttons, so they remain focusable and screen reader users can discover
  WHY the button is disabled (via tooltip or context)

EXCEPTION: Form inputs that are truly read-only (not user-editable) should
use aria-readonly="true" and show dashed border instead of solid, to distinguish
from "disabled" (unavailable) vs "read-only" (intentionally not editable).

DISABLED FORM FIELDS: slightly lighter background, muted text, dashed border

7.6 ANIMATION SYSTEM
────────────────────────────────────────────────────────────────────────────────

TIMING TOKENS:
  duration-instant:  50ms   — press feedback (scale animation)
  duration-fast:    100ms   — hover color transitions
  duration-normal:  200ms   — standard transitions (background, border)
  duration-enter:   300ms   — elements entering (modals, toasts slide-in)
  duration-content: 400ms   — card/section entrances
  duration-reveal:  600ms   — confidence bar fill, data reveal
  duration-slow:    800ms   — page-level transitions, complex sequences
  duration-extra:  1000ms+  — only for onboarding animations (welcome step)

EASING TOKENS:
  ease-standard:  cubic-bezier(0.4, 0, 0.2, 1)   — standard transitions
  ease-decelerate: cubic-bezier(0.0, 0, 0.2, 1)   — elements entering view
  ease-accelerate: cubic-bezier(0.4, 0, 1, 1)     — elements leaving
  ease-spring:    cubic-bezier(0.34, 1.56, 0.64, 1) — bouncy (onboarding only)
  ease-linear:    linear                           — spinners, progress bars

REDUCED MOTION:
  All animations wrapped in:
    @media (prefers-reduced-motion: reduce) { ... no animation ... }
  Reduced motion replacements:
    - Slide-in → instant opacity fade
    - Confidence bar fill → instant display at final value
    - Scale effects → none
    - Shimmer → static skeleton background
    - Pulsing → static indicator

ANIMATION INVENTORY (all animations in the product):

  1. Verdict card entrance (S10):
     fade-in + scale(0.97→1), 400ms ease-decelerate, on result load

  2. Confidence bar fill (S10, S12):
     width: 0% → final%, 600ms ease-decelerate, starts after verdict appears
     + 200ms delay after card appears

  3. Result sections stagger (S10):
     Each section (verdict → breakdown → viz → limitations) fades in
     with translateY(8px→0), 400ms ease-decelerate, +80ms stagger per section

  4. Modal enter (all modals):
     scale(0.95→1) + opacity(0→1), 250ms ease-decelerate, overlay fades in

  5. Modal exit:
     scale(1→0.95) + opacity(1→0), 200ms ease-accelerate

  6. Toast enter:
     translateX(100%→0) + opacity(0→1), 300ms ease-decelerate (from right)
     Mobile: translateY(-100%→0) (from top)

  7. Toast exit:
     translateX(0→100%) + opacity(1→0), 200ms ease-accelerate

  8. Sidebar collapse/expand:
     width transition, 250ms ease-standard, with icon cross-fade

  9. Mobile drawer open:
     translateX(100%→0), 300ms ease-decelerate, overlay fades in 200ms

  10. Processing spectrogram animation:
      Bars oscillate in wave pattern, 2s linear loop, pauses when tab hidden

  11. Processing step transition:
      Spinner appears for active step, check appears for done
      Check: scale(0→1) + opacity, 200ms ease-spring

  12. Page transitions (between routes):
      Content: opacity(1→0) + opacity(0→1), 200ms (exit) + 300ms (enter)
      Shell (sidebar/topbar): does not animate, stays stable

  13. Onboarding step change:
      Current step: translateX(0→-30px) + opacity(1→0), 250ms ease-accelerate
      Next step: translateX(30px→0) + opacity(0→1), 350ms ease-decelerate

  14. Dropzone drag-over:
      Border color: 150ms, background: 150ms ease-standard

  15. Record button pulse:
      Outer ring: scale(1→1.3), opacity(1→0.3), 1.5s linear infinite

  16. Button press (all buttons):
      scale(1→0.97), 100ms ease-standard, releases on mouseup/touchend

7.10 UNDO PATTERNS
────────────────────────────────────────────────────────────────────────────────

SINGLE SCAN DELETE:
  Action: user confirms delete in ConfirmDialog
  Optimistic: scan row immediately removed from UI
  Toast: "Scan deleted" + [Undo] link (5-second window)
  If Undo clicked: scan row reappears (fade in), toast dismisses
  If 5s passes: server delete executes, no more undo possible
  If toast dismissed manually before 5s: server delete executes immediately

BULK DELETE:
  Same pattern but: "X scans deleted" + [Undo]
  Undo restores all deleted scans

ACCOUNT DELETE:
  No undo via toast (too significant)
  Instead: 30-day soft-delete recovery window
  Email sent with: "Changed your mind? Recover your account within 30 days"
  Recovery link navigates to special page that reactivates account

SETTINGS CHANGES:
  No undo (settings are reversible — just change back)
  No undo toast (auto-saved settings would generate too many toasts)
  Exception: "Export my data" — shows toast confirming download started

  Alert:    role="alert" (urgent); role="status" (non-urgent)
  Progress: role="progressbar" aria-valuenow/min/max/label
  Meter:    role="meter" aria-valuenow/min/max/label (confidence bar)
  Tooltip:  role="tooltip" with id; trigger has aria-describedby pointing to it

LIVE REGIONS:
  Scan processing steps: role="status" aria-live="polite" (non-urgent updates)
  Login error: aria-live="assertive" (requires immediate attention)
  Toast notifications: aria-live="polite" (informational)
  Form field errors: aria-live="polite" (associated via aria-describedby)
  Verdict reveal: aria-live="assertive" (the result is critical information)

IMAGES:
  Meaningful images: alt="[descriptive text]"
  Decorative images: alt="" (empty, not absent)
  Complex images (spectrogram, Grad-CAM): alt + adjacent long description
  SVG icons (decorative): aria-hidden="true"
  SVG icons (informational): role="img" aria-label="[description]"

9.5 SCREEN READER SPECIFIC BEHAVIOR
────────────────────────────────────────────────────────────────────────────────

NVDA + Chrome (Windows):
  - Browse mode vs forms mode: ensure interactive elements are reachable
    in both browse mode and forms mode
  - Announce form labels before inputs
  - Focus announcements for modal open/close

VoiceOver + Safari (macOS/iOS):
  - Swipe navigation on iOS: all content reachable with swipe right/left
  - Custom components (tabs, accordion): test with VO specifically

  - Touch exploration: all elements reachable by touch
  - Gesture shortcuts tested

SCREEN READER ANNOUNCEMENTS (critical moments):

  Page navigation:
    Announce: "Navigated to [page title]" — done by focus moving to H1

  Scan submission (S08 → S09):

9.7 ERROR ACCESSIBILITY
────────────────────────────────────────────────────────────────────────────────

Form validation errors must:
  1. Be associated with their input via aria-describedby
  2. Announce via aria-live (polite for inline, assertive for submit errors)
  3. Move focus to the first field with an error (on form submit failure)
  4. Use descriptive language: "Enter a valid email address"
     NOT: "Invalid input" or "Error in field 2"

Global errors (system errors) must:
  1. Appear as role="alert" for immediate announcement
  2. Be at the top of the page or modal (not below the fold)
  3. Include a recovery action (Retry, Contact support, or specific fix)

Processing failures (S09 error) must:
  1. Focus moves to the error heading when error replaces processing state
  2. Announce: "Analysis failed. [brief reason]. Try again or go to Dashboard."

────────────────────────────────────────────────────────────────────────────────
11.1 CONTENT PRINCIPLES
────────────────────────────────────────────────────────────────────────────────

1. PLAIN LANGUAGE: Write for a 12-year-old. Use short sentences. Avoid jargon
   unless the audience requires it (professionals can see technical terms in
   the expanded details sections).

2. ACTIVE VOICE: "The model detected patterns" not "Patterns were detected."

3. HONEST: Never oversell confidence. Never minimize limitations. If the model
   is uncertain, say so clearly. Never use absolute language for uncertain results.

4. SPECIFIC: Error messages name the problem. "File exceeds 10MB limit" not
   "Upload error." Action buttons say what they do. "Delete scan" not "OK."

5. HUMAN: Short, direct. VoiceGuard is a technical product but speaks simply.

6. CONSISTENT: Same terminology everywhere. Never call it "recording" in one
   place and "audio" in another for the same thing. Glossary:
     audio file / recording    (not: track, clip by default)
     scan / analysis           (not: test, check)
     verdict                   (not: result, output, prediction)
     Human Voice               (not: real, genuine, authentic, bonafide)
     AI-Generated Voice        (not: fake, synthetic, deepfake — too loaded)
     Uncertain                 (not: inconclusive, mixed, unknown)
     Grad-CAM / model attention (not: heatmap — too technical for casual users)
     confidence                (not: probability, score — too technical)

SECTION 13 — LOADING STATES
================================================================================

LOADING STATE RULES:
  - Any operation > 100ms gets a visual indicator
  - Any operation > 500ms gets a descriptive indicator (not just spinner)
  - Any operation > 3s gets a progress indicator or estimated time
  - Skeleton loaders match the EXACT shape of the final content
  - Never show a full-page blank screen during loading
  - Shell (nav, sidebar) renders immediately; content loads in
  - Minimum loading duration: 300ms (prevent flash of loading state for
    very fast operations — looks like a UI bug if instantly disappears)

SECTION 15 — ERROR STATES
================================================================================

ERROR STATE HIERARCHY (see Batch 01 Section 13 for strategy):
  Layer 1 — Inline: component-level, no page disruption
  Layer 2 — Toast: transient, non-blocking
  Layer 3 — Page-level: requires full attention / recovery action

────────────────────────────────────────────────────────────────────────────────
UPLOAD / DETECTION ERRORS
────────────────────────────────────────────────────────────────────────────────

File too large:
  Layer:     Inline (below dropzone)
  Icon:      warning icon (16px, alert color)
  Message:   "File exceeds 10MB. Please try a shorter clip or compress it first."
  Recovery:  User selects a new file; error clears when new valid file chosen

Format not supported:
  Layer:     Inline (below dropzone)
  Message:   "Format not supported. Use WAV, FLAC, MP3, M4A, OGG, or AIFF."
  Recovery:  User selects a supported format

Audio too short:
  Layer:     Inline warning (not error — still allows submission with caution)
  Icon:      info icon (warning color)
  Message:   "This file is very short ([0.3]s). Results may be unreliable for
             audio under 0.5 seconds."
  Recovery:  User proceeds (warning, not block) or selects longer file

File appears empty/corrupt:
  Layer:     Inline error (below dropzone)
  Message:   "This file appears to be empty or corrupted. Try a different file."
  Recovery:  Select new file

Processing failed (server error):
  Layer:     Page-level (S09 error state)
  Heading:   "Analysis failed"
  Body:      "Something went wrong during analysis. Your file was not stored."
  Actions:   [Try again] [Go to Dashboard]
  Try again: re-submits same file (if still in browser memory)

Processing timeout:
  Layer:     Page-level (S09 timeout state after 30s)
  Heading:   "Analysis is taking too long"
  Body:      "This may be due to high demand or server load. Your file was
             not stored."
  Actions:   [Try again] [Cancel]

Network error during upload:
  Layer:     Page-level (upload fails, S08 error)
  Message:   "Upload failed. Check your connection and try again."
  Actions:   [Retry]

Model/service error (500):
  Layer:     Page-level (S09)
  Heading:   "The AI service encountered an error"
  Body:      "This is a rare issue on our end. Your file was not stored."
  Actions:   [Try again] [Report this →] (opens S16 with bug type pre-selected)

SECTION 18 — FINAL UX RECOMMENDATIONS
================================================================================

────────────────────────────────────────────────────────────────────────────────
REC 01 — BUILD THE RESULT PAGE (S10) BEFORE EVERYTHING ELSE
────────────────────────────────────────────────────────────────────────────────
Priority:      CRITICAL
Build order:   S10 → S08 → S09 → S07 → S11 → Auth

S10 is the product. Every other screen exists to bring users to S10 or to
return them to past results. Build and validate S10 with real model output
before touching the navigation, history, or settings.

The confidence bar animation, the Grad-CAM panel layout, and the plain-
language summary copy are the three elements that earn user trust. If these
three don't work perfectly, no amount of polished navigation will compensate.

Test S10 with:
  - A genuine human recording (expected: high-confidence Human)
  - An AI-generated clip (expected: high-confidence AI)
  - A borderline recording (expected: Uncertain, clear communication)
  - A very short clip (< 0.5s, expected: graceful warning, not crash)
  - A noisy recording (expected: honest confidence reduction)

────────────────────────────────────────────────────────────────────────────────
REC 02 — NEVER HIDE THE LIMITATIONS NOTICE
────────────────────────────────────────────────────────────────────────────────
Priority:      HIGH

The limitations section is collapsed by default on S10 for usability.
But it MUST be:
  - Always present (never removed by a user setting or A/B test)
  - One click to expand (not buried in a help article)
  - Comprehensive (neural codec weaknesses, 4-second limit, etc.)
  - Identical across S10, S12, and S20 (consistency)

Do not condense the limitations to save space. Professionals will read this
section and trust VoiceGuard MORE, not less, because of it.

────────────────────────────────────────────────────────────────────────────────
REC 03 — THE GUEST MODE CONVERSION MOMENT IS DESIGNED, NOT DEFAULTED
────────────────────────────────────────────────────────────────────────────────
Priority:      HIGH

The post-scan guest CTA ("Save this result — create a free account") is
potentially the highest-converting touchpoint in the entire product.
A guest user who just received their answer has demonstrated they found
value. They are 5–10× more likely to convert here than on the landing page.

This CTA must:
  - Be visually prominent but not disruptive (between primary and secondary actions)
  - Name the specific benefit: "Save this result" (not generic "Create account")
  - Carry the scan context through sign-up (scan saved to account on verify)

Test this CTA's placement and copy in v1.1. Even a 1% improvement in guest
conversion rate at this moment compounds significantly over time.

────────────────────────────────────────────────────────────────────────────────
REC 04 — THE SHA-256 HASH IS A FIRST-CLASS FEATURE
────────────────────────────────────────────────────────────────────────────────
Priority:      HIGH

The SHA-256 hash is currently in the LimitationsCard (expanded section).
For forensic users (Persona 7 — Law Enforcement / Digital Forensics),
this is the most important metadata on the page.

Recommendation: compute SHA-256 client-side (Web Crypto API, before upload)
and display it prominently in the scan result header alongside the filename
and date — not buried in an expandable section.

For v1.2: consider adding an explicit "Evidence Package" section in the
result that groups: scan ID + SHA-256 + timestamp + model version. This
makes VoiceGuard defensible as a forensic tool.

────────────────────────────────────────────────────────────────────────────────
REC 05 — THE FEEDBACK LOOP IS WORTH DEDICATED PRODUCT ATTENTION
────────────────────────────────────────────────────────────────────────────────
Priority:      HIGH

S16 Feedback / Report Incorrect Result is not a support feature. Each
submission is a labeled data point: scan_id → model verdict → user verdict.
With 100+ reports, this becomes training signal for v2 model updates.

Actions required:
  1. Make the feedback form short (3 fields: model said, I believe, why)
  2. Pre-populate from scan context (zero friction to fill in)
  3. Store every submission — even general feedback can surface patterns
  4. Create an internal dashboard (v2) to review flagged scans
  5. Track feedback volume as a product health metric

If VoiceGuard gets 500 scans/week and 5% of users submit feedback, that is
25 labeled corrections per week. In 3 months: 300 labels — meaningful for
fine-tuning.

────────────────────────────────────────────────────────────────────────────────
REC 06 — IMPLEMENT DESIGN TOKENS BEFORE THE FIRST COMPONENT
────────────────────────────────────────────────────────────────────────────────
Priority:      HIGH (architectural)

Every color, spacing value, border radius, shadow, and typography value
defined in Section 5 must be implemented as CSS custom properties (or
equivalent in the chosen styling system) before any component is built.

Recommended structure:
  tokens.css (or tokens.json → generated CSS):
    - Color tokens (dark mode)
    - Color tokens (light mode, scoped to [data-theme="light"])
    - Spacing scale
    - Typography scale
    - Radius scale
    - Shadow scale
    - Motion tokens (duration + easing)

Every component references tokens only. Zero raw hex values in components.
This makes dark/light mode switching a one-line attribute change, and brand
evolution a token-file update rather than a cross-codebase find-and-replace.

────────────────────────────────────────────────────────────────────────────────
REC 07 — DESIGN THE PROCESSING SCREEN FOR PERCEIVED TRUSTWORTHINESS
────────────────────────────────────────────────────────────────────────────────
Priority:      MEDIUM

Research on perceived AI trustworthiness shows that a result that takes
1.5–3 seconds FEELS more trustworthy than an instant result. An instant
result looks like it wasn't analyzed.

Implementation: S09 Processing has a minimum display time of 1.5 seconds
even if the server responds faster. The step animations play out.

However: this only applies to the first step transition. Once the animation
communicates that work is happening, subsequent steps can complete at actual
speed. Do not artificially slow the processing — just ensure the minimum
1.5s so the animation plays at least once.

────────────────────────────────────────────────────────────────────────────────
REC 08 — ACCESSIBILITY IS NOT A SECOND PASS
────────────────────────────────────────────────────────────────────────────────
Priority:      HIGH

Accessibility should be built into components at creation time, not audited
and patched after. The cost of retrofitting accessibility is 5–10× the cost
of building it correctly from the start.

Required before any component ships:
  - All interactive elements: keyboard accessible
  - All images: alt text
  - All error messages: associated with inputs
  - All dynamic content: ARIA live regions
  - Color contrast: verified against tokens

The specific ARIA patterns for every component in this document are listed
in Sections 9 and 16. Engineers should reference these as acceptance criteria,
not suggestions.

────────────────────────────────────────────────────────────────────────────────
REC 09 — MOBILE IS NOT A SIMPLIFIED DESKTOP
────────────────────────────────────────────────────────────────────────────────
Priority:      MEDIUM

The most common mobile use case is a user who received a suspicious audio
message and wants a quick answer. This user is on a small screen, possibly
in a rush, possibly not technical.

Mobile-specific design priorities:
  1. The upload flow must work without drag-and-drop (tap to browse is primary)
  2. The verdict card must be readable without zooming (font sizes not reduced)
  3. The Analyze button must be sticky (above keyboard on iOS)
  4. The recording UI must have 72px+ touch targets
  5. The History screen must use card layout (table is unusable on 375px)

Test VoiceGuard on:
  - iPhone SE (375px) — smallest supported width
  - iPhone 14 Pro (393px) — common real-world
  - iPad Mini (768px) — tablet transition point

────────────────────────────────────────────────────────────────────────────────
REC 10 — PDF REPORT IS A GROWTH VECTOR, NOT JUST A FEATURE
────────────────────────────────────────────────────────────────────────────────
Priority:      MEDIUM

Every PDF report downloaded includes the VoiceGuard branding, the
voiceguard.app URL, and "Analyzed by VoiceGuard · Model: LCNN v1".
When a journalist submits this report to an editor, when a forensic
analyst includes it in a case file, when an HR professional attaches it
to personnel documentation — every one of those is word-of-mouth marketing.

The PDF layout must look professional:
  - Not a screenshot or browser print
  - Properly typeset with the product's visual identity
  - Contains all the forensically important metadata
  - Footer with URL and branding on every page

Invest in PDF design quality at parity with the web UI quality.
