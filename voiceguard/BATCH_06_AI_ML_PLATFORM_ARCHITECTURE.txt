SECTION 1 — EXECUTIVE SUMMARY
================================================================================

VoiceGuard is a free audio deepfake detection platform whose entire product
value proposition rests on a single AI capability: the ability to distinguish
human speech from AI-synthesized speech, reliably, in under 10 seconds, for
every user who arrives at the platform.

The current AI core is an LCNN (Light CNN) model trained on the ASVspoof 2019
LA benchmark. The model has 699,938 parameters and achieves 7.07% Equal Error
Rate (EER) on that benchmark — outperforming the published academic baseline.
It produces three outputs per inference: a human probability score, an
AI-generated probability score, and a Grad-CAM frequency heatmap that
visualizes which acoustic regions drove the decision. These three outputs are
the product. Every screen, every user flow, every trust signal in VoiceGuard
derives from this inference result.

This document specifies the complete AI platform that must surround that model
to make it production-grade. A research model is not a production AI system.
A production AI system requires:

  — An inference pipeline that handles arbitrary real-world audio safely
  — A model registry that tracks every deployed artifact with cryptographic
    integrity, training lineage, and performance benchmarks
  — A model versioning contract that defines what constitutes a breaking change
    and how to migrate safely
  — An evaluation framework with offline benchmarks, online monitoring, and
    acceptance criteria that must be satisfied before any model reaches users
  — A Responsible AI framework that makes the model's limitations explicit,
    measurable, and surfaced in the product UI
  — A monitoring system that detects confidence drift, concept drift, and
    silent degradation before users notice
  — A dataset governance framework that controls what training data is used,
    how it is documented, and how user feedback feeds back into the model
  — A full MLOps lifecycle from research to retirement
  — Security controls that prevent model theft, adversarial inputs, and
    supply chain attacks on model artifacts
  — A disaster recovery plan that defines how to respond to a corrupt model,
    a bad deployment, or a complete inference outage

This document addresses all of these requirements. It does not implement the
model. It designs the platform that makes the model trustworthy, governable,
observable, and improvable over time.

KEY PLATFORM DECISIONS (SUMMARY)
─────────────────────────────────
Decision 1: Single-model production, registry-governed.
  The LCNN is the sole production model in v1. All future model variants
  (including ensemble, larger architectures, or domain-specialized models)
  enter through the same model registry and promotion workflow.

Decision 2: Inference workers own the model lifecycle boundary.
  The model is loaded once at Celery inference worker startup. No request
  path ever loads the model. This architectural boundary is inviolable.

Decision 3: Feedback is a first-class AI platform concern.
  Every user feedback submission (incorrect verdict report) is a labeled
  correction datapoint. The platform explicitly stores model_verdict and
  user_verdict together for every piece of feedback to build a supervised
  correction dataset for v2 model improvement.

Decision 4: Version string on every prediction, forever.
  Every scan result stores the model_version_string that produced it. This
  enables reproducibility auditing, A/B comparison across deployed versions,
  and future analytics on model drift. This is non-negotiable.

Decision 5: Explainability is a first-class inference output, not an afterthought.
  Grad-CAM is computed as part of every inference run — not on demand, not
  optionally. The heatmap is a product deliverable, not a debug tool. Its
  generation is part of the inference SLA.

Decision 6: User-facing limitations are derived from AI platform data.
  The confidence threshold definitions (≥85%, 65–85%, <65%), the known
  weakness disclosures (A17 neural codec attacks, 36.8% EER on that type),
  and the model version displayed in the result UI are all driven by data
  in the model registry and model_versions database table. The UI never
  hardcodes these values.

SECTION 2 — AI PLATFORM VISION
================================================================================

2.1 WHAT THE AI PLATFORM IS
─────────────────────────────
The VoiceGuard AI Platform is the operational infrastructure that surrounds
the LCNN inference model. It is the collection of systems, processes, and
contracts that make the model:

  — Reliable (every scan returns a result or fails gracefully)
  — Reproducible (the same audio produces the same result for the same model version)
  — Observable (every inference is traced, timed, and monitored)
  — Governable (every model artifact is registered, versioned, and auditable)
  — Improvable (feedback flows back to training; new models enter through
    defined promotion workflows)
  — Trustworthy (the platform makes its limitations visible, not hidden)

The AI Platform is NOT the model itself. It is the scaffolding around the
model that turns a research artifact into a production system that users can
trust and operators can maintain.

2.2 PLATFORM SCOPE
───────────────────
IN SCOPE — AI Platform Responsibilities:

  INFERENCE LAYER
  — Audio ingestion, validation, and preprocessing for inference
  — Feature extraction (STFT, LPS, normalization, segmentation)
  — Model loading, warmup, and lifecycle management in workers
  — Forward pass execution and output interpretation
  — Grad-CAM explanation generation
  — Confidence calibration and threshold application
  — Result packaging and persistence

  GOVERNANCE LAYER
  — Model registry: artifact storage, metadata, checksums, lineage
  — Model versioning: semantic versioning, compatibility contracts
  — Dataset governance: registration, validation, documentation, lineage
  — Experiment management: training metadata, hyperparameter history,
    evaluation results, approval workflows
  — Responsible AI: bias monitoring, fairness metrics, limitation disclosures

  OPERATIONAL LAYER
  — Model monitoring: latency, confidence distribution, drift detection
  — Observability: inference traces, structured logs, metrics, dashboards
  — MLOps lifecycle: from research through retirement
  — Quality assurance: golden test suites, regression testing, calibration
  — Deployment strategy: worker management, scaling, rollback
  — Disaster recovery: model corruption, bad deployment, inference outage

  SECURITY LAYER
  — Model artifact integrity verification (SHA-256 checksums)
  — Adversarial input detection and handling
  — Model theft mitigation
  — Dataset security and access controls

OUT OF SCOPE — NOT AI Platform:
  — The LCNN model architecture itself (research/ML team concern)
  — Training code and training infrastructure (research concern)
  — The web application frontend (Batch 03)
  — The API routing and authentication layer (Batch 04)
  — The database schema design (Batch 05)
  — Email, PDF generation, notifications (backend platform concern)

2.3 NORTH STAR METRICS FOR THE AI PLATFORM
─────────────────────────────────────────────
The AI Platform is successful when:

  1. Inference SLA: p95 inference latency ≤ 5 seconds for files ≤ 60 seconds
  2. Inference availability: ≥ 99.5% uptime for the inference pipeline
  3. Model quality: production EER ≤ 10% on monitored evaluation set
  4. Explanation quality: Grad-CAM heatmap generated on ≥ 99% of successful scans
  5. Drift detection: confidence distribution shift detected within 24 hours
  6. Feedback loop velocity: new labeled feedback available for training review
     within 48 hours of submission
  7. Deployment safety: zero silent model regressions reaching production
     (caught by golden test suite before deployment)

SECTION 3 — AI PLATFORM PHILOSOPHY
================================================================================

3.1 INFERENCE PHILOSOPHY
─────────────────────────
Every inference request is a trust transaction. The user is asking VoiceGuard
to make a claim about audio they care about. The platform must be able to
justify that claim, acknowledge uncertainty, and never overclaim.

Three principles govern inference:

  PRINCIPLE: CONFIDENCE IS A FIRST-CLASS OUTPUT
  The model's softmax probabilities are not just implementation details — they
  are the primary output. The confidence score determines the verdict tier
  (definitive, borderline, uncertain) and drives the UI's visual treatment of
  the result. Confidence calibration (ensuring that "90% confidence" actually
  means correct 90% of the time) is an active engineering concern, not an
  assumption.

  PRINCIPLE: UNCERTAINTY IS AN HONEST ANSWER
  The "uncertain" verdict is not a failure mode. It is a correct response when
  the model cannot reliably determine authenticity. The platform must present
  uncertainty as a legitimate outcome with equal status to a definitive verdict,
  never treating it as an error to be hidden or masked.

  PRINCIPLE: EXPLANATION IS NOT OPTIONAL
  Grad-CAM explanation generation is part of every inference run. If Grad-CAM
  fails, the scan succeeds with a null heatmap and the UI degrades gracefully.
  But Grad-CAM failure is logged as a monitoring event because it indicates a
  platform issue. Explanation is a product deliverable, not a debug feature.

3.2 MODEL LIFECYCLE PHILOSOPHY
────────────────────────────────
Every model artifact that touches production must pass through the registry.
There are no shortcuts, hotfixes, or "quick deployments" that bypass the
registry → evaluation → approval → canary → production sequence. The registry
is the immutable chain of custody for every model that has ever served users.

  PHILOSOPHY: REGISTRY FIRST
  No model runs in any environment except local development without a registry
  entry. Staging and production environments refuse to load models that are not
  present in the registry with a valid checksum.

  PHILOSOPHY: EVALUATION BEFORE EXPOSURE
  No model reaches users without passing the golden test suite and the
  acceptance criteria defined in Section 9. An ML researcher's intuition that
  a model is better is not sufficient. Numbers are required.

  PHILOSOPHY: RETIREMENT IS PLANNED, NOT REACTIVE
  Every model version has a planned deprecation date established at promotion
  time. Retirement is a scheduled event in the MLOps lifecycle, not an
  emergency response to a model breaking.

3.3 DATA LIFECYCLE PHILOSOPHY
──────────────────────────────
Training data, evaluation data, and feedback data are governed assets with the
same rigor as production code. Every dataset has a registry entry, a version,
a lineage record, and a documented quality assessment.

  PHILOSOPHY: DATA LINEAGE IS NON-NEGOTIABLE
  Every model must be traceable to the exact dataset version and preprocessing
  pipeline used to train it. If a dataset version cannot be identified for a
  model in production, that model must not be in production.

  PHILOSOPHY: FEEDBACK DATA IS RESEARCH DATA
  User correction feedback (scan_id, model_verdict, user_verdict, description)
  is a permanently retained, research-grade dataset. It is never deleted. It
  is never overwritten. It is the seed of every future model improvement.

  PHILOSOPHY: AUDIO IS NEVER TRAINING DATA WITHOUT CONSENT
  VoiceGuard's core privacy promise (Batch 01, Batch 04) is that audio files
  are never stored permanently. This extends to the AI platform: audio files
  submitted by users are NEVER used as training data. Training data comes
  exclusively from public benchmark datasets and explicitly consented sources.
  This is a product promise that cannot be violated by the AI platform under
  any circumstance.

3.4 FEATURE LIFECYCLE PHILOSOPHY
──────────────────────────────────
Feature extraction is versioned alongside model versions. A change to the
preprocessing pipeline (different STFT parameters, different normalization
strategy) is a breaking change that requires a new model version. The features
produced by the extraction pipeline and the model that consumes them are a
matched pair — they are never decoupled.

  PHILOSOPHY: FEATURES AND MODELS SHIP TOGETHER
  The preprocessing specification (STFT parameters, normalization strategy,
  segmentation parameters) is documented in the model's registry entry.
  When the model version changes, the feature specification is re-validated.
  Feature drift (a change in real-world audio properties that shifts the
  feature distribution) is monitored explicitly.

3.5 PREDICTION LIFECYCLE PHILOSOPHY
─────────────────────────────────────
Every prediction has a lifecycle: created, delivered, optionally challenged
(by user feedback), and eventually part of the historical record. The
prediction lifecycle is immutable after delivery: the stored verdict, confidence,
and scores for a given scan never change, even if a new model would produce a
different result.

  PHILOSOPHY: PREDICTIONS ARE IMMUTABLE ONCE STORED
  A scan result stored in the database represents what the platform believed
  at the time of analysis. It is never retroactively updated when a new model
  is deployed. Users who want a re-analysis must submit a new scan. This
  preserves forensic integrity.

3.6 EXPERIMENT LIFECYCLE PHILOSOPHY
─────────────────────────────────────
Experiments are the research phase of the MLOps lifecycle. They are governed
by the same documentation discipline as production deployments, because the
best experiment becomes next production model. An experiment without documented
hyperparameters, training dataset version, and evaluation results cannot be
promoted to production.

  PHILOSOPHY: EXPERIMENTS ARE FUTURE PRODUCTION CANDIDATES
  Every experiment is treated as if it might be the next production model.
  Shortcuts taken in experiments (undocumented hyperparameters, unlabeled
  evaluation data) become blockers at promotion time.

3.7 EVALUATION PHILOSOPHY
───────────────────────────
Model evaluation is not a one-time gate at deployment. It is an ongoing
process that continues throughout the model's production lifetime. Offline
evaluation establishes a baseline before deployment; online monitoring
confirms that baseline holds in production.

  PHILOSOPHY: ACCEPTANCE CRITERIA ARE NUMERIC, NOT SUBJECTIVE
  No model is promoted to production by a verbal decision or code review
  alone. Acceptance criteria are published, numeric, and verifiable. Every
  promotion decision cites the specific evaluation numbers that qualified
  the model.

3.8 RESPONSIBLE AI PHILOSOPHY
──────────────────────────────
VoiceGuard is a tool that makes claims about the authenticity of human voices.
These claims have real-world consequences: a journalist publishing a false-
negative result, a court submission relying on an incorrect verdict, an HR
professional making a hiring decision based on a wrong score. The platform
must be honest about what the model can and cannot do.

  PHILOSOPHY: LIMITATIONS ARE PRODUCT FEATURES
  The model's known failure cases (A17 neural codec attacks), its EER on
  specific attack types, and its confidence thresholds are documented in the
  product UI (S10 Scan Result, "About This Result" card) as first-class
  product information. Hiding limitations would undermine credibility with
  exactly the professional users who matter most.

  PHILOSOPHY: CONFIDENCE IS CALIBRATED, NOT ASSUMED
  The platform does not assume that the model's softmax probabilities are
  well-calibrated. Calibration is measured explicitly. If the model is
  systematically overconfident or underconfident, calibration correction
  (Platt scaling or isotonic regression) is applied as a post-processing
  step before confidence values reach users.

3.9 HUMAN OVERSIGHT PHILOSOPHY
────────────────────────────────
The AI platform is not autonomous. Every model promotion, every change to
acceptance criteria, and every change to confidence thresholds requires
human approval. The platform provides data; humans make decisions.

  PHILOSOPHY: THE PLATFORM RECOMMENDS; HUMANS DECIDE
  The MLOps pipeline can automate evaluation and surface candidates for
  promotion. It cannot autonomously deploy a model to production. An ML
  Platform Engineer or AI Safety reviewer must approve every production
  deployment.

  PHILOSOPHY: EVERY PREDICTION IS REVIEWABLE
  Any user can report an incorrect prediction via the feedback mechanism.
  Any admin can inspect any scan result with its model version, inference
  time, confidence, and scores. No prediction is a black box after the fact.

3.10 VERSIONING PHILOSOPHY
────────────────────────────
Model versions follow semantic versioning with explicit breaking-change
definitions. A change that could cause previously "human" verdicts to become
"ai_generated" is a MAJOR version change. A change that improves accuracy
without altering the verdict distribution materially is a MINOR change.

  PHILOSOPHY: BREAKING CHANGES ARE EXPLICIT AND COMMUNICATED
  A major model version change is communicated to users via the notification
  system. Historical scan results are never retroactively updated. Users who
  care about version continuity can see which model version produced each of
  their results.

3.11 BACKWARD COMPATIBILITY PHILOSOPHY
────────────────────────────────────────
The inference API contract (input: audio file → output: verdict, confidence,
scores, heatmap, model_version) is stable across model versions. The schema
of the ScanResultResponse (Batch 04 Section 6.4) does not change when the
underlying model changes. New output fields may be added (additive changes);
existing fields are never removed or renamed.

  PHILOSOPHY: THE INFERENCE CONTRACT IS STABLE; THE MODEL IS NOT
  The contract between the AI platform and the backend API is fixed. The model
  behind that contract can change on any deployment without the API layer being
  aware of it. This is the primary isolation boundary between AI platform and
  backend platform.

3.12 RESPONSIBLE AI AND GOVERNANCE PHILOSOPHY
───────────────────────────────────────────────
AI governance at VoiceGuard is not a compliance checkbox. It is an operational
discipline embedded in the MLOps lifecycle. Every model deployment carries
with it a set of documented limitations, fairness measurements, and use-case
guidance that flows from the AI platform into the product UI.

  PHILOSOPHY: GOVERNANCE IS EMBEDDED IN THE PIPELINE
  Model governance documents (limitation disclosure, fairness assessment,
  use-case guide) are required artifacts for every model promotion. A model
  that has not been assessed for fairness across accent groups, audio quality
  conditions, and attack types cannot be promoted, regardless of its aggregate
  EER. The governance checklist is a gate in the promotion workflow, not an
  optional recommendation.

SECTION 4 — MODEL ARCHITECTURE
================================================================================

4.1 CURRENT PRODUCTION MODEL — LCNN v1
────────────────────────────────────────

Model Identity:
  Name:                    LCNN (Light CNN)
  Version String:          lcnn-v1.0.0-asvspoof2019la
  Architecture Class:      Convolutional Neural Network (lightweight)
  Task:                    Binary audio classification (human vs. AI-synthesized)
  Output:                  Softmax probabilities over 2 classes:
                           Class 0 = bonafide (human)
                           Class 1 = spoof (AI-generated)
  Parameter Count:         699,938 (~2.8MB model weights file)
  Benchmark:               ASVspoof 2019 LA (Logical Access)
  Benchmark Metric:        Equal Error Rate (EER)
  Production EER:          7.07% (lower is better; 0% = perfect)
  Known Weakness:          A17 attack type (Neural Codec/VALL-E style):
                           36.8% EER on this specific attack category

Architecture Concept (for platform purposes — NOT implementation):
  The LCNN applies a learned max-pooling-based feature selection (MFM —
  Maximum Feature Map activation) to spectrogram features. The model processes
  a Log Power Spectrum (LPS) input — a 2D representation of audio in the
  frequency-time domain — and classifies it as human or AI-synthesized.

  Feature map layer referenced for Grad-CAM: features[9]
  (The 9th feature map layer captures the acoustic patterns most relevant to
  the classification decision. Grad-CAM hooks into this layer to generate the
  frequency heatmap that identifies which spectral regions drove the verdict.)

Input Specification (what the model consumes):
  — Format: 2D tensor (Log Power Spectrum)
  — Spectrogram parameters: Hamming window, 25ms frame length, 10ms frame shift,
    FFT size 512
  — Sample rate: 16,000 Hz (all input audio normalized to this rate)
  — Channels: mono (stereo averaged to mono before feature extraction)
  — Duration: handled as overlapping 3-second segments with 1.5-second hop
  — Per-segment normalization: mean/variance normalization per frequency dimension,
    clipped to [-5, 5]

Output Specification (what the model produces):
  — Raw logits: [batch_size, 2] — unnormalized class scores
  — After softmax: [human_probability, ai_probability]
  — human_score + ai_score = 1.0 (always, by construction)
  — confidence = max(human_score, ai_score)

Post-Processing (applied by the platform, not the model):
  — Verdict determination via confidence thresholds (platform logic):
      confidence ≥ 0.85 → definitive verdict (human or ai_generated)
      0.65 ≤ confidence < 0.85 → borderline verdict (uses dominant score)
      confidence < 0.65 → uncertain verdict
  — Multi-segment aggregation: mean of human_score and ai_score across all
    segments; confidence recomputed from aggregated scores
  — Calibration correction: if calibration assessment shows systematic bias,
    Platt scaling or isotonic regression is applied to softmax outputs before
    threshold evaluation

Grad-CAM Output:
  — Layer hooked: features[9]
  — Technique: Gradient-weighted Class Activation Mapping
  — Output: 2D activation map normalized to [0, 1]
  — Colormap: viridis (or jet — configurable via model registry metadata)
  — Overlay: activation map overlaid on the mel-spectrogram at 50% alpha
  — Final encoding: PNG encoded as base64 text
  — Storage: scan_results.frequency_heatmap column (base64 in v1, URL in v2)

4.2 FUTURE MODEL SUPPORT — ENSEMBLE AND SUCCESSOR ARCHITECTURES
────────────────────────────────────────────────────────────────

The AI platform is designed to support model evolution without breaking
the inference API contract. Future model architectures that the platform
must be capable of supporting:

  SCENARIO A: LCNN v2 (same architecture, retrained on expanded dataset)
  — Same input spec, same output spec
  — Different model weights, different EER
  — Registry: new version_string, new checksum, same architecture_class
  — Backward compatibility: full (minor version change)

  SCENARIO B: Ensemble Model (LCNN + RawNet2 or similar)
  — Multiple underlying models; outputs aggregated (weighted average or voting)
  — May require multiple artifact files in the registry
  — Inference pipeline must support ensemble aggregation as a post-processing
    step without changing the output contract
  — Each constituent model has its own registry entry; the ensemble has a
    top-level registry entry that references them
  — Grad-CAM: computed for the primary model in the ensemble; future may support
    consensus heatmaps

  SCENARIO C: Domain-Specialized Models
  — Separate models for telephone-bandwidth audio (8kHz) vs. full-bandwidth
  — Platform routes inference to the appropriate model based on detected
    audio properties (sample rate, bandwidth) determined at preprocessing
  — Both models share the same output contract

  SCENARIO D: LLM-Augmented Reasoning (future v3)
  — If a future version adds LLM-based natural language explanation of
    acoustic findings, it is an additional output, not a replacement
  — The core classification remains the LCNN or successor
  — Platform must support prompt injection equivalent risks for any text
    generation layer (see Section 17)

  PLATFORM COMMITMENT FOR ALL FUTURE MODELS:
  — The ScanResultResponse schema (Batch 04 Section 6.4) does not change
  — model_version is always present in every response
  — human_score and ai_score always sum to 1.0
  — confidence is always max(human_score, ai_score)
  — verdict is always one of: human | ai_generated | uncertain

4.3 MODEL REGISTRY — STRUCTURAL OVERVIEW
─────────────────────────────────────────
The model registry is the single authoritative source of truth for every
model artifact that has ever been deployed to VoiceGuard. It is implemented
as a combination of:

  — The model_versions database table (Batch 05 Section 5, Entity 15):
    stores metadata, benchmark metrics, checksums, deployment dates
  — The artifact storage location (local filesystem path or object storage
    bucket in v2): stores the actual model weights file (.pt file)
  — An operational runbook document per model version: explains the model's
    architecture decisions, training configuration summary (not the full
    training script, but the architectural choices), known limitations, and
    operating assumptions

Every component of the registry is required before a model may be deployed
to staging or production.

4.4 MODEL METADATA SPECIFICATION
──────────────────────────────────
Each registered model version carries the following metadata (aligned with
the model_versions database entity in Batch 05):

  IDENTITY FIELDS
  version_string        Canonical ID (e.g., "lcnn-v1.0.0-asvspoof2019la")
  display_name          Human-readable name for UI and reports
  architecture_class    Architecture family (lcnn, rawnet2, ensemble, etc.)
  description           Technical summary (not > 500 words)

  PROVENANCE FIELDS
  training_dataset      Registered dataset version string (see Section 14)
  experiment_id         Reference to the experiment record (Section 13)
  paper_url             Associated research paper (if any)

  PERFORMANCE FIELDS
  eer_percentage        Primary benchmark metric (numeric, e.g., 7.070)
  auc_roc               Area under ROC curve on held-out evaluation set
  f1_human              F1 score for the human class
  f1_ai                 F1 score for the AI-generated class
  calibration_ece       Expected Calibration Error (lower is better)
  known_weaknesses      JSON array of documented failure modes with EER per type

  ARTIFACT FIELDS
  parameter_count       Integer count of trainable parameters
  model_file_size_bytes Integer; size of .pt weights file
  checksum_sha256       SHA-256 of the model weights file (64-char hex)
  artifact_path         Path to model weights file in artifact storage
  inference_time_ms_p95 Measured p95 inference time on the reference hardware
                        at model registration time (single segment, CPU)

  LIFECYCLE FIELDS
  is_active             Boolean; true for the currently active production model
  status                Enum: experimental | canary | production | deprecated | retired
  created_at            Registration timestamp
  deployed_at           When this version became production (set at promotion)
  deprecated_at         When this version was superseded (set at retirement)
  approved_by           Identity of the engineer who approved production deployment
  canary_started_at     When canary deployment began

  CONFIDENCE THRESHOLD FIELDS
  threshold_certain     Float; confidence ≥ this → definitive verdict (default 0.85)
  threshold_uncertain   Float; confidence < this → uncertain verdict (default 0.65)
  colormap              String; colormap name for Grad-CAM visualization ("viridis")
  gradcam_layer         String; layer name for Grad-CAM hook ("features.9")

The confidence threshold fields being model-registry-resident (not hardcoded)
means that a future model with better calibration can ship with different
threshold values without any code change — only a registry update.

4.5 ARTIFACT STORAGE
──────────────────────

v1 Storage Location:
  Local filesystem on the Celery inference worker machine.
  Path convention: /opt/voiceguard/models/{version_string}/model.pt
  Access: read-only to the inference worker process
  Permission: owned by deployment service account; readable by inference
    worker service account only; no write access at runtime
  Backup: included in scheduled system backup; also stored as a separately
    archived copy in cold storage

v2 Storage Location (Object Storage):
  When batch processing or multi-region deployment arrives, model artifacts
  move to object storage (S3-compatible).
  Bucket: voiceguard-model-artifacts (private, no public access)
  Key prefix: models/{version_string}/model.pt
  Access control: worker IAM role has GetObject only; no PutObject at runtime
  Versioning: bucket versioning enabled; artifacts are immutable once written

Integrity at Load Time:
  At every worker startup, the SHA-256 checksum of the model weights file is
  computed and compared against the checksum_sha256 stored in the registry.
  If checksums do not match:
    — Worker refuses to accept tasks
    — CRITICAL alert is sent immediately
    — Incident response: Section 20

SECTION 5 — INFERENCE PIPELINE
================================================================================

5.1 PIPELINE OVERVIEW
──────────────────────
The inference pipeline is the complete sequence of operations from audio file
receipt to result storage. It runs entirely within the dedicated Celery
inference worker process. The API tier submits a job and polls for status;
it never touches the inference pipeline directly.

The pipeline has 17 stages. Each stage is described below: its purpose, its
inputs and outputs, its failure behavior, and its contribution to the final
result.

5.2 STAGE-BY-STAGE SPECIFICATION
──────────────────────────────────

STAGE 1 — AUDIO UPLOAD RECEIPT
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Transfer audio file from the HTTP request to ephemeral temp storage. This
  stage is owned by the backend API layer (Batch 04 Section 7), not the
  inference pipeline. It is documented here for completeness.

Input:
  HTTP multipart/form-data POST containing the audio file and user context.

Output:
  Audio file written to /tmp/voiceguard/{scan_id}/audio{extension}
  Scan record created in database with status = PENDING
  Celery task published: run_inference_task(scan_id)

Failure Behavior:
  File write failure → scan status = FAILED; temp directory cleaned; 500 error.
  The inference pipeline never receives a task for a scan that failed at
  this stage.

Platform Note:
  The AI Platform's concern begins at Stage 2. Stage 1 is the backend platform's
  domain. The boundary is the Celery task queue.

STAGE 2 — INPUT VALIDATION
──────────────────────────────────────────────────────────────────────────────
Purpose:
  The inference worker validates the file before beginning any audio processing.
  This is the AI Platform's first defense against malformed, malicious, or
  unexpected inputs.

Input:
  scan_id → worker retrieves file_path from database

Validations Performed:
  V1: File existence check
    Verify that /tmp/voiceguard/{scan_id}/audio{ext} exists.
    If not: scan → FAILED (error category 1 per Batch 04 Section 8.7).
    Do not retry. File may have been cleaned up by the failsafe job.

  V2: File size check
    Read file size from filesystem (not from database record).
    If > 10MB: scan → FAILED. Log anomaly (should have been caught upstream).

  V3: Magic bytes re-verification
    Re-read first 16 bytes and verify against known audio format signatures.
    This is a defense-in-depth check; the upload pipeline already verified
    magic bytes but the inference worker re-verifies to ensure the file was
    not modified between upload and inference.
    Supported signatures: WAV (RIFF), MP3 (ID3/FF frame sync), FLAC (fLaC),
    OGG (OggS), M4A (ftyp box at offset 4).
    If invalid: scan → FAILED. Log format with file_size.

  V4: File format self-consistency
    Attempt to open the audio file header only (not decode the full audio).
    Verify that the file is internally consistent: valid header, readable
    format metadata, extractable duration.
    If corrupt: scan → FAILED. Log corruption event.

Output:
  Validated file path ready for preprocessing.
  Scan status updated: PENDING → PROCESSING (and cached in Redis).

Failure Behavior:
  Any validation failure → scan → FAILED → delete temp file → log event.
  No retry for validation failures (file is the problem, not the system).

STAGE 3 — AUDIO PREPROCESSING — LOADING
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Load the raw audio waveform into memory. Normalize sample rate and channel
  count. Enforce maximum duration. This produces a canonical waveform
  representation that all subsequent stages operate on.

Input:
  Validated audio file path.

Operations:
  OP1: Audio Loading
    Load audio file using a Python audio I/O library (not ffmpeg subprocess).
    Capture both the raw samples (waveform array) and the sample rate.
    Handle loading errors gracefully: if the file fails to decode despite
    passing magic byte checks, it contains an unsupported codec variant.
    → scan → FAILED (error category 2).

  OP2: Sample Rate Normalization
    Target sample rate: 16,000 Hz (the sample rate the LCNN was trained on).
    If loaded sample rate ≠ 16,000 Hz: resample to 16,000 Hz.
    Resampling algorithm: sinc interpolation (anti-aliasing quality).
    Log: original_sample_rate, resampled=true/false.

  OP3: Channel Normalization
    Target: mono (1 channel).
    If stereo (2 channels): average both channels into a single mono signal.
    If more than 2 channels: average all channels into mono.
    Rationale: The LCNN was trained on mono audio. Feeding stereo without
    averaging would double the frequency content and distort the spectrogram.

  OP4: Duration Validation
    Compute duration = waveform length / sample_rate.
    Minimum duration: 0.5 seconds. If shorter: log warning, continue.
      (UI shows "Files under 0.5 seconds may produce unreliable results."
       The inference pipeline proceeds but the result is flagged as low-
       reliability via a low segment_count in scan_results.)
    Maximum duration enforcement: if > 300 seconds (5 minutes): truncate to
    first 300 seconds. This is a defense-in-depth check; the upload pipeline
    already enforces this limit.
    Store computed duration_seconds in scan_results.

Output:
  Canonical waveform: numpy array of float32 samples at 16,000 Hz, mono.
  Metadata: sample_rate=16000, channels=1, duration_seconds.

STAGE 4 — SILENCE DETECTION AND HANDLING
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Detect pathological silence conditions that would produce meaningless
  inference results. This protects result quality for edge-case inputs.

Input:
  Canonical waveform (Stage 3 output).

Operations:
  Compute RMS (root-mean-square) energy of the waveform.
  If RMS < silence_threshold (configurable; default: -60 dBFS):
    → Log warning: "near-silence audio detected"
    → Continue inference but store segment_quality_flag = "silence" in
      scan_results details JSONB field
    → The UI confidence will likely be low (the model was not trained on
      silence) and the result will likely resolve to "uncertain"
    → Do NOT fail the scan; surface the result with the flag

  Detect leading/trailing silence:
    If the audio has more than 2 seconds of silence at the start or end:
    trim silence. This improves the signal content entering the STFT.
    Log: leading_silence_ms, trailing_silence_ms.

Output:
  Preprocessed waveform with silence metadata.

STAGE 5 — NOISE AND CORRUPTION HANDLING
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Detect audio conditions that fall outside the model's training distribution
  and flag them for downstream result interpretation.

Input:
  Canonical waveform.

Checks Performed:
  CLIPPING DETECTION:
    If > 5% of samples are at the maximum amplitude value (clipping): the
    audio is likely distorted. Log warning, set quality_flag = "clipping".
    The model may still produce a result; it will likely have lower confidence.

  BANDWIDTH CHECK:
    Compute energy above 4kHz. If telephone-bandwidth audio (8kHz sample rate
    resampled to 16kHz, where energy > 4kHz is near zero): log warning,
    set quality_flag = "telephone_bandwidth".
    Known concern: the LCNN uses frequency patterns in 4-8kHz range to detect
    synthesis artifacts. Telephone-bandwidth audio eliminates this evidence and
    may increase false-negative rate. This must be surfaced in the result UI.

  CODEC ARTIFACT DETECTION (INFORMATIONAL ONLY):
    Detect characteristics of heavy MP3 compression (< 64 kbps artifacts)
    or lossy codec distortion. Log for monitoring purposes. The model handles
    compressed audio but heavily compressed audio may affect accuracy.

Output:
  Quality flags object: {silence, clipping, telephone_bandwidth, codec_artifact}
  These flags are stored in scan_results.details JSONB field and used to
  generate appropriate user-facing warnings in the result UI.

STAGE 6 — FEATURE EXTRACTION — STFT
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Transform the raw waveform into the 2D frequency-time representation that
  the LCNN model processes. This is the most critical preprocessing step —
  the model's entire perception of the audio derives from this transformation.

Input:
  Preprocessed waveform: float32 array, 16,000 Hz, mono.

STFT Parameters (fixed; must not change without a model version bump):
  Window function:  Hamming
  Frame length:     25ms → 400 samples at 16,000 Hz
  Frame shift:      10ms → 160 samples at 16,000 Hz
  FFT size:         512
  Number of frequency bins: FFT_size/2 + 1 = 257 bins

Operation:
  Apply Short-Time Fourier Transform to the waveform using the above parameters.
  Output: complex-valued STFT matrix of shape (257, num_frames).
  Compute power spectrum: |STFT|² (element-wise squared magnitude).
  Apply log compression: log(1 + power_spectrum) → Log Power Spectrum (LPS).
  Result: LPS matrix of shape (257, num_frames), float32, non-negative values.

Output:
  LPS matrix representing the full audio file.
  Metadata: num_frames (computed from duration and frame shift).

STAGE 7 — NORMALIZATION
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Normalize the LPS matrix to remove per-utterance energy level differences
  and scale features into the range the model was trained on. Without
  normalization, loudness differences between recordings would confound the
  model's perception of synthesis artifacts.

Input:
  LPS matrix (Stage 6 output).

Operations:
  PER-UTTERANCE MEAN-VARIANCE NORMALIZATION:
    For each frequency bin (row): compute mean and variance across all time frames.
    Subtract the mean; divide by the standard deviation.
    Apply across-frequency (not across-time) — the normalization is per-frequency-bin.
    This preserves the relative temporal dynamics within each frequency band
    while removing absolute energy level differences.

  CLIPPING TO VALID RANGE:
    After normalization, clip all values to [-5, 5].
    Rationale: Extreme outlier values (caused by silent frames or numerical
    instability) would dominate the model's attention. Clipping at ±5
    standard deviations retains all meaningful spectral variation while
    preventing numerical pathologies.

Output:
  Normalized LPS matrix, float32, clipped to [-5, 5].

STAGE 8 — SEGMENTATION
──────────────────────────────────────────────────────────────────────────────
Purpose:
  The LCNN expects fixed-length input segments. This stage partitions the
  full normalized LPS matrix into overlapping segments that match the model's
  input requirements.

Input:
  Normalized LPS matrix (Stage 7 output).

Segmentation Parameters (fixed; must not change without a model version bump):
  Segment duration:  3 seconds → 300 frames at 10ms frame shift
  Hop size:          1.5 seconds → 150 frames
  Segment shape:     (257 frequency bins, 300 time frames)

Segmentation Algorithm:
  Extract all 3-second segments with 1.5-second hop from the LPS matrix.
  If the last segment is shorter than 3 seconds:
    Pad with zeros to reach the full 300 frames.
    Mark the padded segment with a padding_flag for downstream awareness.
  If total duration < 3 seconds:
    A single segment is extracted (padded to 300 frames if needed).
    segment_count = 1; this is valid but produces less reliable results.

Output:
  List of segment LPS matrices, each of shape (257, 300).
  segment_count: integer (number of segments, stored in scan_results).
  The segment_count is an important quality signal: very short files (< 3s)
  produce segment_count = 1 and may have less reliable results.

STAGE 9 — TENSOR PREPARATION
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Convert the list of numpy segment arrays into the tensor format required
  by the LCNN model, and move the tensor to the appropriate compute device.

Input:
  List of segment LPS numpy arrays.
  Target device: CPU (v1); CUDA if GPU is available (v2).

Operations:
  Stack all segments into a batch tensor: shape (N, 1, 257, 300)
  where N = segment_count, 1 = channel dimension (greyscale spectrogram),
  257 = frequency bins, 300 = time frames.
  Convert dtype to float32 tensor.
  Move tensor to the same device as the loaded model (CPU or CUDA).

Output:
  Batched input tensor ready for LCNN forward pass.

STAGE 10 — INFERENCE
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Execute the LCNN model forward pass. This is the core AI computation.

Input:
  Batched input tensor (N, 1, 257, 300) on the model's device.
  Pre-loaded LCNN model (loaded at worker startup, not per-task).

Execution:
  Disable gradient computation (inference mode, not training mode).
  Run model forward pass.
  Output: logit tensor of shape (N, 2), where N = segment_count.
  Column 0: logit for bonafide (human) class.
  Column 1: logit for spoof (AI-generated) class.
  Apply softmax along dimension 1 → probability tensor (N, 2).
  Each row: [human_probability, ai_probability] summing to 1.0.

Timing:
  Measure wall-clock time from tensor input to softmax output.
  Store as inference_time_ms in scan_results (not including pre/post-processing).

GPU Handling (if available):
  Model and tensor are on CUDA device. Move softmax output back to CPU for
  all downstream processing.

Error Handling:
  CUDA OOM: catch exception; retry once on CPU (fallback).
  Numerical overflow (NaN/Inf in logits): log CRITICAL, scan → FAILED.
  Timeout enforcement: hard 30-second limit on the entire inference task.

Output:
  Probability tensor: (N, 2), float32, on CPU.

STAGE 11 — CONFIDENCE CALIBRATION
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Apply confidence calibration correction if the registered calibration model
  for this model version indicates that raw softmax probabilities are
  systematically biased.

Input:
  Probability tensor (N, 2).
  Calibration configuration from model registry: calibration_method,
  calibration_parameters.

Calibration Methods:
  NONE (default for v1):
    Raw softmax probabilities are used directly. This is the starting point.
    The model's calibration is measured (see Section 9) but correction is
    not applied unless calibration_ece > 0.05 (5% Expected Calibration Error).

  TEMPERATURE SCALING:
    Divide logits by a learned temperature parameter T before softmax.
    T > 1 softens probabilities (reduces overconfidence).
    T < 1 sharpens probabilities (addresses underconfidence).
    Temperature T is stored in the model registry calibration_parameters field.

  ISOTONIC REGRESSION:
    A non-parametric monotonic mapping from raw probability to calibrated
    probability. Stored as a serialized calibration model in the registry.
    Applied after softmax on the per-segment probabilities.

Calibration Application:
  If calibration_method = NONE: pass through.
  If calibration_method = TEMPERATURE: apply T to logits before softmax
    (requires re-running softmax with adjusted logits).
  If calibration_method = ISOTONIC: apply calibration model to human_probs.
    Recompute ai_probs = 1 - calibrated_human_probs.

Output:
  Calibrated probability tensor (N, 2).

STAGE 12 — MULTI-SEGMENT AGGREGATION
──────────────────────────────────────────────────────────────────────────────
Purpose:
  For files with multiple segments, aggregate per-segment probabilities into
  a single audio-level verdict. This is the platform's multi-segment policy.

Input:
  Calibrated probability tensor (N, 2), N > 0.

Aggregation Method (v1): MEAN POOLING
  human_score = mean of column 0 across all N segments.
  ai_score = mean of column 1 across all N segments.
  These means sum to 1.0 by construction.
  confidence = max(human_score, ai_score).

Alternative Aggregation Methods (for future consideration, not v1):
  — MAX POOLING on AI score: take the highest AI probability across segments.
    More sensitive to short synthesis artifacts anywhere in the clip.
    Risk: more false positives from isolated glitches.
  — VOTING: each segment casts a binary vote; majority determines verdict.
    More robust to outlier segments but loses confidence calibration.
  — WEIGHTED MEAN: segments closer to the audio start weighted more heavily
    (first impression matters). Requires tuning.

The aggregation method is stored in the model registry (aggregation_method
field). Changing from MEAN to another method requires a new model version
registration (it changes the prediction distribution).

Output:
  human_score: float [0, 1]
  ai_score: float [0, 1]
  confidence: float [0, 1]
  segment_scores: array of per-segment (human, ai) pairs (for audit/debug)

STAGE 13 — THRESHOLD EVALUATION
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Apply the confidence thresholds from the model registry to determine the
  final three-state verdict: human, ai_generated, or uncertain.

Input:
  human_score, ai_score, confidence.
  Thresholds from model registry: threshold_certain (default 0.85),
  threshold_uncertain (default 0.65).

Logic:
  IF confidence ≥ threshold_certain:
    IF human_score > ai_score: verdict = "human"
    ELSE: verdict = "ai_generated"
  ELIF confidence < threshold_uncertain:
    verdict = "uncertain"
  ELSE (threshold_uncertain ≤ confidence < threshold_certain):
    IF human_score > ai_score: verdict = "human"  [borderline]
    ELSE: verdict = "ai_generated"  [borderline]
    Log: borderline=true, confidence=X
    (The UI renders borderline verdicts with lower visual certainty)

The thresholds are NOT hardcoded in application code. They are read from the
model registry at worker startup and cached in worker memory. A threshold
change does not require a code deployment — only a model registry update
and worker restart.

Output:
  verdict: "human" | "ai_generated" | "uncertain"
  borderline: boolean (true when confidence is in the middle band)
  human_score, ai_score, confidence (passed through for storage)

STAGE 14 — EXPLANATION GENERATION (GRAD-CAM)
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Generate the frequency heatmap that visualizes which spectral regions drove
  the model's classification decision. This is a product deliverable.

Input:
  Original (pre-aggregated) segments for the representative segment.
  LCNN model with gradient computation temporarily enabled.
  gradcam_layer identifier from model registry (default: "features.9").

Representative Segment Selection:
  For single-segment files: use the only segment.
  For multi-segment files: use the segment whose individual confidence most
  closely matches the aggregated confidence (most representative segment).
  This ensures the heatmap reflects the evidence that drove the final verdict,
  not an arbitrary segment.

Grad-CAM Computation:
  Step 1: Re-run forward pass on the representative segment with gradient
    tracking enabled (unlike the batch inference pass).
  Step 2: Register forward hook on gradcam_layer to capture feature maps.
  Step 3: Register backward hook to capture gradients.
  Step 4: Compute target class score (the predicted class, not the true class).
  Step 5: Backward pass from the target class score.
  Step 6: Pool gradients: global average pool across spatial dimensions →
    weight vector (one weight per feature map channel).
  Step 7: Weighted combination: sum(weight_i × feature_map_i) → activation map.
  Step 8: ReLU activation map (retain only positive influences).
  Step 9: Resize activation map to match spectrogram dimensions (257, 300).
  Step 10: Normalize to [0, 1].
  Step 11: Apply colormap from model registry (default: viridis) → RGB image.
  Step 12: Load the LPS spectrogram of the representative segment.
    Normalize to [0, 255] uint8 for display.
    Convert to RGB greyscale.
  Step 13: Overlay heatmap on spectrogram at 50% alpha → composite image.
  Step 14: Encode composite image as PNG.
  Step 15: Base64 encode PNG bytes.

Failure Handling:
  If Grad-CAM fails at any step: log WARNING with the failure step and exception.
  Store null in scan_results.frequency_heatmap.
  Continue to Stage 15. Do NOT fail the scan because Grad-CAM failed.
  Emit metric: gradcam_failure_count (monitored; alert if > 1% of scans).

Output:
  gradcam_base64: string (base64-encoded PNG) or null.
  gradcam_generated: boolean (for monitoring).

STAGE 15 — WAVEFORM AND SPECTROGRAM GENERATION
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Generate the waveform visualization and the raw mel-spectrogram (greyscale)
  for display in the result UI alongside the Grad-CAM overlay.

Input:
  Canonical waveform (Stage 3 output).
  LPS matrix of the representative segment.

Waveform Generation:
  Purpose: Displayed in the S10 Result UI inline audio player.
  Downsample waveform to a display resolution (e.g., 800 points using
  RMS envelope decimation, not simple decimation, to preserve peak visibility).
  Encode as a JSON array of float values OR as a PNG image (implementation
  choice; the result API can return either format).
  Store in scan_results.details JSONB field or as a separate result field.

Raw Spectrogram Generation:
  Take the LPS matrix of the representative segment.
  Normalize to [0, 255] uint8 for greyscale image rendering.
  Encode as PNG. Base64 encode.
  This is the "left panel" of the Grad-CAM visualization card in S10.
  The right panel is the Grad-CAM overlay from Stage 14.

Failure Handling:
  If waveform or spectrogram generation fails: log WARNING, set nulls.
  The core scan result is unaffected.

Output:
  waveform_json: float array or null.
  spectrogram_base64: string (PNG) or null.

STAGE 16 — RESULT PACKAGING
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Assemble all inference outputs into the structured result object that will
  be written to the database.

Input:
  All outputs from Stages 10–15.
  scan_id, model_version from worker context.
  duration_seconds, segment_count from preprocessing.

Result Package (maps to scan_results columns per Batch 05):
  scan_id:              UUID from task input
  verdict:              "human" | "ai_generated" | "uncertain"
  confidence:           float [0, 1]
  human_score:          float [0, 1]
  ai_score:             float [0, 1]
  frequency_heatmap:    base64 PNG string or null
  duration_seconds:     float
  model_version:        version_string from model registry
  inference_time_ms:    integer (core inference time, Stage 10)
  segment_count:        integer
  details: JSONB containing:
    {
      "borderline": boolean,
      "quality_flags": { "silence": bool, "clipping": bool,
                         "telephone_bandwidth": bool, "codec_artifact": bool },
      "gradcam_generated": boolean,
      "aggregation_method": "mean_pool",
      "calibration_applied": "none" | "temperature" | "isotonic",
      "segment_scores": [[h1, a1], [h2, a2], ...],
      "waveform": [...] or null,
      "spectrogram_base64": string or null,
      "threshold_certain": float,
      "threshold_uncertain": float
    }

STAGE 17 — PERSISTENCE AND NOTIFICATION
──────────────────────────────────────────────────────────────────────────────
Purpose:
  Write the result to the database, update scan status, notify the user,
  and clean up the temp file. This is the terminal stage of the inference
  pipeline.

Operations (in order):
  1. Write scan_results record with all fields from the result package.
  2. Update scans.status = "complete", scans.completed_at = now().
  3. Cache scan status in Redis: key scan_status:{scan_id}, value "complete",
     TTL 300 seconds. (This unblocks the frontend polling loop.)
  4. Dispatch Celery general task: create_scan_notification(user_id, scan_id,
     verdict). (Not dispatched for guest scans where user_id is null — or a
     lightweight guest notification may be emitted via Redis pub/sub.)
  5. Delete temp directory: /tmp/voiceguard/{scan_id}/ recursively.
     Log: temp_file_deleted, scan_id, age_seconds.
  6. Emit metrics: inference_completed, verdict=X, confidence=Y,
     inference_time_ms=Z, segment_count=N, model_version=V.

Database Write Failure:
  If scan_results write fails: retry 3 times with exponential backoff.
  If all retries fail: scan status → FAILED; delete temp file; log CRITICAL.
  No partial results are ever served.

Output:
  scan_results record committed to PostgreSQL.
  Scan status = "complete" in database and Redis cache.
  Notification queued.
  Temp file deleted.
  Metrics emitted.

SECTION 6 — FEATURE ENGINEERING STRATEGY
================================================================================

6.1 FEATURE ENGINEERING PHILOSOPHY
─────────────────────────────────────
Feature engineering for VoiceGuard v1 is deliberately minimal and matched
to the LCNN model's training conditions. The model was trained on Log Power
Spectrum (LPS) features extracted with specific STFT parameters. Changing
any of these parameters constitutes a feature distribution shift that requires
model retraining and a new model version. Feature engineering changes and model
changes are inseparable.

6.2 INPUT REQUIREMENTS
────────────────────────

SUPPORTED AUDIO FORMATS:
  Format    Container   Codec           Magic Bytes
  ────────────────────────────────────────────────────
  WAV       RIFF        PCM / ADPCM     52 49 46 46
  FLAC      FLAC        FLAC lossless   66 4C 61 43
  MP3       MPEG        MP3             49 44 33 / FF FB
  OGG       Ogg         Vorbis          4F 67 67 53
  M4A       MP4/QuickTime  AAC          ftyp at offset 4
  AIFF      AIFF        PCM             46 4F 52 4D

SAMPLE RATE NORMALIZATION:
  All input audio is resampled to 16,000 Hz before any feature extraction.
  This is the sample rate used in ASVspoof 2019 LA training data.
  Resampling is non-destructive: no audio content is permanently altered.
  Only the in-memory representation is resampled; the original file is not
  modified (it is deleted after inference regardless).

CHANNEL NORMALIZATION:
  All multi-channel audio is averaged to mono before feature extraction.
  Rationale: The LCNN was trained on mono data. Channel averaging preserves
  energy while reducing dimensionality. Selecting one channel (e.g., left
  only) would introduce channel bias for stereo recordings.

DURATION LIMITS:
  Minimum effective duration: 0.5 seconds (below this, flag as low-reliability)
  Maximum duration: 300 seconds (5 minutes; enforced at upload layer)
  Model processing window: 3-second segments with 1.5-second hop
  Files shorter than 3 seconds: one padded segment; less reliable result
  Files 3–300 seconds: multiple segments; aggregated result is more stable

6.3 SILENCE HANDLING
──────────────────────
  Detection threshold: RMS energy < -60 dBFS = near-silence
  Leading/trailing silence: trim up to 2 seconds before feature extraction
  Pure silence input: allow inference; result will likely be "uncertain"
  Silence-heavy audio: set quality_flag = "silence"; surface in UI

6.4 NOISE HANDLING
────────────────────
  Background noise does not invalidate the inference result. The LCNN was
  evaluated on ASVspoof 2019 LA data which includes varied recording conditions.

  Known degradation scenarios (flagged but not rejected):
  — Heavy MP3 compression (< 64 kbps): may mask high-frequency synthesis
    artifacts; confidence may be reduced
  — Telephone bandwidth (8kHz effective): removes evidence in 4–8kHz range
    which the model uses for synthesis detection; flag as telephone_bandwidth
  — Clipping: flag as clipping; confidence likely reduced
  — Reverberation: not flagged in v1; known to affect accuracy for some
    TTS systems; documented as a known limitation

6.5 CORRUPTED FILE HANDLING
────────────────────────────
  A file that passes magic byte validation but fails to load or decode:
  → scan → FAILED (error category 2)
  → Log: file_size, claimed_mime_type, failure_stage
  → No retry (the file is corrupt, not the system)
  → User is notified: "This file could not be processed. Please check that
    the audio file is not corrupted and try again."

6.6 FEATURE EXTRACTION LIFECYCLE
──────────────────────────────────
The feature extraction specification is a versioned component of the model
registry. Each model_versions registry entry contains the full feature
specification used to train that model:

  STFT parameters:    window, frame_length_ms, frame_shift_ms, fft_size
  Normalization:      method (per-utterance MVN), clip_range [-5, 5]
  Segmentation:       segment_duration_s, hop_duration_s
  Sample rate:        16000 Hz
  Channels:           mono
  Feature type:       "lps" (Log Power Spectrum)

When a new model is registered, its feature specification is verified to match
the preprocessing pipeline code. Mismatches are a blocking error.

6.7 FEATURE VALIDATION
────────────────────────
At the boundary between Stage 7 (Normalization) and Stage 8 (Segmentation),
the feature matrix is validated:

  SHAPE CHECK: feature matrix shape must be (257, num_frames) where
    num_frames > 0. If num_frames = 0 (empty audio after preprocessing):
    scan → FAILED.

  VALUE RANGE CHECK: after clipping, all values must be in [-5, 5].
    If values outside this range are detected, log WARNING. Do not fail
    (clipping guarantees this; the check is a sentinel against implementation
    bugs in the normalization step).

  NAN/INF CHECK: if any NaN or Inf values exist in the feature matrix:
    scan → FAILED. Log CRITICAL. This indicates a serious preprocessing bug.

6.8 FEATURE VERSIONING
────────────────────────
Feature versions are not independently versioned from model versions. They
are co-versioned: the feature specification is part of the model's registry
entry. This means:

  — You cannot change the STFT parameters without registering a new model.
  — You cannot change the normalization strategy without registering a new model.
  — You cannot change the segmentation parameters without registering a new model.

This coupling is intentional. Feature engineering changes are not backward
compatible with the trained model — a different preprocessing pipeline produces
a different feature distribution, and the model's trained weights are
calibrated to the original distribution. Treating feature specs and model
weights as inseparable prevents the silent accuracy degradation that occurs
when preprocessing is updated without retraining.

SECTION 7 — MODEL REGISTRY
================================================================================

7.1 REGISTRY PURPOSE AND SCOPE
────────────────────────────────
The model registry is the single source of truth for every model artifact that
has touched any VoiceGuard environment. Its scope:

  — Every model that has run inference in production, staging, or canary
  — Every model that was evaluated but never deployed
  — Every model that was deployed and subsequently retired
  — The current active production model
  — Upcoming canary models

The registry does NOT contain training code, training scripts, or experiment
notebooks. Those belong in the experiment management system (Section 13).
The registry is the post-training, pre-deployment artifact store.

7.2 REGISTRY STRUCTURE
────────────────────────
The registry is implemented in two layers:

LAYER 1 — DATABASE (model_versions table, Batch 05 Entity 15):
  The relational truth about every registered model: version string, metadata,
  benchmarks, lifecycle state, checksum, and references to artifacts.
  Always-available, transactionally consistent, queryable by admin and
  monitoring systems.

LAYER 2 — ARTIFACT STORE (filesystem or object storage):
  The actual model weights files, stored at a well-known path derived from
  the version string. The database holds the path; the artifact store holds
  the bytes.

The two layers must be consistent: every database entry must have a
corresponding artifact, and every artifact must have a corresponding database
entry. Orphaned artifacts (artifacts without database entries) are flagged by
the registry integrity check job (runs daily).

7.3 REGISTRY OPERATIONS
─────────────────────────

OPERATION: REGISTER NEW MODEL
  Trigger: ML team produces a new trained model artifact
  Steps:
    1. Compute SHA-256 checksum of the model weights file
    2. Upload artifact to artifact store at path: {version_string}/model.pt
    3. Insert row in model_versions with status = "experimental"
    4. Record training metadata (training_dataset, experiment_id, parameter_count)
    5. Record benchmark performance (eer_percentage, auc_roc, f1_human, f1_ai)
    6. Document known limitations (known_weaknesses JSON array)
    7. Set feature specification fields (matching the training configuration)
    8. Send notification to AI Platform team: "New model registered: {version_string}"
  Output: model_versions record with status = experimental

OPERATION: PROMOTE TO CANARY
  Trigger: Model passes offline evaluation (Section 9) and receives approval
  Prerequisite: status = experimental; evaluation_passed = true;
    approval recorded in registry (approved_by, approved_at)
  Steps:
    1. Deploy model artifact to canary inference worker(s)
    2. Update status = "canary", canary_started_at = now()
    3. Route a percentage of inference traffic to canary workers
       (initial: 5–10% of traffic; increase based on monitoring)
    4. Begin online monitoring for canary (Section 11)
  Output: model_versions record with status = canary

OPERATION: PROMOTE TO PRODUCTION
  Trigger: Canary validation period complete (minimum 48 hours or 1,000 scans)
    with no regressions; human approval granted
  Prerequisite: status = canary; canary monitoring shows no regressions;
    approval recorded
  Steps:
    1. Set current production model: is_active = false on old version
    2. Set is_active = true, status = "production", deployed_at = now()
       on new version
    3. Deploy model artifact to all inference workers
    4. Restart inference workers to load new model (rolling restart)
    5. Log: model_promoted_to_production, old_version, new_version
    6. Send user notification if MAJOR version change
  Output: new production model; old model status = deprecated

OPERATION: DEPRECATE MODEL
  Trigger: A newer model has been promoted to production
  Steps:
    1. Set old model status = "deprecated", deprecated_at = now()
    2. Old model may still be referenced by historical scan results (valid)
    3. Old model workers are stopped after routing is switched
  Note: A deprecated model version is NEVER deleted from the registry.

OPERATION: RETIRE MODEL
  Trigger: Model version is no longer running on any worker and has been
    superseded for long enough that it is no longer being canary-evaluated
  Steps:
    1. Set status = "retired"
    2. Archive artifact to cold storage (do not delete — may be needed for
       forensic re-analysis or regulatory compliance)
    3. Remove artifact from active inference worker paths
  Note: Retired model metadata (version_string, checksum, EER) is retained
    forever. Artifacts are retained in cold storage per data retention policy.

OPERATION: ROLLBACK
  Trigger: Production model shows regression; emergency rollback required
  See Section 20 (Disaster Recovery) for full rollback procedure.

7.4 REGISTRY INTEGRITY CHECKS
──────────────────────────────
A scheduled daily job verifies the integrity of the registry:

  CHECK 1: Artifact existence
    For every model_versions row with status ≠ retired: verify that the
    artifact file exists at artifact_path. Alert if missing.

  CHECK 2: Checksum verification
    For the active production model and any canary models: verify that the
    artifact's SHA-256 matches checksum_sha256 in the registry.
    Alert (CRITICAL) if mismatch — possible tampering.

  CHECK 3: Exactly one active model
    Verify that exactly one row has is_active = true.
    Alert if zero (no active model — inference workers will fail to start)
    or more than one (ambiguous routing).

  CHECK 4: Canary has monitoring
    Verify that any model with status = "canary" has active monitoring
    dashboards. Alert if canary exists but no monitoring is running.

  CHECK 5: Orphaned artifacts
    List artifacts in artifact store; verify that each has a corresponding
    model_versions row. Alert on orphans (may indicate a failed registration).

7.5 REGISTRY ACCESS CONTROL
──────────────────────────────
  READ access:
    — Inference workers: read model artifact path and checksum only
    — Backend API: read model_version metadata for display in result UI
      (display_name, eer_percentage, description, known_weaknesses)
    — Admin panel: full read access to all registry fields

  WRITE access:
    — AI Platform Engineers: create new registry entries, update lifecycle fields
    — Automated deployment pipeline: update is_active, status, deployed_at
    — NO automated system may update checksum_sha256 or artifact_path after
      initial registration (immutable fields)

  IMMUTABLE FIELDS (cannot be updated after creation):
    version_string, checksum_sha256, artifact_path, training_dataset,
    parameter_count, eer_percentage, created_at

  MUTABLE LIFECYCLE FIELDS:
    status, is_active, deployed_at, deprecated_at, canary_started_at,
    approved_by, known_weaknesses (can be supplemented with new findings)

7.6 ARCHIVE POLICY
────────────────────
  Experimental models that were never promoted:
    Artifact: deleted after 90 days from creation
    Registry row: retained forever (for experiment lineage)

  Deprecated production models:
    Artifact: retained in warm storage for 12 months after deprecation,
    then moved to cold storage indefinitely
    Registry row: retained forever

  Retired models:
    Artifact: cold storage indefinitely
    Registry row: retained forever

  Rationale for permanent registry retention: any historical scan result
  references a model_version string. The registry must always be able to
  answer "what model was version X, and what did it do?" for forensic,
  legal, and user trust reasons.

SECTION 8 — MODEL VERSIONING
================================================================================

8.1 VERSION STRING FORMAT
───────────────────────────
All model versions follow this format:

  {architecture}-v{major}.{minor}.{patch}-{dataset}

  Examples:
    lcnn-v1.0.0-asvspoof2019la         (current production)
    lcnn-v1.1.0-asvspoof2019la         (same architecture, minor improvement)
    lcnn-v2.0.0-asvspoof2019la+wild    (breaking change + expanded dataset)
    ensemble-v1.0.0-asvspoof2019la     (new architecture family)
    rawnet2-v1.0.0-asvspoof2019la      (different architecture)

  Architecture identifiers: lcnn, rawnet2, ensemble, wav2vec2, whisper-cls
  Dataset identifiers: asvspoof2019la, asvspoof2021la, wild (in-the-wild data)
  Combined datasets: separated by +

8.2 SEMANTIC VERSIONING DEFINITIONS
─────────────────────────────────────

MAJOR VERSION (Breaking Change):
  A major version increment indicates that the model produces materially
  different verdicts for the same audio compared to the previous version.
  Breaking changes include:

  — Verdict distribution shift: a meaningful percentage of previously
    "human" audio is now classified as "ai_generated" or vice versa
    (threshold: > 2% of the production inference distribution changes verdict)
  — Confidence threshold changes: threshold_certain or threshold_uncertain
    change by more than 0.05
  — Feature specification change: different STFT parameters, normalization,
    or segmentation (requires model retraining)
  — Output schema change: new fields in the result, changed field semantics
  — Architecture change: switching from LCNN to a different model family

  Breaking change actions:
  — User notification via in-app notification system and email
    (email only if users opted in to model update notifications per preferences)
  — The result UI must not retroactively re-interpret old results
  — Old scan results retain their original model_version string (immutable)
  — Admin panel shows version distribution in historical scan results

MINOR VERSION (Non-Breaking Change):
  A minor version increment indicates an improvement within the same behavior
  contract. The model produces the same kind of output with (hopefully) better
  accuracy, but users and historical results are unaffected. Non-breaking
  changes include:

  — EER improvement on benchmark (same model architecture, better training)
  — Calibration improvement (same thresholds, better-calibrated probabilities)
  — Inference latency improvement (model quantization or compilation)
  — Addition of new known_weakness documentation (informational only)
  — Expansion of training dataset (same feature spec, more training data)

  Minor version actions:
  — No user notification required (silent improvement)
  — Canary deployment still required before production
  — Changelog entry in admin panel

PATCH VERSION (Operational Fix):
  A patch version increment addresses a defect in the model deployment that
  does not change the model weights or training. Patch changes include:

  — Checksum file update (file was re-serialized identically)
  — Calibration parameter correction (fixing a miscalculated temperature)
  — Documentation correction in registry metadata
  — Colormap or visualization parameter change

  Patch version actions:
  — No user notification
  — Registry update only; may not require worker restart depending on the change

8.3 EXPERIMENTAL MODELS
─────────────────────────
  Status: experimental
  Purpose: in development; evaluated in offline environments only
  Traffic: zero production traffic; isolated evaluation environment only
  Promotion requires: passing evaluation in Section 9 + human approval

  Experimental models may be tested on the developer's local machine with
  production-representative audio samples from the evaluation dataset.
  They must NEVER be deployed to staging or production without passing
  through the evaluation gate and the registry workflow.

8.4 CANARY MODELS
───────────────────
  Status: canary
  Purpose: limited production exposure for online evaluation
  Traffic: 5–10% initially, increased to 25–50% if stable
  Duration: minimum 48 hours; minimum 1,000 scans at any percentage
  Monitoring: dedicated monitoring dashboard (Section 12)
  Promotion requires: no regressions detected during canary period + human approval
  Rollback trigger: EER estimate > current production EER + 2%, or latency
    regression > 20%, or any CRITICAL error in canary workers

  Canary models run in parallel with the production model. A scan is routed
  to a canary worker with the configured traffic percentage (chosen at the
  Celery task dispatch level by setting a routing key or worker affinity).

8.5 PRODUCTION MODELS
───────────────────────
  Status: production
  Purpose: serves all non-canary inference traffic
  Count: exactly one active production model at any time
  Traffic: 100% minus any canary percentage
  Monitoring: full production monitoring suite (Section 11)
  Retirement: when superseded by a promoted canary

8.6 RETIRED MODELS
────────────────────
  Status: retired (or deprecated as intermediate state)
  Purpose: no longer serving traffic; registry record retained
  Traffic: zero
  Artifact: archived (not deleted)
  Access: historical scan results still reference this version string
  Impact: the model_versions database row is permanent; inference is impossible
    but metadata is always queryable

8.7 COMPATIBILITY GUARANTEES
──────────────────────────────
  GUARANTEED:
  — The inference API contract (input → output) is stable across all minor
    and patch versions. New minor versions produce the same output fields.
  — scan_results.model_version correctly identifies the model that produced
    each result for the lifetime of the database
  — The verdict enum values (human, ai_generated, uncertain) do not change
    without a major version increment and a migration plan for UI strings
  — The ScanResultResponse JSON schema does not gain required fields between
    minor versions (additive changes only)

  NOT GUARANTEED (major version break):
  — Verdict consistency across major versions: the same audio may get a
    different verdict from v1.x and v2.x. This is documented behavior.
  — Confidence scores are not comparable across major versions: calibration
    may differ
  — Threshold values are specific to each model version

8.8 DEPRECATION STRATEGY
──────────────────────────
  The deprecation lifecycle:
    production → deprecated (when replaced) → retired (after 12 months)

  Deprecation notice period for MAJOR versions:
    Minimum 30 days between announcing a major version upgrade and deploying it
    to production. During this period, the new model runs in canary.
    Announcement via: admin panel, in-app notification (model_updates enabled),
    optionally email.

  No deprecation notice required for minor or patch versions.

SECTION 9 — MODEL EVALUATION FRAMEWORK
================================================================================

9.1 EVALUATION PHILOSOPHY
───────────────────────────
Evaluation is the gate between a research model and a production model.
No model bypasses this gate. Evaluation has two phases:

  PHASE 1 — OFFLINE EVALUATION (before any deployment)
    Runs against static benchmark datasets on the researcher's machine or
    evaluation server. Produces numeric results that must meet acceptance
    criteria before the model can be registered with status = experimental.

  PHASE 2 — ONLINE EVALUATION (canary phase)
    Runs against real production traffic during the canary deployment.
    Monitors production distribution without labels (we don't have ground
    truth for real user uploads). Detects distributional shifts, latency
    regressions, and error rate changes.

9.2 OFFLINE EVALUATION DATASETS
─────────────────────────────────

PRIMARY BENCHMARK (required):
  Dataset: ASVspoof 2019 LA (Logical Access) evaluation partition
  Purpose: Standard academic benchmark that establishes comparable EER
  Metric: Equal Error Rate (EER) on the full evaluation set
  Partition: Must use the official evaluation partition (not the training
    or development partitions); no data contamination allowed

HELD-OUT EVALUATION SET (required):
  A curated held-out partition that is NEVER used for training, validation,
  or hyperparameter tuning. This partition is controlled by the AI Platform
  team, not the model training team.
  Contents: a stratified mix of:
    — ASVspoof 2019 LA evaluation samples (subset)
    — In-the-wild samples from public sources (labeled)
    — Difficult edge cases: heavily compressed audio, telephone bandwidth,
      concatenated real+synthesized, partial voice conversion
  Size: minimum 2,000 samples; target 5,000 samples
  Label integrity: all labels verified by at least two independent reviewers
  Update cadence: new samples added quarterly; never relabeled retroactively

GOLDEN DATASET (required):
  A small, fixed, hand-curated set of samples with highly confident labels.
  Size: exactly 200 samples (100 human, 100 AI-generated)
  Purpose: Regression testing. If a model produces a different verdict on
    any golden sample compared to the reference verdicts, that is a regression
    event. The golden dataset must be run on every new model version.
  Maintenance: new samples added when new attack types are discovered;
    existing samples never removed or relabeled.

ATTACK-TYPE BREAKDOWN SET (required):
  Samples labeled by attack type (A01–A19 in ASVspoof 2019 LA taxonomy).
  Purpose: Detect per-attack regressions. A model with better overall EER
    but worse EER on a previously-good attack type is a regression for users
    submitting that type of audio.
  Evaluation: per-attack EER must be reported; no attack type may regress
    by more than 5 percentage points compared to the previous production model.

9.3 PERFORMANCE METRICS
─────────────────────────

PRIMARY METRIC:
  Equal Error Rate (EER)
  Definition: The operating point where FAR (False Accept Rate) = FRR
    (False Reject Rate). Lower is better. At 0% EER the model is perfect.
  Target for production: ≤ 10% EER on ASVspoof 2019 LA evaluation partition
  Current production: 7.07% EER (lcnn-v1.0.0-asvspoof2019la)
  A new model must not regress beyond the acceptance threshold, and ideally
    improves on the current production model's EER.

SECONDARY METRICS (all required in evaluation report):
  AUC-ROC:
    Area Under the Receiver Operating Characteristic Curve.
    Measures ranking quality across all thresholds.
    Target: ≥ 0.95
    Interpretation: AUC-ROC = 0.97 means the model ranks 97% of spoof samples
    higher (more AI-like) than genuine samples.

  Precision (AI-generated class):
    Of all samples classified as AI-generated, what fraction actually are?
    A low precision means many false alarms (human audio incorrectly flagged).
    Target: ≥ 0.90

  Recall (AI-generated class):
    Of all actual AI-generated samples, what fraction were correctly detected?
    A low recall means AI-generated audio is slipping through.
    Target: ≥ 0.85

  F1 Score (AI-generated class):
    Harmonic mean of precision and recall.
    Target: ≥ 0.87

  F1 Score (Human class):
    Harmonic mean of precision and recall for the human class.
    Target: ≥ 0.90

  FALSE NEGATIVE RATE (FNR / Miss Rate):
    Of all AI-generated samples: fraction classified as human.
    This is the most dangerous error for VoiceGuard — AI audio labeled human.
    Target: ≤ 15% (corresponds to recall ≥ 85% for the AI class)
    Failure mode context: A journalist relying on VoiceGuard may publish a
    story citing a verdict that incorrectly cleared AI-generated audio.

  FALSE POSITIVE RATE (FPR):
    Of all human samples: fraction classified as AI-generated.
    This is the trust-damaging error — innocent recordings labeled as fakes.
    Target: ≤ 10%

9.4 CALIBRATION QUALITY
─────────────────────────
Confidence calibration is evaluated separately from accuracy metrics. A model
that is accurate but poorly calibrated produces confidence scores that
mislead users (e.g., "97% confidence" but actually correct only 70% of the time).

  EXPECTED CALIBRATION ERROR (ECE):
    The primary calibration metric. Bins predictions by confidence; measures
    average absolute difference between confidence and accuracy per bin.
    Target: ECE ≤ 0.05 (5% average miscalibration)
    If ECE > 0.05: calibration correction (temperature scaling or isotonic
    regression) must be applied and re-evaluated before promotion.

  RELIABILITY DIAGRAM:
    A visual representation of calibration — confidence on X-axis, actual
    accuracy on Y-axis. A perfectly calibrated model produces a diagonal line.
    Required as part of every evaluation report; inspected visually by
    human reviewer in addition to ECE metric.

  CONFIDENCE DISTRIBUTION:
    Plot the distribution of max(human_score, ai_score) across all evaluation
    samples. A model that produces many uncertain predictions (distribution
    peak near 0.5) is less useful than one that produces confident, calibrated
    predictions. Monitor for multimodal distributions that could indicate
    calibration problems.

9.5 ACCEPTANCE CRITERIA (PROMOTION GATES)
───────────────────────────────────────────
A model must satisfy ALL of the following to be registered as experimental
(offline evaluation gate):

  GATE 1: EER on ASVspoof 2019 LA eval ≤ 10%
  GATE 2: AUC-ROC ≥ 0.95
  GATE 3: F1 (AI class) ≥ 0.87
  GATE 4: FNR ≤ 15%
  GATE 5: ECE ≤ 0.05 (or calibration correction applied and re-evaluated)
  GATE 6: No attack type EER regression > 5pp vs. current production model
  GATE 7: Golden dataset: all 200 golden samples match reference verdicts
    (or a documented, reviewed exception list is provided)
  GATE 8: Evaluation report complete:
    — All metrics present and computed on the correct datasets
    — Known weaknesses documented
    — Fairness assessment complete (see below)
    — Human reviewer sign-off

A model must additionally satisfy the following to be promoted from canary
to production (online evaluation gate):

  GATE 9: Canary period ≥ 48 hours
  GATE 10: Canary scan count ≥ 1,000
  GATE 11: Canary inference error rate ≤ production error rate + 0.5%
  GATE 12: Canary p95 latency ≤ production p95 latency × 1.2 (≤ 20% slower)
  GATE 13: No CRITICAL monitoring alerts during canary period
  GATE 14: Human approval from AI Platform Engineer + one additional reviewer

9.6 BENCHMARK DATASETS
────────────────────────
  ASVspoof 2019 LA:
    The primary academic benchmark. Contains 2,580 genuine utterances and
    22,800 spoofed utterances across 13 TTS/VC attack systems (A01–A19).
    Available publicly. Must not be used for training the model being evaluated.
    Use: compute primary EER metric.

  ASVspoof 2021 LA:
    The subsequent challenge dataset with harder attacks and more varied
    recording conditions. Recommended for held-out evaluation in v2.

  In-the-Wild Dataset:
    A growing set of real-world deepfake audio collected from public sources
    (social media, news, research datasets). Labels verified by reviewers.
    Represents the true distribution of audio VoiceGuard users submit.
    This is the most important evaluation dataset for real-world performance.

9.7 REGRESSION TESTING
────────────────────────
Regression testing ensures that a new model does not perform worse than the
current production model on scenarios that are already working well.

  GOLDEN DATASET REGRESSION:
    Every new model version must produce identical verdicts on all 200
    golden samples (or within the approved exception list).
    A regression on any golden sample is a blocking issue.

  PER-ATTACK REGRESSION:
    EER on each of ASVspoof 2019 LA's attack types must not worsen by > 5pp.
    A model that improves overall EER by gaining on easy attacks while
    regressing on a hard attack type is not an improvement for the users
    who encounter that specific type of audio.

  CALIBRATION REGRESSION:
    ECE of new model must not exceed current production model's ECE by > 0.02.

  LATENCY REGRESSION:
    p95 inference time on the reference hardware must not exceed current
    production model's p95 by > 20%.

9.8 EVALUATION TOOLING
────────────────────────
  Evaluation is performed using the evaluation framework scripts managed
  by the AI Platform team (separate from training scripts).
  Outputs: standardized evaluation report JSON containing all metrics.
  Report format is versioned; adding new metrics is additive and backward
  compatible; removing metrics requires a framework version bump.
  Reports are stored in the experiment management system (Section 13)
  and referenced from the model registry entry (experiment_id link).

10.2 EXPLAINABILITY
─────────────────────
Explainability is provided at two levels:

  LEVEL 1 — PLAIN-LANGUAGE EXPLANATION (for all users):
    Generated from the verdict, confidence, and quality flags:
    — HUMAN: "The acoustic patterns in this recording are consistent with
      natural human speech. No synthesis artifacts were detected in the
      frequency range the model analyzes."
    — AI_GENERATED: "This audio shows strong indicators of AI synthesis.
      The model detected characteristic patterns in the high-frequency
      range (4–8 kHz) commonly produced by neural vocoders."
    — UNCERTAIN: "The model detected some patterns that could indicate AI
      synthesis, but confidence is below the reliable threshold. Treat this
      result with caution."
    — TELEPHONE_BANDWIDTH flag: "This audio may be telephone-bandwidth quality.
      The model analyzes frequencies above 4 kHz to detect synthesis artifacts;
      telephone audio lacks this range, which may reduce reliability."

    Plain-language explanations are template-based and populated from the
    result fields. They are maintained in a content management layer so that
    updating the wording does not require a model redeployment.

  LEVEL 2 — VISUAL EXPLANATION (Grad-CAM heatmap):
    The frequency heatmap shows which spectral regions the model weighted most
    heavily. High activation at 4–8 kHz typically indicates vocoder artifact
    detection. This is shown in the two-panel spectrogram card in S10.
    Caption: "The highlighted regions show which frequency ranges influenced
    the AI's decision. Strong activation at 4–8 kHz (high frequencies) is
    characteristic of vocoder synthesis artifacts."
    Technical annotation is available for professional users (toggle in
    user preferences).

10.3 KNOWN LIMITATIONS — COMPLETE DISCLOSURE
──────────────────────────────────────────────
The following limitations are documented and must be maintained in the
model registry as the known_weaknesses JSON field:

  LIMITATION 1: A17 Neural Codec Attacks
    EER: 36.8% on A17 attack type (VALL-E, EnCodec, SoundStream style)
    Risk: Modern end-to-end neural codec systems produce synthesis artifacts
    in different frequency ranges than traditional TTS/VC methods. The LCNN
    trained on ASVspoof 2019 LA may miss these.
    User guidance: "If the audio is suspected to be generated by a modern
    neural codec (VALL-E, MusicGen, or similar), consider additional
    verification beyond this tool."

  LIMITATION 2: Telephone-Bandwidth Audio
    Risk: Audio with effective bandwidth ≤ 4kHz lacks the frequency range
    where the model detects synthesis artifacts. Results on telephone-quality
    audio are less reliable.
    Detection: The platform flags telephone_bandwidth in quality_flags.
    User guidance: Surfaced automatically when flag is set.

  LIMITATION 3: Heavy Lossy Compression
    Risk: Audio heavily compressed with lossy codecs (< 64 kbps MP3, heavily
    compressed AAC) may have synthesis artifacts masked or introduced by
    the codec itself.
    Detection: Flagged as codec_artifact if detected.

  LIMITATION 4: Cross-Lingual Audio
    Risk: The ASVspoof 2019 LA dataset is primarily English-language audio.
    Performance on non-English languages may differ.
    Note: Acoustic deepfake detection is theoretically language-independent
    at the feature level, but empirical verification on non-English data
    was limited in the v1 training.

  LIMITATION 5: Partial Audio Authentication
    Risk: The model analyzes the audio as a whole (or representative segments).
    A recording that is mostly genuine but contains a short AI-synthesized
    segment may produce a "human" verdict.
    Detection: Multi-segment scoring exposes per-segment variation via the
    details.segment_scores field (visible in technical details view).

  LIMITATION 6: Adversarial Perturbations
    Risk: An adversary who knows the model architecture could craft audio
    that evades detection. The model is not adversarially hardened.
    This is disclosed in the methodology documentation.

10.6 HUMAN VERIFICATION GUIDANCE
──────────────────────────────────
For professional users (journalists, HR professionals, law enforcement):

  GUIDANCE PROVIDED IN THE UI:
  "VoiceGuard provides a probabilistic assessment, not a forensic certification.
  For high-stakes decisions, we recommend:
  1. Run the analysis multiple times with different segments of the audio
  2. Consult with a qualified audio forensics professional
  3. Consider additional authentication methods (speaker recognition,
     acoustic environment analysis, provenance tracing)
  4. Document the VoiceGuard result alongside the model version, confidence
     score, and file SHA-256 hash"

10.7 BIAS MONITORING
──────────────────────
The AI platform monitors for potential bias in model outputs across
observable dimensions:

  MONITORING TARGETS:
  — Confidence distribution by audio duration: shorter clips may produce
    lower confidence; monitor for systematic bias
  — Error rate by file format: is one format producing systematically
    more uncertain results?
  — Error rate by detected sample rate: 8kHz vs. 44kHz audio
  — Feedback rate by verdict type: are users reporting incorrect results
    more for one verdict type?

  FAIRNESS CONSIDERATIONS:
  — Accent and language diversity in training data is limited (ASVspoof 2019
    LA is primarily English). The platform acknowledges this limitation.
  — No demographic data is collected from users; bias assessment is indirect
    (via file characteristics, not speaker demographics).

10.8 ABUSE PREVENTION
──────────────────────
  RATE LIMITING: Enforced at the API layer (10 scans/hr guest, 50 scans/day
    authenticated). This prevents automated abuse of the inference endpoint.

  ADVERSARIAL INPUT PROTECTION: See Section 17.7.

  MISUSE DETERRENCE: The platform is not designed for surveillance, mass
    analysis of people without their knowledge, or political targeting.
    Terms of Service must prohibit these uses. The feedback mechanism
    allows users to report misuse.

SECTION 11 — MODEL MONITORING
================================================================================

11.1 MONITORING PHILOSOPHY
────────────────────────────
Production models degrade. The degradation can be sudden (a bad deployment)
or gradual (concept drift as new TTS systems emerge that the model has not
seen). The monitoring system must detect both patterns.

  SUDDEN DEGRADATION: Detected by error rate spikes, latency spikes,
    and confidence distribution changes within minutes. Alert threshold: ≤ 5
    minutes to detection.

  GRADUAL DEGRADATION (DRIFT): Detected by statistical tests on confidence
    distributions, feedback rates, and performance on periodic evaluation
    runs. Detection window: weekly monitoring reviews.

11.2 INFERENCE LATENCY MONITORING
────────────────────────────────────
  METRIC: inference_time_ms
  Source: logged by inference worker at Stage 10 completion; stored in
    scan_results.inference_time_ms; also emitted as a Prometheus histogram
  Labels: model_version, device (cpu/gpu), segment_count

  TARGETS:
    p50: ≤ 1,000ms (CPU, single segment)
    p95: ≤ 5,000ms (CPU, files up to 60 seconds)
    p99: ≤ 10,000ms

  ALERTS:
    WARNING: p95 > 4,000ms (approaching SLA)
    CRITICAL: p95 > 5,000ms (SLA breached)
    CRITICAL: p99 > 15,000ms (severe latency issue)

  TOTAL END-TO-END LATENCY:
    Includes: upload, validation, preprocessing, inference, result storage.
    Target: < 10 seconds p95 end-to-end (Batch 01 requirement).
    Measured: from HTTP request receipt to HTTP response on the status
    endpoint returning "complete".

11.3 MEMORY MONITORING
────────────────────────
  METRIC: worker_memory_usage_mb
  Source: Prometheus node exporter on inference worker host
  Labels: worker_pid, model_version

  TARGETS:
    Model size in RAM: ~2.8MB (LCNN weights)
    Peak per-task memory: model + audio tensor + feature matrix ≈ 200–500MB
    Worker RSS limit: 4GB (alert at 80%; kill+restart at 95%)

  ALERTS:
    WARNING: worker RSS > 3.2GB
    CRITICAL: worker RSS > 3.8GB (approaching OOM; worker at risk)
    CRITICAL: worker OOM kill (check auto-restart; log incident)

11.4 CPU AND GPU MONITORING
─────────────────────────────
  CPU MONITORING:
    METRIC: worker_cpu_percent
    Target: ≤ 80% sustained (inference is CPU-bound; high CPU means workers
      are approaching capacity)
    Alert: WARNING at > 70% sustained 5-min average
    Alert: CRITICAL at > 90% sustained 2-min average

  GPU MONITORING (when GPU workers are added in v2):
    METRIC: gpu_utilization_percent, gpu_memory_used_mb
    Target GPU utilization: 60–85% (below 60% = underutilized; above 85% =
      approaching saturation)
    Target GPU memory: ≤ 80% of VRAM capacity
    Alert: GPU utilization > 90% sustained 5-min
    Alert: GPU memory > 85% of VRAM capacity

11.5 INFERENCE FAILURE MONITORING
────────────────────────────────────
  METRIC: inference_failure_rate (failed / total scans)
  Target: ≤ 1% failure rate
  Source: scan status transitions to "failed" in database

  ALERT TIERS:
    INFO: single inference failure → logged, no alert
    WARNING: failure rate > 1% in any 15-minute window → alert
    CRITICAL: failure rate > 5% in any 5-minute window → page on-call
    CRITICAL: any CRITICAL-level error in worker logs → page on-call

  FAILURE BREAKDOWN BY CATEGORY:
    — File not found (category 1): orphaned tasks; monitor for cleanup lag
    — Audio processing error (category 2): corrupt files; normal at low rate
    — Model inference error (category 3): CUDA OOM, NaN; alert at > 0.1%
    — Task timeout (category 4): worker overload; alert at > 0.5%
    — Worker crash (category 5): alert immediately; auto-restart policy

11.6 PREDICTION DISTRIBUTION MONITORING
─────────────────────────────────────────
The prediction distribution is the statistical fingerprint of the model's
behavior on real user traffic. Shifts in this distribution indicate either:
  a) A change in the types of audio users are submitting (input drift)
  b) A change in the model's behavior (should not happen without deployment)
  c) A concept drift event (new types of AI-generated audio emerging)

  MONITORED DISTRIBUTIONS:
    VERDICT DISTRIBUTION:
      Proportion of human / ai_generated / uncertain verdicts per day.
      Baseline established in first 2 weeks of production.
      Monitor with chi-squared test for distributional shift.
      Alert: if daily distribution deviates from baseline by > 3 standard
        deviations in any verdict category for 3 consecutive days.

    CONFIDENCE DISTRIBUTION:
      Distribution of confidence scores across all daily scans.
      Monitor mean and variance; monitor KL divergence from baseline.
      Alert: mean confidence drops by > 0.05 sustained over 48 hours
        (indicates model is seeing more uncertain inputs or is degrading).

    BORDERLINE RATE:
      Proportion of scans with 0.65 ≤ confidence < 0.85.
      Spike in borderline rate may indicate input drift toward attack types
      where the model is less certain.
      Alert: borderline rate > 2× baseline sustained over 24 hours.

11.7 CONFIDENCE DRIFT MONITORING
──────────────────────────────────
  Confidence drift means the model's output distribution is shifting over
  time. This can be caused by input drift (audio characteristics change)
  or by model drift (model behavior changes, which should only happen at
  deployment).

  METHOD: Kolmogorov-Smirnov (KS) test comparing the current week's
    confidence distribution to the baseline period's distribution.
    Run weekly. If KS statistic exceeds threshold (p < 0.01), trigger
    review.

  BASELINE: First 2 weeks of production data (minimum 500 scans required
    to establish baseline). Updated quarterly with a rolling 90-day window.

11.8 FEATURE DRIFT MONITORING
───────────────────────────────
  Feature drift: the distribution of input audio characteristics changes.
  This may cause model performance to degrade without the model itself changing.

  MONITORED FEATURES:
    — Input sample rate distribution (before normalization)
    — Input duration distribution
    — Input file format distribution
    — Quality flag rate (telephone_bandwidth, silence, clipping)
    — Segment count distribution

  METHOD: Monitor daily aggregates; alert if any distribution shifts by
    > 2 standard deviations from the 30-day rolling baseline.

  EXAMPLE: If telephone_bandwidth flags suddenly spike (indicating more users
    are submitting telephone recordings), the confidence distribution will
    likely worsen — this is input drift, not model drift.

11.9 CONCEPT DRIFT MONITORING
───────────────────────────────
  Concept drift: the relationship between audio features and the true label
  changes because new types of AI-synthesized audio emerge that the model
  has not been trained to detect.

  INDICATORS (no ground truth available in production, so indirect measures):
  — Spike in user feedback reports ("result seems wrong")
  — Sudden drop in model confidence on audio that previously scored high
  — Unusual feature patterns in flagged scans (manual review trigger)
  — External signals: new TTS/VC systems published by researchers that
    fall outside the model's training distribution

  RESPONSE TO SUSPECTED CONCEPT DRIFT:
    1. Capture flagged scans (with user consent) as evaluation samples
    2. Collect labeled examples of the new attack type from public sources
    3. Evaluate current production model on new attack type samples
    4. If EER > 30% on new type: document as new known weakness; prioritize
       in next training cycle
    5. Issue user guidance for the new limitation

11.10 ERROR RATE MONITORING
─────────────────────────────
  METRIC: inference_error_rate
  Calculated: failed scans / total scans per 15-minute window
  Breakdown by error category (categories 1–5 from Section 8.7)

  GRADCAM FAILURE RATE:
    METRIC: gradcam_failure_rate (gradcam_generated=false / total scans)
    Target: ≤ 1%
    Alert: WARNING at > 1%; CRITICAL at > 5%
    A high Grad-CAM failure rate indicates a model loading or hooking issue.

11.11 QUEUE DEPTH MONITORING
──────────────────────────────
  METRIC: inference_queue_depth (number of pending tasks in the inference queue)
  Source: Celery queue inspection; Redis list length for the inference queue key
  Target: ≤ 10 pending tasks at any time (with 2 workers each processing
    one task, depth > 10 means > 5 minutes of wait time)
  Alerts:
    WARNING: queue depth > 10 (processing lag emerging)
    CRITICAL: queue depth > 50 (severe backlog; users waiting > 25 minutes)
    CRITICAL: queue depth growing monotonically for > 5 minutes (worker stuck)

11.12 MODEL AVAILABILITY
─────────────────────────
  METRIC: model_available (boolean; true if inference workers are healthy
    and accepting tasks)
  Source: Celery worker heartbeat + health check endpoint
  Target: 99.5% uptime
  Measurement: 5-minute windows; mark unavailable if no heartbeat received

  COMPONENTS:
    Worker heartbeat: Celery sends heartbeats every 30 seconds
    Model loaded flag: set at worker startup after checksum verification
    Queue acceptance: verify workers are consuming from the inference queue

  Alert: CRITICAL if model_available = false for > 2 minutes

12.1 OBSERVABILITY PILLARS
────────────────────────────
The VoiceGuard AI Platform observability strategy is organized around three
classical pillars, with a fourth pillar specific to AI systems:

  PILLAR 1 — METRICS: Numeric time-series data about system behavior.
    What is happening right now? What was happening an hour ago?
    Tools: Prometheus + Grafana (or equivalent)

  PILLAR 2 — LOGS: Structured records of individual events.
    What happened for this specific scan? Why did this task fail?
    Tools: Structured JSON logs → ELK / CloudWatch / Datadog

  PILLAR 3 — TRACES: End-to-end timing of operations across boundaries.
    How long did each stage of the inference pipeline take for this scan?
    Tools: OpenTelemetry spans, distributed trace collector

  PILLAR 4 — PREDICTION AUDIT TRAIL: The ML-specific observability layer.
    What exactly did the model predict, for what input, with which model
    version, and what did the user say about it?
    Tools: scan_results database table + structured inference logs

12.4 TRACING
─────────────
  Every scan that enters the inference pipeline is assigned an inference_id
  (derived from the scan_id) and carries the request_id from the originating
  HTTP request. These IDs are propagated through:

  HTTP Request → API layer (request_id) →
  Celery task (task_id + scan_id + request_id) →
  Inference worker stages (inference_id = scan_id) →
  Database write (scan_results.scan_id + scan_results.model_version) →
  Log records (all three IDs present)

  This allows an operator to take any scan_id and reconstruct the complete
  lifecycle: when the HTTP request arrived, when the task was queued, when
  each stage completed, what the final result was, and whether any warnings
  were logged.

  OPENTELEMETRY SPANS (for distributed trace collection):
    Span: http_request (root span, from API middleware)
      Child span: celery_task_queue (from Celery task publish)
        Child span: inference_pipeline (from task start to result write)
          Child span: audio_preprocessing
          Child span: feature_extraction_stft
          Child span: model_forward_pass
          Child span: gradcam_generation
          Child span: result_persistence

  Trace data is emitted to an OpenTelemetry collector and stored in
  a distributed tracing backend (Jaeger or Tempo).

12.5 PREDICTION AUDIT TRAIL
─────────────────────────────
The prediction audit trail is the AI-specific observability record that
enables retroactive investigation of any scan result.

  STORED IN DATABASE (scan_results, permanent):
    scan_id, verdict, confidence, human_score, ai_score, model_version,
    inference_time_ms, segment_count, details (JSONB with full inference
    metadata including per-segment scores, quality flags, calibration applied)

  ACCESSIBLE VIA ADMIN PANEL:
    Any admin can query any scan by scan_id and see the complete inference
    metadata. No prediction is opaque to the platform operators.

  FEEDBACK CORRELATION:
    The feedback table stores model_verdict (what the model said) and
    user_verdict (what the user says it should be). This creates a labeled
    correction dataset that is the foundation of model improvement.

SECTION 13 — EXPERIMENT MANAGEMENT
================================================================================

13.1 EXPERIMENT MANAGEMENT PURPOSE
─────────────────────────────────────
Experiment management bridges the research phase (training a new model) and the
deployment phase (registering the model in the registry). Every training run
that could potentially produce a production candidate must be tracked in the
experiment system.

13.2 WHAT CONSTITUTES AN EXPERIMENT
──────────────────────────────────────
An experiment is any training run that:
  a) Uses a versioned dataset to train a model
  b) Produces a model artifact (trained weights file)
  c) Is evaluated against at least one standard metric

An experiment does NOT include:
  — Exploratory data analysis (not a training run)
  — Hyperparameter sweeps where no model is retained (the sweep is an
    experiment set; each constituent run may or may not be retained)
  — Fine-tuning without a new artifact (patch-level changes tracked in
    the registry, not as separate experiments)

13.3 EXPERIMENT TRACKING METADATA
────────────────────────────────────
Every registered experiment carries the following metadata:

  IDENTITY:
    experiment_id:      Unique identifier (UUID or human-readable slug)
    experiment_name:    Short descriptive name
    researcher:         Who ran the experiment
    created_at:         When the experiment was initiated
    status:             running | complete | abandoned | promoted

  DATASET LINEAGE:
    training_dataset_id:    Reference to registered dataset (Section 14)
    training_dataset_version: Dataset version used
    dev_dataset_id:         Development/validation dataset
    preprocessing_config:   Hash or reference to the preprocessing config used
    data_split:             Training/dev/eval split proportions

  HYPERPARAMETERS (complete, no omissions):
    architecture:           Model architecture class
    learning_rate:          Initial and schedule
    batch_size:             Training batch size
    optimizer:              Optimizer type and parameters
    num_epochs:             Number of training epochs (or steps)
    early_stopping:         Policy and threshold
    regularization:         L1/L2 coefficients if used
    augmentation:           Any data augmentation applied
    pretrained_weights:     If transfer learning: source model reference

  EVALUATION RESULTS (from standardized evaluation framework):
    eer_asvspoof2019la:     EER on primary benchmark
    auc_roc:                AUC-ROC on held-out set
    f1_ai_class:            F1 for AI-generated class
    f1_human_class:         F1 for human class
    calibration_ece:        Expected Calibration Error
    inference_time_ms_p95:  Measured on reference hardware
    evaluation_report_ref:  Path to full JSON evaluation report

  ARTIFACT:
    artifact_path:          Path to trained model weights file
    checksum_sha256:        SHA-256 of the artifact
    artifact_size_bytes:    File size
    framework_version:      ML framework version (e.g., PyTorch 2.x)

  LIFECYCLE:
    registry_version_string: If promoted: the model_versions version_string
    promotion_date:          If promoted: when it entered the registry

13.4 EXPERIMENT APPROVAL WORKFLOW
───────────────────────────────────
Experiments follow this workflow before a model can be registered:

  PHASE 1 — RESEARCH (no governance required)
    Researcher trains and evaluates models locally. No tracking required
    for pure exploration. Tracking begins when the researcher identifies
    a model as a candidate for production consideration.

  PHASE 2 — CANDIDATE REGISTRATION
    Researcher registers the experiment with full metadata (above).
    Experiment status = "complete".
    The evaluation report is submitted (computed on the held-out evaluation
    set by the standardized framework, not custom scripts).

  PHASE 3 — PEER REVIEW
    At least one other ML team member reviews the experiment record:
    — Verifies that the evaluation dataset is the correct partition
    — Reviews the evaluation report for anomalies
    — Checks that all hyperparameters are documented
    — Verifies that the training dataset is a registered, versioned dataset
    Sign-off recorded in experiment record.

  PHASE 4 — AI PLATFORM REVIEW
    AI Platform team reviews for production-readiness:
    — Does this model meet acceptance criteria (Section 9.5)?
    — Is the feature specification compatible with the current pipeline?
    — Are known weaknesses documented?
    — Is the inference latency within SLA?
    Sign-off recorded; model may now be registered in model registry.

  PHASE 5 — REGISTRY REGISTRATION
    Model artifact is uploaded to artifact store.
    model_versions row created with status = experimental.
    experiment_id linked in registry entry.
    Normal promotion workflow begins (registry → evaluation → canary → production).

13.5 REPRODUCIBILITY
──────────────────────
  Every experiment must be reproducible. Reproducibility requirements:

  REQUIRED FOR REPRODUCIBILITY:
    — Training dataset version (exact; see Section 14)
    — Preprocessing config version (hash of the preprocessing script config)
    — Hyperparameters (exact, complete list — no "default" shorthand)
    — Random seed(s) used for data shuffling and weight initialization
    — ML framework version (exact patch version, not just major.minor)
    — CUDA version and driver version if GPU training was used
    — Hardware specification (for timing reproducibility)

  VERIFICATION:
    The peer reviewer in Phase 3 should be able to re-run the evaluation
    (not the training) on the registered artifact and obtain identical metrics.
    Training reproducibility (getting the same trained weights from scratch)
    is ideal but may not be achievable for GPU training with non-deterministic
    operations; training reproducibility within ± 0.5% EER is acceptable.

13.6 RESEARCH WORKFLOW
────────────────────────
  The research workflow is intentionally open-ended. Researchers are free
  to explore architectures, datasets, and preprocessing strategies without
  governance constraints until they identify a production candidate.

  WHAT THE AI PLATFORM PROVIDES TO RESEARCHERS:
    — Access to registered datasets (Section 14) for training
    — Reference evaluation scripts that produce standardized JSON reports
    — The golden dataset for regression testing (read-only access)
    — The feature extraction pipeline specification (so new models are
      trained on features consistent with the deployment pipeline)
    — The model registry API for registering artifacts when ready

  WHAT THE AI PLATFORM DOES NOT CONTROL IN RESEARCH:
    — Choice of architecture
    — Exploration of new features or preprocessing approaches
    — Experimental training techniques
    — Number of experiments run

SECTION 14 — DATASET GOVERNANCE
================================================================================

14.1 DATASET GOVERNANCE PURPOSE
──────────────────────────────────
Training data quality is a direct determinant of model quality. Dataset
governance ensures that every training run uses datasets that are:
  — Correctly labeled (human vs. AI-generated)
  — Traceable to their source (public benchmark, synthetic, licensed)
  — Privacy-respecting (no user audio from VoiceGuard submissions)
  — Versioned (reproducible across time)
  — Documented (what is in the dataset, how it was collected)

14.2 DATASET REGISTRY
───────────────────────
Every dataset used for training, evaluation, or fine-tuning is registered
in the dataset registry. The dataset registry is a separate system from the
model registry (experiments reference dataset IDs; models reference
experiment IDs).

  DATASET REGISTRY RECORD:
    dataset_id:         UUID
    name:               Human-readable name (e.g., "ASVspoof 2019 LA")
    version:            Version string (e.g., "asvspoof2019la-v1.0")
    partition:          training | development | evaluation | held_out
    source_type:        public_benchmark | licensed | synthetic | internal
    source_url:         URL or reference to source
    license:            License identifier (e.g., "ASVspoof Research License")
    description:        What is in the dataset
    sample_count_genuine: Integer; number of labeled genuine (human) samples
    sample_count_spoof:   Integer; number of labeled spoof (AI) samples
    total_duration_hrs:   Float; total audio duration
    language_distribution: JSON object; {language: proportion}
    attack_types:         JSON array; attack type labels present (if applicable)
    labeling_method:      How labels were created (benchmark-provided, manual,
                          automatic with human review)
    created_at:           Registration date
    checksum_sha256:      SHA-256 of a manifest file listing all samples and
                          their checksums; verifies dataset integrity
    privacy_assessment:   Documented review that no user audio is included;
                          confirmation of consent status for all audio sources

14.3 DATASET VERSIONING
─────────────────────────
  Datasets are immutable once registered. A new version must be created for
  any change to the dataset content, labels, or preprocessing.

  VERSION STRING FORMAT: {dataset_name}-v{major}.{minor}
    Major: adding samples from new attack types or new sources
    Minor: label corrections, sample removals, quality filter changes

  When a new dataset version is registered:
    — Previous version remains available and referenced by existing experiments
    — New experiments must explicitly choose which version to use
    — A model trained on version 2.0 must document this in its experiment record

14.4 DATASET VALIDATION
─────────────────────────
  A new dataset registration requires the following validation checks:

  STRUCTURAL VALIDATION:
    — File format consistency: all files in the registered formats
    — Sample rate consistency: all files at expected sample rate or flagged
    — No corrupted files: all files open and decode without error
    — No empty files: all files have duration > 0.5 seconds
    — No duplicate files: SHA-256 hashes of all audio files are unique

  LABEL VALIDATION:
    — Label distribution: at least 20% of each class (genuine, spoof)
    — Label file completeness: every audio file has a label
    — Label format: standardized format (binary: genuine=0, spoof=1)
    — Label review: at least one independent review of a random 5% sample

  PRIVACY VALIDATION:
    — Source documentation: every source file is traceable to its origin
    — User audio exclusion: confirmation that no VoiceGuard user submissions
      are included (this is a hard invariant; violation is a product ethics breach)
    — Consent verification: for licensed datasets, license terms permit
      ML training use

  INTEGRITY VALIDATION:
    — Manifest checksum computed and stored in registry
    — Manifest checksum re-verified before any training run

14.5 DATA QUALITY CHECKS
──────────────────────────
  Before a dataset is used for training, a quality analysis report is generated:

  BALANCE ANALYSIS:
    Genuine-to-spoof ratio. Target: 1:1 to 1:5 (genuine:spoof).
    Highly imbalanced datasets require weighting or sampling strategy.

  DURATION DISTRIBUTION:
    Histogram of clip durations. Flag if > 20% of clips are < 1 second
    (very short clips may not produce reliable training signal).

  SAMPLE RATE DISTRIBUTION:
    All clips should be at 16,000 Hz after preprocessing. Flag if > 5%
    required aggressive resampling from unusual rates.

  ATTACK TYPE COVERAGE (for spoof samples):
    Ensure training data covers diverse attack types. A dataset dominated
    by one attack type will produce a model that generalizes poorly.

  LANGUAGE DISTRIBUTION:
    Document language distribution. Flag if > 90% is a single language
    (limits cross-lingual generalization).

14.6 CORRUPTION DETECTION
───────────────────────────
  The dataset validation pipeline detects:
  — Truncated audio files (file claims longer duration than actual content)
  — Zero-amplitude files (silence)
  — Clipped audio (> 10% samples at max amplitude)
  — Extreme outlier durations (< 0.1s or > 600s)
  — Files where SHA-256 does not match the manifest entry

  Corrupted files are removed from the training set and documented in the
  dataset quality report. The registry records the number of files removed
  and the reason.

14.7 LABEL VERIFICATION
─────────────────────────
  For benchmark datasets (ASVspoof 2019 LA):
    Labels are provided by the challenge organizers and are authoritative.
    Use them as-is; do not relabel.

  For in-the-wild datasets (collected from public sources):
    Every sample must be labeled by at least two independent reviewers.
    Disagreements go to a third reviewer (majority vote).
    Samples with persistent disagreement are removed.

  For synthetic datasets (generated specifically for training):
    Labels are derived from the generation process (provably AI-generated).
    Spot-check 1% of samples with human reviewers to confirm.

14.8 PRIVACY REQUIREMENTS
───────────────────────────
  ABSOLUTE REQUIREMENT: VoiceGuard user submissions are NEVER training data.
    — The VoiceGuard product privacy policy promises this explicitly.
    — The inference pipeline deliberately deletes audio within 60 seconds.
    — No pipeline, background job, or manual process may save user audio
      for training purposes.
    — This prohibition applies regardless of consent: v1 does not have a
      consent mechanism for training data use; therefore no user audio is used.

  FOR FUTURE CONSENT-BASED DATA COLLECTION (v3+):
    If VoiceGuard v3 adds an opt-in consent mechanism for contributing
    audio samples for model improvement, this must be:
    — Explicit opt-in (not opt-out)
    — Reversible: user can withdraw consent and their samples are deleted
    — Documented in the privacy policy
    — Governed by the dataset registration process above (consented user
      audio becomes a registered, versioned dataset)

14.9 RETENTION POLICY
───────────────────────
  Dataset registry records: permanent (for model lineage traceability)
  Dataset artifacts (audio files):
    — Public benchmark datasets: retained indefinitely (on research storage,
      not production infrastructure)
    — In-the-wild datasets: retained per license terms; minimum until the
      model trained on them is retired
    — Evaluation/held-out datasets: retained indefinitely (evaluation
      reproducibility requires the same evaluation data across time)

14.10 DATASET APPROVAL
────────────────────────
  A new dataset must be approved by:
    1. A dataset owner (the person who registered and validated it)
    2. An AI Platform reviewer (privacy compliance, quality check review)
  Approval is recorded in the dataset registry entry.
  Unapproved datasets may not be used for training production candidates.

SECTION 15 — MLOPS LIFECYCLE
================================================================================

15.1 LIFECYCLE OVERVIEW
─────────────────────────
The VoiceGuard MLOps lifecycle defines the complete journey from research
idea to production model to retirement. Every stage has defined entry
criteria, exit criteria, and artifacts produced.

  LIFECYCLE STAGES:
  1. Research → Dataset Creation → Dataset Validation → Training →
     Evaluation → Approval → Packaging → Registry →
     Canary → Production → Monitoring → Retirement

15.2 STAGE DEFINITIONS AND TRANSITIONS
──────────────────────────────────────

STAGE 1: RESEARCH
  Activities: Literature review, architecture exploration, preliminary
    experiments on development data, hyperparameter exploration.
  Entry: Any time (research is open-ended)
  Exit: Researcher identifies a model candidate for production consideration.
  Artifacts: None required (exploratory phase)
  Transition to Dataset Creation: Researcher decides to train a model on
    a registered dataset with documented configuration.

STAGE 2: DATASET CREATION
  Activities: Curating training data (public benchmarks + in-the-wild
    samples), applying data quality checks, labeling, registering in
    dataset registry.
  Entry: Training dataset requirements are defined.
  Exit: Dataset registered in dataset registry with approved status.
  Artifacts: Dataset registry entry, quality report, manifest checksum.
  Transition to Dataset Validation: Dataset registration complete.

STAGE 3: DATASET VALIDATION
  Activities: Running the full dataset validation pipeline (Section 14),
    reviewing quality report, verifying privacy compliance.
  Entry: Dataset registration submitted.
  Exit: Dataset validation report produced; AI Platform reviewer approval.
  Artifacts: Validation report, approved dataset registry record.
  Transition to Training: Dataset approved.

STAGE 4: TRAINING
  Activities: Training the model using the registered, approved dataset
    and documented hyperparameters.
  Entry: Registered dataset + documented training config.
  Exit: Training completes; model artifact produced; experiment registered.
  Artifacts: Trained model weights file, experiment record (partial).
  Transition to Evaluation: Training complete; artifact produced.

STAGE 5: EVALUATION
  Activities: Running the standardized evaluation framework on the trained
    model against the held-out evaluation set, ASVspoof 2019 LA benchmark,
    and golden dataset.
  Entry: Model artifact available; experiment record created.
  Exit: Evaluation report produced with all required metrics.
  Artifacts: JSON evaluation report; updated experiment record.
  Transition to Approval: Evaluation report complete.

STAGE 6: APPROVAL
  Activities: Peer review of experiment record, evaluation report review,
    checking acceptance criteria, AI Platform team review.
  Entry: Complete evaluation report.
  Exit: Signed approval from researcher (peer) + AI Platform reviewer.
  Artifacts: Approval signatures in experiment record.
  Transition to Packaging: Approval received.

STAGE 7: PACKAGING
  Activities: Computing model artifact checksum, uploading artifact to
    artifact store, preparing model registry entry with all metadata.
  Entry: Approved experiment.
  Exit: Artifact available at artifact_path; checksum verified.
  Artifacts: Model artifact in artifact store, checksum file.
  Transition to Registry: Packaging complete.

STAGE 8: REGISTRY
  Activities: Creating the model_versions row in the database with all
    metadata, performance metrics, known weaknesses, and feature spec.
  Entry: Packaged artifact.
  Exit: model_versions row with status = experimental created.
  Artifacts: model_versions record in database.
  Transition to Canary: Human decision to proceed to canary deployment.

STAGE 9: CANARY
  Activities: Deploying the model to a subset of inference workers,
    routing a fraction of production traffic to the canary workers,
    monitoring online performance against production model.
  Entry: model_versions status = experimental; deployment team approval.
  Exit: Canary validation criteria met (Section 9.5 Gates 9–13) + human approval.
    OR: Canary shows regression; rollback to experimental status.
  Artifacts: Canary monitoring report; deployment log.
  Transition to Production: Canary approved.

STAGE 10: PRODUCTION
  Activities: Full traffic routing to new model; old model deprecated;
    monitoring dashboards updated; user notification for MAJOR versions.
  Entry: Canary approved.
  Exit: A newer model is promoted to production.
  Artifacts: Deployment record (approved_by, deployed_at in registry).
  Transition to Monitoring: Model is live.

STAGE 11: MONITORING
  Activities: Ongoing production monitoring (Section 11) for the full
    production lifetime of the model.
  Entry: Model in production.
  Exit: Model is deprecated (succeeded by a newer model).
  Activities: Continuous; no separate artifacts produced.
  Transition to Retirement: Deprecation + 12 months archive period.

STAGE 12: RETIREMENT
  Activities: Removing model from inference workers; archiving artifact
    to cold storage; updating registry status to retired.
  Entry: Deprecated status + 12 months elapsed (or admin decision).
  Exit: Model fully retired; no traffic; artifact in cold storage.
  Artifacts: Retirement record (deprecated_at, cold_storage_ref in registry).
  Transition: End of lifecycle (record retained forever).

SECTION 16 — DEPLOYMENT STRATEGY
================================================================================

16.1 INFERENCE WORKER ARCHITECTURE
─────────────────────────────────────
Inference workers are the compute units that execute the ML model. They are
dedicated Celery worker processes that consume tasks from the "inference" queue.

  WORKER PROPERTIES:
    — Each worker process loads the model ONCE at startup
    — Each worker processes ONE task at a time (CPU-bound; no parallelism)
    — Workers share NO state with each other (independent processes)
    — Workers share NO state with the API tier (decoupled via queue)
    — Worker concurrency = 1 (Celery prefork; each fork is a separate process)

  WORKER STARTUP SEQUENCE:
    1. Read model_version configuration from environment
    2. Resolve artifact path from model registry (or from env config)
    3. Compute SHA-256 of artifact; compare to registry checksum
    4. If mismatch: log CRITICAL; refuse to accept tasks; alert
    5. Load model weights into memory
    6. Set model to eval mode (disable dropout, batch norm uses running stats)
    7. Run warmup inference pass: synthetic 1-second silent audio, full pipeline
    8. Log: model_loaded event with load_time_ms, device, checksum_verified=true
    9. Register with Celery; begin consuming from "inference" queue

  WORKER FAILURE RECOVERY:
    If a worker crashes (OOM kill, hardware fault):
    — Celery supervisor (systemd or Docker restart policy) restarts the worker
    — The task being processed is re-queued after the Celery visibility timeout (60s)
    — Worker restart triggers the full startup sequence (including checksum verification)

16.2 CPU DEPLOYMENT (V1)
──────────────────────────
  The LCNN model (699,938 parameters, ~2.8MB) runs efficiently on CPU.
  p95 inference time on CPU (reference hardware: 4 vCPU, 16GB RAM): ≤ 5 seconds.
  This meets the SLA without requiring GPU.

  v1 CPU deployment configuration:
    — 2 inference worker processes on the worker VM
    — Each worker: 1 concurrency, 1 task at a time
    — Combined throughput: ~2 simultaneous scans, ~12–24 scans/minute
    — Max queue depth before degradation: ~10 tasks
    — Resource allocation: 2 vCPU and 4GB RAM per worker (8 vCPU, 16GB total
      for both workers plus system overhead)

16.3 GPU DEPLOYMENT (V2)
──────────────────────────
  GPU deployment is planned for v2 when scan volume exceeds CPU capacity.

  GPU deployment considerations:
    — GPU adds batching capability: process multiple segments simultaneously
    — LCNN is small enough that multiple scans can batch on a single GPU
    — GPU warm-up time must be factored into worker startup sequence
    — GPU OOM fallback to CPU must be implemented (per Batch 04 Section 8.7)
    — GPU memory isolation: each worker gets its own CUDA context

  BATCHING POLICY (GPU mode):
    Within a single scan: batch all segments of that scan (already done in
    Stage 9 of the inference pipeline).
    Across scans: do NOT batch across concurrent scans in v1 GPU mode —
    each task processes its own scan independently. Cross-scan batching
    (waiting for multiple tasks to arrive, batching them together) is
    complex and introduces latency variance; defer to v3 if warranted.

16.4 AUTOSCALING
──────────────────
  v1: Manual scaling (add worker processes by SSH and restarting Celery).
  
  SCALING TRIGGER CRITERIA:
    — Queue depth > 20 tasks for > 5 minutes → add one worker
    — p95 latency > 4,000ms sustained for > 10 minutes → add one worker
    — Worker CPU > 80% sustained for > 10 minutes → add one worker

  SCALING DOWN:
    — Queue depth ≤ 2 for > 30 minutes → remove one worker (minimum: 2 workers)
    — Minimum workers: 2 (for redundancy and availability)

  v2 HORIZONTAL AUTOSCALING:
    When containerized (Docker/Kubernetes):
    — Celery workers as a Deployment with HPA (Horizontal Pod Autoscaler)
    — Scale metric: custom metric "inference_queue_depth" from Prometheus
    — Min replicas: 2; Max replicas: 10 (adjust based on hardware budget)
    — Scale-up threshold: queue_depth > 5 for > 2 minutes
    — Scale-down threshold: queue_depth < 2 for > 5 minutes
    — Scale-down cooldown: 5 minutes (prevent thrashing)

16.5 MODEL WARM-UP
────────────────────
  Cold start problem: when a worker starts, the model must be loaded and
  the first inference will be slower than subsequent inferences (JIT
  compilation, cache warming, OS page cache effects).

  WARM-UP STRATEGY:
    — Every worker runs a warmup inference pass at startup (Section 16.1 step 7)
    — Warmup pass: synthetic 1-second audio (zero array at 16kHz), full pipeline
    — Warmup ensures: model forward pass JIT-compiled, STFT kernels warm,
      OS page cache loaded with model weights
    — Worker does not accept tasks until warmup completes
    — Warmup time: typically 2–5 seconds (included in worker startup time)

16.6 COLD START MITIGATION
────────────────────────────
  KEEP-ALIVE POLICY:
    Workers are persistent processes (not spawned per request). The model
    stays in memory indefinitely as long as the worker is running.
    Worker restart policy: restart on crash (not on idle timeout).

  MINIMUM WORKER COUNT:
    Always 2 workers minimum, even at zero traffic.
    This ensures that a worker restart does not cause inference unavailability.

  QUEUE ROUTING:
    The inference queue is dedicated. General workers never execute inference
    tasks. This prevents inference worker starvation when the general queue
    has high load.

16.7 RESOURCE ISOLATION
─────────────────────────
  Inference workers and general workers MUST run in separate processes and
  ideally on separate VMs or containers.

  Rationale: An OOM event in a general worker (e.g., PDF generation on a
  large document) must not kill an inference worker. Mixing queue types
  on the same Celery worker process pool defeats this isolation.

  Process boundaries:
    VM-2 or Container-2: Celery inference workers ONLY
    VM-3 or Container-3: Celery general workers + Celery Beat

16.8 BLUE/GREEN DEPLOYMENT
────────────────────────────
  Blue/green deployment for model version updates:

  BLUE: Current production workers (old model version)
  GREEN: New workers (new model version), initially receiving 0% traffic

  Procedure:
    1. Start GREEN workers with new model version (they pass startup checks)
    2. Verify GREEN workers are healthy (model_loaded=true, warmup complete)
    3. Route 5% of new inference tasks to GREEN workers (Celery routing key)
    4. Monitor GREEN workers for errors; compare to BLUE worker metrics
    5. Gradually increase GREEN traffic to 25%, 50%, 100%
    6. Once GREEN is at 100%: drain BLUE workers (finish in-flight tasks)
    7. Stop BLUE workers; deployment complete

  Rollback: Route all traffic back to BLUE workers; stop GREEN workers.
  Maximum rollback time: < 2 minutes (time to drain in-flight GREEN tasks).

16.9 CANARY DEPLOYMENT
────────────────────────
  Canary deployment is a subset of blue/green where GREEN is deliberately
  limited to a small percentage of traffic for monitoring purposes.

  Canary traffic control: implemented at the Celery task routing level.
    — Tasks are published to either "inference" (BLUE) or "inference-canary" (GREEN)
    — The routing decision is made by a configurable traffic-split mechanism
      in the API/scan service layer (configurable via Redis without code change)
    — Default canary split: 5% of tasks to inference-canary

  Canary monitoring requirements (parallel dashboards):
    — Both BLUE and GREEN workers emit the same metrics with model_version label
    — Grafana dashboards compare BLUE vs. GREEN side by side
    — Automatic alerting if GREEN metrics deviate from BLUE by defined thresholds

  Canary promotion: only after manual review confirms GREEN is performing
  at least as well as BLUE across all monitoring metrics.

16.10 ROLLBACK PROCEDURE
──────────────────────────
  See Section 20 (Disaster Recovery) for the complete rollback procedure.
  Summary: rollback is possible at any point by routing all traffic back
  to the previous model version's workers and restarting if needed.

SECTION 17 — SECURITY ARCHITECTURE
================================================================================

17.1 MODEL INTEGRITY
──────────────────────
  Model integrity is protected by SHA-256 checksums verified at every
  worker startup. This is the primary control against model tampering.

  CHECKSUM VERIFICATION POLICY:
    — Checksum is computed from the model weights file at registration time
    — Checksum is stored in the model registry (immutable after registration)
    — At every worker startup: checksum is re-computed and compared
    — Any mismatch triggers: worker refuses tasks, CRITICAL alert, incident
    — Checksum is computed by the deployment tooling, not by the inference
      worker code (separation of concerns)

  CHECKSUM CHAIN OF CUSTODY:
    Researcher trains model → computes checksum → submits to AI Platform
    AI Platform reviewer → independently verifies checksum on artifact
    Registry → stores verified checksum
    Deployment → copies artifact to worker path
    Worker → computes checksum at startup and compares to registry

17.2 ARTIFACT SIGNING
───────────────────────
  In v2, model artifacts will be signed with a digital signature in addition
  to checksums.

  SIGNING MECHANISM:
    — AI Platform team holds a code-signing key pair (private key in secrets
      manager; public key embedded in the inference code)
    — Each artifact is signed with the private key at registration time
    — Workers verify the signature at startup before loading

  Rationale for v2 (not v1): checksum verification is sufficient for v1
  under the assumption that the artifact store is access-controlled. Digital
  signing provides protection against an insider threat who has write access
  to the artifact store; this risk is low for a v1 system with a small team.

17.3 CHECKSUM VALIDATION
──────────────────────────
  Checksum algorithm: SHA-256 (256-bit hash)
  Stored as: 64-character lowercase hex string in model_versions.checksum_sha256
  Computed on: the raw bytes of the model weights file (.pt file)
  Verification code: runs in the worker startup sequence, before any task
    acceptance
  Failure response:
    log CRITICAL: model_checksum_mismatch event with expected vs. actual
    Worker transitions to a "quarantined" state: accepts the task but
    immediately fails it with a descriptive error
    Alert: paged to on-call immediately
    Investigation: treat as a potential security incident

17.4 DATASET SECURITY
───────────────────────
  TRAINING DATA ACCESS CONTROL:
    Training datasets are stored on research infrastructure (not production
    servers). Access is limited to ML researchers and AI Platform engineers.
    No training data is stored on production inference servers.

  EVALUATION DATA ISOLATION:
    The held-out evaluation dataset is controlled by the AI Platform team.
    Researchers do not have direct access to evaluation labels.
    Evaluation is performed by AI Platform scripts, not researcher scripts.
    This prevents inadvertent label leakage into model training.

  DATASET AUDIT LOG:
    Every access to a registered dataset (for training or evaluation) is
    logged with: who accessed it, when, for what purpose (experiment_id).

17.5 INFERENCE ENDPOINT PROTECTION
─────────────────────────────────────
  The inference endpoint is protected by the backend platform's existing
  security controls (Batch 04 Section 11):
    — Rate limiting: 10 scans/hour per guest IP; 50 scans/day per user
    — Authentication: valid session or guest token required
    — File validation: magic bytes, size limits, format allowlist
    — CORS and CSP enforcement
    — Audit logging of all scan submissions

  AI Platform additional controls:
    — The inference worker never directly exposes any network port
    — Workers communicate only via the Celery task queue (Redis)
    — Workers have no direct database write access except via the scan
      service layer
    — The model weights file path is not exposed in any API response

17.6 ADVERSARIAL ROBUSTNESS
─────────────────────────────
  The LCNN model is NOT adversarially hardened against crafted inputs.
  This is a known limitation documented in the Responsible AI section.

  KNOWN ADVERSARIAL RISK:
    An adversary who knows the LCNN architecture and has query access to
    the prediction endpoint could potentially craft audio (via gradient-based
    adversarial attacks) that evades detection while sounding natural to humans.

  CURRENT MITIGATIONS (v1):
    — Rate limiting prevents automated query-intensive adversarial attacks
    — Model version is not exposed to anonymous users in the raw API (reduces
      architectural information available to attackers)
    — Input preprocessing (normalization, clipping) may disrupt some
      adversarial perturbations that depend on specific input magnitudes

  PLANNED MITIGATIONS (v2):
    — Adversarial training: include adversarially perturbed samples in training
    — Input randomization: apply random preprocessing perturbations before
      inference (breaks gradient-based attacks that assume a fixed pipeline)
    — Model ensemble: harder to simultaneously evade multiple models

17.7 INPUT VALIDATION FOR AI SECURITY
───────────────────────────────────────
  From the AI platform perspective, additional input validation protects
  the model from pathological inputs:

  NUMERICAL SAFETY CHECKS (Stage 7):
    — Feature matrix values clamped to [-5, 5] (prevents numerical overflow
      in model forward pass)
    — NaN/Inf detection before tensor construction (fails gracefully)

  SHAPE VALIDATION:
    — Input tensor shape verified before every forward pass
    — Unexpected shapes trigger immediate task failure (not crash)

  DURATION ENFORCEMENT:
    — Hard limit at 300 seconds enforced in worker (defense in depth)
    — Prevents resource exhaustion via very long audio files

17.8 MODEL THEFT MITIGATION
─────────────────────────────
  MODEL INVERSION / EXTRACTION RISK:
    An attacker who sends many queries and observes the confidence scores
    could potentially reconstruct the model's decision boundary or extract
    a surrogate model.

  MITIGATIONS:
    — Rate limiting: limits the number of queries an attacker can make
    — Authentication: anonymous access is rate-limited more aggressively
    — Confidence precision: confidence returned to 2 decimal places
      (not full float64 precision), reducing the information per query
    — No logit exposure: raw logits are never returned; only softmax
      probabilities (still vulnerable to extraction attacks but at reduced
      precision)

  V2 CONSIDERATION:
    — Model watermarking: embed a statistical fingerprint in model outputs
      that allows attribution if a stolen surrogate model is discovered

17.9 FUTURE LLM FEATURES — PROMPT INJECTION RISKS
────────────────────────────────────────────────────
  VoiceGuard v1 does not use LLMs. If v3 adds natural language explanation
  generation using an LLM (e.g., Claude or GPT-4), the following risks arise:

  PROMPT INJECTION RISK:
    If the LLM receives any user-provided text as part of its prompt (e.g.,
    the audio file name), an attacker could embed prompt injection in the
    filename to manipulate the LLM's output.

  MITIGATIONS (for future LLM features):
    — Never include user-provided text directly in LLM prompts
    — Use structured data injection only (verdict, confidence, scores)
    — Output validation: LLM output must not contain code, HTML, or
      suspicious structures before being served to the user
    — Separate the LLM call from the LCNN inference in the pipeline
      (LLM output does not influence the classification result)
    — Rate-limit LLM calls separately from LCNN calls

SECTION 18 — PERFORMANCE STRATEGY
================================================================================

18.1 INFERENCE LATENCY TARGETS
─────────────────────────────────
  The end-to-end performance target is derived from Batch 01:
  "From file upload to result display: under 10 seconds on standard hardware."

  LATENCY BUDGET BREAKDOWN (targeting 8 seconds end-to-end):
    File upload (network): 0.5–2.0s (depends on user bandwidth; not controllable)
    Upload processing + validation: ≤ 0.3s
    Task queue wait (queue depth 0): ≤ 0.1s
    Stage 2 (input validation): ≤ 0.1s
    Stage 3–5 (preprocessing): ≤ 0.5s
    Stage 6 (STFT): ≤ 0.3s per minute of audio
    Stage 7 (normalization): ≤ 0.1s
    Stage 8 (segmentation): ≤ 0.05s
    Stage 9 (tensor prep): ≤ 0.05s
    Stage 10 (inference, per segment): ≤ 0.5s on CPU
    Stage 11–12 (calibration, aggregation): ≤ 0.05s
    Stage 14 (Grad-CAM): ≤ 1.0s
    Stage 15 (waveform/spectrogram): ≤ 0.2s
    Stage 17 (persistence, notification): ≤ 0.3s
    Result API response: ≤ 0.1s

    TOTAL (for 10-second file at 16kHz → 4 segments):
      Network + processing: ~5–6 seconds typical; ≤ 8 seconds p95

  LATENCY TARGETS BY PERCENTILE:
    p50: ≤ 3 seconds (simple, short files, CPU idle)
    p95: ≤ 5 seconds (file up to 60s, CPU at moderate load)
    p99: ≤ 10 seconds (long files, high queue depth)

18.2 MEMORY TARGETS
────────────────────
  PER WORKER MEMORY BUDGET:
    Model weights:        ~2.8MB
    Model activation memory (peak): ~50MB (during inference on single segment)
    Feature matrices:     ~10MB (LPS matrix for 60s file: 257 × 6000 frames)
    Grad-CAM tensors:     ~30MB (intermediate activations and gradients)
    Python runtime:       ~100MB
    Worker overhead:      ~200MB
    TOTAL PEAK:           ~400MB per worker process

  Worker memory limit: 4GB RSS (alert at 3.2GB; kill+restart at 3.8GB)
  With 2 workers: peak memory ≤ 800MB combined (well within 16GB VM)

18.3 GPU UTILIZATION (V2 TARGETS)
───────────────────────────────────
  Target GPU utilization: 60–85% sustained
  Target VRAM usage: ≤ 80% of available VRAM
  Batch size for GPU inference: determined by VRAM capacity; start with 8
  Target GPU p95 inference time: ≤ 1 second (significant over CPU)

18.4 BATCHING POLICY
─────────────────────
  WITHIN-SCAN BATCHING (v1, CPU):
    Segments from a single scan are batched into one forward pass.
    Batch size = segment_count (typically 1–20 for files up to 60s).
    This is already implemented in Stage 9.

  CROSS-SCAN BATCHING (not in v1):
    Processing segments from multiple concurrent scans in one forward pass.
    Not implemented in v1. CPU inference does not benefit significantly
    from cross-scan batching. Add for GPU in v2.

18.5 QUEUE STRATEGY
────────────────────
  The inference queue is designed for low latency, not high throughput.
  A shallow queue (≤ 10 tasks) with 2 fast workers is preferable to a deep
  queue with slow throughput.

  QUEUE PRIORITIES (within the inference queue):
    All inference tasks have equal priority in v1.
    In v2 (API key tiers): higher-tier API keys may receive priority routing.

  BACK PRESSURE:
    If queue depth > 50: the scan submission endpoint should return a
    rate_limit-like response: "Service temporarily at capacity. Estimated
    wait: X minutes." (computed from queue depth and average task time).
    This prevents unbounded queue growth.

18.6 CACHING STRATEGY
───────────────────────
  MODEL WEIGHTS CACHING:
    Model is loaded once into worker memory; no caching needed beyond
    the OS page cache for the .pt file. The OS page cache warms naturally
    after first worker startup.

  INFERENCE RESULT CACHING:
    Inference results are NOT cached by default. Every scan submission
    runs a full inference pass.
    Rationale: The same audio file can be uploaded by different users at
    different times; the result is deterministic given the same model version
    but caching by file hash raises privacy questions (can be used to detect
    whether a specific audio file was previously analyzed).
    V2 consideration: opt-in result caching for API key users who explicitly
    request it for duplicate detection workflows.

  SCAN STATUS CACHING:
    Redis caches scan status (PENDING/PROCESSING/COMPLETE/FAILED) with TTL
    as specified in Batch 04 Section 5.2. This is the primary performance
    optimization for the frontend polling loop.

18.7 CONCURRENCY STRATEGY
───────────────────────────
  Inference workers: 1 task per process (CPU-bound; threading does not help)
  Worker count: scales horizontally (add more processes/containers)
  API tier: async concurrency (uvicorn async workers); does not block on inference

  THREAD SAFETY NOTE:
    The PyTorch model is NOT thread-safe for concurrent forward passes.
    This is why each worker runs at concurrency = 1. Each process has its
    own model instance in its own memory space (no sharing across processes).

18.8 LARGE UPLOAD HANDLING
────────────────────────────
  Maximum file size: 10MB (enforced at Nginx and FastAPI layers)
  Streaming write: file is streamed to /tmp in 64KB chunks; never fully
    buffered in API worker RAM
  Large file inference: a 10MB audio file at 128kbps bitrate is approximately
    10 minutes of audio. This would exceed the 300-second duration limit.
    The duration limit acts as a proxy for the processing cost limit.
    Very large files within the 300-second limit (high bitrate) process
    similarly to smaller files at the same duration.

SECTION 19 — QUALITY ASSURANCE STRATEGY
================================================================================

19.1 QUALITY ASSURANCE PHILOSOPHY
────────────────────────────────────
Quality assurance for the AI platform operates at multiple levels:
  — Model quality: accuracy, calibration, regression testing
  — Pipeline quality: inference pipeline correctness, preprocessing fidelity
  — Operational quality: latency, availability, error rates
  — Governance quality: documentation completeness, approval chain integrity

QA is continuous, not a one-time gate. The golden test suite runs before
every deployment. Production monitoring is the QA system that never stops.

19.2 GOLDEN TEST SUITE
────────────────────────
The golden test suite is the highest-priority QA artifact in the AI platform.
It is a fixed set of 200 samples with reference verdicts that must be
reproduced by every model version before deployment.

  COMPOSITION:
    100 human samples: diverse recording conditions, formats, durations,
      languages, audio quality levels, microphone types
    100 AI-generated samples: diverse TTS systems, VC systems, attack types
      including A01–A19 from ASVspoof 2019 LA taxonomy

  REFERENCE VERDICTS:
    For each sample: reference_verdict (human or ai_generated), with the
    model version that originally established this reference.
    Reference verdicts are set by the first production model and are
    only changed when a sample is added or there is a documented reason
    to update a reference (requires a separate approval process).

  EXECUTION:
    Run automatically in the deployment pipeline before any model is
    promoted from experimental to canary.
    Run takes < 5 minutes (200 samples × typical inference time).

  PASS CRITERIA:
    All 200 samples must produce the reference verdict.
    Any deviation is a regression event that blocks deployment.
    Exception process: a deviation may be accepted if the AI Platform team
    and one additional reviewer document why the new verdict is correct
    and the reference verdict was wrong. This exception is added to an
    approved exception list that is maintained permanently.

  MAINTENANCE:
    New samples added quarterly (minimum 5 samples per quarter from
    new attack types or newly discovered edge cases).
    No samples ever removed (the suite only grows).
    New samples do not have reference verdicts until a production model
    produces their first verdict, which becomes the reference.

19.3 REGRESSION TEST SUITE
────────────────────────────
The regression suite is broader than the golden test suite. It covers the
full evaluation set and measures metric regressions, not just verdict
regressions.

  COMPOSITION:
    Full held-out evaluation set (minimum 2,000 samples, target 5,000)
    Attack-type breakdown evaluation set
    Format-specific evaluation (one test per supported format)
    Edge-case set (telephone bandwidth, silence, very short, very long,
      clipped, heavy compression)

  METRICS COMPUTED:
    EER, AUC-ROC, precision, recall, F1, ECE (full set from Section 9)
    Per-attack-type EER breakdown
    Per-file-format success rate

  PASS CRITERIA:
    No metric may regress beyond the thresholds defined in Section 9.5.
    Regression suite is run in evaluation (Stage 5 of MLOps lifecycle),
    not at deployment time (it takes > 1 hour; golden suite is the fast gate).

19.4 INFERENCE CONSISTENCY TESTS
──────────────────────────────────
  Inference must be deterministic for the same model version and the same
  input. Consistency tests verify this property.

  CONSISTENCY TEST 1 — SAME INPUT, MULTIPLE RUNS:
    Take 20 samples from the golden set. Run inference 5 times each.
    Verify: verdict, confidence, human_score, ai_score are identical in
    all 5 runs.
    Failure: indicates non-deterministic operations in the pipeline (e.g.,
    dropout left on in eval mode, random augmentation applied during inference).
    Expected result: all 5 runs produce identical outputs (100% pass required).

  CONSISTENCY TEST 2 — WORKER RESTARTS:
    Take 10 samples. Run inference. Restart the worker. Run the same samples.
    Verify: identical results before and after restart.
    This tests that model loading is deterministic and that warmup does not
    alter the model's behavior.

  CONSISTENCY TEST 3 — CROSS-FORMAT:
    Take 5 audio samples. Re-encode each in all 5 supported formats at
    lossless quality (WAV → FLAC for true lossless equivalence).
    Verify: identical verdicts from WAV and FLAC versions of the same audio.
    Note: lossy re-encoding (WAV → MP3) will not produce identical results;
    that is expected and not a test failure.

19.5 CROSS-VERSION COMPARISON
───────────────────────────────
  When a new model version is being evaluated for promotion, a cross-version
  comparison is required as part of the evaluation report.

  COMPARISON SCOPE:
    Run both the current production model AND the candidate model on the
    same evaluation set. Compare:
    — Agreement rate: proportion of samples where both models agree on verdict
    — Disagreement analysis: for samples where models disagree, which model
      is correct? (requires ground truth labels)
    — Confidence comparison: does the new model produce better-calibrated
      confidence scores?
    — Per-attack-type performance difference

  REPORT REQUIREMENT:
    The cross-version comparison report must be included in the evaluation
    artifacts (alongside the standard evaluation report) before the approval
    workflow (Section 13 Stage 6) can proceed.

19.6 CALIBRATION VERIFICATION
───────────────────────────────
  Calibration verification is run as part of the offline evaluation:
    1. Compute ECE on the held-out evaluation set
    2. Generate reliability diagram (confidence vs. accuracy)
    3. If ECE > 0.05: apply calibration correction (temperature scaling)
    4. Re-compute ECE after calibration; verify ECE ≤ 0.03 (post-calibration target)
    5. Store calibration parameters in model registry
    6. Verify that calibration parameters are correctly loaded by workers
       (integration test: run 10 samples, check that confidence values
       reflect calibration correction)

19.7 PERFORMANCE BENCHMARKING
──────────────────────────────
  Before any model is promoted to canary, performance benchmarking on the
  reference hardware (4 vCPU, 16GB RAM, no GPU) is required.

  BENCHMARK PROTOCOL:
    — Run 100 inference tasks sequentially (no parallelism) measuring
      inference_time_ms for each
    — Report: p50, p95, p99, max
    — Target: p95 ≤ 5,000ms
    — Include: 10 short files (<5s), 50 medium files (5–60s), 40 long files (60–300s)
    — Measure each stage separately (preprocessing, STFT, inference, Grad-CAM)
      to identify bottlenecks

  BENCHMARK ENVIRONMENT:
    Must be on the reference hardware in an isolated environment (no competing
    processes). Results on developer laptops are informational only.

19.8 STRESS TESTING
────────────────────
  Stress testing verifies that the inference pipeline remains stable under
  load and does not accumulate memory leaks.

  STRESS TEST 1 — SUSTAINED LOAD:
    Run 1,000 consecutive inference tasks on two workers.
    Monitor: worker memory RSS (should not grow monotonically),
    inference latency (should not degrade over time),
    error rate (should remain at baseline).
    Duration: approximately 2–3 hours.

  STRESS TEST 2 — BURST LOAD:
    Submit 100 tasks simultaneously (queue depth = 100 at start).
    Monitor: queue drain time, per-task latency under load,
    worker stability (no OOM kills).
    Expected: queue drains in approximately 50 minutes with 2 workers.

  STRESS TEST 3 — PATHOLOGICAL INPUT GAUNTLET:
    Submit 50 pathological inputs: silence, clipped, telephone bandwidth,
    1ms clip, 300s clip, corrupt header (should fail at validation),
    valid header with corrupt body.
    Expected: all fail gracefully with scan → FAILED; no worker crashes;
    no resource leaks.

19.9 LONG-DURATION TESTING
────────────────────────────
  Long-duration testing (soak testing) runs the inference pipeline for an
  extended period to detect gradual degradation, memory leaks, and
  intermittent failures.

  DURATION: 7 days continuous operation in staging environment
  TRAFFIC: Simulated production-representative traffic pattern
    (15 scans/hour during peak, 2 scans/hour at night)
  MONITORING: Full production monitoring active during soak test
  ACCEPTANCE: No worker restarts required; no memory growth > 10% over 7 days;
    failure rate ≤ 1% throughout

SECTION 20 — DISASTER RECOVERY PLAN
================================================================================

20.1 DISASTER CATEGORIES
──────────────────────────

  DR-1: MODEL CORRUPTION
    Definition: Model weights file on disk does not match registered checksum.
    Trigger: Detected at worker startup via checksum mismatch.
    Severity: CRITICAL — all inference halted if all workers are affected.

  DR-2: REGISTRY FAILURE
    Definition: model_versions database table is unavailable or contains
    no active model.
    Trigger: Registry integrity check fails; no is_active=true row.
    Severity: HIGH — new worker startups will fail; existing workers unaffected.

  DR-3: BAD DEPLOYMENT (regression deployed to production)
    Definition: A newly deployed model version is causing unacceptable
    verdict regression or latency regression in production.
    Trigger: Production monitoring alerts; human detection.
    Severity: HIGH — affects user experience immediately.

  DR-4: INFERENCE OUTAGE (all workers down)
    Definition: No inference workers are accepting tasks.
    Trigger: model_available = false for > 2 minutes; queue accumulating.
    Severity: CRITICAL — product feature completely unavailable.

  DR-5: GPU FAILURE (when GPU workers deployed in v2)
    Definition: GPU device unavailable; GPU workers fail to start.
    Severity: HIGH — must fall back to CPU workers.

20.2 DR-1: MODEL CORRUPTION RESPONSE
──────────────────────────────────────

  Detection:
    Worker startup log: model_checksum_mismatch event.
    CRITICAL alert sent immediately.

  Immediate Actions (within 5 minutes):
    1. Identify which workers are affected (check all worker logs).
    2. If any workers started without a mismatch: they are serving the
       correct model. Keep them running.
    3. For workers with checksum mismatch: quarantine them (remove from
       queue consumer group); do not attempt to run inference on them.
    4. Do not restart quarantined workers until the artifact is restored.

  Resolution (within 30 minutes):
    5. Retrieve backup copy of the model artifact from cold storage backup.
    6. Compute SHA-256 of the restored artifact; verify it matches registry.
    7. Replace corrupt file with restored artifact.
    8. Restart quarantined workers; confirm checksum verification passes.
    9. Verify model_loaded=true for all workers; resume normal operations.

  Root Cause Investigation:
    10. Investigate how the corruption occurred:
        — Hardware fault on the artifact storage disk?
        — Partial overwrite from a failed deployment?
        — Security incident (tampering)?
    11. If tampering is suspected: treat as a security incident; escalate.
    12. Add the event to the incident log.

  Fallback (if restoration takes > 30 minutes):
    If the current workers (those without mismatch) can serve traffic:
    maintain minimal service on those workers while resolving the corruption.
    If ALL workers have a mismatch (no workers running): the product enters
    a "Scan Unavailable" state (graceful degradation, not a 500 error).
    The frontend displays: "AI analysis is temporarily unavailable. We are
    working to restore service. Please try again in a few minutes."
    This message is triggered by the API returning 503 for scan submissions.

20.3 DR-2: REGISTRY FAILURE RESPONSE
──────────────────────────────────────

  Detection:
    Registry integrity check job fails; admin alert.
    Worker startup fails with "no active model found."

  Immediate Actions:
    1. Check PostgreSQL availability (is the database up?).
    2. If database is down: follow database disaster recovery (Batch 05
       Section 14). AI platform is secondary victim; restore DB first.
    3. If database is up but registry is empty or corrupt:
       a. Restore model_versions table from the most recent DB backup.
       b. Verify the restored registry has exactly one is_active=true row.
       c. Verify the artifact at artifact_path exists and checksum matches.
       d. Restart workers.

  Workers Already Running Are Unaffected:
    Existing workers have the model in memory and do not re-read the registry
    during task processing. Only new worker startups are affected by registry
    failures. Existing workers continue serving traffic.

20.4 DR-3: BAD DEPLOYMENT RESPONSE (ROLLBACK)
───────────────────────────────────────────────

  Detection:
    Production monitoring alerts: EER regression, latency regression,
    CRITICAL errors in new model workers, user feedback spike.

  Immediate Actions (within 10 minutes):
    1. Identify that the issue is model-related (vs. infrastructure).
       Check: did the regression start immediately after the last deployment?
    2. Decision: if > 50% degradation on any monitoring metric → immediate rollback.

  Rollback Procedure:
    3. Identify the previous production model version (deprecated status
       in model registry; deployed_at is the most recent deprecated_at).
    4. Retrieve previous model artifact from artifact store (warm storage;
       not yet archived if deprecation is recent).
    5. Start new worker processes with the previous model version.
    6. Verify previous model workers pass startup checks (checksum OK).
    7. Route all traffic to previous model workers.
    8. Stop new (bad) model workers.
    9. Update model registry:
       — Set new (bad) model: status = "deprecated", is_active = false
       — Set previous model: status = "production", is_active = true,
         deployed_at = now() (re-deployment)
    10. Monitor: confirm metrics return to baseline within 5 minutes.
    11. Issue rollback notification if this was a MAJOR version rollback
        (users already notified of upgrade; notify of rollback).

  Post-Rollback:
    12. Conduct root cause analysis: why did the new model fail in production
        when it passed evaluation and canary?
    13. Review canary monitoring: was the regression present in canary but
        missed? Update monitoring thresholds if so.
    14. Document incident in incident log.

  Maximum rollback time: 15 minutes (limited by worker startup sequence).

20.5 DR-4: INFERENCE OUTAGE RESPONSE
──────────────────────────────────────

  Detection:
    model_available = false for > 2 minutes (CRITICAL alert).
    Queue accumulating without workers draining it.

  Immediate Actions:
    1. Check worker process status (are workers running? ps aux | grep celery).
    2. If workers are dead: restart them (systemctl restart celery-inference).
    3. If workers fail to start: check startup logs for cause:
       — Checksum mismatch → DR-1 procedure
       — Model file not found → restore from backup
       — DB connection failure → DB incident
       — Out of disk space → emergency cleanup of /tmp
    4. If workers are running but not consuming:
       — Check Redis connectivity (Celery broker)
       — Check queue name routing

  User Communication:
    At 5 minutes without resolution: API returns 503 for scan submissions.
    Frontend shows: "Scan analysis is temporarily unavailable."
    At 15 minutes: consider publishing a status page update.

  Recovery Verification:
    After workers restart: verify model_loaded=true in logs.
    Send a test scan via the admin panel to verify end-to-end.
    Monitor queue depth: it should drain as workers process the backlog.

20.6 DR-5: GPU FAILURE RESPONSE (V2)
──────────────────────────────────────

  Detection:
    GPU worker logs: CUDA device unavailable; worker falls back to CPU.
    Or: GPU workers fail to start (CUDA device not visible).

  Response:
    1. If GPU workers fall back to CPU automatically: no immediate action;
       monitor latency (CPU inference is slower than GPU).
    2. If GPU workers fail entirely: start CPU-only workers as fallback.
       CPU workers load the same model artifact; no model change required.
    3. Scale up CPU workers to compensate for lost GPU throughput.
    4. Notify infrastructure team of GPU hardware issue.
    5. Do not attempt GPU recovery in production while inference is running;
       recover GPU on a separate maintenance window.

20.7 RECOVERY WORKFLOW (GENERAL)
──────────────────────────────────

  INCIDENT RESPONSE PROTOCOL:
    1. DETECT: Alert fires (automated) or user report triggers investigation.
    2. ASSESS: On-call engineer determines severity and category.
    3. COMMUNICATE: Update status page if user-visible impact.
    4. MITIGATE: Apply immediate fix (restart, rollback, fallback).
    5. VERIFY: Confirm metrics return to baseline.
    6. DOCUMENT: Write incident report within 24 hours.
    7. PREVENT: Update runbooks, monitoring, or deployment process to
       prevent recurrence.

  RUNBOOK LOCATION:
    All incident runbooks maintained in the AI Platform team's operations
    documentation. Each DR scenario above has a corresponding runbook.

SECTION 21 — ENGINEERING STANDARDS

21.1 NAMING CONVENTIONS
─────────────────────────

MODEL VERSION STRINGS:
  Pattern: {architecture}-v{major}.{minor}.{patch}-{dataset}
  Examples: lcnn-v1.0.0-asvspoof2019la, ensemble-v1.0.0-asvspoof2019la+wild
  Rules: lowercase, hyphens only (no underscores, no spaces), URL-safe

DATASET IDENTIFIERS:
  Pattern: {source}-v{major}.{minor}
  Examples: asvspoof2019la-v1.0, wild-v1.0
  Combined: datasets joined with + in model version string

EXPERIMENT IDENTIFIERS:
  Pattern: exp-{YYYYMMDD}-{short-description}
  Examples: exp-20260801-lcnn-v2-expanded-dataset
  Rules: lowercase, hyphens, contains date for chronological sorting

ARTIFACT FILE NAMES:
  Model weights: model.pt (always — the version string is the directory name)
  Calibration: calibration.pkl (if applicable)
  Manifest: manifest.sha256 (checksum manifest for the artifact directory)

METRIC NAMES (Prometheus):
  Pattern: voiceguard_{subsystem}_{metric_name}_{unit}
  Examples: voiceguard_inference_duration_ms, voiceguard_queue_depth_tasks
  Consistent with Prometheus naming conventions (no camelCase)

LOG EVENT NAMES:
  Pattern: {action}_{object} (snake_case)
  Examples: model_loaded, inference_completed, inference_failed,
    model_checksum_mismatch, gradcam_generation_failed

21.2 MODEL CONVENTIONS
────────────────────────
  — Models are always in eval mode during inference (no exceptions)
  — Models are always loaded from a registered artifact (no ad-hoc loading)
  — Models run under torch.no_grad() during inference (no gradient tracking)
  — Models are never modified at runtime (weights are frozen)
  — The model forward pass is never called from the API tier (only Celery tasks)
  — Model version is always included in every inference log record

21.3 DATASET CONVENTIONS
──────────────────────────
  — Every dataset used for training a production candidate must be registered
  — Dataset labels are binary: 0 = genuine (human), 1 = spoof (AI-generated)
  — Dataset splits (train/dev/eval) are documented and version-controlled
  — No dataset overlaps with another: train, dev, and eval partitions are disjoint
  — Dataset checksums are verified before every training run
  — User audio is never included in any dataset (no exceptions)

21.4 ARTIFACT CONVENTIONS
───────────────────────────
  — Artifacts are stored at: {artifact_store_root}/{version_string}/model.pt
  — Artifacts are read-only after upload (immutable in artifact store)
  — Checksums are always SHA-256 (not MD5, not SHA-1)
  — Artifact storage paths never contain user data or personally identifiable
    information

21.5 EXPERIMENT CONVENTIONS
─────────────────────────────
  — Experiments are registered before training begins (not after)
  — All hyperparameters are documented before the first training run
  — Evaluation is always run on the correct partition (never on training data)
  — Random seeds are always documented (for training reproducibility)
  — Experiments are never deleted, only marked as abandoned

21.6 DOCUMENTATION STANDARDS
──────────────────────────────
  REQUIRED DOCUMENTATION PER MODEL VERSION:
    — Evaluation report (JSON, standardized format)
    — Known limitations document (updated from registry known_weaknesses)
    — Cross-version comparison report
    — Calibration assessment
    — Governance checklist (completed and signed)
    — Approval signatures

  REQUIRED DOCUMENTATION PER DATASET:
    — Source documentation (where did each sample come from?)
    — Labeling methodology
    — Quality report
    — Privacy assessment
    — Dataset version changelog

  REQUIRED DOCUMENTATION PER INCIDENT:
    — Timeline (detection time, escalation time, resolution time)
    — Root cause analysis
    — Impact assessment (how many scans were affected?)
    — Resolution steps taken
    — Prevention measures

21.7 REVIEW REQUIREMENTS
──────────────────────────
  MODEL PROMOTION TO CANARY: requires 2 reviewers (peer + AI Platform)
  MODEL PROMOTION TO PRODUCTION: requires 2 reviewers + deployment sign-off
  DATASET REGISTRATION: requires 1 AI Platform reviewer
  ACCEPTANCE CRITERIA CHANGES: requires team lead sign-off + documentation
  CONFIDENCE THRESHOLD CHANGES: requires AI Platform lead + Responsible AI review
  KNOWN LIMITATIONS ADDITIONS: requires AI Platform review + product notification
    if user-facing change

21.8 PROMOTION REQUIREMENTS
─────────────────────────────
  A model may not be promoted unless:
    □ All evaluation gates pass (Section 9.5)
    □ Golden test suite: 100% pass (or approved exceptions documented)
    □ Evaluation report complete and reviewed
    □ Calibration verified (ECE ≤ 0.05 or correction applied)
    □ Known limitations documented in registry
    □ Feature specification verified against pipeline
    □ Performance benchmarks meet SLA
    □ Approval signatures obtained
    □ Deployment runbook reviewed by on-call engineer

SECTION 22 — AI PLATFORM SELF AUDIT
================================================================================

22.1 AUDIT METHODOLOGY
────────────────────────
This self-audit reviews the AI platform design against each domain defined
in the prompt: governance gaps, security weaknesses, monitoring gaps,
deployment risks, scalability issues, Responsible AI gaps, performance
bottlenecks, and operational risks.

22.2 MODEL GOVERNANCE — AUDIT RESULTS
────────────────────────────────────────

  FINDING: Registry immutability partially addressed
  STATUS: ACCEPTABLE
  Detail: The model registry stores checksums and version strings as immutable
    once written. However, the known_weaknesses field was designed as mutable
    (can be supplemented with new findings). This is intentional — new
    failure cases discovered post-deployment should be documentable without
    creating a new version. The mutable fields are audited via change log.
  Action: None required. Document the change log policy.

  FINDING: No automated data lineage validation
  STATUS: RISK
  Detail: The experiment record documents the training_dataset_id, but there
    is no automated check that the model artifact was actually trained on that
    dataset. A researcher could document the wrong dataset version.
  Action: Implement a training job that embeds the dataset version hash in
    the model artifact metadata (v2). For v1: peer review is the control.

  FINDING: Single approval gate for canary promotion
  STATUS: MINOR RISK
  Detail: Canary to production requires human approval, but only one approver
    is strictly required by the current design. Two approvers reduce the
    risk of a wrong decision.
  Action: Update Section 9.5 Gate 14 — require two approvers for production
    promotion. Already documented as "AI Platform Engineer + one additional
    reviewer." Enforce this in the deployment checklist.

22.3 SECURITY — AUDIT RESULTS
───────────────────────────────

  FINDING: No digital signature on model artifacts (v1)
  STATUS: ACCEPTABLE FOR V1
  Detail: SHA-256 checksum protects against accidental corruption and
    tampering by external actors. Digital signatures (v2) add protection
    against insider threats with write access to the artifact store.
  Action: Plan digital signing for v2. Document current risk in the
    threat model.

  FINDING: Confidence precision exposed in API
  STATUS: LOW RISK
  Detail: Confidence returned to 2 decimal places. This reduces (but does
    not eliminate) the information available for model extraction attacks.
  Action: This is a conscious trade-off: rounding to 1 decimal would
    significantly reduce user value (confidence at 1 decimal is coarse for
    professional use cases). Accept the risk; implement rate limiting as
    the primary control. Document in threat model.

  FINDING: No adversarial input detection layer
  STATUS: KNOWN GAP FOR V1
  Detail: The model is not adversarially hardened. Crafted inputs could
    potentially evade detection.
  Action: Document as a known limitation (Section 10.3). Plan adversarial
    training for v2. Rate limiting is the primary runtime control.

  FINDING: No monitoring for unusual query patterns that suggest adversarial exploration
  STATUS: GAP
  Detail: The monitoring system tracks error rates and latency but does not
    detect patterns consistent with an adversary systematically probing the
    model (e.g., many queries with slight audio variations).
  Action: Add a behavioral anomaly detection rule: if a single user/IP submits
    > 20 scans in 1 hour with the same verdict distribution, flag for review.
    This is an additional abuse detection layer beyond rate limiting.

22.4 MONITORING — AUDIT RESULTS
─────────────────────────────────

  FINDING: No ground truth for online performance measurement
  STATUS: FUNDAMENTAL LIMITATION
  Detail: In production, we cannot measure accuracy (EER, AUC-ROC) without
    ground truth labels. We can only monitor proxy metrics (confidence
    distribution, feedback rate). True online accuracy is unknown.
  Action: This is inherent to unsupervised production AI. The mitigation is:
    (1) periodic evaluation on labeled held-out data, (2) user feedback as
    noisy labels, (3) a model that is accurate on training data is expected
    to generalize. Document the limitation and its mitigations.

  FINDING: Feedback as noisy ground truth
  STATUS: KNOWN LIMITATION
  Detail: User feedback (incorrect result reports) is used as a signal for
    model improvement, but user verdicts are not always correct. A user who
    believes a genuine recording is AI-generated will submit "incorrect" feedback
    that is itself incorrect.
  Action: Feedback labels must be independently reviewed before being used
    in training data. The feedback table is research data, not ground truth.
    Document in dataset governance (Section 14.7).

  FINDING: Concept drift detection relies on indirect signals
  STATUS: ACCEPTABLE FOR V1
  Detail: Concept drift (new TTS systems emerging) cannot be directly
    detected from production metrics without ground truth. Indirect signals
    (confidence drops, feedback spikes) may lag the actual drift by days.
  Action: Establish a quarterly "model freshness review" where the AI Platform
    team evaluates the current production model on newly collected in-the-wild
    samples. This proactive review supplements reactive drift monitoring.

22.5 DEPLOYMENT — AUDIT RESULTS
──────────────────────────────────

  FINDING: Model rollback takes up to 15 minutes
  STATUS: ACCEPTABLE WITH MITIGATION
  Detail: Rollback requires starting new workers with the old model, which
    takes ~5–10 minutes (worker startup sequence including checksum and warmup).
    During this time, the bad model may continue to serve some traffic.
  Action: Keep the previous model artifact in warm storage (not archived)
    for the full canary + production period (minimum 30 days). Consider
    keeping "standby" workers pre-loaded with the previous model version
    as a fast-rollback option. For v2, implement zero-downtime rollback
    with pre-warmed previous-version workers always running at 0% traffic.

  FINDING: No automated rollback trigger
  STATUS: KNOWN GAP
  Detail: Rollback is initiated manually by a human after reviewing alerts.
    This introduces human delay of 5–30 minutes depending on time of day
    and on-call response time.
  Action: For v2, implement automated rollback trigger if:
    (1) canary inference_error_rate > 5% AND (2) production error_rate is normal
    → automatically route all traffic back to production workers and alert.
    Human confirmation still required but the automated step stops the bleeding.

  FINDING: Single region deployment
  STATUS: ACCEPTED V1 CONSTRAINT
  Detail: V1 is a single-region deployment. A regional cloud outage would
    take down inference entirely.
  Action: Acceptable for v1. Multi-region is a v2/v3 priority.

22.6 SCALABILITY — AUDIT RESULTS
──────────────────────────────────

  FINDING: Manual scaling of inference workers
  STATUS: V1 CONSTRAINT; V2 ROADMAP
  Detail: Worker scaling requires SSH access and manual Celery restart.
    This is not suitable for sudden traffic spikes.
  Action: Containerize workers (Docker/Kubernetes) in v2 with Horizontal
    Pod Autoscaler driven by queue depth metric. Documented in Section 16.4.

  FINDING: Cross-scan batching not implemented
  STATUS: DEFERRED TO V2
  Detail: CPU inference doesn't benefit much from cross-scan batching.
    GPU inference would benefit significantly.
  Action: Implement cross-scan batching when GPU workers are deployed in v2.

  FINDING: Base64 heatmap in database may become a bottleneck
  STATUS: DOCUMENTED AND MONITORED
  Detail: Storing large base64 strings in the scan_results table will
    eventually stress PostgreSQL storage and query performance.
  Action: Benchmark at 100K scans as specified in Batch 05 Section 3.4.
    Migrate to object storage (S3) using the discriminator pattern when
    average row size exceeds 500KB.

22.7 RESPONSIBLE AI — AUDIT RESULTS
──────────────────────────────────────

  FINDING: Accent and language bias not directly measured
  STATUS: KNOWN GAP
  Detail: The training dataset (ASVspoof 2019 LA) is primarily English.
    EER on non-English audio has not been directly measured.
  Action: Add non-English test samples to the held-out evaluation set (v2).
    Until measured, document "Cross-Lingual Audio" as a known limitation
    (Section 10.3 Limitation 4). Do not make accuracy claims for non-English.

  FINDING: No differential privacy analysis
  STATUS: LOW PRIORITY FOR V1
  Detail: No individual user's audio is used for training. The training
    data is public benchmarks. Differential privacy is not a concern for v1.
  Action: If user-contributed data is ever added to training (v3+), a
    differential privacy analysis must be performed.

  FINDING: Confidence thresholds not user-configurable
  STATUS: PRODUCT DECISION
  Detail: Confidence thresholds (0.85/0.65) are set by the model registry.
    Professional users (forensic analysts) might prefer different thresholds.
  Action: Add user_preferences fields for custom thresholds in v2
    (confidence_threshold_certain, confidence_threshold_uncertain —
    already noted in Batch 05 user_preferences future extensibility).
    Implement server-side threshold application based on user preferences.

22.8 PERFORMANCE — AUDIT RESULTS
──────────────────────────────────

  FINDING: Grad-CAM computation adds ~1 second to every inference
  STATUS: ACCEPTABLE; MONITOR
  Detail: Grad-CAM requires an additional backward pass, adding latency.
    For the target p95 of ≤ 5 seconds, this is within budget.
  Action: If Grad-CAM becomes a latency bottleneck (p95 > 4 seconds without
    Grad-CAM already), move Grad-CAM to an async post-processing step:
    store null initially, generate asynchronously, update result when ready.
    The frontend already handles null heatmap gracefully.

  FINDING: Very long files (60–300s) may exceed 10-second latency target
  STATUS: ACCEPTED AND COMMUNICATED
  Detail: Files approaching 300 seconds will take longer than 10 seconds
    to process (multiple segments). The Batch 01 "under 10 seconds" target
    applies to standard-length files.
  Action: For files > 60 seconds, return an estimated_wait_seconds in
    the scan submission response (Section 5.17 of Batch 04). The UI shows
    the estimate. This sets correct expectations without blocking.

22.9 OPERATIONAL — AUDIT RESULTS
──────────────────────────────────

  FINDING: No model serving framework (TorchServe, Triton)
  STATUS: APPROPRIATE FOR V1
  Detail: V1 uses direct PyTorch inference in a Celery worker. This is
    simpler and sufficient for the v1 scale. A model serving framework
    (TorchServe, NVIDIA Triton) would add GPU batching, multiple model
    management, and REST/gRPC serving — not needed at v1 scale.
  Action: Evaluate TorchServe or Triton when GPU deployment and multi-model
    serving are needed (v2).

  FINDING: No A/B experiment framework for model comparison
  STATUS: DEFERRED TO V2
  Detail: The canary deployment serves as A/B testing infrastructure. A
    more sophisticated A/B experiment framework (with statistical significance
    testing, user cohort assignment) is not needed for v1.
  Action: The canary mechanism (Section 16.9) is sufficient for v1. Design
    a proper A/B framework in v2 when multiple model variants need simultaneous
    testing.

SECTION 23 — RISKS & MITIGATIONS
================================================================================

23.1 TECHNICAL RISKS
──────────────────────

RISK T1: CONCEPT DRIFT — NEW AI SYNTHESIS METHODS EMERGE
  Likelihood: HIGH (the AI audio generation field is advancing rapidly)
  Impact: HIGH (model becomes less accurate for new attack types)
  Current Mitigation: Known limitation disclosure; quarterly freshness review
  Planned Mitigation: In-the-wild dataset updated quarterly with new attack
    type samples; continuous model improvement pipeline; alerts on feedback spikes
  Residual Risk: There will always be a lag between a new synthesis method
    emerging and VoiceGuard detecting it. This lag is unavoidable.
  Owner: AI Platform team

RISK T2: MODEL WEIGHTS CORRUPTION OR TAMPERING
  Likelihood: LOW (artifact store is access-controlled)
  Impact: CRITICAL (all inference produces wrong results or fails)
  Current Mitigation: SHA-256 checksum verified at every worker startup;
    access-controlled artifact store; backup copies
  Planned Mitigation: Digital signing in v2
  Residual Risk: Insider threat (employee with write access to artifact store)
  Owner: AI Platform + Security

RISK T3: PYTORCH OR LIBRARY VULNERABILITY
  Likelihood: MEDIUM (PyTorch has regular security patches)
  Impact: MEDIUM (potential for arbitrary code execution if exploited)
  Current Mitigation: Dependency pinning; pip-audit in CI; regular updates
  Residual Risk: Zero-day vulnerabilities in the ML library ecosystem
  Owner: Backend Platform team

RISK T4: INFERENCE LATENCY REGRESSION WITH SCALE
  Likelihood: MEDIUM (as user volume grows, queue depth increases)
  Impact: MEDIUM (user experience degradation; product trust at risk)
  Current Mitigation: Queue depth monitoring; scaling runbook
  Planned Mitigation: Horizontal autoscaling in v2; GPU workers
  Residual Risk: Sudden viral traffic spike outpaces scaling response time
  Owner: AI Platform + Infra

RISK T5: GRAD-CAM GRADIENT HOOK FAILURE
  Likelihood: LOW (stable after initial implementation)
  Impact: LOW (heatmap missing; scan succeeds without it)
  Current Mitigation: Failure is non-blocking; null heatmap returned
  Residual Risk: User experience degradation if heatmap is missing
  Owner: AI Platform

23.2 RESPONSIBLE AI RISKS
───────────────────────────

RISK RA1: FALSE VERDICT IN HIGH-STAKES CONTEXT (JOURNALIST / LEGAL)
  Likelihood: MEDIUM (model has 7.07% EER; some incorrect verdicts are expected)
  Impact: HIGH (journalist publishes incorrect story; evidence misused in court)
  Current Mitigation: Limitations disclosure in UI; confidence thresholds;
    "uncertain" verdict; professional guidance text; model disclaimers
  Residual Risk: A user may override warnings and present a VoiceGuard result
    as definitive evidence. VoiceGuard cannot control post-decision behavior.
  Owner: Product + AI Platform

RISK RA2: SYSTEMATIC BIAS AGAINST NON-ENGLISH AUDIO
  Likelihood: MEDIUM (training data is primarily English)
  Impact: MEDIUM (different EER for non-English audio, potentially unknown)
  Current Mitigation: Documented as known limitation; no claims made for
    non-English audio
  Planned Mitigation: Add non-English samples to evaluation set in v2;
    measure and publish EER by language
  Residual Risk: Users may not read the limitations disclosure
  Owner: AI Platform + Product

RISK RA3: MISUSE FOR SURVEILLANCE OR POLITICAL TARGETING
  Likelihood: LOW (rate limiting reduces mass analysis feasibility)
  Impact: HIGH (ethical harm; reputational damage to VoiceGuard)
  Current Mitigation: Rate limiting; Terms of Service prohibition
  Residual Risk: Rate limits can be circumvented with multiple accounts
  Owner: Product + Legal

23.3 OPERATIONAL RISKS
────────────────────────

RISK O1: SINGLE POINT OF FAILURE — INFERENCE WORKERS
  Likelihood: LOW (workers are stable processes)
  Impact: HIGH (product feature completely unavailable)
  Current Mitigation: Minimum 2 workers (redundancy); auto-restart policy;
    model_available monitoring with CRITICAL alerts
  Planned Mitigation: Multiple VMs for workers in v2; containerized with
    restart policies and health checks
  Residual Risk: Common-mode failure (VM crash taking both workers)
  Owner: Infra + AI Platform

RISK O2: ARTIFACT STORE UNAVAILABILITY
  Likelihood: LOW (artifact store is a filesystem; stable)
  Impact: HIGH (worker restarts will fail without the model artifact)
  Current Mitigation: Artifact stored on a separate, backed-up partition;
    workers keep model in memory once loaded (restart needed to notice outage)
  Planned Mitigation: Object storage (S3) with high availability in v2
  Residual Risk: If all workers restart simultaneously (e.g., host reboot)
    and artifact store is down, inference is unavailable until store recovers
  Owner: Infra

RISK O3: CELERY BROKER (REDIS) FAILURE
  Likelihood: LOW–MEDIUM (Redis is generally stable but can OOM)
  Impact: HIGH (task queue unavailable; scan submissions fail)
  Current Mitigation: Redis monitoring; alert on Redis connection failures
  Planned Mitigation: Redis Sentinel or Redis Cluster for HA in v2
  Residual Risk: Redis is a single point of failure for task queuing in v1
  Owner: Infra

24.1 V1 LAUNCH RECOMMENDATIONS (IMMEDIATE)
────────────────────────────────────────────

  RECOMMENDATION 1: REGISTER THE CURRENT MODEL IN THE REGISTRY BEFORE LAUNCH
  Priority: CRITICAL
  The existing LCNN model (running in the Gradio prototype, app.py) must be
  formalized as a registry entry before VoiceGuard launches. This means:
  — Computing and recording the SHA-256 checksum of the current lcnn_best.pt
    file downloaded from HuggingFace (imsoumya18/audio-deepfake-detector)
  — Creating the model_versions row: version_string = "lcnn-v1.0.0-asvspoof2019la",
    is_active = true, status = production, eer_percentage = 7.070,
    known_weaknesses documented (A17 attack type, telephone bandwidth)
  — Verifying the model artifact at its deployment path matches the checksum
  Without this, the model is unregistered and unverifiable. The product cannot
  make credible claims about the model version or traceability.

  RECOMMENDATION 2: IMPLEMENT CHECKSUM VERIFICATION AT WORKER STARTUP
  Priority: CRITICAL
  The worker startup sequence (Section 16.1) must verify the SHA-256 checksum
  before loading the model. This is the single most important security control
  for the AI platform. It takes one day to implement and prevents the model
  corruption disaster scenario (DR-1).

  RECOMMENDATION 3: ESTABLISH THE GOLDEN DATASET BEFORE LAUNCH
  Priority: HIGH
  Curate and document the 200-sample golden dataset (Section 19.2) before launch.
  Run the current model against it to establish reference verdicts.
  This is the regression baseline that all future models will be tested against.
  Without a golden dataset, future model improvements have no automated safety net.

  RECOMMENDATION 4: IMPLEMENT THE GRADCAM FAILURE METRIC
  Priority: HIGH
  The gradcam_failure_rate metric must be tracked from day one (Section 11).
  If Grad-CAM is silently failing for a percentage of users, they are receiving
  results without the heatmap visualization that is a core product promise.
  A 1% alert threshold catches this early.

  RECOMMENDATION 5: DOCUMENT ALL KNOWN LIMITATIONS IN THE UI BEFORE LAUNCH
  Priority: HIGH
  The A17 neural codec weakness, telephone bandwidth degradation, and model
  disclaimers (Section 10) must appear in the product UI at launch — not in v2.
  Professional users (journalists, law enforcement) will ask about limitations.
  Launching without these disclosures would undermine credibility with exactly
  the users who matter most for product trust.

  RECOMMENDATION 6: ENSURE CONFIDENCE THRESHOLDS ARE REGISTRY-DRIVEN
  Priority: MEDIUM
  The 0.85/0.65 thresholds must be read from the model registry, not hardcoded
  in the inference pipeline or the frontend. This future-proofs the system for
  models with different calibration characteristics. Implementation cost is low;
  the benefit of never having to coordinate a code change + registry update
  simultaneously (and risking a threshold mismatch during deployment) is high.

24.2 V2 AI PLATFORM ROADMAP
─────────────────────────────

  PRIORITY 1: Horizontal Autoscaling
    Containerize inference workers with Kubernetes HPA driven by queue depth.
    Eliminates the manual scaling limitation identified in the audit.
    Prerequisite: move to Docker/Kubernetes infrastructure.

  PRIORITY 2: GPU Workers
    Add NVIDIA GPU support to the inference pipeline.
    Reduces p95 inference latency from ~5 seconds to ~1 second.
    Prerequisite: CUDA support in PyTorch (already supported by PyTorch);
    a GPU-enabled VM or cloud instance.

  PRIORITY 3: Expanded Evaluation Dataset
    Add in-the-wild samples to the held-out evaluation set.
    Add non-English samples.
    Measure and publish EER by language and attack type.
    Critical for honest Responsible AI disclosure.

  PRIORITY 4: Digital Artifact Signing
    Sign model artifacts with a team signing key.
    Adds insider threat protection beyond SHA-256 checksums.

  PRIORITY 5: Ensemble Model Support
    Design the inference pipeline to support ensemble models
    (multiple constituent models, aggregated verdict).
    Required when a single model can no longer achieve the desired EER.

  PRIORITY 6: User-Configurable Confidence Thresholds
    Allow professional users (API key tier) to set custom thresholds
    in user_preferences. Implement server-side threshold application.

  PRIORITY 7: Calibration Pipeline
    Implement an automated calibration pipeline (temperature scaling)
    that runs as part of every model evaluation.
    Store calibration parameters in the registry automatically.

  PRIORITY 8: Automated Rollback Trigger
    Implement automated traffic routing back to previous model version
    if canary error rate exceeds threshold.
    Reduces rollback time from 15 minutes (human-in-the-loop) to < 2 minutes.
