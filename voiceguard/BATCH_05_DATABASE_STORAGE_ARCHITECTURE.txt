SECTION 1 — EXECUTIVE SUMMARY
================================================================================

VoiceGuard is a free audio deepfake detection platform that accepts audio file
uploads, processes them through an LCNN model, and returns a three-state verdict
(human / ai_generated / uncertain) with a Grad-CAM frequency heatmap. The
platform supports anonymous guest sessions, registered user accounts, scan
history, PDF report generation, shareable result links, a feedback pipeline,
a help center, API key access, and an administrative oversight layer.

This document specifies the complete persistence architecture for VoiceGuard v1,
covering PostgreSQL (primary relational store), Redis (cache, rate limiting,
ephemeral state), and ephemeral filesystem storage for temporary audio files.
It also specifies the future-readiness roadmap for object storage, data
warehousing, analytics, and search.

The defining constraint of this architecture is the product's core privacy
promise: audio files are NEVER stored permanently. Every design decision in the
storage layer flows from this constraint. What IS stored is metadata: verdicts,
confidence scores, frequency heatmaps (as base64 in the database), file hashes,
and user account data.

Key architectural decisions:
  — PostgreSQL 15+ as the single relational source of truth
  — Redis 7+ for ephemeral state (rate limits, OAuth flow, scan status cache)
  — No object storage for audio in v1 (audio is ephemeral by design)
  — JSONB for flexible AI output data (details, event metadata in audit logs)
  — UUID v4 primary keys throughout for security and future distribution
  — All timestamps stored as timestamptz (UTC, timezone-aware)
  — Soft delete with 30-day recovery for user accounts
  — Hard delete for guest scan data after 24-hour session expiry
  — Append-only audit log with 2-year retention minimum

The architecture supports:
  — 10,000+ users at v1 launch without structural changes
  — Horizontal scaling of the API tier with no database schema changes
  — Clean future extraction to microservices (domain-aligned tables)
  — Future batch processing, API tiers, team workspaces, and mobile apps
  — GDPR compliance (data export, right to erasure, data minimization)

SECTION 2 — DATABASE PHILOSOPHY
================================================================================

2.1 DATA OWNERSHIP
───────────────────
Every piece of data has exactly one owning module. No table is co-owned. The
owning module is the only module permitted to write to that table directly. Other
modules access cross-domain data exclusively through the owning module's service
interface.

  Table → Owning Module
  ─────────────────────────────────────────────────────────────
  users, user_preferences       → user module
  oauth_accounts                → auth module (on behalf of user module)
  refresh_tokens                → auth module
  email_verifications           → auth module
  password_reset_tokens         → auth module
  api_keys                      → user module
  scans                         → scan module
  scan_results                  → scan module (written by inference worker)
  notifications                 → notification module
  feedback                      → feedback module
  help_articles                 → help module
  article_feedback              → help module
  audit_logs                    → core module (written by all modules)
  model_versions                → admin module (seeded, rarely written)
  deleted_accounts              → user module

This ownership model ensures module boundaries are structurally enforced and
enables future extraction to separate services with separate databases.

2.2 DATA LIFECYCLE
───────────────────
Three distinct data lifecycles govern all entities in VoiceGuard:

  LIFECYCLE A — PERMANENT (until user-initiated deletion)
  User accounts, scan metadata, scan results, notifications, feedback.
  These persist for the lifetime of the account and are deleted only when the
  user explicitly requests account deletion or data purge.

  LIFECYCLE B — EPHEMERAL (time-bounded by design)
  Audio files on temp filesystem (60 seconds after scan completion).
  Guest sessions (24 hours).
  OAuth state in Redis (10 minutes).
  Password reset tokens (1 hour).
  Email verification tokens (24 hours).
  Rate limit counters in Redis (window duration).
  Scan status cache in Redis (300 seconds for terminal states).

  LIFECYCLE C — COMPLIANCE RETENTION (cannot be user-deleted)
  Audit logs (2-year minimum, append-only).
  Deleted account records (30 days post-deletion for recovery, then purged).
  Anonymized audit entries (user_id replaced with hash after account purge,
  retained for 2 years from creation).

2.3 DATA INTEGRITY
───────────────────
VoiceGuard enforces data integrity at three levels:

  LEVEL 1 — APPLICATION LAYER
  Pydantic validation on all inputs before database writes.
  Business rule enforcement in service layer before repository calls.
  Enum validation for all status and type fields.

  LEVEL 2 — DATABASE LAYER
  Foreign key constraints on all relationship columns.
  NOT NULL constraints on all required fields.
  UNIQUE constraints on all natural keys (email, OAuth identity, etc.).
  CHECK constraints on numeric ranges (confidence scores 0.0–1.0).
  Enum-equivalent constraints via PostgreSQL check constraints or native
  ENUM types (see Engineering Standards section for convention choice).

  LEVEL 3 — PERIODIC INTEGRITY CHECKS
  Scheduled jobs verify referential integrity, detect orphan records,
  and alert on constraint violations that somehow passed all prior layers.

2.4 NORMALIZATION STRATEGY
────────────────────────────
The schema is normalized to Third Normal Form (3NF) as the default, with
targeted denormalization applied only where read performance is measurably
improved and where the denormalized values can be reliably kept in sync.

  NORMALIZED (3NF) — all main entities:
  Users, scans, scan_results, notifications, feedback are fully normalized.
  No repeating groups. No transitive dependencies. Every non-key attribute
  depends on the whole primary key only.

  DENORMALIZED BY INTENT (with justification):
  scans.file_hash_sha256 — stored redundantly in both scans and scan_results
    for the access pattern where scan list views show hash without joining
    to scan_results. Acceptable because the hash is immutable once written.

  notifications.scan_id — optional FK makes notification queries self-contained
    without a second lookup when rendering the notification center.

  Article helpful counts (helpful_yes_count, helpful_no_count on help_articles)
    are denormalized counters maintained via increment on article_feedback insert.
    Avoids expensive COUNT aggregates on the feedback table per article per page
    load. Tolerable inconsistency risk: counts may lag by one increment under
    race; correctable by periodic reconciliation job.

2.5 REFERENTIAL INTEGRITY
───────────────────────────
All foreign keys are enforced at the database level, not only at the application
level. This is non-negotiable. Application bugs can bypass FK enforcement in the
application layer; database-level FKs cannot be bypassed.

  Cascade strategy (decided per relationship):
  — user deletion → scan deletion (CASCADE): When a user is purged after the
    30-day soft-delete window, all their scans cascade-delete automatically.
    This is correct because scan data without a user is meaningless and
    non-recoverable orphan data.
  — scan deletion → scan_result deletion (CASCADE): scan_results are
    inseparable from their parent scan.
  — user deletion → notifications (CASCADE): Notifications without a user
    serve no purpose.
  — user deletion → refresh_tokens (CASCADE): All sessions must invalidate.
  — user deletion → api_keys (CASCADE): All programmatic access must revoke.
  — user deletion → feedback (SET NULL on user_id): Feedback records are
    research value independent of the submitting user. Preserve the content,
    anonymize the attribution.
  — scan deletion → feedback.scan_id (SET NULL): Feedback linked to a deleted
    scan retains research value; the scan_id becomes null.
  — help_article deletion → article_feedback (CASCADE): No orphan ratings.

  Soft delete does NOT cascade. When a user's deletion is scheduled (soft delete
  phase), their data remains fully intact and accessible to the user during the
  30-day recovery window. Cascades only fire on the hard delete (purge).

2.6 CONSISTENCY MODEL
───────────────────────
VoiceGuard uses strong consistency (PostgreSQL's default serializable-capable
ACID model) for all critical writes. Specific consistency requirements:

  STRONG CONSISTENCY REQUIRED:
  — User registration (email uniqueness must be globally consistent)
  — Scan ownership verification (must not serve another user's result)
  — Refresh token rotation (detect reuse attack immediately)
  — Account deletion initiation (must atomically revoke all sessions)
  — Guest scan migration (must atomically transfer all scans)

  EVENTUAL CONSISTENCY ACCEPTABLE:
  — Notification unread count (stale by up to 60 seconds via Redis cache)
  — Dashboard scan statistics (cached aggregates, stale by up to 5 minutes)
  — Article helpful counts (lag by one increment under concurrent writes)
  — Global scan counter on landing page (approximate is sufficient)

2.7 TRANSACTIONAL BOUNDARIES
──────────────────────────────
A transaction contains exactly the operations that must succeed or fail together.
Transactions are kept as short as possible to minimize lock contention.

Critical transaction boundaries are defined in Section 10 (Transaction Design).

The general rule: a transaction spans exactly one module's data layer. Cross-
module operations are handled by application-layer orchestration (service calling
multiple repositories sequentially), not distributed transactions. If the second
module's write fails after the first succeeds, a compensating operation is
triggered (not a rollback across module boundaries).

2.8 SOFT DELETE PHILOSOPHY
────────────────────────────
Soft delete is applied only to user accounts, not to individual scans.

Rationale for soft-deleting user accounts:
  — Product UX (Batch 01): "Delete account → soft delete → 30-day recovery window"
  — Legal requirement: Users must be able to recover accidental deletion
  — Business requirement: Prevent reuse of deleted email addresses immediately
    while keeping recovery possible

Rationale for hard-deleting individual scans:
  — Scan deletion is low-risk; users can always run a new scan
  — No recovery requirement for scans (Batch 01: "This cannot be undone")
  — Hard delete keeps history table clean and simple

Soft delete implementation for users:
  — users.deletion_scheduled_at is set to the initiation timestamp
  — users.deletion_purge_at is set to initiation + 30 days
  — All refresh tokens immediately revoked (hard delete)
  — User can still log in during recovery window; login prompts cancellation
  — A Celery Beat job queries for deletion_purge_at < now() and purges

2.9 HARD DELETE PHILOSOPHY
────────────────────────────
Hard delete applies to: individual scans (user-initiated), bulk scan deletion,
guest scan expiry, expired tokens, temp files, and the final account purge.

The account purge (hard delete) sequence:
  1. Delete all scan_results records for this user's scans
  2. Delete all scans records for this user
  3. Delete all notifications for this user
  4. Delete all api_keys for this user
  5. Delete all refresh_tokens for this user
  6. DELETE the user record itself
  7. Anonymize audit_logs entries: replace user_id with SHA-256(user_id + salt)
  8. Mark deleted_accounts.deletion_completed_at = now()

Steps 1–6 are performed within a single database transaction.
Step 7 (audit log anonymization) is performed separately as it is an UPDATE
on the audit_logs table, which is otherwise append-only.

2.10 GUEST DATA LIFECYCLE
───────────────────────────
Guest sessions are governed by a 24-hour expiry and never require account data.

  Birth: Guest token is generated (32 random bytes, hex-encoded) and set as a
    browser cookie. No database record is created for the guest session itself.
    The token is used as a foreign-key-like value on scan records.

  Active state: Guest scans are written to the scans table with user_id = NULL
    and guest_token = {token value}. The guest can poll scan status using their
    token for ownership verification.

  Migration: When a guest creates an account, all their completed/failed scans
    (where guest_token = their token) are updated in a single transaction:
    user_id is set, guest_token is cleared.

  Expiry: Guest scans not migrated within 24 hours become inaccessible. The
    guest_token cookie expires. A Celery Beat job (hourly) deletes scan records
    with guest_token IS NOT NULL AND created_at < 24 hours ago AND status IN
    (complete, failed). PENDING/PROCESSING guest scans are left until they
    resolve, then cleaned up in the next hourly sweep.

  Privacy: Guest token values are never logged in application logs. Only hashes
    are used in audit events referencing guest activity.

2.11 USER DATA LIFECYCLE
──────────────────────────
  Registration → Pending verification → Verified → Active → [Deletion initiated]
  → [30-day recovery window] → [Purged]

  During Active: All data accumulates (scans, notifications, preferences).
  During Deletion window: All data is intact. User can still log in and cancel.
  On Purge: All user data is deleted. Audit logs are anonymized (not deleted).
  Email hash is stored in deleted_accounts to prevent immediate re-registration
  with the same address while still enabling deregistration confirmation.

2.12 SCAN LIFECYCLE
─────────────────────
  PENDING → PROCESSING → COMPLETE → [soft-deleted by user] → [hard-deleted]
                       → FAILED → [cleaned up automatically]

  Every scan has a status field. Status transitions:
    pending:    Written on upload receipt. Audio file exists in /tmp.
    processing: Inference worker picked up the task. Audio file still in /tmp.
    complete:   Inference succeeded. Results in scan_results. Audio deleted.
    failed:     Inference failed. Audio deleted. User can retry via new upload.

  Scan records in state complete are user-accessible indefinitely until:
    a) The user explicitly deletes the scan
    b) The user's account is purged
    c) A bulk delete operation removes it

  Scan records in state failed remain in the database (for audit and error
  analysis) but show a "failed" state to the user. Cleaned up by the guest
  expiry job if they are guest scans.

SECTION 3 — TECHNOLOGY DECISIONS
================================================================================

3.1 PRIMARY DATABASE — PostgreSQL 15+
────────────────────────────────────────
SELECTED: PostgreSQL 15 or later.

Justification:
  a) ACID guarantees — VoiceGuard has multiple critical atomic operations
     (token rotation with reuse detection, guest scan migration, account
     deletion). PostgreSQL's full ACID compliance with serializable isolation
     is essential. SQLite lacks concurrent write capability; MySQL's ACID
     implementation historically had edge cases under high load.

  b) JSONB support — scan_results needs to store arbitrary AI output metadata
     and audit_log entries need flexible JSON detail payloads. PostgreSQL's
     JSONB provides indexed, queryable JSON storage without the performance
     cost of TEXT JSON.

  c) Native UUID support — All primary keys are UUID v4. PostgreSQL handles
     UUID natively (gen_random_uuid() function, UUID equality operators,
     B-tree indexing on UUID columns) without extension complexity in newer
     versions.

  d) Row-Level Security (RLS) — While v1 does not enable RLS (enforcement is
     done in the application layer), the database role architecture is designed
     to enable RLS in v2 for multi-tenant team workspaces without schema changes.

  e) Full-text search capability — PostgreSQL's tsvector/tsquery can serve
     scan history search (by filename) and help article search in v2 without
     introducing a separate search engine at that scale.

  f) Mature ecosystem — SQLAlchemy (async), Alembic (migrations), pgBouncer
     (connection pooling), pg_dump/pg_restore (backup), Patroni (HA) all
     have first-class PostgreSQL support. The Python/FastAPI backend already
     assumes PostgreSQL (Batch 04 Decision 3).

  g) Active record partitioning — PostgreSQL's native declarative partitioning
     (RANGE on created_at) enables the scans table to be partitioned by month
     when it grows beyond 10 million rows, without schema changes to the
     application layer.

  Minimum version: 15 (for improved MERGE syntax, logical replication
  improvements, and better planner statistics).
  Recommended version: 16 for parallel query improvements.

3.2 CACHING LAYER — Redis 7+
──────────────────────────────
SELECTED: Redis 7 or later.

Justification:
  a) Rate limiting — Batch 01 and 04 mandate Redis-based sliding window rate
     limiting. Redis INCR with EXPIRE provides atomic counter operations in
     sub-millisecond time. PostgreSQL-based rate limiting would add database
     pressure on the hottest code path (every scan submission).

  b) Scan status pub/sub — Batch 04 specifies a pub/sub channel per scan for
     status delivery (scan_status:{scan_id}). Redis Pub/Sub is the canonical
     solution. Alternative: polling against PostgreSQL, which is the v1
     fallback but adds database load.

  c) OAuth flow state — The PKCE code_verifier and state parameter must be
     ephemeral (10-minute TTL), strongly consistent (one-time use), and
     extremely fast to retrieve. Redis with TTL is the exact fit.

  d) Celery broker — Batch 04 designates Redis as the Celery message broker
     for the inference task queue. Redis's list-based queue semantics with
     atomic LPUSH/BRPOP are the foundation of Celery's Redis backend.

  e) Session status cache — scan status is polled every 3 seconds by the
     frontend during inference. Caching the status in Redis (TTL: 5s for
     pending/processing, 300s for terminal states) prevents 20+ database
     queries per scan per user during the processing window.

  f) Notification count cache — The notification bell badge unread count is
     fetched on every page load. Redis caches this per user with TTL 60s,
     reducing constant COUNT queries against the notifications table.

  Minimum version: Redis 7 (for Redis Functions support and improved ACL
  per-command granularity for security hardening).

  Redis data persistence strategy:
  — RDB snapshots every 60 seconds (bgsave)
  — AOF logging disabled for performance (Redis data is reconstructible from
    PostgreSQL; it is a cache, not a source of truth)
  — Exception: if Redis is used as the primary Celery result backend, AOF
    should be enabled with fsync=everysec for task result durability

3.3 TEMPORARY STORAGE — Ephemeral Filesystem
──────────────────────────────────────────────
SELECTED: Local filesystem /tmp/voiceguard/ partition.

Justification:
  Audio is NEVER stored permanently (product's core privacy promise, Batch 01).
  No object storage is required for audio in v1. Temp files live for at most
  60 seconds after scan completion. The filesystem temp path approach (with
  scan-scoped UUID subdirectories) was fully designed in Batch 04 (Section 7).
  The database architecture does not persist any path or reference to these files
  except internally in the scans table (file_path column, marked internal-only,
  never exposed to clients).

  Recommended partition: dedicated /tmp partition, 1GB minimum, monitored
  separately from root filesystem. Alert threshold: 70% utilization.

3.4 BLOB STORAGE — Future Object Storage (v2+)
────────────────────────────────────────────────
DEFERRED: Not required for v1.

  Batch 04 Section 8.5 notes: "For very large heatmaps: if base64 > 500KB,
  consider storing as a file in object storage and returning a signed URL."
  In v1, Grad-CAM heatmaps are stored as base64-encoded PNG text in the
  scan_results.frequency_heatmap column. This is acceptable for v1 given:
  — Average heatmap is 150–300KB as base64 text
  — PostgreSQL handles large text columns efficiently with TOAST storage
  — No CDN or signed URL complexity in v1

  When to introduce object storage (trigger conditions):
  — When average scan_results row size exceeds 500KB (benchmark at 100K scans)
  — When batch processing (v2) produces bulk heatmaps that stress DB storage
  — When PDF reports need to be stored and re-served (currently generated on demand)

  Technology selection for object storage (when needed):
  — Self-hosted: MinIO (S3-compatible, deploy on same infrastructure)
  — Cloud: AWS S3, Google Cloud Storage, or Cloudflare R2
  — The scan_results.frequency_heatmap column design must accommodate a
    migration from base64 text to a storage URL without application schema
    changes. Use a discriminator pattern: if the value starts with "data:",
    it is base64; if it starts with "https://", it is a signed URL.

3.5 FUTURE DATA WAREHOUSE
───────────────────────────
PLANNED: For v2 (6 months post-launch).

  Use case: ML model improvement analytics, product usage dashboards,
  user behavior analysis, feedback correlation to scan accuracy.

  Technology selection:
  — ClickHouse: Columnar, extremely fast for aggregations, handles time-series
    event data natively. Best for high-cardinality analytics on scan events.
  — Alternative: BigQuery (fully managed, no ops, pay-per-query) if the team
    is on GCP and prefers managed infrastructure.

  What feeds the warehouse:
  — scan events (scan_id, verdict, confidence, model_version, duration, timestamp)
  — user events (registration, login, scan, delete, export events from audit_logs)
  — feedback events (scan_id, user_verdict, model_verdict)
  — API key usage events

  Sync strategy: CDC (Change Data Capture) via PostgreSQL logical replication
  or a periodic ETL job (simpler for v1 data volumes). Kafka as a streaming
  layer is premature for v1.

3.6 FUTURE ANALYTICS STORAGE
──────────────────────────────
PLANNED: Alongside the data warehouse.

  Metrics time-series: Prometheus + long-term storage via Thanos or VictoriaMetrics
  for operational metrics (inference latency, error rates, queue depth).

  Product analytics: Privacy-first analytics tool (Plausible or PostHog self-hosted)
  for page-level product metrics. These tools do NOT require a separate database
  design — they are off-the-shelf. VoiceGuard only needs to emit events to them.

3.7 FUTURE SEARCH ENGINE
─────────────────────────
PLANNED: For v2 if scan volume exceeds search performance thresholds.

  v1 approach: PostgreSQL ILIKE query on scans.original_filename with a
  B-tree index (truncated). Effective for up to ~1 million rows.

  v2 approach if search degrades: Meilisearch (lightweight, self-hostable,
  excellent for filename and article title fuzzy search) or Typesense.
  Elasticsearch is over-engineered for this use case at v1/v2 scale.

  What to index in search: scan filename, verdict (for filter), model version.
  Help article full text for the Help Center search (currently client-side in v1).

SECTION 4 — DATA DOMAINS
================================================================================

4.1 IDENTITY DOMAIN
─────────────────────
Business responsibility:
  Owns the authoritative record of who a person is. Every other domain
  references this domain's user record as the principal. The identity domain
  is the root of all access control decisions.

Entities: users, user_preferences, deleted_accounts

Relationships:
  — User has one preferences record (1:1, mandatory after first login)
  — User may have one deleted_accounts record (1:1, only during deletion)
  — User is referenced by all other domains via user_id

Ownership: user module
Retention: Permanent while account is active. Purged 30 days after deletion.
  deleted_accounts record retained until purge_completed_at is set.
Security classification: PII — HIGHEST sensitivity. Email address, display
  name, password hash (bcrypt). Encrypted at rest (database-level encryption).

4.2 AUTHENTICATION DOMAIN
───────────────────────────
Business responsibility:
  Owns all mechanisms by which identity is proven: OAuth identities, active
  refresh tokens, pending email verifications, and pending password resets.
  Critically does NOT own the user profile itself — that is the identity domain.

Entities: oauth_accounts, refresh_tokens, email_verifications, password_reset_tokens

Relationships:
  — Each OAuth account belongs to exactly one user (N:1)
  — Each refresh token belongs to exactly one user (N:1)
  — Each email verification token belongs to exactly one user (N:1, one active)
  — Each password reset token belongs to exactly one user (N:1, one active)

Ownership: auth module
Retention:
  — oauth_accounts: permanent (until user deletes account or delinks provider)
  — refresh_tokens: until used/expired/revoked, maximum 30 days
  — email_verifications: until used or expired (24 hours)
  — password_reset_tokens: until used or expired (1 hour)
Security classification: CRITICAL — token hashes are secrets. Access limited to
  auth module only. Never exposed in any API response.

4.3 API ACCESS DOMAIN
───────────────────────
Business responsibility:
  Owns the API keys that grant programmatic access to VoiceGuard (v2 feature,
  table designed now for forward compatibility). Rate limiting tiers per key.

Entities: api_keys

Relationships:
  — Each API key belongs to exactly one user (N:1)
  — Multiple keys per user are permitted (user can create keys per integration)

Ownership: user module
Retention: Until explicitly revoked, or cascaded from user deletion.
Security classification: HIGH — key hashes are secrets. Raw key shown once at
  creation; only the scrypt hash is stored.

4.4 SCAN DOMAIN
─────────────────
Business responsibility:
  Owns the complete scan lifecycle from upload receipt through inference
  completion to user-facing result. This is the core product domain.
  No audio content is persisted — only metadata and computed outputs.

Entities: scans, scan_results

Relationships:
  — Each scan belongs to at most one user OR one guest session (exclusive OR)
  — Each completed scan has exactly one scan_result (1:1)
  — scan_result is dependent on scan (composition, not aggregation)

Ownership: scan module (scans), inference pipeline writes scan_results via
  Celery worker (still logically owned by scan module)
Retention: Permanent while user account is active. Purged with user account.
  Guest scans purged after 24 hours if not migrated.
Security classification: MEDIUM — verdict and confidence scores are not PII,
  but file_name and scan context could be sensitive in forensic use cases.
  Shared scans are accessible publicly by UUID; sharing is opt-out.

4.5 NOTIFICATION DOMAIN
─────────────────────────
Business responsibility:
  Owns the in-app notification center: scan completion alerts, model update
  announcements, system messages. Notifications are created by other domains
  (scan completion → notification module) but owned here.

Entities: notifications

Relationships:
  — Each notification belongs to exactly one user (N:1)
  — Notifications optionally reference a scan (via scan_id FK)

Ownership: notification module
Retention: 90 days from creation (then purged by scheduled job).
  System-wide announcements retained 180 days.
Security classification: LOW — notification content is non-sensitive system data.

4.6 FEEDBACK DOMAIN
─────────────────────
Business responsibility:
  Owns the correction and feedback pipeline. This is strategically critical:
  feedback records link scan results to user-reported ground truth, forming
  the labeled training correction dataset for v2 model improvement.

Entities: feedback

Relationships:
  — Feedback optionally references a user (N:1, nullable for guest feedback)
  — Feedback optionally references a scan (N:1, nullable for general feedback)

Ownership: feedback module
Retention: Permanent — feedback data has permanent research value. Even after
  user deletion, feedback records are retained with user_id set to NULL.
Security classification: MEDIUM — feedback content may contain sensitive
  descriptions of audio recordings. Reviewer notes are internal only.

4.7 HELP DOMAIN
─────────────────
Business responsibility:
  Owns the knowledge base content and per-article helpfulness ratings.
  v1 seeds articles from fixtures; v2 adds a CMS-backed admin editor.

Entities: help_articles, article_feedback

Relationships:
  — Each article_feedback belongs to one article (N:1) and optionally one
    user (N:1, nullable for anonymous ratings)

Ownership: help module
Retention: Articles retained indefinitely (managed by admin). Article feedback
  retained for the lifetime of the associated article.
Security classification: LOW — public content.

4.8 AUDIT DOMAIN
──────────────────
Business responsibility:
  Owns the append-only audit trail of all security-relevant events. This
  domain is the forensic record of the system's behavior. It is write-only
  from all modules and read-only from the admin module.

Entities: audit_logs

Relationships:
  — Audit logs optionally reference a user_id (no FK — intentional; the
    user may be deleted, but the audit log must survive. User_id is stored
    as a raw UUID, not a FK, with the understanding that it may become an
    orphaned reference post-deletion)

Ownership: core module (all other modules write to it via core/audit.py)
Retention: 2 years minimum from event timestamp. Legal baseline.
  Anonymized records (post-purge) retained for the full 2 years.
Security classification: HIGHEST — contains IP hashes, user actions, and
  security event details. Access restricted to admin role only.

4.9 MODEL METADATA DOMAIN
───────────────────────────
Business responsibility:
  Owns the reference data about AI model versions deployed in VoiceGuard.
  Every scan result records which model version produced it, enabling future
  reproducibility auditing and A/B comparison.

Entities: model_versions

Relationships:
  — scan_results reference model_version as a string (not FK, for resilience).
    The model_versions table is a lookup, not a hard dependency.

Ownership: admin module (seeded at deployment)
Retention: Permanent — model version records must survive for reproducibility
  of any historical scan result.
Security classification: LOW — public information about AI models used.

4.10 GUEST SESSION DOMAIN
───────────────────────────
Business responsibility:
  Guest sessions are stateless from a database perspective. The guest_token
  value stored on scan records IS the session identifier. There is no separate
  session table. This minimizes the footprint of anonymous data in the database.

Entities: None (session is a cookie value stored as a column on scans)

Redis keys: None required for guest session (the token is in the cookie;
  the database is the authoritative record of ownership)

Design note: This is a deliberate architectural choice. A separate guest_sessions
  table would add complexity (TTL management, joinable queries) without benefit
  in the v1 model where the only guest-owned data is scans. The guest_token
  on the scans table is sufficient for ownership verification and migration.

ENTITY 1 — USERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  The authoritative record of every registered user. Every other entity that
  belongs to a person references this record. This is the root of the identity
  domain and the root of all access control decisions.

Business Owner: user module

Primary Identifier:
  id — UUID v4, generated at registration time, never changes, never recycled.
  Rationale: UUIDs prevent enumeration attacks (sequential IDs reveal user count).
  UUIDs are globally unique and safe to expose in JWTs and API responses.

Alternate Identifiers:
  email — the user's login identity; unique across all users; normalized to
  lowercase on write. This is the human-facing identifier for login flows.

Required Attributes:
  id              [PK]  UUID v4. Never null, never changes.
  email           [UK][NN]  varchar(254). Normalized lowercase. RFC 5322
                  format validated at application layer. 254 is the maximum
                  email length per RFC 3696.
  password_hash   [NN nullable]  varchar(72). bcrypt output. Nullable because
                  OAuth-only users have no password. If null, the user MUST
                  have at least one OAuth account linked.
  role            [NN]  enum: 'user' | 'admin'. Default 'user'. Admin role
                  is set manually only, never via registration flow.
  email_verified  [NN]  boolean. Default false. Set true on email verification
                  or OAuth login (OAuth providers verify email ownership).
  onboarding_completed  [NN]  boolean. Default false. Set true when user
                  completes or skips the S06 onboarding wizard.
  created_at      [NN]  timestamptz. Default: current time at INSERT. Never
                  mutated after creation.
  updated_at      [NN]  timestamptz. Default: current time at INSERT. Updated
                  on every mutation via application layer (not DB trigger).

Optional Attributes:
  display_name    varchar(64). Nullable. Collected in onboarding (Step 1).
                  Alphanumeric + spaces + basic punctuation. May be null if
                  user skipped onboarding.
  usage_context   enum: 'personal' | 'journalist' | 'hr' | 'cybersecurity' |
                  'creator' | 'developer' | 'unknown'. Nullable. Set during
                  onboarding Step 2. Drives help article prioritization and
                  dashboard defaults.
  deletion_scheduled_at  timestamptz. Nullable. Set when user initiates
                  account deletion. Null during normal account operation.
  deletion_purge_at  timestamptz. Nullable. Set to deletion_scheduled_at + 30
                  days. The purge job queries this field.

Relationships:
  — Has one user_preferences record (1:1, created automatically at or after
    registration; the preferences record is created on first access if missing)
  — Has many refresh_tokens (1:N)
  — Has many oauth_accounts (1:N)
  — Has many scans (1:N)
  — Has many notifications (1:N)
  — Has many api_keys (1:N)
  — Has many feedback records (1:N, soft reference — user_id set to null on purge)
  — Has at most one email_verification token at a time (1:1, with TTL control)
  — Has at most one password_reset token at a time (1:1, with TTL control)
  — Has at most one deleted_accounts record (1:1, only during deletion window)

Constraints:
  — email must match a valid email format pattern (enforced in application layer
    before database write; database adds a CHECK constraint as defense in depth)
  — If password_hash is null, at least one row in oauth_accounts must exist
    for this user_id (enforced at application layer; not expressible as a single
    DB CHECK constraint without a function)
  — role must be one of the ENUM values
  — deletion_purge_at must be exactly 30 days after deletion_scheduled_at
    (enforced at application layer; not a DB constraint)

Validation Rules:
  — email: lowercase, max 254 chars, valid format
  — display_name: 1–64 chars, alphanumeric + spaces + . ' - _ punctuation
  — password_hash: always 60 chars (bcrypt format); application validates before write
  — role: whitelist validation

Lifecycle:
  registered → [email_verified=false] → [email_verified=true] → active
  → [deletion_scheduled_at set] → [deletion_purge_at reached] → PURGED

Deletion Policy:
  Soft delete: deletion_scheduled_at set; user can log in and cancel.
  Hard delete: purge_user job after 30 days. Full cascade.

Retention Policy:
  Active user: indefinite.
  Post-deletion: 30 days recovery window, then permanent deletion.

Audit Requirements:
  — Registration event logged to audit_logs
  — Login success and failure logged
  — Password change logged
  — Email change logged (with old email hash)
  — Role change logged (admin action)
  — Deletion initiation and cancellation logged
  — Account purge logged

Future Extensibility:
  — avatar_url: varchar(512) — for v2 avatar upload feature
  — public_profile: boolean — for v2 opt-in public scan stats
  — team_id: UUID FK — for v2 team workspaces
  — locale: varchar(10) — for v2 localization
  — last_login_at: timestamptz — for security monitoring and inactivity detection

ENTITY 3 — OAUTH_ACCOUNTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Links a VoiceGuard user account to one or more OAuth provider identities
  (Google, GitHub). Enables OAuth login without requiring a separate password.
  A user may link multiple providers; each is a separate row.

Business Owner: auth module

Primary Identifier:
  id — UUID v4

Alternate Identifiers:
  (provider, provider_user_id) — composite unique constraint. This is how
  VoiceGuard maps an OAuth callback to an existing account. If this pair
  already exists, it is an existing user logging in; if not, it is a new
  account or a new link.

Required Attributes:
  id                  [PK] UUID v4
  user_id             [FK][IDX][NN] UUID → users.id. ON DELETE CASCADE.
  provider            [NN] varchar(32). Values: 'google', 'github'. Expandable
                      for future providers without schema change.
  provider_user_id    [NN] varchar(255). The user's unique ID in the provider's
                      system. Stable; does not change even if provider email changes.
  created_at          [NN] timestamptz

Optional Attributes:
  provider_email      varchar(254). The email address on the provider account at
                      the time of linking. Informational only; may differ from
                      the VoiceGuard account email. Not used for lookup.

Relationships:
  — Belongs to exactly one user (N:1)
  — A user can have multiple OAuth accounts (one per provider, potentially
    multiple if we allow multiple GitHub accounts in future)

Constraints:
  — UNIQUE (provider, provider_user_id) — prevents two VoiceGuard accounts
    from claiming the same OAuth identity
  — provider must be in the allowlist (application-layer check; DB-level via
    CHECK constraint on the varchar column)

Lifecycle:
  Created at first OAuth login. Updated (provider_email) if provider email
  changes on re-authentication (optional refresh). Never deleted except
  on user account purge cascade.

Deletion Policy: CASCADE on user purge.
Retention: Duration of the user account.

Future Extensibility:
  — access_token_encrypted: text — if future features require provider API calls
  — token_expires_at: timestamptz — if storing provider tokens
  — scope: text — OAuth scope granted at link time

ENTITY 4 — REFRESH_TOKENS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Stores hashed refresh tokens for JWT session management. Each active browser
  or client session has exactly one active (non-revoked, non-expired) refresh
  token row. Enables token rotation with reuse detection (a fundamental security
  property in VoiceGuard's auth design per Batch 04 Section 10).

Business Owner: auth module

Primary Identifier:
  id — UUID v4

Alternate Identifiers:
  token_hash — varchar(64), UNIQUE. SHA-256 hex of the opaque refresh token
  sent to the client. Used as the lookup key on every token rotation call.

Required Attributes:
  id              [PK] UUID v4
  user_id         [FK][IDX][NN] UUID → users.id. ON DELETE CASCADE.
  token_hash      [UK][NN] varchar(64). SHA-256(raw_token). Never store raw.
  expires_at      [NN] timestamptz. Computed: created_at + 30 days.
  revoked         [NN] boolean. Default false.
  created_at      [NN] timestamptz

Optional Attributes:
  revoked_at      timestamptz. Set when revoked=true is set.
  last_used_at    timestamptz. Updated on each successful rotation (fire-and-
                  forget update; acceptable lag for this field).
  user_agent      varchar(512). Browser/client fingerprint at session creation.
                  Useful for session management UI (v2: "active sessions" page).
  ip_hash         varchar(64). SHA-256 of IP at session creation. For security
                  monitoring without storing raw IP (GDPR consideration).

Relationships:
  — Belongs to exactly one user (N:1)
  — Multiple tokens per user permitted (multiple concurrent sessions)

Constraints:
  — token_hash must be unique across all rows (including revoked ones)
  — expires_at must be > created_at
  — revoked_at must be null if revoked=false, and not null if revoked=true
    (application-layer constraint; DB CHECK is possible but verbose)

Reuse Detection Logic (enforced in application, not DB):
  If a token arrives that has revoked=true in the database, it indicates
  token theft. The application must immediately revoke ALL tokens for that
  user_id (UPDATE refresh_tokens SET revoked=true WHERE user_id=X AND
  revoked=false) and force re-login.

Lifecycle:
  Created at login / OAuth callback.
  Updated (revoked=true) on logout, password change, account deletion.
  Deleted by cleanup_expired_tokens Celery Beat job (every 6 hours).

Deletion Policy:
  Hard delete by cleanup job after expiry + grace period. CASCADE on user purge.

Retention: Until expires_at + 7 days grace (for audit correlation), then deleted.

Future Extensibility:
  — device_name: varchar(128) — for v2 "active sessions" list with friendly names
  — family_id: UUID — for tracking token families in rotation chains

ENTITY 5 — EMAIL_VERIFICATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Stores pending email verification tokens issued at registration or email change.
  The token_hash is sent to the user's email as a link or 6-digit code (the
  code is derived from the first 6 characters of the hex token for the OTP input
  UI, or the full token is embedded in a magic link URL).

Business Owner: auth module

Primary Identifier:
  id — UUID v4

Alternate Identifiers:
  token_hash — unique, used for verification lookup.

Required Attributes:
  id              [PK] UUID v4
  user_id         [FK][IDX][NN] UUID → users.id. ON DELETE CASCADE.
  token_hash      [UK][NN] varchar(64). SHA-256 of the raw verification token.
  expires_at      [NN] timestamptz. created_at + 24 hours.
  used            [NN] boolean. Default false.
  created_at      [NN] timestamptz

Optional Attributes:
  used_at         timestamptz. Set when used=true.
  email_address   varchar(254). The email address being verified (important for
                  email change flows where users.email might already be updated
                  to the new value or the old value depending on the change flow).

Constraints:
  — At most one non-used, non-expired token per user_id (enforced at application

  — token_hash globally unique

Lifecycle:
  Created at registration or email change initiation.
  Marked used=true on successful verification.
  Deleted by cleanup_expired_tokens job (every 6 hours) for expired+used tokens.

Deletion Policy: Hard delete by cleanup job. CASCADE on user purge.
Retention: Maximum 24 hours active, cleaned up within 6 hours of expiry.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ENTITY 7 — API_KEYS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Stores hashed API keys for programmatic access to VoiceGuard (v2 developer
  feature). The table is designed now to enable v2 without a schema migration.
  Raw key is shown to the user once at creation; only the scrypt hash is stored.

Business Owner: user module

Primary Identifier: id — UUID v4

Alternate Identifiers:
  key_prefix — the first 12 characters of the key (e.g., "vg_live_ab12")
  stored in cleartext for identification in listings. Unique by convention
  (collision probability negligible given 8 random hex chars in prefix).

Required Attributes:
  id              [PK] UUID v4
  user_id         [FK][IDX][NN] UUID → users.id. ON DELETE CASCADE.
  name            [NN] varchar(64). User-provided descriptive name for the key.
  key_prefix      [NN] varchar(16). First 12 chars for display in key lists.
  key_hash        [NN] text. scrypt(full_key, salt, N=16384, r=8, p=1).
                  Stored as a string that includes the scrypt parameters for
                  future parameter upgrades (use a standard hash encoding like
                  modular crypt format or a custom JSON prefix).
  rate_limit_tier [NN] enum: 'free' | 'pro' | 'enterprise'. Default 'free'.
  revoked         [NN] boolean. Default false.
  created_at      [NN] timestamptz

Optional Attributes:
  revoked_at      timestamptz
  last_used_at    timestamptz. Updated on each successful API call. Fire-and-
                  forget: acceptable lag; use Redis counter for real-time rate
                  limiting rather than querying this field.
  description     varchar(256). Optional user-provided notes about this key.
  expires_at      timestamptz. Nullable. For future time-limited keys.

Constraints:
  — key_hash must be unique (two different API keys must never share a hash)
  — A user cannot have more than 10 active (non-revoked) API keys at once
    (enforced at application layer to prevent abuse)

Lifecycle:
  Created via POST /api/v1/user/api-keys. Raw key returned once.
  Revoked via DELETE /api/v1/user/api-keys/{key_id}.
  CASCADE-deleted on user purge.

Retention: Until revoked + user purge. Revoked keys retained for 90 days for
  audit correlation (rate limit abuse investigation), then hard deleted.

Future Extensibility:
  — allowed_ips: text[] — IP allowlist per key
  — webhook_url: varchar(512) — callback for async results (v2)
  — scopes: text[] — granular permission scopes per key (v3)

ENTITY 8 — SCANS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  The central entity of VoiceGuard. Records every audio analysis request from
  submission through completion or failure. No audio content is stored here —
  only metadata sufficient to describe the analyzed file, track the analysis
  lifecycle, and serve the result to the correct owner.

Business Owner: scan module

Primary Identifier:
  id — UUID v4, the scan_id used throughout the backend and in API responses.
  This same UUID is used in the shareable link URL (/r/{id}).

Alternate Identifiers:
  (guest_token, created_at) — for guest scan ownership queries.
  (user_id, created_at) — for user history queries.

Required Attributes:
  id                  [PK] UUID v4. Generated before file write.
  status              [NN] enum: 'pending' | 'processing' | 'complete' | 'failed'.
                      Default 'pending'. Transitions are one-directional:
                      pending → processing → complete OR failed. Never reverses.
  original_filename   [NN] varchar(255). The filename as provided by the user,
                      sanitized (null bytes removed, length truncated). Stored
                      for display in history and PDF reports. NOT used as any
                      path or system identifier.
  file_size_bytes     [NN] bigint. Actual file size after write. Used for
                      monitoring, abuse detection, and PDF report display.
  file_extension      [NN] varchar(10). The sanitized extension (wav, mp3, etc.).
                      Stored separately from original_filename for filtering.
  claimed_mime_type   [NN] varchar(64). The MIME type claimed by the client.
                      Stored for audit; actual type is determined by magic bytes.
  is_shared           [NN] boolean. Default true. Controls whether the public
                      shared link (S20) is active. User can revoke sharing.
  created_at          [NN] timestamptz. Scan submission time.

Optional Attributes:
  user_id             [FK][IDX] UUID → users.id. NULL for guest scans.
                      ON DELETE CASCADE (user purge deletes all their scans).
  guest_token         [IDX] varchar(64). NULL for authenticated scans.
                      Hex-encoded guest session token from cookie.
                      CONSTRAINT: exactly one of user_id or guest_token must
                      be non-null (CHECK constraint: user_id IS NOT NULL OR
                      guest_token IS NOT NULL, enforced at application layer).
  completed_at        timestamptz. Set when status transitions to complete or failed.
  celery_task_id      varchar(64). Celery task UUID for the inference job.
                      Stored for debugging and monitoring only. Not exposed to
                      clients. May be null if task dispatch failed before recording.
  deleted_at          timestamptz. For user-initiated scan deletion (soft delete
                      of individual scans). NULL means not deleted.
  view_count          integer. Default 0. Incremented on each result view.
                      Fire-and-forget increment; acceptable lag.

CRITICAL DESIGN DECISION — File Path Handling:
  The temp file path (/tmp/voiceguard/{scan_id}/audio.wav) is NOT stored in the
  scans table in any user-accessible column. It is an internal implementation
  detail used only by the inference worker to locate the file. If stored, it
  must be in a column explicitly marked internal and never serialized to API
  responses. In v1, the path is derivable from scan_id (the directory is always
  /tmp/voiceguard/{scan_id}/), so storing it is redundant. The inference worker
  reconstructs the path from scan_id.

Constraints:
  — status must be one of the ENUM values
  — file_size_bytes must be > 0 and ≤ 10,485,760 (10MB in bytes)
  — Either user_id OR guest_token must be set, not both, not neither
  — original_filename must not be empty after sanitization
  — deleted_at is only set for COMPLETE or FAILED scans (cannot delete PENDING
    or PROCESSING scans; enforced at application layer)

Validation Rules:
  — File extension: only wav, mp3, flac, ogg, m4a allowed
  — claimed_mime_type: validated against MIME type allowlist
  — status transitions: monotonic; never moves backward

Lifecycle: See Section 2.12 (Scan Lifecycle).

Deletion Policy:
  User-initiated: deleted_at is set (soft delete); records with deleted_at set
  are excluded from all user-facing queries. A background job hard-deletes
  records with deleted_at older than 30 days (giving an implicit undo window
  for the "Undo" toast action in the UI, per Batch 01 Section 16).

  Wait — reconsider: Batch 01 Section 16 says "Undo" link in toast (5-second
  window before actual deletion executes on the server — optimistic UI). This
  is a 5-second client-side delay, not a server-side soft delete. The server
  can immediately hard-delete, but the frontend delays calling the API for 5
  seconds. Therefore: scan deletion is HARD DELETE immediately at API call.
  The "Undo" is entirely client-side (the API call is queued for 5 seconds
  before firing). No soft delete on individual scans is needed.

  Revised: deleted_at column REMOVED from scans. Scan deletion is immediate
  hard delete. CASCADE to scan_results. This simplifies all history queries.

  Guest scan expiry: Hard delete by Celery Beat job (hourly).
  User account purge: CASCADE from user delete.

Retention:
  Active user scans: indefinitely until user-deleted or account purged.
  Guest scans: 24 hours maximum.

Audit Requirements:
  — Scan submission: logged (user_id or guest_token hash, file_size, IP hash)
  — Scan deletion (single): logged
  — Bulk scan deletion: logged with count

Future Extensibility:
  — parent_scan_id: UUID FK (self-referential) — for batch processing (v2)
  — batch_id: UUID FK → batches.id — for batch grouping (v2)
  — tags: text[] — for user annotations (v1.2)
  — notes: text — for scan annotations (v1.2)

ENTITY 9 — SCAN_RESULTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Stores the computed output of the LCNN inference pipeline for each completed
  scan. This is the data that drives the result page (S10), the scan detail
  page (S12), shared result links (S20), and PDF reports. One scan_result per
  completed scan, written once by the inference worker, never mutated.

Business Owner: scan module (written by inference Celery worker)

Primary Identifier:
  id — UUID v4

Alternate Identifiers:
  scan_id — UUID FK to scans.id, UNIQUE. Since this is 1:1 with completed
  scans, scan_id is the natural lookup key for all result queries.

Required Attributes:
  id                  [PK] UUID v4
  scan_id             [FK][UK][NN] UUID → scans.id. ON DELETE CASCADE.
  verdict             [NN] enum: 'human' | 'ai_generated' | 'uncertain'.
  confidence          [NN] numeric(5,4). Range 0.0000–1.0000.
                      NUMERIC is used (not FLOAT) to ensure exact decimal
                      representation for reproducibility and audit purposes.
                      numeric(5,4): up to 1.0000 with 4 decimal places.
  human_score         [NN] numeric(5,4). The softmax probability for the human
                      class. Range 0.0000–1.0000.
  ai_score            [NN] numeric(5,4). The softmax probability for the
                      AI-generated class. Range 0.0000–1.0000.
  file_hash_sha256    [NN] varchar(64). SHA-256 hex of the original audio file.
                      Computed client-side (Web Crypto API per Batch 03) and
                      optionally verified server-side. Critical for forensic
                      chain-of-custody (Batch 01 Recommendation 7).
  duration_seconds    [NN] numeric(8,3). Actual audio duration. Supports up to
                      99,999.999 seconds (27+ hours), well beyond the 300s cap.
  model_version       [NN] varchar(64). Version string of the model that
                      produced this result (e.g., "lcnn-v1.0.0-asvspoof2019la").
                      Stored as a string reference to model_versions; not a FK
                      to allow the model_versions table to be truncated/re-seeded
                      without invalidating historical results.
  inference_time_ms   [NN] integer. Wall-clock time for the inference pipeline
                      in milliseconds. Used for performance monitoring.
  segment_count       [NN] integer. Number of audio segments processed. Relevant
                      for long files processed in overlapping chunks.
  created_at          [NN] timestamptz. Time the result was written. Immutable.

Optional Attributes:
  frequency_heatmap   text. Base64-encoded PNG of the Grad-CAM overlay.
                      Large field stored in PostgreSQL TOAST. Nullable because
                      Grad-CAM generation can fail without failing the scan
                      (Batch 04 Section 8.5: "If Grad-CAM fails: Log warning,
                      store null in frequency_heatmap, continue.").
                      Storage format discriminator: if starts with "data:image",
                      it is base64; if starts with "https://", it is a storage
                      URL (future object storage migration).
  sample_rate_hz      integer. Detected sample rate of the audio. Informational;
                      displayed in the result technical details section.

Constraints:
  — confidence must be between 0.0000 and 1.0000 (DB CHECK constraint)
  — human_score must be between 0.0000 and 1.0000
  — ai_score must be between 0.0000 and 1.0000
  — human_score + ai_score should approximately equal 1.0 (within floating
    point precision; enforced at application layer, not DB — softmax output)
  — verdict must be consistent with confidence and scores (application layer):
    confidence ≥ 0.85 AND human_score > ai_score → verdict MUST be 'human'
    confidence ≥ 0.85 AND ai_score > human_score → verdict MUST be 'ai_generated'
    confidence < 0.65 → verdict MUST be 'uncertain'
  — file_hash_sha256 must be exactly 64 hex characters (DB CHECK)
  — inference_time_ms must be > 0
  — segment_count must be ≥ 1

Validation Rules: All numeric ranges strictly validated before write.
  Verdict-score consistency validated in inference service before DB insert.

Lifecycle:
  Written once by inference worker on completion. Never updated. Immutable.
  Deleted on scan deletion (CASCADE).

Deletion Policy: CASCADE from scan deletion.
Retention: As long as parent scan exists.

Audit Requirements:
  — No specific audit log entry per result write (the scan submission event
    covers the lifecycle; result creation is an internal system event)
  — inference_time_ms is a performance metric emitted to monitoring

Future Extensibility:
  — segment_scores: JSONB — per-segment confidence scores for long audio analysis
  — spectrogram_url: varchar(512) — URL to stored spectrogram image (v2)
  — additional_model_scores: JSONB — for multi-model comparison (v2 AASIST)
  — attack_type_probabilities: JSONB — per-attack-type classification (v3)

  request_id      UUID. The request that triggered this event. Enables cross-
                  referencing with application logs.
  details         JSONB. Event-specific structured data. Examples:
    LOGIN_FAILURE: {"reason": "wrong_password", "email_hash": "..."}
    SCAN_SUBMITTED: {"file_size_bytes": 4194304, "file_extension": "wav"}
    ADMIN_ACTION: {"action": "list_users", "filters": {"role": "admin"}}
    RATE_LIMIT_EXCEEDED: {"limit": 10, "window": "1h", "endpoint": "/api/v1/scans"}

Constraints:
  — APPEND ONLY: No UPDATE, no DELETE permitted by application roles (see
    Security Architecture Section 16 for role definitions).
  — event_type must be one of the canonical values (enforced at application layer;
    DB adds a partial allowlist CHECK or uses a DOMAIN type)
  — timestamp cannot be in the future (DB CHECK: timestamp <= now() + interval '5 seconds'
    to allow for clock skew)

Lifecycle:
  Written at event time. Never modified (exception: anonymization on purge).
  Purged by compliance retention job after 2 years from timestamp.

Deletion Policy: Hard delete at 2-year retention boundary by compliance job.
  Anonymization step on account purge is the only mutation.

Retention: 2 years minimum from event timestamp.

Performance Note:
  Audit logs are write-heavy and read-rarely (admin queries only). The table
  benefits from:
  — Partitioning by timestamp range (monthly) to enable fast old-partition drops
  — Separate tablespace or physical disk from operational tables
  — Asynchronous write path: the application writes audit logs via a buffered
    async INSERT, not in the same transaction as the business operation.
    This prevents audit log write failures from blocking business operations.

ENTITY 15 — MODEL_VERSIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Reference table for AI model versions deployed in VoiceGuard. Every
  scan_result records the model_version string that produced it. This table
  provides metadata about each version for display in the admin panel and
  in the result Limitations card. Enables future reproducibility auditing
  and A/B model comparison (v2).

Business Owner: admin module (seeded at deployment)

Primary Identifier:
  version_string — varchar(64). The canonical identifier used in scan_results.
  This is the natural primary key (not a surrogate UUID) because the version
  string IS the unique identity and is referenced by scan_results as a string.

Required Attributes:
  version_string    [PK] varchar(64). e.g., "lcnn-v1.0.0-asvspoof2019la".
                    Immutable once created.
  display_name      [NN] varchar(128). Human-readable name for UI display.
  is_active         [NN] boolean. Default false. Only one model should be
                    active at a time (enforced at application layer).
  created_at        [NN] timestamptz

Optional Attributes:
  description       text. Technical description of the model architecture.
  eer_percentage    numeric(5,3). Equal Error Rate on the training benchmark.
                    e.g., 7.070 for 7.07% EER.
  training_dataset  varchar(128). e.g., "ASVspoof 2019 LA".
  paper_url         varchar(512). Link to associated research paper.
  parameter_count   integer. Model parameter count (699938 for LCNN v1).
  deployed_at       timestamptz. When this version was made active in production.
  deprecated_at     timestamptz. When this version was superseded.
  checksum_sha256   varchar(64). SHA-256 of the model weights file. Used by
                    the inference worker at startup to verify model integrity.

Constraints:
  — version_string: URL-safe, no spaces, lowercase with hyphens
  — eer_percentage: RANGE 0.000–100.000 if present
  — Only one row should have is_active=true at a given time

Lifecycle:
  Seeded at deployment via migration fixture. New rows added when new model
  versions are deployed. Never deleted (historical scan results reference them).

Deletion Policy: Never deleted. Set deprecated_at if retired.
Retention: Permanent.

ENTITY 16 — DELETED_ACCOUNTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Purpose:
  Tracks accounts scheduled for deletion during the 30-day recovery window.
  After purge is complete, the record is marked completed. Also used to prevent
  immediate re-registration with a recently-deleted email (the email_hash enables
  lookups without storing the plaintext deleted email, since the users row is gone).

Business Owner: user module

Primary Identifier: id — UUID v4

Required Attributes:
  id                      [PK] UUID v4
  user_id                 [NN] UUID. The original user ID. Not an FK (the user
                          row may already be deleted). Stored for audit trail.
  email_hash              [NN] varchar(64). SHA-256(email + email_salt).
                          Used to check if a re-registration email belonged to
                          a recently-deleted account.
  deletion_initiated_at   [NN] timestamptz. When the user requested deletion.
  deletion_scheduled_for  [NN] timestamptz. deletion_initiated_at + 30 days.
  initiated_by            [NN] enum: 'user' | 'admin'. Who initiated the deletion.
  created_at              [NN] timestamptz

Optional Attributes:
  deletion_completed_at   timestamptz. Set when purge_user job completes
                          successfully. Null until purge runs.
  cancellation_at         timestamptz. Set if user cancelled deletion during
                          recovery window.

Constraints:
  — deletion_scheduled_for must be exactly 30 days after deletion_initiated_at
  — email_hash must be unique in this table (one deletion record per email)
  — If cancellation_at is set, deletion_completed_at must be null

Lifecycle:
  Row created when users.deletion_scheduled_at is set.
  deletion_completed_at set when purge job runs.
  Or cancellation_at set when user cancels.
  Row retained for 30 days after completion/cancellation, then hard deleted.

Retention: 60 days from deletion_initiated_at, then hard deleted.

SECTION 6 — RELATIONSHIP ARCHITECTURE
================================================================================

6.1 COMPLETE CONCEPTUAL ER MODEL
──────────────────────────────────

  users ──────────────── user_preferences        (1:1, mandatory after onboarding)
  users ──────────────── oauth_accounts           (1:N, one per provider)
  users ──────────────── refresh_tokens           (1:N, one per active session)
  users ──────────────── email_verifications      (1:N, at most one active at a time)
  users ──────────────── password_reset_tokens    (1:N, at most one active at a time)
  users ──────────────── api_keys                 (1:N, up to 10 active)
  users ──────────────── scans                    (1:N, all authenticated scans)
  users ──────────────── notifications            (1:N, all in-app notifications)
  users ──────────────── feedback                 (1:N, soft ref — SET NULL on purge)
  users ──────────────── article_feedback         (1:N, soft ref — SET NULL on purge)
  users ──────────────── deleted_accounts         (1:1, only during deletion window)

  scans ──────────────── scan_results             (1:1, only for COMPLETE scans)
  scans ──────────────── notifications            (1:N, via scan_id, SET NULL)
  scans ──────────────── feedback                 (1:N, via scan_id, SET NULL)

  help_articles ──────── article_feedback         (1:N, CASCADE on article delete)

  model_versions ─────── scan_results             (1:N, string reference, no FK)

  audit_logs ─────────── (no FK relationships — intentionally isolated)

  Guest sessions:
  guest_token (cookie) ──── scans                 (1:N, as column value, no table)

6.2 ONE-TO-ONE RELATIONSHIPS
──────────────────────────────

  users → user_preferences
    Cardinality: Exactly one preferences record per user (lazy-created).
    Enforcement: UNIQUE constraint on user_preferences.user_id.
    Cascade: ON DELETE CASCADE (preferences are meaningless without a user).
    Access pattern: Always loaded alongside user profile for settings pages.
    Design rationale: Separated from users to keep auth queries lean.

  scans → scan_results
    Cardinality: At most one scan_result per scan; exactly one for COMPLETE scans.
    Enforcement: UNIQUE constraint on scan_results.scan_id.
    Cascade: ON DELETE CASCADE.
    Access pattern: Almost always loaded together (result page always needs both).
    Design rationale: Separated to allow scans table to be queried without
    pulling large frequency_heatmap text blobs. History list queries only touch
    scans; result detail queries join to scan_results.

  users → deleted_accounts
    Cardinality: At most one deleted_accounts record per user at any time.
    Enforcement: UNIQUE (user_id) on deleted_accounts.
    Cascade: None (deleted_accounts may outlive the user row).

6.3 ONE-TO-MANY RELATIONSHIPS
───────────────────────────────

  users → scans (1:N)
    A user can have unlimited scans (subject to rate limits during collection).
    No practical upper bound; the history page paginates to manage UI load.
    Deletion: CASCADE when user is purged. SET NULL is not appropriate because
    scans without an owner are inaccessible and orphan data.

  users → refresh_tokens (1:N)
    A user can have multiple active sessions concurrently (different devices).
    Each session has exactly one active refresh token.
    Multiplicity: typically 1–5 active tokens per user (mobile + desktop + API).
    Deletion: CASCADE on user purge. Individual tokens deleted on logout or expiry.

  users → notifications (1:N)
    No hard limit per user. Volume: approximately 2–5 notifications per scan
    (completion, low-confidence warning if applicable). High-frequency users
    may accumulate hundreds of notifications before the 90-day retention job clears them.
    Deletion: CASCADE on user purge.

  users → api_keys (1:N)
    Soft limit: 10 active keys per user (application-layer enforcement).
    Deletion: CASCADE on user purge.

  users → oauth_accounts (1:N)
    At most one per provider in v1 (Google, GitHub = maximum 2 rows per user).
    Expandable: adding new providers requires no schema change (new provider
    string value in the provider column).
    Deletion: CASCADE on user purge.

  scans → notifications (1:N via scan_id)
    A scan typically generates 1 notification (completion). May generate more
    in v2 (retry notifications, batch completion).
    Relationship: weak (SET NULL on scan delete; notification still exists
    as a system message but loses its scan reference).

  scans → feedback (1:N via scan_id)
    A single scan may receive multiple feedback submissions (e.g., if the scan
    result page is shared publicly and multiple people report it as incorrect).
    Relationship: weak (SET NULL on scan delete).

  help_articles → article_feedback (1:N)
    Each article can accumulate unlimited helpfulness ratings over time.
    Relationship: strong (CASCADE on article delete).

6.4 MANY-TO-MANY RELATIONSHIPS
────────────────────────────────

  There are no explicit many-to-many relationships in VoiceGuard v1.

  Implicit M:N: A model version is used by many scans; a scan uses exactly
  one model version. This is realized as a string reference on scan_results
  (not a FK join table) because model_versions is a small reference table.

  Future M:N relationships (v2):
  — users ↔ teams: through a team_members junction table
  — scans ↔ tags: through a scan_tags junction table
  — api_keys ↔ scopes: through an api_key_scopes junction table

6.5 LOOKUP AND REFERENCE ENTITIES
────────────────────────────────────

  LOOKUP ENTITIES (small, rarely-changing, used for filtering and display):
  — model_versions: looked up by scan_results.model_version string.
    Not enforced as FK to allow historical scan data to survive model table
    cleanup. Queried by admin panel and result limitations card.

  REFERENCE ENTITIES (effectively static, seeded at deployment):
  — help_articles: content is essentially static in v1 (seeded, rarely updated).
    Not a "lookup" in the traditional sense but behaves like one.

6.6 AGGREGATION RULES
───────────────────────

  Dashboard statistics are aggregated from the scans table:
  — Total scan count: COUNT(*) WHERE user_id = X
  — Human scan count: COUNT(*) WHERE user_id = X AND ... JOIN scan_results
    WHERE verdict = 'human'
  — AI scan count: similar to human count
  — These aggregations are expensive at large history sizes and are cached
    in Redis with a 5-minute TTL (key: stats:{user_id}, value: JSON).

  Notification unread count:
  — COUNT(*) WHERE user_id = X AND read = false
  — Cached in Redis with 60-second TTL (key: notif_count:{user_id}).
  — Invalidated (DEL key) when: a new notification is created for this user,
    or when mark-all-read is called.

  Article helpfulness:
  — helpful_yes_count and helpful_no_count on help_articles are incremented
    atomically (application-layer: increment with UPDATE ... SET count = count + 1).
  — Reconciliation job runs weekly to verify counts match actual rows in
    article_feedback (detects increment/decrement bugs).

6.7 COMPOSITION RULES
───────────────────────

  scan_results is a COMPOSITION of scans (not aggregation).
  — scan_results cannot exist independently; it is always created FROM a scan
    and is meaningless without its parent scan.
  — Lifecycle is entirely governed by the parent scan.
  — Deleting a scan always deletes its scan_result.

  user_preferences is a COMPOSITION of users.
  — Preferences have no meaning without a user.
  — Created as part of user setup.
  — Always deleted with the user.

6.8 INHERITANCE
────────────────

  No table inheritance is used in VoiceGuard v1.

  Discriminator pattern (used in two places):
  — scans.user_id vs scans.guest_token: a scan belongs to either an authenticated
    user or a guest session. These are mutually exclusive. This is a discriminated
    union, not inheritance. The CHECK constraint (at application layer) ensures
    exactly one is set.

  — scan_results.frequency_heatmap: the storage format is discriminated by the
    value prefix ('data:image' → base64; 'https://' → object storage URL). This
    is a discriminated union within a single text column, enabling zero-migration
    transition from v1 (base64) to v2 (object storage).

SECTION 7 — STORAGE ARCHITECTURE
================================================================================

7.1 POSTGRESQL STORAGE
────────────────────────

  Database name: voiceguard (single database for v1)
  Schema: public (single schema for v1; consider separating into auth, scan,
    notification schemas in v2 when module count grows)

  Table storage estimates (at 100,000 users, 500,000 scans):

  Table                   Avg Row Size  Est. Rows    Est. Size
  ──────────────────────────────────────────────────────────────
  users                   ~500 bytes    100,000      ~50 MB
  user_preferences        ~200 bytes    100,000      ~20 MB
  oauth_accounts          ~200 bytes    120,000      ~24 MB
  refresh_tokens          ~250 bytes    500,000*     ~125 MB
  email_verifications     ~150 bytes    ~10,000**    ~2 MB
  password_reset_tokens   ~150 bytes    ~5,000**     ~1 MB
  api_keys                ~300 bytes    ~50,000      ~15 MB
  scans                   ~600 bytes    500,000      ~300 MB
  scan_results            ~200 KB       500,000      ~100 GB***
  notifications           ~300 bytes    2,000,000    ~600 MB
  feedback                ~500 bytes    ~10,000      ~5 MB
  help_articles           ~5 KB         ~50          ~250 KB
  article_feedback        ~100 bytes    ~50,000      ~5 MB
  audit_logs              ~500 bytes    5,000,000    ~2.5 GB
  model_versions          ~500 bytes    ~5           negligible
  deleted_accounts        ~200 bytes    ~5,000       ~1 MB

  * refresh_tokens accumulates; cleanup job runs every 6 hours
  ** at any given time; cleanup runs frequently
  *** CRITICAL: scan_results.frequency_heatmap is the dominant storage consumer.
    A 200KB base64 heatmap × 500,000 scans = 100 GB. This is the primary
    driver for migrating heatmaps to object storage. Monitor this table size
    closely. Alert when total size exceeds 50 GB (trigger object storage migration).

  PostgreSQL TOAST storage:
  — frequency_heatmap will exceed PostgreSQL's inline storage threshold (8KB
    per row). PostgreSQL automatically stores large text values in TOAST tables
    (out-of-line storage). TOAST is transparent but has performance implications:
    retrieving TOAST values requires an additional I/O operation.
  — THEREFORE: all history list queries MUST exclude scan_results.frequency_heatmap
    from the SELECT column list. Only load the heatmap when rendering the result
    page or detail page. This is the most important query optimization rule in
    the entire schema.

  Tablespace strategy:
  — audit_logs: consider a dedicated tablespace on a separate disk path to isolate
    high-write audit traffic from operational tables. Not required for v1 but
    plan the tablespace configuration before launch.
  — scan_results: consider a dedicated tablespace for the large TOAST data,
    potentially on cheaper/larger storage than the operational SSD.

7.2 REDIS STORAGE
──────────────────

  Memory estimate at steady state:

  Key Pattern                             Typical Count  Per-Key Size  Total
  ───────────────────────────────────────────────────────────────────────────
  rl:scan:guest:{ip_hash}:{bucket}        ~1,000 active  ~50 bytes     ~50 KB
  rl:scan:user:{user_id}:{bucket}         ~5,000 active  ~50 bytes     ~250 KB
  rl:auth:{endpoint}:{ip_hash}:{bucket}   ~2,000 active  ~50 bytes     ~100 KB
  scan_status:{scan_id}                   ~100 active    ~100 bytes    ~10 KB
  oauth_state:{state}                     ~50 active     ~200 bytes    ~10 KB
  job_result:{scan_id}                    ~100 active    ~200 bytes    ~20 KB
  notif_count:{user_id}                   ~10,000 cached ~50 bytes     ~500 KB
  stats:{user_id}                         ~5,000 cached  ~200 bytes    ~1 MB
  global:scan_count                       1              ~20 bytes     negligible
  Celery broker queues                    ~10–20 tasks   ~500 bytes    ~10 KB

  Total estimated Redis memory: ~3–5 MB at 10,000 active users
  Redis maxmemory recommendation: 256 MB (comfortable headroom for spikes)
  Eviction policy: allkeys-lru (allows Redis to evict least-recently-used
    cache entries under memory pressure; appropriate for a cache-heavy workload)

  Key naming convention:
  — All keys use colon-separated namespaces: {domain}:{entity}:{identifier}:{bucket}
  — No spaces. Lowercase. UUIDs without hyphens for compactness in high-volume keys.
  — TTLs are always set on write; no persistent keys except global:scan_count

7.3 TEMPORARY FILE STORAGE
────────────────────────────

  Location: /tmp/voiceguard/{scan_id}/
  File naming: audio.{extension} (sanitized; original filename discarded)

  Active file count at peak:
  — 10 concurrent uploads × 1 file each = 10 active uploads
  — 2 inference workers × 1 file being processed = 2 processing files
  — Total active files: ≤ 12 at peak

  Peak storage usage:
  — Each audio file: maximum 10 MB
  — Each Grad-CAM interim file (if written to disk): maximum 2 MB
  — Per-scan total: ≤ 12 MB
  — 12 concurrent scans × 12 MB = 144 MB peak
  — Recommended /tmp partition: 1 GB (7× safety margin)

  The /tmp partition must be:
  — On a fast local disk (SSD preferred; inference reads the audio file)
  — Separate from root filesystem (to prevent temp files filling / and crashing)
  — Monitored: alert at 70% utilization (~700 MB)
  — tmpfs is acceptable if RAM permits (faster but loses data on process crash;
    acceptable because files are ephemeral and failure is handled by retry)

7.4 GENERATED PDF STORAGE
───────────────────────────

  PDFs are NOT stored. They are generated on demand by the Celery general worker
  and streamed directly to the API response (Batch 04 Section 9 report task).

  PDF generation input: data loaded from scan_results and users tables.
  PDF size estimate: 200–500 KB per report (4 pages with images).
  Generation time: < 3 seconds (Batch 01 performance requirement).

  Future consideration (v2): If PDFs are requested to be re-downloadable without
  regeneration (for high-volume API users), store them in object storage with
  a signed URL cached in Redis for 1 hour. Not required for v1.

7.5 GRAD-CAM IMAGE STORAGE
────────────────────────────

  Grad-CAM heatmaps are stored as base64-encoded PNG text in
  scan_results.frequency_heatmap. This column is handled by PostgreSQL TOAST.

  Storage format: base64-encoded PNG embedded in the database row.
  Average size: 150–300 KB as base64 text (original PNG: ~100–200 KB).
  Maximum recommended size: 500 KB as base64 (alert if regularly exceeded).

  Retrieval: Only loaded when the full result is requested. Never included in
  history list queries. The API's ScanResultResponse includes the base64 string
  directly; the frontend decodes it with a data URI (<img src="data:image/png;base64,...">).

  Migration path to object storage (when triggered by size monitoring):
  — New scans: write PNG to object storage, store URL in frequency_heatmap column.
  — Existing scans: background migration job reads base64, uploads to object
    storage, updates the column with the URL, clears the base64 value.
  — The discriminator pattern in the column value ('data:image' vs 'https://')
    enables zero-downtime migration without application code changes.

7.6 LOG STORAGE
────────────────

  Application logs (structured JSON from FastAPI and Celery workers):
  — Written to stdout (container/process standard output)
  — Captured by the host's log collection agent (Docker logging driver,
    systemd journal, or equivalent)
  — Forwarded to log aggregation system (CloudWatch, Datadog, ELK stack)
  — Not stored in the database

  Audit logs:
  — Written to the audit_logs PostgreSQL table (Section 5, Entity 14)
  — Also mirrored to the log aggregation system via the structured log pipeline
    for SIEM integration (two copies: DB for query access, log system for streaming)

  Log volume estimates:
  — API requests: ~50 log lines/request × 1,000 req/hr = ~50,000 lines/hr
  — Celery tasks: ~20 log lines/task × 200 tasks/hr = ~4,000 lines/hr
  — Retention: 30 days active, 90 days cold (log aggregation system)

7.7 METRICS STORAGE
─────────────────────

  Time-series metrics are NOT stored in PostgreSQL. They are emitted to a
  metrics collection system (Prometheus format recommended).

  Metrics emitted:
  — API request duration histogram (per endpoint, per status code)
  — Inference task duration histogram (per verdict, per model version)
  — Queue depth gauge (Celery inference queue length)
  — Database connection pool utilization gauge
  — Redis memory usage gauge
  — Scan submission rate counter (per minute)
  — Error rate counter (per endpoint, per error type)

  Storage recommendation: Prometheus + Grafana for v1. VictoriaMetrics or
  Thanos for long-term storage (> 30 days) in v2.
  Retention: 30 days high-resolution, 1 year downsampled (5-minute resolution).

7.8 BACKUP STORAGE
────────────────────

  See Section 13 (Backup Strategy) for full backup architecture.

  Backup files: stored in a separate location from the primary database,
  ideally a different physical server or cloud region.
  Format: pg_dump custom format (compressed, parallel-restore capable).
  Encryption: AES-256 encryption applied before backup transfer (at-rest
  encryption in transit to backup storage).

7.9 FUTURE OBJECT STORAGE LAYOUT

  voiceguard-prod/
  ├── heatmaps/{scan_id}/gradcam.png         — Grad-CAM overlay images

SECTION 8 — INDEX STRATEGY
================================================================================

8.1 INDEX PHILOSOPHY
─────────────────────
Indexes are designed bottom-up from query patterns, not top-down from convention.
Every index has an explicit justification linked to a named query pattern.
Over-indexing wastes write throughput and storage. Under-indexing causes query
degradation at scale. The right index count is the minimum set that meets all
latency targets.

Rule: Every index must answer the question "Which specific query, and why is
this the optimal structure?" If that cannot be answered, the index is not created.

8.2 USERS TABLE INDEXES
────────────────────────

  Primary Index (B-tree on id):
    Justification: UUID primary key. Used for all FK lookups from child tables.
    Also used for JWT user_id claim verification on every API request.

  Unique Index on email (B-tree):
    Justification: Login query ("find user by email"). Called on every login
    attempt, every OAuth callback, and every registration duplicate check.
    email is normalized to lowercase, so the index is on the normalized form.
    This is the most-hit index in the entire system after id.

  Index on (deletion_scheduled_at) WHERE deletion_scheduled_at IS NOT NULL:
    Partial index. Justification: The purge job queries "find users whose
    deletion_purge_at < now()". Without this index, the job scans all users
    daily. With this partial index, it only scans users in deletion state
    (typically a tiny fraction of the user table).

  Index on role WHERE role = 'admin':
    Partial index. Justification: Admin middleware verifies role = 'admin'.
    This is a tiny subset of users; a partial index is extremely compact.

8.3 SCANS TABLE INDEXES
─────────────────────────

  Primary Index (B-tree on id):
    Justification: UUID primary key. FK target from scan_results, notifications,
    feedback. Also the public scan URL identifier (/r/{scan_id}).

  Index on (user_id, created_at DESC):
    Composite, B-tree. The most important scan index.
    Justification: History list query — "Get scans for user X, ordered by
    most recent first." Covers: dashboard recent scans (top 5), full history
    page (paginated), CSV export. The DESC ordering matters: PostgreSQL can
    use this index for ORDER BY created_at DESC without a sort step.

  Index on (user_id, status):
    Composite, B-tree.
    Justification: Dashboard statistics query — "Count scans WHERE user_id = X
    AND status = 'complete'". Covers the stats row (total, human, AI counts)
    by combining with a join to scan_results. Without this, a full scan of all
    user scans is needed for each stat card.

  Index on (guest_token) WHERE guest_token IS NOT NULL:
    Partial, B-tree.
    Justification: Guest scan ownership verification and guest scan migration.
    "Find all scans WHERE guest_token = X." Called on every guest poll for
    scan status, and during migration. The partial index (only non-null rows)
    is very compact because most scans are by authenticated users.

  Index on (status, created_at) WHERE status IN ('pending', 'processing'):
    Partial composite, B-tree.
    Justification: The Celery cleanup job and monitoring queries scan for
    stuck scans (status=pending AND created_at < 5 minutes ago). Without this
    index, a full table scan on a potentially large scans table occurs every
    60 seconds.

  Index on (created_at DESC):
    B-tree.
    Justification: Admin panel "list all scans" query, ordered by most recent.
    Also used by the global scan counter query if not using Redis.

  Index on (user_id, original_filename) — text prefix index:
    B-tree on (user_id, original_filename varchar_pattern_ops).
    Justification: History search by filename ("find scans WHERE user_id = X
    AND original_filename ILIKE 'recording%'"). varchar_pattern_ops enables
    prefix-match queries to use the index. Full text search (ILIKE '%term%')
    still requires a sequential scan; that is acceptable for v1 history sizes.

  Future: Full-text index on original_filename using tsvector for v2 fuzzy search.

8.4 SCAN_RESULTS TABLE INDEXES
────────────────────────────────

  Primary Index (B-tree on id):
    Standard primary key.

  Unique Index on scan_id:
    Justification: The primary lookup pattern is "get result for scan X."
    Also enforces the 1:1 constraint with scans.

  Index on (verdict, model_version):
    Composite B-tree.
    Justification: Admin analytics query — "How many scans returned human verdict
    with model version X in the last 30 days?" Combined with a created_at range
    filter, this enables model performance monitoring without a full table scan.

  Index on created_at DESC:
    Justification: Time-range queries for admin analytics and data warehouse export.

  NOTE: DO NOT include frequency_heatmap in any index or covering index. It is
  a large text column; indexing it is both impossible (size limit) and useless.
  All queries that return heatmaps must specifically SELECT the heatmap column;
  all queries that do NOT need the heatmap must explicitly exclude it.

8.5 REFRESH_TOKENS TABLE INDEXES
──────────────────────────────────

  Primary Index (B-tree on id).

  Unique Index on token_hash:
    Justification: Token rotation query — "Find token by hash." Called on every
    token refresh request (every 15 minutes per active session). Critical path;
    must be O(log n) lookup.

  Index on (user_id, revoked, expires_at):
    Composite B-tree.
    Justification: "Count/list active sessions for user X" (future session
    management page) and "Revoke all tokens for user X" (logout-all, password
    change, deletion initiation). revoked=false filter means a partial index
    WHERE revoked=false is also viable.

  Index on expires_at WHERE revoked=false:
    Partial B-tree.
    Justification: Cleanup job — "Delete expired non-revoked tokens." The partial
    index keeps only active tokens in scope, making the cleanup query fast even
    as the table accumulates historical rows.

8.6 EMAIL_VERIFICATIONS AND PASSWORD_RESET_TOKENS INDEXES
───────────────────────────────────────────────────────────

  Both tables have the same index pattern:

  Primary Index (B-tree on id).
  Unique Index on token_hash: Lookup by token on verification/reset. Critical path.
  Index on (user_id, used, expires_at): Find pending tokens per user.
  Index on expires_at WHERE used=false: Cleanup job pattern.

8.7 API_KEYS TABLE INDEXES
────────────────────────────

  Primary Index (B-tree on id).

  Index on key_hash (hashed, B-tree, UNIQUE):
    Justification: API authentication — "Find key by scrypt hash." Called on
    every API request using an API key. Critical path.

  Index on (user_id, revoked):
    Justification: List keys for user (settings page), count active keys per user
    (enforcement of 10-key limit).

8.8 NOTIFICATIONS TABLE INDEXES
─────────────────────────────────

  Primary Index (B-tree on id).

  Index on (user_id, read, created_at DESC):
    Composite B-tree. The most important notification index.
    Justification: Notification list — "Get notifications for user X, unread
    first, then by date." Covers: notification center list, unread count query.
    The partial form (WHERE read=false) could be a separate partial index for
    the unread count specifically, but the composite covers both patterns.

  Index on (user_id, created_at DESC):
    Justification: "Get all notifications for user X ordered by date" (for the
    full notification list including read items).

  Index on expires_at WHERE expires_at IS NOT NULL:
    Partial B-tree. Justification: Retention cleanup job — "Delete notifications
    older than 90 days." Without this, a full scan occurs daily.

8.9 FEEDBACK TABLE INDEXES
────────────────────────────

  Primary Index (B-tree on id).

  Index on (scan_id) WHERE scan_id IS NOT NULL:
    Partial B-tree. Justification: "Find all feedback for scan X" — admin review.

  Index on (type, reviewed, created_at DESC):
    Composite. Justification: Admin panel — "List unreviewed incorrect_result
    feedback sorted by newest first" — the primary ML pipeline query.

  Index on (user_id) WHERE user_id IS NOT NULL:
    Partial. Justification: "What feedback did user X submit?" (user data export).

8.10 AUDIT_LOGS TABLE INDEXES
───────────────────────────────

  Primary Index (B-tree on id).

  Index on (timestamp DESC):
    Justification: Admin audit log viewer — "Show recent events." Most audit
    queries are time-range filtered. This is the primary audit query index.

  Index on (user_id, timestamp DESC) WHERE user_id IS NOT NULL:
    Partial composite. Justification: "Show all events for user X" — incident
    investigation or user data export. Partial because many audit events have
    no user_id (unauthenticated events).

  Index on (event_type, timestamp DESC):
    Composite. Justification: "Show all LOGIN_FAILURE events in the last 24 hours"
    — security monitoring query. Also: "Show all RATE_LIMIT_EXCEEDED events."

  Index on (outcome, timestamp DESC) WHERE outcome = 'failure':
    Partial. Justification: Security dashboards focused on failures.

  Partitioning note: When audit_logs exceeds 10 million rows (approximately 2 years
  at 100K users), the table should be partitioned by timestamp (monthly RANGE
  partitioning). Each partition can be individually vacuumed, and old partitions
  can be detached and archived without impacting current operations. Plan the
  partitioning scheme from the start; retrofitting partitioning is expensive.

  The primary index on timestamp DESC combined with partitioning means that
  queries for "last 30 days" only scan the current and previous month's partitions.

8.11 HELP_ARTICLES TABLE INDEXES
──────────────────────────────────

  Primary Index (B-tree on id).
  Unique Index on slug: Lookup by slug (GET /api/v1/help/articles/{slug}).
  Index on (category, published) WHERE published=true:
    Justification: List articles by category — the Help Center browse query.
  Full-text index on (title, body_markdown) as tsvector:
    Justification: v2 server-side search. In v1 (client-side search), this index
    is deferred. CREATE THE TSVECTOR COLUMN NOW but defer the GIN index to v2.
    Pre-creating the column avoids a table rewrite migration in v2.

8.12 COVERING INDEXES
───────────────────────

  A covering index stores additional non-key columns alongside the index entry,
  allowing certain queries to be answered from the index alone without visiting
  the heap (table). Use sparingly; covering indexes increase write overhead.

  Covering index: scans (user_id, created_at DESC) INCLUDE (id, status, verdict)
    Wait — verdict is in scan_results, not scans. Revised:
  Covering index: scans (user_id, created_at DESC) INCLUDE (id, status, original_filename, file_extension, file_size_bytes)
    Justification: The history list query selects these exact columns for each row.
    With this covering index, the history page query never visits the table heap
    for the listed columns. This is significant at 10,000+ scans per user because
    it eliminates thousands of heap fetches per page load.

  Covering index: notifications (user_id, read, created_at DESC) INCLUDE (id, type, title, read_at)
    Justification: Notification center renders title and read state in the list.
    With covering, the notification list is served entirely from the index.

SECTION 9 — QUERY OPTIMIZATION STRATEGY
================================================================================

9.1 DASHBOARD QUERY PATTERN
─────────────────────────────

  Endpoint: GET /api/v1/dashboard/stats

  Queries executed:
  1. User profile lookup: SELECT id, display_name, email, role FROM users WHERE id = {user_id}
     — O(1) via primary key. No optimization needed.

  2. Scan count stats: SELECT COUNT(*) total, SUM(CASE WHEN verdict='human' THEN 1 END) human,
     SUM(CASE WHEN verdict='ai_generated' THEN 1 END) ai FROM scans s LEFT JOIN scan_results sr
     ON s.id=sr.scan_id WHERE s.user_id={user_id} AND s.status='complete'
     — Uses (user_id, status) composite index on scans.
     — At 10,000 scans: ~1ms. At 100,000 scans: ~10ms.
     — CACHE in Redis: key stats:{user_id}, TTL 5 minutes.
     — Cache invalidation: on every scan completion for this user (Celery task
       deletes the cache key as part of the scan completion handler).

  3. Recent scans: SELECT id, original_filename, status, created_at, file_extension
     FROM scans WHERE user_id={user_id} ORDER BY created_at DESC LIMIT 5
     — Uses covering index (user_id, created_at DESC) INCLUDE (id, original_filename, status, ...)
     — Verdict for recent scans requires JOIN to scan_results — worth it for only 5 rows.
     — Total query time: < 5ms.

  Read frequency: Every dashboard page load. Estimated: 1,000–10,000 reads/hour.
  Write frequency: 0 (read-only endpoint).
  Expected latency target: < 100ms total (including Redis cache check).
  Caching: Redis for stats (5-min TTL). Recent scans are not cached (5 rows, fast).

9.2 HISTORY LIST QUERY PATTERN
────────────────────────────────

  Endpoint: GET /api/v1/scans/?page=N&page_size=20&verdict=human&from_date=...

  Query strategy:
  1. Build WHERE clause dynamically from filters: user_id = X AND status = 'complete'
     AND created_at BETWEEN {from_date} AND {to_date}
  2. Join to scan_results for verdict filter (if verdict filter specified):
     INNER JOIN scan_results ON scan_results.scan_id = scans.id WHERE verdict = {filter}
  3. Use (user_id, created_at DESC) covering index for ordering.
  4. Paginate with LIMIT + OFFSET (page × page_size).
     At page 1: extremely fast.
     At page 500+ (deep pagination): OFFSET becomes expensive.
     Mitigation: Use keyset pagination for pages > 10 (use created_at < {last_seen_date}
     AND id < {last_seen_id} as cursor instead of OFFSET).

  Total count query (for pagination UI):
     SELECT COUNT(*) FROM scans WHERE user_id=X AND ... — can be expensive.
     Optimization: Run count query only for page 1 (cache it). For subsequent
     pages, use the cached total count. Cache key: hist_count:{user_id}:{filter_hash}.

  Filename search:
     WHERE original_filename ILIKE '{query}%' — prefix match uses index.
     WHERE original_filename ILIKE '%{query}%' — requires seqscan on user's scans.
     Acceptable for v1 (max ~10,000 scans per user). Use tsvector in v2.

  Read frequency: Moderate — history page is less frequent than dashboard.
  Write frequency: 0.
  Expected latency: < 200ms for first page, < 500ms for deep pages.
  Caching: Not cached (dynamic filters make caching impractical). DB is fast enough.

9.3 SCAN STATUS POLL QUERY PATTERN
─────────────────────────────────────

  Endpoint: GET /api/v1/scans/{scan_id}/status (polled every 3 seconds)

  Step 1: Redis lookup: GET scan_status:{scan_id}
    — Cache HIT: return immediately (< 1ms).
    — Cache MISS: proceed to DB.

  Step 2 (on cache miss): SELECT status, completed_at FROM scans WHERE id = {scan_id}
    — O(1) primary key lookup. ~1ms.
    — Verify ownership: check user_id or guest_token matches caller's context.
    — Write to Redis cache: SET scan_status:{scan_id} {status} EX {ttl}
      (TTL: 5s for pending/processing, 300s for complete/failed)

  This query is called 200 times per active scan (if scan takes 10 minutes and
  is polled every 3 seconds). Redis cache ensures the database only sees this
  query twice: once on creation (cache miss), once on completion (cache miss
  after TTL expired on the processing status). Total DB queries per scan: ~4.

  Read frequency: HIGH — most frequent API call during active scanning.
  Write frequency: 0.
  Expected latency: < 10ms (cache hit), < 50ms (cache miss).

9.4 SCAN RESULT FETCH QUERY PATTERN
──────────────────────────────────────

  Endpoint: GET /api/v1/scans/{scan_id}/result

  Query:
    SELECT s.id, s.original_filename, s.file_extension, s.file_size_bytes,
           s.created_at, s.completed_at, s.is_shared,
           sr.verdict, sr.confidence, sr.human_score, sr.ai_score,
           sr.file_hash_sha256, sr.duration_seconds, sr.sample_rate_hz,
           sr.frequency_heatmap,   ← Only here, never in list queries
           sr.model_version, sr.inference_time_ms, sr.segment_count, sr.created_at
    FROM scans s
    INNER JOIN scan_results sr ON sr.scan_id = s.id
    WHERE s.id = {scan_id}

  — Primary key lookups on both sides: O(1). TOAST fetch for frequency_heatmap.
  — Expected total query time: 5–30ms depending on heatmap TOAST retrieval.
  — Cache result in Redis: key job_result:{scan_id}, TTL 300s.
    Subsequent requests for the same result (e.g., PDF generation + result page
    simultaneously) hit cache instead of DB.

  Read frequency: Moderate — called once per scan view.
  Caching: Redis for 5 minutes after first result load.

9.5 NOTIFICATION QUERIES
─────────────────────────

  Unread count (bell badge): GET /api/v1/notifications/count
    Step 1: Redis GET notif_count:{user_id} → return if cached.
    Step 2 (cache miss): SELECT COUNT(*) FROM notifications WHERE user_id=X AND read=false
    — Uses (user_id, read, created_at DESC) index (index-only scan for COUNT).
    — Cache result: SET notif_count:{user_id} {count} EX 60
    — Expected DB time: < 5ms. Cache hit time: < 1ms.
    — Invalidation: DEL notif_count:{user_id} on notification creation or mark-all-read.

  Notification list: GET /api/v1/notifications/?page=1
    SELECT id, type, title, body, target_url, scan_id, read, read_at, created_at
    FROM notifications WHERE user_id=X ORDER BY created_at DESC LIMIT 20
    — Uses covering index (user_id, read, created_at DESC) INCLUDE (id, type, title, ...).
    — Grouped by date in frontend (Today/Yesterday/Older) — computed in application layer.

  Read frequency: HIGH for unread count (every page load). MODERATE for list.
  Latency target: < 20ms for count (cache hit), < 100ms for list.

9.6 AUTHENTICATION QUERIES
────────────────────────────

  Login by email:
    SELECT id, email, password_hash, role, email_verified, deletion_scheduled_at
    FROM users WHERE email = {normalized_email}
    — Unique index on email: O(log n). ~1ms.
    — No caching. Auth queries must always hit the database for correctness.

  Token rotation:
    SELECT id, user_id, revoked, expires_at FROM refresh_tokens WHERE token_hash = {hash}
    — Unique index on token_hash: O(log n). ~1ms.
    — Then UPDATE refresh_tokens SET revoked=true WHERE id = {token_id}
    — Then INSERT INTO refresh_tokens (new token record)
    — All in a single transaction.

  JWT verification:
    — Access token verification is stateless (HMAC-SHA256 verify + exp check).
    — NO database query for access token verification.
    — Only when the access token is expired: refresh token lookup in DB.

  Read frequency: VERY HIGH (every authenticated request). But JWT verification
  is stateless; DB is only hit for refresh (every 15 minutes per session).

9.7 ADMIN PANEL QUERIES
─────────────────────────

  Admin queries are low-frequency (few admins, infrequent access) and can tolerate
  higher latency. No caching required for admin queries.

  Platform stats:
    Multiple COUNT queries across users, scans, scan_results tables.
    Run via separate background job, not in-request, if aggregations are slow.
    Store results in a admin_stats:{date} Redis key with TTL 1 hour.

  User list (admin):
    SELECT id, email, display_name, role, email_verified, created_at
    FROM users ORDER BY created_at DESC LIMIT 50
    — Uses created_at DESC index on users.

  Scan list (admin, all users):
    SELECT s.id, s.user_id, s.original_filename, s.status, s.created_at,
           sr.verdict, sr.confidence
    FROM scans s LEFT JOIN scan_results sr ON s.id = sr.scan_id
    ORDER BY s.created_at DESC LIMIT 50
    — Uses (created_at DESC) index on scans.

  Latency target: < 2 seconds for admin queries (acceptable for admin UX).

9.8 ANALYTICS QUERY PATTERN
─────────────────────────────

  v1 analytics are minimal (admin dashboard only). v2 requires a separate
  analytics database (see Section 3.5).

  Scan trend query (last 30 days):
    SELECT DATE(created_at) as day, COUNT(*) as scan_count,
           SUM(CASE WHEN verdict='human' THEN 1 ELSE 0 END) as human_count
    FROM scans s JOIN scan_results sr ON s.id=sr.scan_id
    WHERE s.created_at > now() - interval '30 days'
    GROUP BY DATE(created_at)
    ORDER BY day DESC
    — Full scan of last 30 days' data. Acceptable at v1 volume.
    — Cache in Redis admin_trend:30d with TTL 3600 (1 hour).

SECTION 10 — TRANSACTION DESIGN
================================================================================

10.1 USER REGISTRATION TRANSACTION
─────────────────────────────────────

  Atomic operations:
    1. INSERT INTO users (id, email, password_hash, role, email_verified, created_at)
    2. INSERT INTO email_verifications (id, user_id, token_hash, expires_at, created_at)

  Rollback scenario:
    If either INSERT fails (e.g., email uniqueness violation on users, or
    email_verifications INSERT fails), the entire transaction rolls back.
    No partial state is possible: a user row without a verification token,
    or a verification token without a user, cannot exist.

  Post-transaction (outside the transaction, non-atomic):
    — Dispatch Celery email task: send_verification_email
    — Dispatch Celery scan migration task (if guest_token present)
    These are not part of the transaction. If they fail, the user account
    still exists and the user can request a resend.

  Consistency guarantee: Email uniqueness is guaranteed. Two simultaneous
  registrations with the same email: the first commits; the second receives
  a unique constraint violation and returns 409 Conflict.

10.2 LOGIN AND SESSION CREATION TRANSACTION
─────────────────────────────────────────────

  Atomic operations:
    1. SELECT user by email (read-only, not in transaction yet)
    2. Verify bcrypt hash (CPU operation, not in DB)
    3. BEGIN TRANSACTION
    4. INSERT INTO refresh_tokens (id, user_id, token_hash, expires_at, created_at)
    5. COMMIT

  Rollback scenario:
    If token INSERT fails, the user sees a 500 error and must retry login.
    The user record is unchanged.

  Post-transaction:
    — Set HttpOnly cookies in response headers.
    — No Celery task needed for login.

10.3 REFRESH TOKEN ROTATION TRANSACTION
─────────────────────────────────────────

  This is the most critical transaction for security (reuse attack detection).

  Atomic operations:
    1. BEGIN TRANSACTION with SERIALIZABLE isolation
    2. SELECT * FROM refresh_tokens WHERE token_hash={hash} FOR UPDATE
       (Pessimistic lock prevents concurrent rotation of the same token)
    3. IF row.revoked=true:
         a. UPDATE refresh_tokens SET revoked=true WHERE user_id={user_id} AND revoked=false
            (Revoke ALL tokens — reuse attack)
         b. COMMIT
         c. Return 401 with force_relogin=true
       IF row.expires_at < now():
         a. COMMIT (no-op, just close transaction)
         b. Return 401 with expired=true
    4. UPDATE refresh_tokens SET revoked=true, revoked_at=now() WHERE id={token_id}
    5. INSERT INTO refresh_tokens (new token: id, user_id, new_token_hash, new_expires_at)
    6. COMMIT

  Why SERIALIZABLE? Without it, two simultaneous refresh requests for the same
  token (e.g., two tabs refreshing simultaneously) could both see revoked=false,
  both proceed, and both issue new tokens from the same old token — defeating
  rotation. SERIALIZABLE + FOR UPDATE prevents this: the second concurrent
  request will either wait for the lock (and then see revoked=true) or fail with
  a serialization failure (and retry).

  Rollback scenario: If the INSERT of the new token fails, the old token remains
  revoked. The user must re-login. Acceptable — this is an edge case.

10.4 GUEST SCAN MIGRATION TRANSACTION
───────────────────────────────────────

  Trigger: User registers or logs in with an active guest_token.

  Atomic operations:
    1. BEGIN TRANSACTION
    2. SELECT id FROM scans WHERE guest_token={token} AND status IN ('complete','failed')
       FOR UPDATE (lock the rows to prevent concurrent migration)
    3. IF count = 0: COMMIT and return (nothing to migrate)
    4. UPDATE scans SET user_id={new_user_id}, guest_token=NULL
       WHERE guest_token={token} AND status IN ('complete','failed')
    5. INSERT INTO notifications (user_id={new_user_id}, type='info',
       title='Guest scans imported', body='Your {N} scans have been saved.')
    6. COMMIT

  Post-transaction:
    — Invalidate Redis notif_count:{user_id} cache.
    — No Celery task needed; migration is synchronous.

  Consistency guarantee: A scan is never simultaneously owned by both a user and
  a guest token. The FOR UPDATE lock prevents two concurrent migration attempts
  from double-migrating the same scans.

10.5 SCAN SUBMISSION TRANSACTION
──────────────────────────────────

  Atomic operations:
    1. BEGIN TRANSACTION
    2. INSERT INTO scans (id, user_id/guest_token, status='pending',
       original_filename, file_size_bytes, file_extension, claimed_mime_type,
       is_shared=true, created_at)
    3. COMMIT

  Post-transaction:
    — Write temp file to /tmp/voiceguard/{scan_id}/ (already done before transaction)
    — Dispatch Celery inference task: run_inference_task(scan_id)
    — If Celery dispatch fails: UPDATE scans SET status='failed' WHERE id={scan_id}
      (compensating operation, not a rollback)

  Why not include Celery dispatch in the transaction? Celery dispatch is not a
  database operation. Wrapping it in a DB transaction would hold a DB connection
  open while waiting for Celery's Redis publish — an anti-pattern that wastes
  connection pool capacity.

10.6 SCAN COMPLETION TRANSACTION
──────────────────────────────────

  Called inside the Celery inference worker on successful inference.

  Atomic operations:
    1. BEGIN TRANSACTION
    2. INSERT INTO scan_results (id, scan_id, verdict, confidence, human_score,
       ai_score, file_hash_sha256, duration_seconds, frequency_heatmap,
       model_version, inference_time_ms, segment_count, created_at)
    3. UPDATE scans SET status='complete', completed_at=now() WHERE id={scan_id}
    4. COMMIT

  Post-transaction:
    — DELETE /tmp/voiceguard/{scan_id}/ (temp file cleanup)
    — SET scan_status:{scan_id} 'complete' EX 300 (Redis status cache)
    — DEL stats:{user_id} (invalidate dashboard stats cache)
    — Dispatch notification Celery task: create_scan_notification(user_id, scan_id, verdict)

  Rollback scenario: If INSERT into scan_results fails (data integrity error),
  the transaction rolls back. Scan status remains 'processing'. The inference
  task is retried (if within retry policy).

10.7 ACCOUNT DELETION INITIATION TRANSACTION
──────────────────────────────────────────────

  Atomic operations:
    1. BEGIN TRANSACTION
    2. UPDATE users SET deletion_scheduled_at=now(), deletion_purge_at=now()+interval '30 days'
       WHERE id={user_id}
    3. UPDATE refresh_tokens SET revoked=true, revoked_at=now()
       WHERE user_id={user_id} AND revoked=false
       (Immediately revoke all sessions on deletion initiation)
    4. INSERT INTO deleted_accounts (id, user_id, email_hash, deletion_initiated_at,
       deletion_scheduled_for, initiated_by, created_at)
    5. INSERT INTO audit_logs (event_type='ACCOUNT_DELETION_INITIATED', user_id, ...)
    6. COMMIT

  Post-transaction:
    — Clear all Redis caches for this user_id (stats, notif_count, job_result).
    — Dispatch email task: send deletion confirmation email.
    — Session cookies become invalid immediately (refresh tokens are revoked;
      access token will expire within 15 minutes; no new access tokens can be
      issued because the refresh token is gone).

10.8 ACCOUNT PURGE TRANSACTION
────────────────────────────────

  Called by the purge_deleted_accounts Celery Beat job, 30 days after deletion.

  Atomic operations (single transaction for data consistency):
    1. BEGIN TRANSACTION
    2. DELETE FROM scan_results WHERE scan_id IN
       (SELECT id FROM scans WHERE user_id={user_id})
    3. DELETE FROM scans WHERE user_id={user_id}
    4. DELETE FROM notifications WHERE user_id={user_id}
    5. DELETE FROM api_keys WHERE user_id={user_id}
    6. DELETE FROM refresh_tokens WHERE user_id={user_id}
    7. DELETE FROM oauth_accounts WHERE user_id={user_id}
    8. DELETE FROM user_preferences WHERE user_id={user_id}
    9. DELETE FROM users WHERE id={user_id}
    10. COMMIT

  Post-transaction (outside, compensating operations):
    11. UPDATE feedback SET user_id=NULL WHERE user_id={user_id}
        (Not in the main transaction: SET NULL is safe to do outside; the FK
        is SET NULL on delete anyway, so the CASCADE handles this. But if SET NULL
        is defined as the FK behavior, step 9's user DELETE will trigger it automatically.)
    12. UPDATE audit_logs SET user_id=SHA256(original_user_id + audit_salt)
        WHERE user_id={user_id}
        (Anonymization, outside transaction: this is an UPDATE on a large table.
        Run it as a batch UPDATE outside the main transaction to avoid locking
        the audit_logs table for the duration of the main purge.)
    13. UPDATE deleted_accounts SET deletion_completed_at=now() WHERE user_id={user_id}
    14. INSERT INTO audit_logs (event_type='ACCOUNT_PURGED', details={user_id hash}, ...)

  Total rows deleted per purge: potentially millions (scan_results rows).
  For users with very large scan histories (10,000+ scans), delete in batches:
  DELETE FROM scan_results WHERE scan_id IN (SELECT id FROM scans WHERE user_id=X LIMIT 1000)
  Repeat until 0 rows affected, then delete scans in batches, then the user.

10.9 API KEY CREATION TRANSACTION
───────────────────────────────────

  Atomic operations:
    1. COUNT active api_keys WHERE user_id=X AND revoked=false
       (Check 10-key limit before transaction begins)
    2. IF count >= 10: raise LimitExceededError (no transaction needed)
    3. BEGIN TRANSACTION
    4. INSERT INTO api_keys (id, user_id, name, key_prefix, key_hash,
       rate_limit_tier, created_at)
    5. INSERT INTO audit_logs (event_type='API_KEY_CREATED', user_id, ...)
    6. COMMIT

  Post-transaction:
    — Return the raw key (shown once, never retrievable again).

10.10 NOTIFICATION CREATION TRANSACTION
─────────────────────────────────────────

  Usually called from Celery worker, not from an API request transaction.

  Atomic operations:
    1. BEGIN TRANSACTION
    2. INSERT INTO notifications (id, user_id, type, title, body, target_url,
       scan_id, read=false, created_at)
    3. COMMIT

  Post-transaction:
    — DEL notif_count:{user_id} in Redis (invalidate unread count cache).
    — If user's email notification preferences are set: dispatch email task.

================================================================================
SECTION 11 — CONCURRENCY STRATEGY
================================================================================

11.1 MULTIPLE SIMULTANEOUS UPLOADS
────────────────────────────────────

  Scenario: A user submits two scan requests within milliseconds (double-click
  on the Analyze button, or two browser tabs).

  Handling:
  — The rate limiting middleware (Redis atomic INCR) enforces the 50/day limit
    per user before any scan record is created.
  — Each upload generates a unique UUID scan_id before the database INSERT.
    Two simultaneous uploads produce two independent UUID scan records.
    There is no conflict because the primary keys are pre-generated and unique.
  — The frontend should disable the Analyze button during upload (UX prevention).
    The backend does not deduplicate simultaneous uploads from the same user;
    it processes both as independent scans.

  Design choice: We DO NOT apply uniqueness constraints on (user_id, file_hash)
  to prevent duplicate scans. A journalist may legitimately submit the same file
  multiple times to compare results across model versions (v2 feature). Preventing
  re-submission of the same file would be an incorrect constraint.

11.2 DUPLICATE REGISTRATION REQUESTS
──────────────────────────────────────

  Scenario: User double-clicks "Create Account" or submits the form twice.

  Handling:
  — The UNIQUE constraint on users.email is the sole protection.
  — First INSERT succeeds and commits.
  — Second INSERT (same email) receives a unique constraint violation.
  — Application catches the constraint violation and returns 409 Conflict with
    error code EMAIL_ALREADY_EXISTS.
  — No partial state is possible. No cleanup needed.

  Rate limit: 5 registration attempts per hour per IP prevents brute-force
  registration attacks.

11.3 SIMULTANEOUS LOGIN ATTEMPTS
──────────────────────────────────

  Scenario: User opens two browser tabs and clicks login in both within milliseconds.

  Handling:
  — Each login attempt reads the users table (read-only, no lock needed).
  — Each successful login INSERTs a new refresh_token row (UUID primary key,
    no conflict between two INSERTs for the same user).
  — Both logins succeed, both cookies are set. The user has two active sessions.
  — This is correct behavior: multiple active sessions per user are permitted
    (different tabs can be treated as different sessions).

11.4 CONCURRENT REFRESH TOKEN ROTATION
────────────────────────────────────────

  Scenario: Two browser tabs both have an expired access token and both
  simultaneously call the refresh endpoint with the same refresh token cookie.

  Handling:
  — The rotation transaction uses SELECT FOR UPDATE (pessimistic lock).
  — First request acquires the lock on the refresh token row.
  — First request: sees revoked=false, marks old token revoked, inserts new token, commits.
    New cookies are set in the response.
  — Second request: waits for the lock, then acquires it. Sees revoked=true.
    → Triggers the reuse attack handler: revokes ALL tokens for this user.
    → Returns 401 with force_relogin=true.

  This is a known UX pain point: two tabs silently refreshing at the same instant
  causes a logout. Mitigation:
  — Option A (current): Accept this rare edge case. The user re-logs in, both tabs
    work again. This is the simplest and most secure approach.
  — Option B (v2): Implement token families (parent/child tracking). If the second
    request presents a token that was rotated from a known parent (not a stolen copy),
    it is treated as a valid sibling rotation. Significantly more complex.
  — Recommendation: Start with Option A. If user complaints emerge, move to Option B.

11.5 CONCURRENT SCAN STATUS UPDATES
──────────────────────────────────────

  Scenario: The inference worker completes a scan and updates status='complete'
  while the frontend is simultaneously polling status='pending'.

  Handling:
  — Status transitions are monotonic (pending → processing → complete/failed).
  — The UPDATE in the completion transaction uses WHERE id={scan_id} (primary key).
    This is a targeted UPDATE with no range lock.
  — The frontend polling SELECT is a read-only query that sees either the old
    status or the new status (PostgreSQL's MVCC ensures the read is consistent
    with the state at the start of the read transaction).
  — No deadlock possible because: the worker UPDATEs scans and INSERTs scan_results
    in dependency order (scan_results depends on scans via FK); no cycle exists.

11.6 CONCURRENT HISTORY DELETIONS
────────────────────────────────────

  Scenario: User initiates bulk delete of 50 scans while simultaneously viewing
  one of those scans' result pages.

  Handling:
  — Bulk delete is a DELETE statement by IDs: DELETE FROM scans WHERE id = ANY({ids})
    AND user_id = {user_id}.
  — The concurrent GET /scans/{scan_id}/result is a SELECT.
  — PostgreSQL MVCC: the SELECT sees the scan row as it existed at the start of
    the SELECT transaction. If the DELETE commits before the SELECT completes,
    the SELECT may still return the pre-delete snapshot (acceptable; the UI will
    show a 404 on the next navigation).
  — The DELETE itself: ownership verification (AND user_id = {user_id}) prevents
    users from deleting each other's scans even in a concurrent bulk delete.

11.7 OPTIMISTIC LOCKING
─────────────────────────

  VoiceGuard does NOT use optimistic locking (version counters / ETags) for any
  entity in v1.

  Rationale:
  — User preferences are updated via replace-on-write (PATCH sets all fields).
    If two browser tabs update preferences simultaneously, the last write wins.
    This is acceptable — the user intended both updates and the final state is
    deterministic.
  — Notifications are append-only (create) or simple flag updates (read=true).
    No conflict is possible: setting read=true multiple times is idempotent.
  — Scans are predominantly written by the inference worker (immutable results)
    and read by the user. No user can modify scan content; conflicts do not arise.

  Optimistic locking should be considered in v2 for:
  — Team workspace shared scan annotations (multiple users editing notes on a scan)
  — CMS article editing (admin editing help articles while another admin saves)

11.8 DEADLOCK AVOIDANCE
─────────────────────────

  Deadlocks arise when two transactions lock the same rows in opposite orders.
  VoiceGuard's transaction design avoids deadlocks by:

  1. Lock acquisition order: when a transaction must lock multiple rows across
     tables, always lock in the same order:
     users → scans → scan_results → notifications → refresh_tokens
     (parent before child, in FK dependency order)

  2. Keep transactions short: the longer a transaction runs with locks held,
     the greater the chance of deadlock. No network calls, no Celery dispatches,
     and no user-facing logic inside a transaction.

  3. Prefer SELECT FOR UPDATE over full-table locks: target specific row IDs,
     not range scans with locks, to minimize the lock footprint.

  4. Use advisory locks for application-level coordination: if a guest migration
     must be atomic and exclusive, use pg_advisory_lock(hash(guest_token)) to
     coordinate multiple concurrent migration requests for the same guest.

  PostgreSQL deadlock detection: PostgreSQL automatically detects deadlocks and
  aborts one of the conflicting transactions (the one that acquired its lock last).
  The application must handle the deadlock error (typically error code 40P01) by
  retrying the transaction. All service layer operations should have a retry
  wrapper for deadlock scenarios.

SECTION 12 — DATA RETENTION POLICY
================================================================================

12.1 RETENTION POLICY OVERVIEW
────────────────────────────────

  Every data type in VoiceGuard has a defined retention period, a deletion
  trigger, a recovery period (if any), and legal basis for the retention duration.

  Retention is enforced by:
  — Celery Beat scheduled jobs (automated, running on server)
  — Explicit user actions (account deletion, scan deletion, data export/purge)
  — Foreign key CASCADE rules (cascades on parent deletion)

12.2 USER ACCOUNT DATA
────────────────────────

  Data: users table, user_preferences table, oauth_accounts table
  Retention Period: Indefinite while account is active.
  Deletion Trigger: User initiates deletion via Settings (S18) → 30-day
    soft delete window → automatic purge.
  Recovery Period: 30 days from deletion initiation. User can log in and
    cancel deletion during this window.
  Legal Considerations:
  — GDPR Article 17 (Right to Erasure): User has the right to request deletion.
    VoiceGuard honors this via the delete account flow.
  — The 30-day recovery window is a product decision (UX safety net), not
    a legal requirement. The user must be informed of this at deletion time.
  — After purge, all user data is irrecoverably deleted from PostgreSQL.
    Anonymized audit log entries remain (cannot be deleted; legal audit trail).

12.3 AUTHENTICATED SCAN DATA
──────────────────────────────

  Data: scans table (user_id IS NOT NULL), scan_results table
  Retention Period: Indefinite while user account is active.
  Deletion Trigger:
  — User explicitly deletes individual scan: immediate hard delete.
  — User bulk-deletes scans: immediate hard delete.
  — User account purge: CASCADE delete of all user's scans and results.
  Recovery Period: None. Scan deletion is permanent (the 5-second "Undo"
    toast in the UI is client-side delay, not server-side recovery).
  Legal Considerations:
  — No regulatory minimum retention for scan metadata.
  — GDPR data minimization: only metadata is stored (no audio). Compliant.
  — SHA-256 hash in scan_results: the hash alone cannot reconstruct the audio
    and is not considered PII under most GDPR interpretations.

12.4 GUEST SCAN DATA
─────────────────────

  Data: scans table (guest_token IS NOT NULL, user_id IS NULL), scan_results
  Retention Period: 24 hours from created_at.
  Deletion Trigger: Automated Celery Beat job runs hourly.
    Deletes: scans WHERE guest_token IS NOT NULL AND created_at < now() - interval '24 hours'
    AND status IN ('complete', 'failed').
    Cascade deletes: scan_results rows.
  Recovery Period: None.
  Guest token expiry: The browser cookie expires after 24 hours. After expiry,
    the guest cannot access their scan even if the DB row still exists.
  Legal Considerations:
  — Guest scans contain no PII (no email, no user account).
  — Guest token is not stored beyond the cookie's lifetime.
  — 24-hour retention is operationally convenient (enough time to convert) and
    privacy-conservative (no long-term anonymous data accumulation).

12.5 REFRESH TOKENS
────────────────────

  Data: refresh_tokens table
  Retention Period: 30 days from creation (the token's natural TTL).
  Deletion Trigger:
  — Explicit logout: immediate revocation (revoked=true set).
  — Password change: all tokens for user immediately revoked.
  — Account deletion initiation: all tokens immediately revoked.
  — Expiry: Celery Beat cleanup job runs every 6 hours.
    Deletes: refresh_tokens WHERE expires_at < now() - interval '7 days'
    (7-day grace period after expiry allows audit correlation of recently-expired tokens).
  Recovery Period: None once revoked.

12.6 EMAIL VERIFICATION AND PASSWORD RESET TOKENS
───────────────────────────────────────────────────

  Data: email_verifications, password_reset_tokens
  Retention Period: Until used or expired (24h for email verification, 1h for
    password reset). Cleanup job retains for 24h after expiry for audit.
  Deletion Trigger: Celery Beat every 6 hours.
    Deletes: WHERE expires_at < now() - interval '24 hours'.
  Recovery Period: None. User must request a new token.

12.7 NOTIFICATIONS
────────────────────

  Data: notifications table
  Retention Period:
  — User notifications (type in info/success/warning): 90 days from created_at.
  — System announcements (type='system'): 180 days from created_at.
  Deletion Trigger: Celery Beat weekly job.
    Deletes: notifications WHERE created_at < now() - interval '90 days'
    AND type != 'system'
  Also deletes: notifications WHERE created_at < now() - interval '180 days'
    AND type = 'system'
  Recovery Period: None.
  Legal Considerations: Notifications are internal system messages, not user-
    generated content. No legal retention requirement. 90 days is chosen
    to balance UX (user can review recent history) and storage efficiency.

12.8 FEEDBACK DATA
────────────────────

  Data: feedback table
  Retention Period: PERMANENT. Feedback has indefinite research value for ML
    model improvement. Even after user deletion, feedback records are retained
    with user_id set to NULL.
  Deletion Trigger: None (feedback is never deleted automatically).
  Manual deletion: Admin can delete specific feedback records if they contain
    harmful content (e.g., PII inadvertently included in the description field).
  Legal Considerations:
  — GDPR: User's right to erasure applies to their personal data. The feedback
    description could contain PII if the user included identifying information.
    When a user's account is purged, the user_id on feedback is set to NULL.
    If the description itself contains PII, the user must contact support for
    manual review and redaction.
  — Consider adding a feedback.is_redacted boolean flag (default false) and
    a redacted_description column. When set, the description is replaced with
    "[redacted]" in all admin views.

12.9 HELP ARTICLES AND ARTICLE FEEDBACK
─────────────────────────────────────────

  Data: help_articles, article_feedback
  Retention Period: Indefinite (articles are editorial content, retained as long
    as the product exists). Article feedback retained for article lifetime.
  Deletion Trigger: Admin explicitly unpublishes or deletes articles.
    Article deletion cascades to article_feedback.
  Legal Considerations: Non-PII public content. No special retention requirements.

12.10 AUDIT LOGS
─────────────────

  Data: audit_logs table
  Retention Period: 2 YEARS minimum from event timestamp.
  Deletion Trigger: Compliance job runs monthly.
    Deletes: audit_logs WHERE timestamp < now() - interval '2 years'
    (If partitioned by month, this is achieved by DROPping old partitions.)
  Recovery Period: None. Audit logs are not recoverable after deletion.
  Legal Considerations:
  — The 2-year retention is a conservative baseline for security audit compliance
    (SOC 2, ISO 27001 requirements typically mandate 1 year; 2 years provides
    buffer for multi-year incident investigations).
  — In jurisdictions with longer requirements (e.g., financial services in some
    regions mandate 7 years), extend the retention period.
  — Audit logs may not be deleted on GDPR right-to-erasure request because they
    serve a legitimate legal basis (security audit, fraud investigation).
    IP hashes are not considered directly identifying under GDPR when salted.

12.11 API KEYS
──────────────

  Data: api_keys table
  Retention Period: Until revoked (active keys). Revoked keys: 90 days after
    revocation for audit correlation.
  Deletion Trigger: Manual revocation by user, or CASCADE on user purge.
    Cleanup job deletes: api_keys WHERE revoked=true AND revoked_at < now() - interval '90 days'.
  Recovery Period: None. Revoked keys cannot be restored.

12.12 DELETED ACCOUNT RECORDS
───────────────────────────────

  Data: deleted_accounts table
  Retention Period: 60 days from deletion_initiated_at.
  Deletion Trigger: Cleanup job runs monthly.
    Deletes: WHERE deletion_initiated_at < now() - interval '60 days'.
  Purpose of retention: During the 60-day window, the email_hash enables the
    system to identify re-registration attempts with the same email address.
    After 60 days, the former user should be able to re-register freely.

12.13 TEMPORARY FILES
──────────────────────

  Data: /tmp/voiceguard/{scan_id}/ filesystem directory
  Retention Period: 60 seconds after scan completion/failure.
    Hard limit: 120 seconds from creation (failsafe cleanup regardless of status).
  Deletion Trigger:
  — Inference task success handler (immediate cleanup after result stored).
  — Inference task failure handler (immediate cleanup on failure).
  — Celery Beat failsafe job every 60 seconds (cleans any directory older than 120s).
  Recovery Period: None.
  Legal Considerations: Audio is ephemeral by design. No audio content is ever
    written to permanent storage. This is the core privacy guarantee.

12.14 REDIS EPHEMERAL DATA
────────────────────────────

  All Redis keys are TTL-bounded. No Redis data requires explicit retention
  management (TTL expiry handles it). Key TTL summary:

  Key Pattern                         TTL
  ───────────────────────────────────────────────────────
  rl:scan:guest:{ip}:{bucket}         Until end of hour window
  rl:scan:user:{user_id}:{bucket}     Until end of day window
  rl:auth:{endpoint}:{ip}:{bucket}    Until end of hour window
  scan_status:{scan_id}               5s (active) / 300s (terminal)
  oauth_state:{state}                 600s (10 minutes)
  job_result:{scan_id}                300s (5 minutes)
  notif_count:{user_id}               60s
  stats:{user_id}                     300s (5 minutes)
  global:scan_count                   No expiry (persistent counter)

SECTION 13 — BACKUP STRATEGY
================================================================================

13.1 BACKUP PHILOSOPHY
────────────────────────
  Backups are only as valuable as their last successful restore test.
  A backup that has never been tested is an assumption, not a guarantee.
  VoiceGuard's backup strategy is designed around the recovery objectives,
  not around the convenience of the backup process.

  Recovery Time Objective (RTO): < 4 hours to full service restoration.
  Recovery Point Objective (RPO): < 1 hour of data loss.

13.2 POSTGRESQL BACKUP TYPES
──────────────────────────────

  CONTINUOUS ARCHIVING (WAL streaming) — PRIMARY BACKUP MECHANISM
  — Method: PostgreSQL Write-Ahead Log (WAL) streaming to backup storage.
  — Tool: pg_basebackup for base backups + WAL archiving (archive_command).
  — Provides: Point-In-Time Recovery (PITR) to any second within the WAL
    retention window.
  — WAL retention: 7 days of WAL segments archived.
  — Base backup frequency: Weekly (every Sunday at 02:00 UTC).
  — Storage: WAL segments + base backups stored in encrypted backup storage.
  — RPO: Achievable RPO < 5 minutes (WAL segment frequency).

  LOGICAL BACKUPS (pg_dump) — SECONDARY BACKUP / PORTABILITY
  — Method: pg_dump --format=custom (compressed, parallel-restorable).
  — Frequency: Daily at 03:00 UTC.
  — Scope: Full database dump (all tables, indexes, constraints, sequences).
  — Retention: 30 daily dumps retained (30-day point-in-time logical recovery).
  — After 30 days: weekly dumps retained for 3 months. Monthly dumps for 1 year.
  — Storage: Separate location from WAL backups (two independent backup stores).
  — Use case: Schema migrations gone wrong, logical data corruption, table-level
    restore (can restore a single table from pg_dump without full cluster restore).

  SNAPSHOT BACKUPS (if cloud/VM) — TERTIARY BACKUP
  — Method: VM/volume snapshot at the storage layer.
  — Frequency: Every 6 hours.
  — Retention: 7 daily snapshots, 4 weekly snapshots.
  — Use case: Full server failure (restore the entire VM to a known state).
  — Not a substitute for PITR; used when the DB state itself is the problem.

13.3 INCREMENTAL BACKUP DESIGN
────────────────────────────────

  WAL archiving IS incremental by nature: only changed blocks are written to WAL.
  Each WAL segment is ~16MB and covers the changes since the previous segment.

  pg_dump logical backups are NOT incremental (full dump each time). This is
  acceptable at v1 database size (~10-20 GB). When the database exceeds 200 GB,
  switch to pg_dump with --exclude-table for the large scan_results.frequency_heatmap
  column (dump metadata separately from blob data).

  Incremental logical backup in v2 (when needed): Use pg_dump with --section=data
  and selective table exclusions. Or switch to a WAL-based logical replication
  approach (pglogical, debezium) that captures row-level changes.

13.4 POINT-IN-TIME RECOVERY
─────────────────────────────

  PITR process using WAL archiving:
  1. Restore the most recent base backup to a new PostgreSQL instance.
  2. Configure recovery.conf (or postgresql.conf in PG13+) to replay WAL
     segments until the target recovery time.
  3. Set recovery_target_time = '{YYYY-MM-DD HH:MM:SS}' (the moment before
     data loss or corruption occurred).
  4. Start PostgreSQL in recovery mode.
  5. Monitor recovery progress; promote to primary when recovery completes.

  PITR capability: Can restore to any second within the 7-day WAL window.
  Beyond 7 days: fall back to daily pg_dump logical backups (less granular).

13.5 BACKUP ENCRYPTION
────────────────────────

  All backup files are encrypted before storage and transfer.
  Algorithm: AES-256-GCM.
  Key management: Encryption key stored in a separate secret manager (NOT in
    the backup file itself and NOT in the database being backed up).
  Key rotation: Annually; re-encrypt existing backups with new key over a
    rolling 30-day window.

13.6 BACKUP VERIFICATION AND RESTORE TESTING
──────────────────────────────────────────────

  Automated restore testing:
  — Weekly: Automated job restores the latest pg_dump backup to a staging
    PostgreSQL instance. Runs a suite of integrity checks:
    1. Row count comparison (production vs. restore within 1% tolerance)
    2. Key data integrity: verify users, scans, scan_results table row counts
    3. Constraint check: verify FK constraints are satisfied post-restore
    4. Index validity: verify all indexes are valid (no corruption)
  — Monthly: Full PITR restore test to a point 6 hours before the test time.
    Verify that the restored database matches expected production state.

  Manual quarterly disaster recovery drill:
  — Complete failover simulation: production database inaccessible.
  — Full restore from backup. Measure actual RTO.
  — Document findings; update runbook if RTO target missed.

13.7 BACKUP STORAGE LOCATIONS
────────────────────────────────

  PRIMARY BACKUP LOCATION: A separate server in the same data center.
  — Fast access for daily restores.
  — Same geographic location (fast but not geo-redundant).

  SECONDARY BACKUP LOCATION: Different geographic location (cloud object storage
  or colocation facility in a different region).
  — Geo-redundant protection against data center disasters.
  — Slightly slower access (cross-region transfer for restore).
  — Minimum: the weekly full backup and all WAL segments are mirrored here.

13.8 BACKUP RETENTION SCHEDULE
────────────────────────────────

  Retention Schedule:
  ─────────────────────────────────────────────────────────────
  WAL segments:              7 days (continuous, rolling window)
  Daily pg_dump:             30 days
  Weekly pg_dump:            3 months (13 weekly backups)
  Monthly pg_dump:           12 months (12 monthly backups)
  Yearly pg_dump:            5 years (compliance archive)
  VM/Volume snapshots:       7 days (daily), 4 weeks (weekly)

13.9 REDIS BACKUP
──────────────────

  Redis does not require strict backup in VoiceGuard because:
  — All critical data (users, scans, results) is in PostgreSQL.
  — Redis is a cache and rate-limiting store; its data is reconstructible
    from PostgreSQL or from natural system activity.

  However, Redis AOF (Append Only File) should be enabled with fsync=everysec
  to protect Celery task queue state (in-flight inference tasks). Without this,
  a Redis crash could lose pending scan tasks.

  Redis backup strategy:
  — AOF enabled, fsync=everysec for Celery broker durability.
  — RDB snapshot every 60 seconds (bgsave) for cache state persistence.
  — No offsite backup required (data is reconstructible).
  — Redis restart recovery: tasks in the queue persist via AOF; rate limit
    counters restart at zero (briefly allows extra requests; acceptable).

================================================================================
SECTION 14 — DISASTER RECOVERY PLAN
================================================================================

14.1 FAILURE TAXONOMY
──────────────────────

  TIER 1 — Component failure (single service down, system degraded):
    Database slow/high latency, Redis unavailable, worker crash.
    RTO: < 15 minutes. System degrades gracefully; core flows may be impacted.

  TIER 2 — Service failure (entire process down, feature unavailable):
    PostgreSQL process crashed, entire Redis instance down.
    RTO: < 30 minutes. Restore from process restart or failover.

  TIER 3 — Infrastructure failure (VM/server unresponsive or corrupted):
    VM failure, disk failure, OS-level crash.
    RTO: < 2 hours. Provision new VM, restore from backup.

  TIER 4 — Catastrophic failure (data center unreachable, data corruption):
    Complete data center loss, database corruption, ransomware.
    RTO: < 4 hours. Full restore from backup in secondary location.

14.2 DATABASE FAILURE SCENARIOS
─────────────────────────────────

  SCENARIO: PostgreSQL process crash (Tier 2)
  Detection: Health check endpoint /api/v1/health returns 503.
  Response:
    1. PostgreSQL auto-restarts (systemd service configured with Restart=always).
    2. PostgreSQL WAL recovery completes automatically (WAL ensures no data loss
       from a clean crash; uncommitted transactions are rolled back).
    3. API server reconnects (connection pool retries with exponential backoff).
    4. System restored: < 5 minutes for clean crash.
  Data loss: Zero (WAL recovery brings back all committed transactions).
  Communications: Alert to on-call. Status page update if downtime > 2 minutes.

  SCENARIO: Database data corruption (Tier 4)
  Detection: Integrity check alerts (scheduled pg_checksum verification).
    Or: Application errors indicating unexpected data formats.
  Response:
    1. Immediately take PostgreSQL offline to prevent further corruption spread.
    2. Identify corruption scope (which tables, which time range).
    3. Determine recovery point: latest clean backup timestamp.
    4. Perform PITR restore to a new PostgreSQL instance.
    5. Validate restore (row counts, integrity checks).
    6. Redirect application traffic to restored instance.
    7. Investigate root cause (disk failure, software bug, hardware fault).
  Data loss: Up to the corruption onset time (could be minutes or hours).
  RTO: 2–4 hours (PITR restore + validation).

  SCENARIO: Accidental data deletion by admin (Tier 3)
  Detection: Admin reports or automated integrity checks.
  Response:
    1. Identify deletion time from audit logs.
    2. Perform PITR restore to a point immediately before the deletion.
    3. Export the deleted rows from the restored instance.
    4. Import the recovered rows into production (selective recovery).
  RTO: 1–2 hours for selective row recovery.
  Data loss: None (PITR to exact pre-deletion moment).

14.3 REDIS FAILURE SCENARIOS
──────────────────────────────

  SCENARIO: Redis process crash (Tier 2)
  Detection: Redis health check fails; rate limiter returns errors.
  Impact:
    — Rate limiting is disabled (requests flow through without limit) — acceptable
      for short outage windows; monitor for abuse during downtime.
    — Scan status cache misses (all polls go to PostgreSQL) — increased DB load.
    — OAuth state lost (users mid-OAuth flow must restart) — minor UX impact.
    — Celery tasks in AOF survive restart (if AOF enabled) — no task loss.
  Response:
    1. Redis auto-restarts via systemd.
    2. AOF replay restores Celery queue state.
    3. Rate limit counters reset to zero (brief permissive window).
    4. OAuth states lost: users in progress must re-initiate OAuth.
  Data loss: Only in-memory rate limit state and OAuth states. No user data loss.
  RTO: < 2 minutes for process restart.

  Redis availability design (v2): Deploy Redis Sentinel or Redis Cluster for
  automatic failover. In v1, manual restart is sufficient given the short RTO.

14.4 TEMPORARY STORAGE FAILURE
────────────────────────────────

  SCENARIO: /tmp partition full (Tier 1)
  Detection: Disk usage alert at 70% of /tmp partition.
  Impact: New scan uploads fail (temp file write fails at the service layer).
  Response:
    1. The failsafe cleanup job runs every 60 seconds; it will clear old
       directories immediately if storage pressure is the cause.
    2. If legitimate accumulation: a stuck inference worker is leaving files.
       Kill and restart the stuck worker process.
    3. If disk is genuinely full despite cleanup: increase /tmp partition size.
  Prevention: Alert at 70%, critical at 90%. Automatic cleanup keeps this rare.

14.5 WORKER FAILURE SCENARIOS
───────────────────────────────

  SCENARIO: Inference worker crash mid-task (Tier 1)
  Detection: Celery visibility timeout (60 seconds). Task appears "stale."
  Response (automatic via Celery):
    1. After 60 seconds, task is re-queued.
    2. New worker picks up the task (or same worker after restart).
    3. Worker reads scan record from DB, attempts to find temp file.
    4. If file exists (unlikely after 60s gap): retry inference.
    5. If file gone: update scan status = failed, create failure notification.
  User impact: Scan completion delayed by up to 60 seconds. May result in
    a "failed" scan requiring re-upload (edge case for files deleted by cleanup).

14.6 REGION FAILURE (FUTURE)
──────────────────────────────

  For v1 (single region), region failure is a complete outage. There is no
  automatic failover to another region.

  Preparation for v2 multi-region:
  — PostgreSQL primary in Region A, async streaming replica in Region B.
  — Redis in Region A; no Redis replication (cache is reconstructible).
  — Nginx/load balancer can be redirected to Region B manually.
  — Promotion of Region B replica to primary: pg_promote() command.
  — DNS TTL: 60 seconds (to allow fast regional failover).
  — RPO for region failure: up to 5 seconds of WAL lag (async replication lag).
  — RTO for region failure: < 30 minutes (manual failover procedure).

14.7 RECOVERY WORKFLOW
───────────────────────

  On any Tier 2+ incident:

  Step 1: ASSESS
    — Determine scope: which service is affected, how many users impacted.
    — Check /api/v1/health/detailed (admin-only) for dependency status.

  Step 2: CONTAIN
    — Put the site in maintenance mode (S22 shown to users).
    — Prevent further writes during recovery (stop API workers if needed).

  Step 3: RECOVER
    — Follow the specific scenario runbook (documented in operations runbook).
    — Start restore from the most recent clean backup point.
    — Validate integrity before bringing service back.

  Step 4: RESTORE
    — Bring service back incrementally: health check → read-only mode →
      full write mode.
    — Monitor error rates and latency for 15 minutes after restore.

  Step 5: POST-MORTEM
    — Document timeline, root cause, impact, and corrective actions.
    — Update runbook if the incident revealed gaps.
    — Schedule follow-up task to address root cause.

14.8 RECOVERY PRIORITIES
──────────────────────────

  Recovery priority order (restore in this sequence):
  1. PostgreSQL (source of truth for all user data)
  2. Redis (enables rate limiting, scan status caching, Celery queue)
  3. Inference workers (enables new scan processing)
  4. General workers (email, PDF, notifications — important but not blocking)
  5. API server (becomes available once above are up)
  6. Nginx/ingress (final step; traffic flows once API is confirmed healthy)

SECTION 15 — PERFORMANCE STRATEGY
================================================================================

15.1 READ OPTIMIZATION
────────────────────────

  The VoiceGuard database is read-heavy in normal operation. The most frequent
  read patterns and their optimizations:

  JWT verification (every authenticated request):
    — Stateless: no DB query. O(1) HMAC-SHA256 verification in memory.
    — Only DB read on token refresh (every 15 minutes per session).

  Notification unread count (every page load):
    — Redis cache with 60-second TTL. DB hit only on cache miss.
    — DB query: COUNT with covering index → < 5ms.

  Dashboard stats (frequent, per dashboard load):
    — Redis cache with 5-minute TTL. DB aggregation only on cache miss.
    — DB aggregation at 10,000 scans: < 50ms. Cache keeps it < 1ms.

  Scan result retrieval:
    — Redis job_result cache for 5 minutes. Handles repeated result views.
    — DB query: two-table JOIN on primary keys → < 30ms + TOAST fetch.

  History list:
    — No caching (dynamic filters). Covering index provides < 100ms for page 1.
    — Deep pagination (> page 100): switch to keyset pagination.

15.2 WRITE OPTIMIZATION
────────────────────────

  Write patterns are less frequent than reads but must not block reads:

  Scan completion (concurrent with ongoing polls):
    — Transaction scope: INSERT scan_results + UPDATE scans.status.
    — Both are primary-key targeted writes (no lock contention on other rows).
    — Expected write time: < 10ms.

  Notification creation (post-scan, async):
    — Single INSERT. Async via Celery (not blocking the API response).
    — Expected write time: < 5ms.

  Audit log writes (every security event):
    — Async buffered writes. Not in the same transaction as the business event.
    — If audit log write fails: log to application log only; do not fail the
      business operation. Audit availability is high-priority but not blocking.

  User preference updates:
    — Simple UPDATE by primary key. < 5ms.

  Batch deletes (bulk scan deletion):
    — DELETE WHERE id = ANY({uuid_array}) — PostgreSQL array operator.
    — Up to 100 IDs per request (enforced at API layer).
    — Expected: < 50ms for 100 row deletes + cascade.

15.3 CONNECTION POOLING
────────────────────────

  PostgreSQL connection management:
  — Each uvicorn API worker: SQLAlchemy async connection pool.
    Min connections: 5, Max connections: 20 per API worker.
  — With 4 uvicorn workers: total max connections to PostgreSQL = 80.
  — PostgreSQL max_connections: 100 (default) — leaves 20 connections for
    admin tools, Celery workers, and monitoring.

  pgBouncer (connection pooler — recommended for > 4 API workers):
  — Mode: Transaction pooling (connections returned to pool after each transaction).
  — This allows many uvicorn workers to share a smaller pool of PostgreSQL connections.
  — Configuration: pgBouncer pool_size=20, API workers connect to pgBouncer.
  — Benefits: Reduces PostgreSQL connection overhead; enables horizontal API scaling.

  Celery workers (PostgreSQL connection pools):
  — Each Celery worker process: max 5 PostgreSQL connections.
  — With 2 inference workers + 1 general worker = 15 maximum connections.

  Total maximum PostgreSQL connections at v1 peak: 80 (API) + 15 (Celery) = 95.
  This is within PostgreSQL's default max_connections=100.
  Increase max_connections to 200 (with pgBouncer) when scaling beyond v1 topology.

15.4 PARTITIONING READINESS
─────────────────────────────

  Tables designed for future partitioning (when row counts exceed thresholds):

  scans table (partition when > 5 million rows, estimated 2+ years at medium scale):
    — Partition by: RANGE on created_at (monthly partitions).
    — Benefit: History queries for "last 30 days" only scan recent partitions.
    — Constraint: All indexes must be local to each partition.
    — Migration: Can be done online via pg_partman or manual partition creation.

  audit_logs table (partition IMMEDIATELY for v1 launch — see Section 8.10):
    — Partition by: RANGE on timestamp (monthly partitions).
    — Benefit: Old partition drop instead of slow DELETE for retention management.
    — Immediate value: Audit logs grow at ~5 million rows/year at scale.
    — Recommendation: Create partitioned table from day one; retrofitting is harder.

  scan_results table (partition when frequency_heatmap storage exceeds 50 GB):
    — Partition by: RANGE on created_at (monthly partitions, same as scans).
    — Benefit: Can move old partitions to cheaper tablespace (archive tier).

15.5 ARCHIVING STRATEGY
────────────────────────

  When scans table exceeds 10 million rows (estimated 3–5 years at scale):
  — Move scans older than 2 years to an archive schema (voiceguard_archive).
  — Archive schema uses cheaper storage (HDD vs. SSD for active data).
  — Users can still access old scans; API queries archive schema if not found
    in primary (transparent to users, slight latency increase for old results).
  — scan_results archives must follow scans (data consistency).

  Archiving trigger: Monitor table size monthly. Alert at 5 million rows.
  Plan archive migration at 8 million rows before performance degradation occurs.

15.6 PAGINATION STRATEGY
─────────────────────────

  v1 pagination: LIMIT + OFFSET for pages 1–10.
  v2 pagination: Keyset pagination (cursor-based) for pages > 10.

  Cursor format: An opaque base64-encoded cursor containing {created_at, id}
  of the last item on the previous page. The next page query is:
  WHERE (created_at, id) < ({cursor_created_at}, {cursor_id}) ORDER BY created_at DESC, id DESC LIMIT 20

  Keyset pagination benefits:
  — Constant-time regardless of page number (no OFFSET scan).
  — Consistent results even if new rows are inserted between page requests.

  API backward compatibility: Both cursor and page/offset parameters accepted.
  Frontend uses cursor for subsequent pages after page 1.

15.7 GROWTH ESTIMATES
──────────────────────

  Growth assumptions (conservative estimates):

  Year 1:
    Users: ~50,000 registered
    Scans per day: ~2,000 (40,000/month)
    Total scans: ~500,000
    scan_results storage (with heatmaps @ 200KB each): ~100 GB
    audit_logs: ~5 million rows, ~2.5 GB
    DB total size: ~110 GB

  Year 2:
    Users: ~200,000 registered
    Scans per day: ~10,000
    Total scans: ~4,000,000 (Year 1 + Year 2 accumulation)
    scan_results storage: ~800 GB — TRIGGER for object storage migration
    audit_logs: ~20 million rows, ~10 GB
    DB total size: ~820 GB

  Year 3 (with object storage for heatmaps):
    scan_results without heatmaps: ~15 MB per 100K scans (metadata only)
    DB total size (without heatmaps): ~50 GB
    Object storage: ~2 TB (all heatmaps)

  Key inflection points:
  — 100 GB DB: Review query performance; add read replica if needed.
  — 500 GB DB: Migrate heatmaps to object storage.
  — 5M scan rows: Enable scans table partitioning.
  — 10M scan rows: Enable scan_results table partitioning.

SECTION 16 — SECURITY ARCHITECTURE
================================================================================

16.1 ENCRYPTION AT REST
────────────────────────

  Database encryption at rest:
  — Recommended: PostgreSQL data directory on an encrypted filesystem (LUKS on
    Linux, or cloud provider disk encryption like AWS EBS encryption).
  — Alternative: PostgreSQL pgcrypto extension for column-level encryption
    of the most sensitive fields.
  — For v1: OS-level filesystem encryption is sufficient and easiest to operate.

  Fields requiring column-level encryption (pgcrypto) even if disk is encrypted:
    None required in v1 with filesystem encryption. In v2 (when PCI or HIPAA
    compliance is needed), consider column-level encryption for:
    — users.email (encrypt at column level for PII protection in DB dumps)
    — feedback.description (if PII detection shows users include identifying info)
    — audit_logs.details JSONB (may contain email addresses in event details)

  Redis encryption at rest:
  — Redis data directory on encrypted filesystem (same as PostgreSQL).
  — Redis does not natively support encryption at rest; rely on OS-level.

16.2 ENCRYPTION IN TRANSIT
────────────────────────────

  PostgreSQL connections:
  — ssl = on in postgresql.conf (require SSL for all connections).
  — Self-signed certificate acceptable for internal network; CA-signed for
    connections from external hosts.
  — ssl_min_protocol_version = TLSv1.2 (disable older TLS versions).
  — Connection string: postgresql+asyncpg://user:pass@host:5432/db?ssl=require

  Redis connections:
  — redis+tls:// scheme with certificate verification.
  — Or: restrict Redis to localhost/private network (no external exposure).
    If Redis is on the same host as the API and workers (v1 topology on a single
    VM), TLS is not required (traffic stays on loopback).

  Backup transfer:
  — All backup files transferred over encrypted channels (SSH/SCP or HTTPS to
    object storage with server-side encryption).

16.3 SENSITIVE FIELDS INVENTORY
─────────────────────────────────

  CRITICAL (never logged, never in API responses except where noted):
  — users.password_hash: bcrypt hash. Never returned in any API response.
  — refresh_tokens.token_hash: SHA-256 hash. DB only.
  — email_verifications.token_hash: SHA-256 hash. DB only.
  — password_reset_tokens.token_hash: SHA-256 hash. DB only.
  — api_keys.key_hash: scrypt hash. DB only. Raw key returned once only at creation.

  HIGH (PII, returned to authenticated user only, never to other users):
  — users.email: PII. In JWT payload (encrypted in transit).
  — users.display_name: PII (potentially). Returned in user profile responses.
  — oauth_accounts.provider_email: PII. Internal only (not in API responses).
  — refresh_tokens.user_agent: PII-adjacent. Internal only.
  — refresh_tokens.ip_hash: Hashed; not directly identifying.
  — feedback.contact_email: PII. Admin-only access.
  — audit_logs.ip_hash: Hashed. Admin-only access.
  — audit_logs.user_agent: PII-adjacent. Admin-only access.

  MEDIUM (sensitive context, access-controlled):
  — scan_results.file_hash_sha256: Not PII but reveals file identity.
  — scan_results.frequency_heatmap: AI model output; access controlled by scan ownership.
  — feedback.description: May contain PII if user included identifying info.

  LOW (non-PII, not sensitive beyond scan ownership):
  — scans.original_filename: filename only; access controlled by scan ownership.
  — scan_results.verdict, confidence, scores: computed results; access controlled.
  — notifications.*: internal system messages; access controlled by user ownership.

16.5 DATABASE ROLES AND LEAST PRIVILEGE
─────────────────────────────────────────

  Four distinct database roles with minimum required permissions:

  ROLE: voiceguard_api (used by API server and general Celery workers)
    Permissions:
    — SELECT, INSERT, UPDATE, DELETE on: users, user_preferences, oauth_accounts,
      refresh_tokens, email_verifications, password_reset_tokens, api_keys,
      scans, scan_results, notifications, feedback, help_articles,
      article_feedback, deleted_accounts, model_versions
    — INSERT ONLY on: audit_logs (cannot UPDATE or DELETE audit logs)
    — No access to: pg_catalog tables beyond necessary system functions
    — Cannot: CREATE TABLE, DROP TABLE, ALTER TABLE, TRUNCATE any table

  ROLE: voiceguard_inference (used by inference Celery workers only)
    Permissions:
    — SELECT on: scans (to retrieve file metadata)
    — INSERT on: scan_results
    — UPDATE on: scans (status updates only)
    — INSERT on: audit_logs
    — No access to: users, authentication tables, notifications, feedback, etc.
    Rationale: The inference worker only needs to read the scan, write the result,
    and update the status. Minimal privilege reduces blast radius if the worker
    process is compromised.

  ROLE: voiceguard_readonly (used by monitoring tools, read-only analytics)
    Permissions:
    — SELECT only on all tables.
    — No INSERT, UPDATE, DELETE anywhere.

  ROLE: voiceguard_admin (used by admin tooling and migration scripts)
    Permissions:
    — Full access to all tables (SELECT, INSERT, UPDATE, DELETE, TRUNCATE).
    — ALTER TABLE only during migrations (not in production runtime).
    — CREATE/DROP INDEX for performance management.
    — Not used by the API server at runtime.

  Password management: Each role has a unique, strong (32+ character random)
  password. Passwords stored in secrets manager (not in application code).

16.6 AUDIT TRAILS
──────────────────

  The audit_logs table is the authoritative security audit trail. It is:
  — Written via GRANT INSERT ONLY (no UPDATE, no DELETE) for the API role.
  — Append-only at the application level (the voiceguard_api role cannot UPDATE
    or DELETE audit_logs; only voiceguard_admin can, for anonymization).
  — The database role enforcement provides defense against application bugs that
    might attempt to delete audit records.
  — All admin access to audit_logs (via admin panel) is itself logged as an
    ADMIN_ACTION event.

  Security events that MUST generate audit log entries (from Batch 04 Section 11.9):
    USER_REGISTERED, EMAIL_VERIFIED, LOGIN_SUCCESS, LOGIN_FAILURE,
    LOGOUT, PASSWORD_CHANGED, PASSWORD_RESET_REQUESTED, PASSWORD_RESET_COMPLETED,
    OAUTH_ACCOUNT_LINKED, OAUTH_LOGIN,
    ACCOUNT_DELETION_INITIATED, ACCOUNT_DELETION_CANCELLED, ACCOUNT_PURGED,
    REFRESH_TOKEN_REUSE_DETECTED (HIGH PRIORITY — log immediately, alert on-call),
    API_KEY_CREATED, API_KEY_REVOKED,
    SCAN_SUBMITTED, SCAN_DELETED, SCAN_BULK_DELETED,
    RATE_LIMIT_EXCEEDED,
    ADMIN_ACTION

SECTION 17 — MONITORING STRATEGY
================================================================================

17.1 SLOW QUERY MONITORING
────────────────────────────

  PostgreSQL configuration:
  — log_min_duration_statement = 1000 (log queries taking > 1 second)
  — log_slow_autovacuum_worker = on (log slow autovacuum operations)
  — pg_stat_statements extension: enabled. Tracks cumulative query statistics.

  Slow query analysis:
  — pg_stat_statements: query "SELECT query, total_exec_time, calls, mean_exec_time
    FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 20" weekly.
  — Alert threshold: any query with mean_exec_time > 500ms in pg_stat_statements.
  — Automated alert: log monitoring system parses PostgreSQL log for
    "duration: [N] ms" lines where N > 1000.

  Response to slow queries:
  1. Use EXPLAIN (ANALYZE, BUFFERS) to identify the execution plan.
  2. Check if the expected index is being used.
  3. Check for table bloat (high dead tuple count from frequent UPDATEs).
  4. Run VACUUM ANALYZE on the affected table.
  5. If the slow query is a new access pattern: add a covering index.

17.2 STORAGE MONITORING
────────────────────────

  PostgreSQL disk usage:
  — Monitor per-table size: SELECT pg_size_pretty(pg_total_relation_size(relid))
    FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC.
  — Alert thresholds:
    /tmp partition: Alert at 70%, Critical at 90%
    PostgreSQL data directory: Alert at 70%, Critical at 85%
    Individual table growth: Alert if scan_results grows > 5 GB/week
  — Monitor: Frequency: every 15 minutes (metrics collected by Prometheus).

  scan_results.frequency_heatmap size:
  — This is the primary storage growth driver. Track the average heatmap size.
  — Alert if average heatmap size > 400 KB base64 (approaching 500 KB threshold).
  — Action: Initiate object storage migration planning.

17.3 CONNECTION MONITORING
───────────────────────────

  PostgreSQL connection monitoring:
  — pg_stat_activity: count active/idle/waiting connections per role.
  — Alert if: connections approaching max_connections limit (> 90%).
  — Alert if: connections in "idle in transaction" state for > 30 seconds.
    (These hold locks and can cause cascading slowdowns.)
  — Alert if: connection pool wait time > 100ms (clients waiting for available connection).

  Metrics to emit (Prometheus format):
  — voiceguard_db_connections_total (by state: active, idle, waiting)
  — voiceguard_db_connection_wait_ms (histogram)
  — voiceguard_db_query_duration_ms (histogram, by query type)

17.4 REPLICATION MONITORING
─────────────────────────────

  v1: No replication (single primary). Monitor instead:
  — WAL write latency (time from commit to WAL write to disk).
  — WAL archiving lag (time from WAL segment creation to archive upload).
  — Alert if WAL archiving lag > 5 minutes (backup freshness at risk).

  v2 (when read replica is added):
  — pg_stat_replication: monitor replication lag in bytes and seconds.
  — Alert if replication lag > 60 seconds.
  — Alert if replica disconnects from primary.

17.5 BACKUP MONITORING
───────────────────────

  Backup success monitoring:
  — Each backup job (pg_dump, WAL archiving) emits a success/failure metric.
  — Alert if: Daily pg_dump does not succeed within 6 hours of expected time.
  — Alert if: WAL archiving fails for any 15-minute window.
  — Alert if: Backup storage free space < 20% of backup partition.

  Backup integrity monitoring:
  — Weekly automated restore test (see Section 13.6) emits:
    SUCCESS or FAILURE metric. Alert on FAILURE.
  — Monthly PITR test: manual process; calendar reminder for ops team.

17.6 INTEGRITY CHECKS
──────────────────────

  Scheduled integrity checks (weekly Celery Beat job):

  1. Orphan check: scans with no scan_result after status='complete' for > 1 hour.
     Alert and log scan_ids (indicates lost Celery task result).

  2. Count reconciliation: helpful_yes_count + helpful_no_count in help_articles
     must match COUNT(*) in article_feedback grouped by article and helpful field.
     Alert if discrepancy > 1 (indicates counter increment bug).

  3. Guest scan expiry: Verify no guest scans older than 25 hours remain in DB
     (should have been deleted by hourly cleanup job).
     Alert if any found (indicates cleanup job failure).

  4. Deletion purge check: Verify no users with deletion_purge_at < now() - 1 hour
     still have deletion_purge_at set (should have been purged by daily job).
     Alert if any found (indicates purge job failure).

  5. Token expiry check: Count refresh_tokens WHERE expires_at < now() - 7 days.
     Alert if count > 1000 (indicates cleanup job not running).

17.7 CAPACITY PLANNING
───────────────────────

  Monthly capacity review (automated report):
  — Current DB size vs. 6-month projection (linear regression on growth rate).
  — scan_results.frequency_heatmap column size projection.
  — /tmp partition usage trend.
  — Redis memory usage trend.
  — PostgreSQL connection pool utilization trend.

  Trigger-based scale actions:
  — DB size > 50% of disk: provision additional storage.
  — scan_results > 50 GB: initiate object storage migration planning (90-day lead time).
  — Connection pool utilization > 70% sustained: add API workers, or introduce pgBouncer.
  — Inference queue depth > 20 tasks for > 5 minutes: add inference worker process.

SECTION 18 — DATA QUALITY STRATEGY
================================================================================

18.1 VALIDATION LAYERS
────────────────────────

  LAYER 1 — Frontend (UX prevention; not trusted):
    — File type/size validation before upload.
    — Email format validation before submission.
    — Password strength meter feedback.
    — These prevent wasted round-trips but are NOT security controls.

  LAYER 2 — API (Pydantic; first trusted boundary):
    — Schema validation on all request bodies.
    — Type coercion (string to int, etc.).
    — Maximum length enforcement on all text fields.
    — UUID format validation on all path parameters.
    — Enum validation for all status/type parameters.

  LAYER 3 — Service (business rules):
    — Email uniqueness pre-check before INSERT attempt.
    — Rate limit verification.
    — Scan ownership verification before returning any result.
    — Verdict-score consistency check before scan_result INSERT.

  LAYER 4 — Database (final safety net):
    — NOT NULL constraints on required fields.
    — UNIQUE constraints on natural keys.
    — CHECK constraints on numeric ranges (confidence 0.0–1.0).
    — FOREIGN KEY constraints on all relationship columns.
    — These constraints ensure the database is ALWAYS in a consistent state
      even if layers 1–3 have bugs.

18.2 INTEGRITY CHECKING
─────────────────────────

  See Section 17.6 for scheduled integrity checks.

  On-demand integrity tools:
  — pg_dump | pg_restore --schema-only: verify schema is as expected.
  — SELECT * FROM pg_indexes WHERE tablename = '...': verify expected indexes exist.
  — VACUUM ANALYZE: refresh table statistics for query planner accuracy.
  — pg_stat_user_tables: check for high n_dead_tup (dead tuples from updates).

18.3 DUPLICATE PREVENTION
──────────────────────────

  User duplicates: UNIQUE constraint on users.email. PostgreSQL enforces this
  at the transaction level; no application-level pre-check needed as defense.

  OAuth account duplicates: UNIQUE constraint on (oauth_accounts.provider,
  oauth_accounts.provider_user_id). Prevents the same OAuth identity from being
  linked to two different VoiceGuard accounts.

  Scan result duplicates: UNIQUE constraint on scan_results.scan_id. Prevents
  two result records for the same scan (defensive against worker retry bugs).

  API key hash duplicates: UNIQUE constraint on api_keys.key_hash. Prevents
  two keys from having the same hash (theoretical hash collision).

  Article feedback duplicates: Partial UNIQUE constraint on (article_slug, user_id)
  WHERE user_id IS NOT NULL. Prevents a user from rating the same article twice.

18.4 ORPHAN PREVENTION
────────────────────────

  Orphans (child records with no valid parent) are prevented by:
  — FOREIGN KEY constraints with appropriate ON DELETE behavior on all FKs.
  — Application layer always creates parent before child.
  — Transaction design ensures parent+child inserts are atomic.

  Known intentional non-FK references (not orphanable by design):
  — audit_logs.user_id: stores a UUID that may become "orphaned" when the user
    is purged. This is intentional; audit logs must survive user deletion.
    The user_id value is anonymized (not deleted) on purge.
  — scan_results.model_version: string reference to model_versions. If a model
    version is removed from the reference table, historical scan results retain
    the version string. No orphan in the traditional sense.
  — feedback.user_id: SET NULL on user delete. The feedback row is not orphaned
    (it still exists); its user reference is nullified.

18.5 SCHEMA EVOLUTION STRATEGY
────────────────────────────────

  All schema changes are managed via Alembic (or equivalent migration tool).

  Migration principles:
  1. Every migration is atomic: it succeeds completely or fails completely.
  2. Every migration is idempotent where possible (safe to retry on failure).
  3. Additive-first: prefer adding nullable columns over dropping required columns.
     Dropping a column or changing its type is a breaking change requiring coordination.
  4. Zero-downtime migrations: for production deployments, use expand-contract pattern:
     EXPAND: Add the new column (nullable). Deploy code that reads both old and new.
     MIGRATE: Backfill data. Deploy code that writes to new column.
     CONTRACT: Remove old column. Deploy code that reads only new column.
  5. Never modify existing migrations: create a new migration for any correction.
  6. Test migrations on a production-sized dataset before applying to production.

  Schema version tracking:
  — Alembic migration files are numbered sequentially (e.g., 0001, 0002, ...).
  — Each migration file is committed to source control with a meaningful filename.
  — Migration history is recorded in the alembic_version table (managed by Alembic).

18.6 DATA VERSIONING
──────────────────────

  Entity-level versioning:
  — No event sourcing or full row version history in v1.
  — updated_at timestamp on mutable entities (users, user_preferences) provides
    a last-modified indicator.
  — For audit-critical changes (email, password, role), the change is recorded
    in audit_logs (the audit log IS the version history for those fields).

  Model versioning:
  — scan_results.model_version records which AI model produced each result.
  — This enables future comparison: "re-analyze this scan with the new model."
  — The model_versions table stores metadata about each version.

SECTION 19 — ENGINEERING STANDARDS
================================================================================

19.1 NAMING CONVENTIONS
────────────────────────

  Table names:
  — Plural snake_case nouns: users, scans, scan_results, refresh_tokens.
  — No prefixes or abbreviations. Full descriptive names.
  — Junction tables (M:N): left_entity_right_entity (e.g., api_key_scopes in v2).

  Column names:
  — Singular snake_case. Never camelCase. Never abbreviations.
  — Primary key: always 'id' (not 'user_id' or 'scan_id' on the owning table).
  — Foreign keys: {referenced_table_singular}_{referenced_pk} convention:
    e.g., user_id (FK to users.id), scan_id (FK to scans.id).
  — Boolean columns: verb_phrase starting with 'is_' or 'has_' or descriptive
    adjective: is_shared, email_verified (not verify_email), revoked (not is_revoked
    when the name is already unambiguous), published.
  — Timestamps: action_at suffix: created_at, updated_at, completed_at,
    deleted_at, revoked_at, expires_at, used_at. Never 'timestamp' as a column name.

  Index names:
  — {table}_{column(s)}_{type}: scans_user_id_created_at_btree
  — Unique indexes: {table}_{column}_unique: users_email_unique
  — Partial indexes: {table}_{column}_{condition}_partial: scans_guest_token_notnull_partial

  Enum types:
  — If using PostgreSQL ENUM types: {table}_{column}_enum: scans_status_enum.
  — If using CHECK constraints (preferred for flexibility): document the allowed
    values in the column comment or migration comment.

  Schema names:
  — v1: public (single schema). v2: consider auth, scan, notification schemas.

19.2 IDENTIFIER CONVENTIONS
─────────────────────────────

  Primary keys:
  — Type: UUID v4 (universally unique, random, non-sequential).
  — Generation: application generates UUID before INSERT (using Python's
    uuid.uuid4() or PostgreSQL's gen_random_uuid()). Pre-generation allows
    the application to use the ID in the response before the DB commit.
  — Format: stored as UUID native type in PostgreSQL (not varchar, not bytea).
    PostgreSQL's UUID type is stored as 16 bytes (more efficient than 36-char
    varchar).
  — Why UUID over serial/bigint? UUIDs prevent enumeration attacks (a sequential
    ID reveals that scan #1001 exists when you know #1000 does). UUID also
    supports future sharding without ID conflicts.

  Foreign keys:
  — Same type as referenced PK: UUID.
  — Named {referenced_table_singular}_id: user_id, scan_id, article_slug (exception
    for the help_articles relationship where slug is the natural PK and FK).

  Token identifiers:
  — All tokens stored as SHA-256 hex hashes (64 characters, varchar(64)).
  — Raw tokens are NEVER stored in the database.

19.3 TIMESTAMP CONVENTIONS
────────────────────────────

  All timestamps:
  — Type: timestamptz (timestamp with time zone).
  — Stored in UTC. PostgreSQL timestamptz stores in UTC internally and converts
    on display based on session timezone setting. Always set session timezone to UTC.
  — Precision: microseconds (PostgreSQL default for timestamptz).
  — Never use timestamp (without time zone) — this causes bugs when servers are
    in different timezones or when daylight saving time changes occur.

  Standard timestamp fields on all mutable entities:
  — created_at: set on INSERT, never mutated.
  — updated_at: set on INSERT, updated on every UPDATE. Not managed by DB trigger
    in v1 (application sets it); consider adding a trigger in v2 for correctness.

  Expires_at convention:
  — All expiry timestamps are future timestamps (expires_at > now() while valid).
  — Checked at application layer: if expires_at < now(), the record is expired.
  — DB does NOT auto-delete expired records; cleanup jobs handle deletion.

19.4 MIGRATION PHILOSOPHY
───────────────────────────

  Migrations are first-class production artifacts:
  — Every migration is peer-reviewed before merging.
  — Every migration includes an upgrade function AND a downgrade function
    (for safe rollback if a deployment must be reverted).
  — Downgrade functions are tested on a copy of production data before going live.
  — Never run a migration on production that has not been tested on a
    production-sized dataset in staging.

  Naming: {NNNN}_{descriptive_verb_noun}.py
  Examples:
    0001_create_users_table.py
    0002_add_usage_context_to_users.py
    0003_create_scans_and_results_tables.py
    0042_add_frequency_heatmap_object_storage_url_discriminator.py

  Lock avoidance for large tables:
  — Adding a nullable column: safe (no table lock required in PostgreSQL).
  — Adding a NOT NULL column with a DEFAULT: may lock the table in older PG.
    In PG 11+: safe (stores default in catalog, not in each row).
  — Adding an index: use CREATE INDEX CONCURRENTLY (does not lock the table).
  — Dropping a column: requires ALTER TABLE (brief lock). Schedule for low-traffic.
  — Changing a column type: requires full table rewrite. Use expand-contract.

19.5 DOCUMENTATION STANDARDS
─────────────────────────────

  Column comments:
  — Any non-obvious column has a COMMENT ON COLUMN describing its purpose,
    allowed values, and any behavioral notes.
  — Example: "COMMENT ON COLUMN scans.frequency_heatmap IS 'Base64-encoded PNG of
    Grad-CAM overlay. Starts with data:image for base64, https:// for object storage
    URL. Nullable if Grad-CAM generation failed.'"

  Table comments:
  — Every table has a COMMENT ON TABLE explaining its domain, owner, and key
    design decisions.

  Migration comments:
  — Every migration file begins with a docstring explaining:
    WHAT is changing, WHY it is changing, and any RISKS.

19.6 REVIEW STANDARDS
──────────────────────

  Database change review checklist (for every migration PR):
  □ Every new column has a type, NOT NULL constraint or nullable justification.
  □ Every FK has an explicit ON DELETE behavior defined.
  □ New indexes are justified with a named query pattern.
  □ CREATE INDEX statements use CONCURRENTLY.
  □ Migration has a tested downgrade path.
  □ Sensitive fields are identified and handling is documented.
  □ Migration has been tested on staging with production data volume.
  □ No raw SQL string interpolation (parameterized queries only).
  □ No SELECT * in repository layer (columns explicitly listed).
  □ No N+1 query patterns (joins used instead of per-row sub-queries).

SECTION 20 — DATABASE SELF-AUDIT
================================================================================

20.1 NORMALIZATION AUDIT
─────────────────────────

  FINDING: helpful_yes_count and helpful_no_count in help_articles are
  denormalized. These counts could become inconsistent with the actual
  article_feedback table counts under race conditions or bugs.

  RESOLUTION: Accepted as a deliberate denormalization with mitigations:
  — Weekly reconciliation job verifies counts match article_feedback rows.
  — If mismatch detected: recalculate and correct the counts.
  — This is the only denormalization in the schema. Justified by the
    performance benefit (avoids COUNT aggregation on every article card render).

  FINDING: feedback.model_verdict duplicates data that could be JOIN'd from
  scan_results via feedback.scan_id.

  RESOLUTION: Accepted. The scan may be deleted (scan_id SET NULL), but the
  model_verdict is the core ML data point. Storing it directly in feedback
  ensures the ML training pair (model_verdict, user_verdict) is retained even
  after scan deletion. This is intentional denormalization for data persistence.

20.2 SCALABILITY AUDIT
────────────────────────

  FINDING: scan_results.frequency_heatmap as a large text field in PostgreSQL
  will dominate storage and slow history queries if selected inadvertently.

  RESOLUTION: Strict architectural rule: frequency_heatmap is NEVER included in
  any history list query. Only loaded in full result detail queries. This is
  enforced by the covering index strategy (history queries use indexes that do
  not touch the heap row containing the TOAST field).

  FINDING: audit_logs table will grow without bound if not partitioned.
  At 100 events/minute and 2-year retention: ~100 million rows.

  RESOLUTION: Partition audit_logs by timestamp (monthly RANGE partitioning)
  from day one. Monthly partitions can be dropped atomically when they age
  out of the 2-year retention window. This is listed as a day-one requirement,
  not a v2 enhancement.

  FINDING: Dashboard statistics query (COUNT aggregation over all user scans)
  becomes slow as scan count grows past 100,000 per user.

  RESOLUTION: Redis cache with 5-minute TTL. Cache invalidated on new scan
  completion. For the highest-volume users, a pre-computed stats table (summary
  table updated by the scan completion handler) should be introduced in v2.

  FINDING: Deep pagination (page 500+ of history) with OFFSET is O(N) in offset.

  RESOLUTION: Keyset pagination for pages > 10 (see Section 15.6). API supports
  both cursor and offset modes; cursor mode is encouraged for history navigation.

20.3 MISSING INDEX AUDIT
─────────────────────────

  FINDING: feedback.ip_hash has no index. Abuse investigation queries ("find
  all feedback from IP hash X") would require a full table scan.

  RESOLUTION: Add index on feedback.ip_hash. The feedback table is small (< 100K
  rows) so this is low-priority but should be added for operational use.

  FINDING: notifications.scan_id has no index. Queries to find notifications
  for a specific scan (admin, or scan deletion cleanup) require a seqscan.

  RESOLUTION: Add index on notifications.scan_id WHERE scan_id IS NOT NULL.
  Partial index because most notifications may not have a scan_id.

  FINDING: deleted_accounts.email_hash has no index. Re-registration check
  requires a full table scan on deleted_accounts.

  RESOLUTION: Add unique index on deleted_accounts.email_hash. Makes the
  re-registration check O(log n) and also enforces the one-record-per-email rule.

  [All three findings above have been incorporated into the Section 8 Index Strategy.
  They are listed here for traceability — they were found during the audit and fixed.]

20.4 SECURITY WEAKNESS AUDIT
──────────────────────────────

  FINDING: audit_logs.user_id is a plain UUID column (not a FK). This is intentional
  but means there is no type-level guarantee that the UUID corresponds to a valid user.

  RESOLUTION: Accepted by design. The alternative (FK with SET NULL on delete)
  would null out the audit entry's user reference on purge, losing the
  causal link between the audit event and its actor. The anonymization approach
  (replace with hash) preserves causality while removing PII. Document clearly.

  FINDING: The discriminator pattern in scan_results.frequency_heatmap
  (base64 vs. URL based on string prefix) is fragile — a bug could write an
  invalid discriminator value.

  RESOLUTION: Add a CHECK constraint that the column value either starts with
  'data:image', starts with 'https://', or is NULL. This prevents invalid
  discriminator values from being stored.

  FINDING: oauth_accounts does not enforce that a user with password_hash=NULL
  has at least one OAuth account. A corruption scenario could create a user
  with no login method.

  RESOLUTION: Add an application-layer invariant check at user creation and
  at account management operations. Additionally, create a scheduled integrity
  job that alerts on users with password_hash=NULL and zero oauth_accounts rows.
  The DB cannot express this constraint natively (it requires a cross-table check).

  FINDING: Multiple refresh tokens per user are permitted but there is no limit.
  A bug could create thousands of token rows per user.

  RESOLUTION: Add an application-layer check before INSERT: if the user already
  has more than 20 non-revoked, non-expired refresh tokens, revoke the oldest
  before creating a new one. Log this event as a WARNING (unusual session count
  may indicate an active session creation attack or a token rotation bug).

20.5 RETENTION GAPS AUDIT
───────────────────────────

  FINDING: article_feedback has no retention policy. A help article can accumulate
  unlimited ratings over years with no cleanup.

  RESOLUTION: Accepted — article_feedback rows are tiny (~100 bytes each) and
  provide valuable data. No retention limit. If volume becomes problematic
  (> 1 million rows), add a policy to keep only the most recent 100,000 ratings
  per article. Not required for v1.

  FINDING: model_versions has no retention policy.

  RESOLUTION: model_versions is a tiny reference table (< 10 rows). Permanent
  retention is appropriate. No cleanup needed.

  FINDING: deleted_accounts retention is 60 days, but the user data is purged
  after 30 days. This creates a 30-day window where the deleted_accounts row
  exists but the user record does not.

  RESOLUTION: This is by design. The email_hash in deleted_accounts serves as
  a block on re-registration with the recently-deleted email for 60 days
  (30 days recovery window + 30 days additional block). The gap is intentional.
  Document this clearly in the deleted_accounts table comment.

20.6 BACKUP RISK AUDIT
───────────────────────

  FINDING: Without WAL archiving, a crash between daily pg_dump backups could
  result in up to 24 hours of data loss.

  RESOLUTION: WAL continuous archiving is REQUIRED from day one (RPO < 1 hour).
  pg_dump is a secondary backup, not the primary.

  FINDING: Redis backup (AOF) is recommended but not strictly required in the
  current design (Redis is a cache). If a Celery task is in-flight when Redis
  crashes WITHOUT AOF, the task is lost and the scan status may be "processing"
  indefinitely.

  RESOLUTION: Enable Redis AOF with fsync=everysec for Celery broker durability.
  Add a failsafe in the scan lifecycle: scans with status='processing' for more
  than 60 seconds are re-queued by the Celery visibility timeout mechanism.
  The 60-second visibility timeout provides additional protection beyond AOF.

20.7 DATA INTEGRITY RISK AUDIT
────────────────────────────────

  FINDING: scan_results is written by the Celery inference worker. If the worker
  writes the scan_result but the subsequent UPDATE of scans.status fails
  (network timeout to DB, for example), the scan_result exists but the scan
  status is still 'processing'. Subsequent polls return 'processing', but the
  result EXISTS in the DB. The user's UI is stuck on the processing screen.

  RESOLUTION: The scan completion transaction wraps both writes in a single
  transaction (INSERT scan_results + UPDATE scans.status). If the transaction
  fails, both operations roll back. The Celery task retries the entire operation.
  This is documented in Section 10.6 (Transaction Design). The risk is mitigated
  by keeping both writes in the same transaction.

  FINDING: View count (scans.view_count) is incremented via fire-and-forget UPDATE.
  Under high concurrency (viral shared scan), multiple increments can conflict.

  RESOLUTION: Use PostgreSQL's atomic increment (UPDATE scans SET view_count =
  view_count + 1 WHERE id = X). PostgreSQL's MVCC handles concurrent increments
  correctly (last write wins for each increment; all increments are applied).
  No risk of lost increments under normal PostgreSQL MVCC behavior.
  This is not a critical data field; minor inconsistency under extreme concurrency
  is acceptable.

20.8 PERFORMANCE BOTTLENECK AUDIT
────────────────────────────────────

  FINDING: The scan completion event triggers: INSERT scan_results, UPDATE scans,
  cache invalidation in Redis (stats, notif_count), notification creation,
  and temp file deletion — all synchronously in the Celery worker task.

  RESOLUTION: The INSERT + UPDATE are in one DB transaction (correct and fast).
  Redis cache invalidations are out-of-transaction (fire-and-forget). Notification
  creation is dispatched as a separate Celery task (async). Temp file deletion
  is async filesystem operation. The only synchronous blocking operations in
  the DB are the two writes in the transaction. Total estimated time: < 50ms
  for the DB transaction. Acceptable.

  FINDING: User data export (GDPR Article 20) requires reading all scans,
  scan_results, notifications, and feedback for a user. For a user with 10,000
  scans and 100,000 notification rows, this is a large read operation.

  RESOLUTION: Data export is a Celery general worker task (async). It is never
  done in an API request. The export streams data in batches (1,000 rows at a time)
  to avoid loading the entire history into memory. The result is written to a
  temporary file (not in the audio /tmp directory) and emailed or provided as a
  timed download link. Estimated export time for 10,000 scans: < 60 seconds.

SECTION 21 — RISKS & MITIGATIONS
================================================================================

RISK 1 — Grad-CAM heatmap storage dominates database size
  Likelihood: HIGH (certain to occur at scale)
  Impact: HIGH (query performance, storage cost, backup size)
  Timeline: Estimated at Year 2 (500,000+ scans)
  Mitigation:
  — Monitor scan_results storage monthly.
  — Design object storage migration path from day one (discriminator pattern).
  — Set alert at 50 GB total scan_results size.
  — Execute migration to object storage before the 50 GB threshold.
  Residual risk: LOW (migration path is designed; execution is the only remaining work).

RISK 2 — Refresh token rotation reuse attack causes false positive logouts
  Likelihood: LOW (requires exact simultaneous token rotation from two tabs)
  Impact: MEDIUM (user is logged out; must re-login)
  Mitigation:
  — The SELECT FOR UPDATE pessimistic lock ensures only one rotation succeeds.
  — The second request sees revoked=true and triggers reuse handler (all tokens revoked).
  — While aggressive (both tabs lose access), it is the correct security response.
  — Document in user-facing FAQ: "If you are logged out unexpectedly, please log
    back in. This may be caused by using multiple browser tabs simultaneously."
  Residual risk: LOW (behavior is correct; only UX impact, not security gap).

RISK 3 — Guest scan migration race condition
  Likelihood: LOW (requires simultaneous migration triggers)
  Impact: MEDIUM (duplicate scans assigned to user)
  Mitigation:
  — SELECT FOR UPDATE on guest scan rows during migration transaction.
  — At most one migration per guest_token per run (atomic UPDATE + notification).
  Residual risk: LOW.

RISK 4 — PostgreSQL connection pool exhaustion under traffic spike
  Likelihood: MEDIUM (traffic spikes are expected at product launch)
  Impact: HIGH (API returns 503 when connection pool is exhausted)
  Mitigation:
  — Deploy pgBouncer from day one (transaction pooling mode).
  — Monitor pool utilization; alert at 70%.
  — Horizontal API scaling does not increase PostgreSQL connections with pgBouncer.
  Residual risk: LOW with pgBouncer; MEDIUM without.

RISK 5 — Audit log table becomes a performance bottleneck
  Likelihood: MEDIUM (high write volume, especially under attack scenarios)
  Impact: MEDIUM (slower API responses if audit write is in-request critical path)
  Mitigation:
  — Audit writes are ASYNC (not in the same transaction as business events).
  — Partition audit_logs from day one (monthly RANGE partitions).
  — Write to a buffered async queue; flush to DB in micro-batches.
  Residual risk: LOW.

RISK 6 — Feedback table accumulates PII inadvertently
  Likelihood: MEDIUM (users may include names, email addresses, audio file
    descriptions in feedback text fields)
  Impact: MEDIUM (GDPR right-to-erasure may require content review)
  Mitigation:
  — Add feedback.is_redacted boolean and redacted_description fields (design now,
    implement in v1.1).
  — When user requests account deletion: scan their feedback records for any
    descriptions containing their email address; auto-redact if found.
  — Admin interface allows manual redaction for escalated cases.
  Residual risk: LOW (redaction capability designed from the start).

RISK 7 — Single-region deployment (v1) creates total outage risk
  Likelihood: LOW (data center outages are rare)
  Impact: CRITICAL (complete service unavailability)
  Mitigation:
  — Geographic backup copies reduce data loss risk.
  — Documented recovery procedure targets < 4 hour RTO.
  — Status page updated immediately on outage detection.
  — Multi-region deployment planned for v2 as the product grows.
  Residual risk: MEDIUM (unavoidable for single-region v1).

RISK 8 — scans.original_filename used in PDF reports could expose path traversal
  Likelihood: LOW (filename is sanitized at upload; only stored for display)
  Impact: LOW (filename is display-only; never used as a file path)
  Mitigation:
  — The original_filename is sanitized at service layer before DB insert.
  — It is used ONLY for display in history, result page, and PDF.
  — The actual temp file path is {scan_id}/audio.{extension} — never derived
    from original_filename.
  Residual risk: NEGLIGIBLE.

RISK 9 — model_versions table string reference from scan_results creates implicit
  coupling that could drift
  Likelihood: LOW
  Impact: LOW (historical scans show an unknown model version string)
  Mitigation:
  — Enforce that model_version string in inference config exactly matches a
    model_versions.version_string row at worker startup.
  — Worker health check fails if model_version not found in model_versions table.
  Residual risk: LOW.

RISK 10 — Data export job loads large history into memory for high-volume users
  Likelihood: LOW (most users have < 1,000 scans)
  Impact: MEDIUM (memory spike in general Celery worker)
  Mitigation:
  — Stream export in batches (1,000 rows per iteration).
  — Set a soft cap on export payload size (100,000 scans maximum per export).
    Users with more scans receive a paginated export with multiple files.
  Residual risk: LOW.

SECTION 22 — FINAL RECOMMENDATIONS
================================================================================

22.1 IMPLEMENT THESE ON DAY ONE (NON-NEGOTIABLE)
──────────────────────────────────────────────────

  REC-01: Partition audit_logs from launch.
    Do not create audit_logs as a plain table. Create it with monthly RANGE
    partitioning from the first migration. Retrofitting partitioning on a large
    table later is expensive and risky. This is a structural decision that is
    trivially cheap to make at launch and extremely expensive to make later.

  REC-02: Enable WAL archiving from launch.
    PostgreSQL continuous archiving with pg_basebackup is the backup foundation.
    Daily pg_dump alone (RPO = 24 hours) is insufficient for a production system
    where users generate scans throughout the day. Enable WAL archiving before
    the first real user data is written.

  REC-03: Deploy pgBouncer from launch.
    Connection pooling at the proxy layer protects PostgreSQL from connection
    exhaustion under traffic spikes. Adding pgBouncer retroactively requires
    a connection string change in all services. Do it right from launch.

  REC-04: Set the four database roles from migration 0001.
    voiceguard_api, voiceguard_inference, voiceguard_readonly, voiceguard_admin.
    The inference worker must use the minimal voiceguard_inference role.
    Role separation cannot be retroactively added safely (requires coordinated
    secret rotation across all services).

  REC-05: Enable Redis AOF with fsync=everysec from launch.
    Celery task durability depends on this. Without AOF, a Redis crash during
    active inference operations loses in-flight tasks permanently.

  REC-06: Add the CHECK constraint on scan_results.frequency_heatmap discriminator.
    Ensures the column value is always a valid discriminator ('data:image',
    'https://', or NULL). Prevents invalid values that would break object
    storage migration tooling.

22.2 IMPLEMENT BY v1.1 (30 DAYS POST-LAUNCH)
──────────────────────────────────────────────

  REC-07: Add feedback.is_redacted and feedback.redacted_description columns.
    User GDPR erasure requests may require content redaction. These columns
    enable redaction without row deletion. Needed before the first GDPR request.

  REC-08: Implement the automated restore test (weekly pg_dump restore).
    Until a restore test has succeeded, the backup strategy is theoretical.
    Set up the automated restore testing framework within 30 days of launch.

  REC-09: Add the scan_results table size alert (50 GB threshold).
    Monitor and alert before the object storage migration becomes urgent. Growth
    rate data collected in the first 30 days will inform the timeline.

  REC-10: Implement keyset pagination for history API.
    Page 1 is fast with OFFSET pagination. Pages 50+ are slow. Users with large
    histories will hit this within weeks of launch if they're power users.

22.3 DESIGN FOR v2 (6 MONTHS POST-LAUNCH)
────────────────────────────────────────────

  REC-11: Object storage migration for Grad-CAM heatmaps.
    The discriminator pattern is already in place. Execute the migration when
    scan_results exceeds 50 GB. Write the migration job before it is urgently
    needed.

  REC-12: PostgreSQL read replica.
    Add a read replica when history query latency exceeds 200ms p95 under load.
    Read replicas serve history and dashboard queries, freeing the primary for writes.

  REC-13: Data warehouse for analytics.
    ClickHouse or BigQuery for product analytics and ML pipeline data.
    Required before batch ML model retraining (needed for v2 AASIST model).

  REC-14: Redis Sentinel or Redis Cluster.
    Automatic Redis failover eliminates the manual restart step and reduces
    Redis failure RTO from 2 minutes to < 30 seconds.

  REC-15: Team workspace schema design.
    When team workspaces are introduced (v2 feature, Batch 01 roadmap), the
    most significant schema change is adding a teams table and a team_members
    junction table. Plan these changes now (they do not require schema changes
    today, but the architecture must be aware of the upcoming 1:N expansion:
    a user will belong to multiple teams; a scan may belong to a team workspace).

22.4 ARCHITECTURAL INVARIANTS (NEVER VIOLATE THESE)
────────────────────────────────────────────────────

  INVARIANT-01: Audio files are NEVER written to any persistent storage.
    Only /tmp/voiceguard/{scan_id}/ with 60-second TTL. This is the product's
    core privacy promise. No object storage for audio. No backup of audio.

  INVARIANT-02: frequency_heatmap is NEVER included in history list queries.
    Only in full result detail queries. This is the primary query optimization
    rule for the database. Violating this causes TOAST I/O on every history
    page load, which will degrade performance catastrophically at scale.

  INVARIANT-03: Audit logs are append-only at the role level.
    voiceguard_api has INSERT only on audit_logs. No UPDATE, no DELETE.
    The only mutation is user_id anonymization by voiceguard_admin during purge.

  INVARIANT-04: All timestamps are timestamptz (UTC-aware).
    Never timestamp (without timezone). Any violation causes subtle bugs during
    daylight saving time transitions and multi-timezone team operations.

  INVARIANT-05: All foreign key ON DELETE behaviors are explicitly defined.
    Never rely on the default (RESTRICT/NO ACTION). Every FK specifies CASCADE,
    SET NULL, or SET DEFAULT — chosen based on the domain logic, not convention.

  INVARIANT-06: scans.user_id and scans.guest_token are mutually exclusive.
    Exactly one is non-null; the other is null. This invariant is enforced at
    the application service layer on every scan creation call. Violation would
    create unownable or doubly-owned scans.

  INVARIANT-07: scan_results is immutable after creation.
    The inference worker writes the result once. No application path updates
    a scan_result. If a re-analysis is needed (v2 feature), a new scan and new
    scan_result are created.

22.5 DECISION LOG
──────────────────

  DECISION: UUID v4 over BIGSERIAL for primary keys.
  RATIONALE: Security (prevents enumeration), future sharding support, and
    consistency with the FastAPI backend which uses UUID throughout.
  TRADE-OFF: Slightly larger index size (16 bytes vs 8 bytes per UUID);
    random insertion pattern causes more index page splits than sequential IDs.
    Acceptable at v1 scale; B-tree UUIDs are well-studied in PostgreSQL.

  DECISION: Single PostgreSQL database (no schema separation) for v1.
  RATIONALE: Simpler connection management; all modules use the same connection
    pool. Schema separation adds complexity (connection routing) with no
    performance benefit at v1 scale.
  TRADE-OFF: Module boundaries enforced by application layer only, not by
    database-level schema permissions. Addressed by the four database roles.

  DECISION: Heatmap stored as base64 text in PostgreSQL, not as a file in v1.
  RATIONALE: Eliminates object storage dependency for v1. Faster development.
    Sufficient for first 100,000 scans.
  TRADE-OFF: TOAST storage overhead; must NEVER select heatmap in list queries.
    Migration path (discriminator pattern) ensures zero-downtime upgrade to v2.

  DECISION: guest_token stored as a column on scans, not in a guest_sessions table.
  RATIONALE: Simplifies guest data model. No TTL management table needed.
    Cleanup by column value is simple. Guest sessions have no metadata beyond
    the token itself (no IP binding, no device info required for v1).
  TRADE-OFF: Cannot query "all scans for a guest across multiple tokens"
    (guests have one token per browser session; this is not a use case).

  DECISION: Feedback is permanently retained even after user deletion.
  RATIONALE: Feedback records are the primary ML correction dataset. Each record
    is a (model_verdict, user_verdict) pair that is irreplaceable training data.
    Deleting feedback on account purge would destroy valuable model improvement signals.
  TRADE-OFF: Feedback may contain user-written PII in the description field.
    Mitigated by the redaction mechanism (REC-07).

  DECISION: Notifications have 90-day retention (not indefinite).
  RATIONALE: Notifications are transient system messages, not permanent records.
    After 90 days, a "Your scan is complete" notification from 3 months ago has
    no value. Bounded retention controls table size growth.
  TRADE-OFF: Users cannot view notifications older than 90 days.
    Acceptable: Batch 01 does not specify notification history beyond the notification
    center UI, which naturally shows recent items.
