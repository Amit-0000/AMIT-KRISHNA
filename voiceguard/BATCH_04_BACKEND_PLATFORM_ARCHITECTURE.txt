SECTION 1: EXECUTIVE SUMMARY
================================================================================

1.1 WHAT THIS DOCUMENT IS
──────────────────────────
This document is the definitive backend architecture specification for the
VoiceGuard audio deepfake detection platform. It defines every architectural
decision a backend engineering team needs to begin implementation: module
boundaries, service responsibilities, data flow contracts, API surface, security
posture, infrastructure topology, and operational concerns.

This document does NOT contain Python, FastAPI code, SQL schemas, or any
implementation artifact. Those belong in the implementation phase. Architecture
decisions made here must be followed exactly; implementation details within those
decisions are left to the engineering team.

1.2 PLATFORM SUMMARY
─────────────────────
VoiceGuard is a web-based platform that accepts audio file uploads, runs them
through an LCNN (Light CNN) model trained on ASVspoof 2019 LA, and returns a
three-state verdict: Human, AI-Generated, or Uncertain. The platform supports
anonymous (guest) sessions, authenticated user accounts, scan history, PDF report
generation, and administrative oversight.

The backend is the trust boundary. All security, validation, rate limiting, and
ML inference happen exclusively on the server. The frontend is untrusted.

1.3 KEY ARCHITECTURAL DECISIONS (SUMMARY)
───────────────────────────────────────────
Decision 1: Monorepo, modular monolith architecture for v1.
  Rationale: Complexity of microservices is unwarranted at initial scale. Module
  boundaries are clean enough to extract later if needed. Shared auth context,
  shared DB connection pool, and shared configuration are simpler inside a single
  process. The inference pipeline is isolated behind an internal service boundary
  that can be promoted to a separate service in v2.

Decision 2: FastAPI as the web framework.
  Rationale: Async-native, type-annotated, OpenAPI generation built-in, excellent
  Python ecosystem integration, Pydantic validation. Aligns with the ML Python
  ecosystem for LCNN inference.

Decision 3: PostgreSQL as primary data store.
  Rationale: ACID guarantees for user data and scan metadata. JSON column support
  for flexible AI output storage. Row-level security capability for multi-tenant
  isolation. Strong ecosystem tooling.

Decision 4: Redis for session state, rate limiting, task queue state, and caching.
  Rationale: Sub-millisecond access for rate limit counters. Pub/Sub for real-time
  scan status delivery. Atomic increment operations for counters. TTL-native for
  guest session expiry.

Decision 5: Celery + Redis broker for async inference jobs.
  Rationale: Decouples HTTP request lifecycle from ML inference time. Supports
  retry logic, dead letter queues, and worker scaling independent of the API tier.

Decision 6: All file processing in ephemeral tmp storage only.
  Rationale: Audio is NEVER stored permanently. Batch 01 security constraint.
  Temp files are deleted within 60 seconds of scan completion or failure.

Decision 7: JWT with HttpOnly cookies, not localStorage.
  Rationale: Batch 01 security constraint. XSS cannot steal HttpOnly cookies.
  CSRF mitigation via SameSite=Strict and CSRF token double-submit pattern.

Decision 8: Inference runs in a single dedicated Celery worker pool.
  Rationale: LCNN model is loaded once into worker process memory. This avoids
  repeated model load latency (cold start). Workers scale horizontally via
  additional worker processes, not threads.

1.4 PERFORMANCE TARGETS (FROM BATCH 01 — MUST BE MET)
───────────────────────────────────────────────────────
  - Scan submission → result render: < 10 seconds end-to-end
  - API response (inference only): < 5 seconds p95
  - PDF report generation: < 3 seconds
  - History page load (50 records): < 1.5 seconds
  - App shell render after auth: < 500ms
  - Rate limits: 10 scans/hour per guest IP; 50 scans/day per account

1.5 SECURITY NON-NEGOTIABLES (FROM BATCH 01 — ALL ENFORCED)
─────────────────────────────────────────────────────────────
  - JWT in HttpOnly cookies, not localStorage
  - bcrypt password hashing with enforced entropy
  - Refresh token rotation on every use
  - HTTPS enforced; HTTP → HTTPS redirect
  - CORS explicit allowlist; no wildcard origins
  - Magic bytes file validation before any parsing
  - Max 10MB file upload
  - Temp files deleted within 60 seconds
  - API keys scrypt-hashed; shown only once at creation
  - All user input validated server-side
  - Content Security Policy: strict, no inline scripts
  - OAuth PKCE flow with state parameter; no implicit flow
  - Audio NEVER stored permanently

SECTION 2: BACKEND VISION & PHILOSOPHY
================================================================================

2.1 ARCHITECTURAL PHILOSOPHY
──────────────────────────────
The VoiceGuard backend is built on five principles:

PRINCIPLE 1 — TRUST NOTHING FROM THE CLIENT
  Every piece of data arriving over the wire is treated as adversarial input.
  File MIME types claimed by the client are ignored; magic bytes are read from
  the file itself. JWTs are verified, never decoded without verification. Rate
  limits apply regardless of authentication status. This is not paranoia—it is
  the minimum correct posture for a security-critical product.

PRINCIPLE 2 — EPHEMERAL DATA IS AN ASSET, NOT A LIABILITY
  Audio files exist on disk for at most 60 seconds. This is not a technical
  shortcut; it is a product privacy guarantee and a security boundary. Building
  the entire upload and inference pipeline around ephemeral temp files means
  there is no persistent audio to breach, no GDPR retention headache for audio,
  and no storage cost for audio at scale.

PRINCIPLE 3 — THE INFERENCE PIPELINE IS A BLACK BOX TO THE API LAYER
  From the perspective of the API router, submitting a scan and receiving a result
  is a job queue interaction. The router submits a job and returns a job ID. The
  frontend polls a status endpoint. The inference pipeline is entirely behind a
  Celery task boundary. This means the ML model, Grad-CAM computation, and
  feature extraction can change independently without touching the API surface.

PRINCIPLE 4 — MODULES OWN THEIR DOMAIN, NOTHING ELSE
  Each backend module owns its database tables, its business logic, its API
  routes, and its service layer. No module reaches into another module's data
  layer directly. Cross-module interactions happen via well-defined service
  function calls or events. This is the foundation that enables future extraction
  into microservices if scale demands it.

PRINCIPLE 5 — OBSERVABILITY IS A FIRST-CLASS FEATURE
  Every request is traced. Every inference job is timed. Every error is
  structured and queryable. From day one, the backend emits structured JSON logs
  at every meaningful boundary. Metrics are emitted for every API endpoint,
  every Celery task, and every external dependency call. An operator can
  diagnose a production incident from logs alone.

2.2 WHAT THE BACKEND IS RESPONSIBLE FOR
─────────────────────────────────────────
  - All authentication and session management
  - All authorization (what this user is allowed to do)
  - File receipt, validation, and ephemeral storage

3.2 PROCESS MODEL
──────────────────

  PROCESS 1: API Server (uvicorn + FastAPI)
    - Multiple workers (recommended: 4 per CPU core, adjust by load)
    - Async event loop per worker
    - Shares nothing between workers except external state (DB, Redis)
    - Handles all HTTP request/response lifecycle
    - Does NOT run inference (hands off to Celery)
    - Does NOT generate PDF (hands off to Celery)
    - Does NOT send email (hands off to Celery)

  PROCESS 2: Celery Inference Workers
    - Dedicated worker pool: queue name "inference"
    - Concurrency: 1 task per worker process (ML model is CPU/GPU-bound)
    - Workers are pre-loaded: model loaded at startup, not per-task
    - Restart policy: restart on OOM; do not share between queues
    - Number of workers: determined by hardware; start with 2 on standard VM

  PROCESS 3: Celery General Workers
    - Queue name: "general"
    - Handles: email dispatch, PDF generation, notification creation, cleanup tasks
    - Concurrency: 4 per worker process (IO-bound tasks)
    - Separate from inference workers to prevent inference starvation

  PROCESS 4: Celery Beat (Scheduler)
    - Single instance
    - Responsible for: periodic cleanup of expired temp files, guest session
      expiry sweeps, soft-delete purge after 30 days, digest notification dispatch

  PROCESS 5: Redis
    - Session store (keys prefixed: session:)
    - Rate limit counters (keys prefixed: rl:)
    - Celery broker (Celery manages its own key namespace)
    - Scan status pub/sub channel (channel: scan_status:{scan_id})
    - Job result short-term cache (keys prefixed: job_result:, TTL: 300s)

  PROCESS 6: PostgreSQL
    - Primary read/write for all persistent data
    - No replica required for v1 (add read replica when history queries degrade)
    - Connection pooling via pgBouncer recommended for > 100 concurrent API workers

3.3 NETWORK CONTRACTS
──────────────────────

  External boundary (client ↔ Nginx):
    - Protocol: HTTPS/TLS 1.2+
    - Certificate: Let's Encrypt or provided TLS cert
    - HTTP connections: 301 redirect to HTTPS
    - Max request body: 10MB (enforced at Nginx level, also at FastAPI level)

  Internal boundary (Nginx ↔ FastAPI):
    - Protocol: HTTP (internal network, no TLS needed)
    - Nginx passes X-Forwarded-For, X-Forwarded-Proto, X-Real-IP headers
    - FastAPI trusts these headers for rate limiting IP extraction

  API ↔ PostgreSQL:
    - Connection pool: min 5, max 20 connections per API worker
    - Connection timeout: 5 seconds
    - Query timeout: 30 seconds (enforced at application level)
    - SSL: required in production

  API ↔ Redis:
    - Connection pool: min 2, max 10 per API worker
    - Connection timeout: 1 second
    - Command timeout: 500ms (rate limit operations must be sub-ms)
    - AUTH password required in production

  API ↔ Celery (via Redis broker):
    - Task publish: fire-and-forget from API perspective
    - Result retrieval: polling via scan status endpoint, not direct Celery result
      backend query (decouple from Celery internals)

3.4 DEPLOYMENT TOPOLOGY (V1 — SINGLE REGION)
──────────────────────────────────────────────

  Minimum production topology:

  VM-1 (API Server):
    - Nginx (port 80/443)
    - FastAPI app server (4 uvicorn workers, port 8000)
    - 4 vCPU, 8GB RAM recommended

  VM-2 (Workers):
    - Celery inference worker pool (2 processes, queue: inference)
    - Celery general worker pool (1 process, 4 concurrency, queue: general)
    - Celery Beat scheduler (1 process)
    - 4 vCPU, 16GB RAM (model must fit in RAM; LCNN is small at ~2.8MB)

  VM-3 (Data):
    - PostgreSQL 15+
    - Redis 7+
    - 2 vCPU, 8GB RAM

  Minimum staging topology: single VM running all processes (dev/staging)

  For scaling: see Section 16.

SECTION 4: MODULE ARCHITECTURE
================================================================================

4.1 MODULE OVERVIEW
─────────────────────
The backend is organized as a modular monolith. Each module is a Python package
with a defined internal structure. Modules communicate only through their public
service interfaces, never through direct database queries into another module's
tables.

  modules/
  ├── auth/              — Authentication, sessions, OAuth, JWT management
  ├── scan/              — Upload handling, job dispatch, result retrieval
  ├── inference/         — LCNN model loading, inference, Grad-CAM
  ├── user/              — User profile, preferences, API keys, soft delete
  ├── history/           — Scan history queries, filtering, pagination
  ├── notification/      — Notification CRUD, delivery, read state
  ├── report/            — PDF generation for scan reports
  ├── feedback/          — User feedback submission and storage
  ├── help/              — Help article storage and retrieval
  ├── admin/             — Admin-only endpoints and data access
  └── core/              — Shared infrastructure (DB, Redis, config, middleware)

4.2 MODULE INTERNAL STRUCTURE
───────────────────────────────
Every module follows this identical internal structure:

  {module}/
  ├── __init__.py         — Public interface. Only exports service functions.
  ├── router.py           — FastAPI router. Routes only; no business logic.
  ├── service.py          — Business logic. Calls repository; calls other services.
  ├── repository.py       — Database access. All SQL/ORM queries live here.
  ├── schemas.py          — Pydantic request/response models for this module.
  ├── models.py           — ORM model definitions for this module's tables.
  ├── tasks.py            — Celery task definitions owned by this module.
  ├── exceptions.py       — Module-specific exception classes.
  └── tests/
      ├── test_router.py
      ├── test_service.py
      └── test_repository.py

Enforcement rules:
  - router.py imports ONLY from service.py and schemas.py (never repository.py)
  - service.py imports ONLY from repository.py, exceptions.py, and other modules'
    __init__.py exports
  - repository.py imports ONLY from models.py and core/database.py
  - No circular imports. If A depends on B and B depends on A, extract shared
    logic to core/ or create a third module.

4.3 MODULE RESPONSIBILITIES
────────────────────────────

MODULE: report

MODULE: feedback

MODULE: help

MODULE: admin

  Public interface:

    - get_user_detail(user_id) → AdminUserDetail

MODULE: core
  Owns: Shared infrastructure used by all modules

    - middleware.py      — All middleware implementations
    - security.py        — JWT utilities, password hashing utilities

    - health.py          — Health check endpoint implementations

SECTION 5: SERVICE ARCHITECTURE
================================================================================

5.1 SERVICE LAYER PATTERN
───────────────────────────
The service layer is where all business logic lives. It sits between the router
(which handles HTTP protocol concerns) and the repository (which handles database
concerns). The service layer is the only layer that knows about business rules.

Each service follows these constraints:
  - Services are stateless functions (or thin classes with no instance state)
  - Services call repositories to read/write data
  - Services call other modules' public service interfaces for cross-module logic
  - Services publish Celery tasks but do NOT await them
  - Services raise module-specific exceptions on business rule violations
  - Services never return database ORM objects to the router; they return schemas

5.2 SCAN SERVICE (MOST COMPLEX — DETAILED)
───────────────────────────────────────────

OPERATION: create_scan

  Input: UploadFile, UserContext (either authenticated or guest)
  Preconditions:
    - File size ≤ 10MB (enforced at middleware level before service call)
    - File magic bytes validated (service layer validates again)
    - Rate limit not exceeded (enforced at middleware level before service call)

  Steps:
    1. Generate scan_id (UUID v4)
    2. Determine storage path: /tmp/voiceguard/{scan_id}/{original_filename}
    3. Write uploaded bytes to temp path (streaming write, no full buffer in RAM)
    4. Validate magic bytes from first 16 bytes of written file
       - Supported: WAV (52 49 46 46), MP3 (49 44 33 / FF FB / FF F2 / FF F3),
                    FLAC (66 4C 61 43), M4A (ftyp box at offset 4), OGG (4F 67 67)
       - On failure: delete temp file, raise InvalidFileTypeError
    5. Record scan in database with status=PENDING, file_path=temp path,
       user_id (if authenticated) or guest_token (if guest)
    6. Dispatch Celery task: inference_tasks.run_scan(scan_id)
    7. Return scan_id and estimated_wait_seconds (computed from queue depth)

  Error paths:
    - File write failure → clean temp directory → raise StorageError
    - Magic byte validation failure → clean temp directory → raise InvalidFileTypeError
    - DB insert failure → clean temp directory → raise DatabaseError
    - Celery publish failure → update scan status to FAILED → raise QueueError

OPERATION: get_scan_status

  Input: scan_id, UserContext
  Steps:
    1. Check Redis key: scan_status:{scan_id}
       - If HIT: return cached status (PENDING/PROCESSING/COMPLETE/FAILED)
    2. On cache MISS: query DB for scan record
    3. Verify scan ownership: scan.user_id == user.user_id OR
       scan.guest_token == user.guest_token
       - On failure: raise ForbiddenError (not 404 — do not leak existence)
    4. Cache status in Redis with TTL based on state:
       - PENDING/PROCESSING: TTL 5s (expected to change soon)
       - COMPLETE/FAILED: TTL 300s (terminal state, cache longer)
    5. Return status with progress_percent (derived from state, not actual progress)

OPERATION: get_scan_result

  Input: scan_id, UserContext
  Steps:
    1. Verify scan ownership (same as above)
    2. Verify scan status is COMPLETE (raise ScanNotCompleteError otherwise)
    3. Query scan_results table for full result (verdict, confidence, scores,
       frequency_heatmap_url, duration, file_hash)
    4. Increment view count (async, fire-and-forget update)
    5. Return ScanResult schema

OPERATION: migrate_guest_scans

  Trigger: Called during user registration or first login when guest_token exists
  Input: guest_token, authenticated user_id
  Steps:
    1. Query all scans matching guest_token with status IN (COMPLETE, FAILED)
    2. If count == 0: return early (nothing to migrate)
    3. Begin database transaction:
       a. Update all matching scans: set user_id = user_id, guest_token = NULL
       b. Create notification: "Your {n} guest scans have been saved to your account"
    4. Commit transaction
    5. Invalidate guest_token in Redis
  Constraint: Only migrate COMPLETE and FAILED scans. PENDING and PROCESSING scans
              are associated with guest token and will resolve on their own;
              they cannot be reliably migrated mid-flight.

5.3 AUTH SERVICE (DETAILED)
────────────────────────────

OPERATION: register_user

  Input: email, password, display_name
  Steps:
    1. Normalize email: lowercase, strip whitespace
    2. Check email uniqueness in users table (raise EmailTakenError if taken)
    3. Validate password entropy (see Section 11 for rules)
    4. Hash password with bcrypt (cost factor 12)
    5. Create user record with email_verified=false, role=USER
    6. Generate email verification token (32 bytes, cryptographically random)
    7. Store email_verification_token in email_verifications table with TTL 24h
    8. Dispatch Celery task: email_tasks.send_verification_email(user_id, token)
    9. If guest_token present in request: dispatch scan migration
   10. Return user_id (do NOT issue JWT yet; require email verification first)

  Security note: Return identical error messages for "email taken" and
  "validation error" in production to prevent user enumeration. Use error codes
  internally for logging; use generic messages externally.

OPERATION: login_user

  Input: email, password
  Steps:
    1. Normalize email
    2. Look up user by email (use constant-time comparison; do not return early
       on "user not found" to prevent timing attacks)
    3. Verify password using bcrypt.checkpw with same timing regardless of outcome
    4. If email not verified: raise EmailNotVerifiedError
    5. If account deletion pending: check if still within 30-day window
       - If within window: allow login, surface deletion cancellation prompt
       - If past window: account should be purged; treat as not found
    6. Generate access token (JWT, 15 minute TTL)
    7. Generate refresh token (opaque random 32 bytes)
    8. Store refresh token hash in refresh_tokens table
    9. Set HttpOnly, SameSite=Strict, Secure cookies:
       - access_token cookie: path=/, max-age=900
       - refresh_token cookie: path=/api/auth/refresh, max-age=2592000 (30 days)
   10. Return user profile (not the tokens; they're in cookies)

OPERATION: rotate_refresh_token

  Input: refresh_token (from cookie)
  Steps:
    1. Hash the incoming refresh token
    2. Look up hash in refresh_tokens table
    3. If not found or expired: raise InvalidRefreshTokenError (force re-login)
    4. Check for token reuse: if this token was already used (revoked=true),
       revoke ALL tokens for this user (session hijacking indicator)
       - Log security event: REFRESH_TOKEN_REUSE
       - Return 401 with force_relogin=true
    5. Mark old token as revoked=true in DB
    6. Generate new access token
    7. Generate new refresh token
    8. Store new refresh token hash
    9. Set new cookies
   10. Return success

OPERATION: oauth_initiate

  Input: provider (google | github)
  Steps:
    1. Generate state parameter (32 bytes random, opaque)
    2. Generate PKCE code_verifier (32 bytes random) and code_challenge (SHA-256)
    3. Store state → {code_verifier, provider, guest_token} in Redis with TTL 10min
    4. Construct authorization URL with: client_id, redirect_uri, scope,
       state, code_challenge, code_challenge_method=S256
    5. Return redirect URL (frontend redirects user)

OPERATION: oauth_callback

  Input: code, state (from OAuth provider redirect)
  Steps:
    1. Look up state in Redis; if not found: raise InvalidOAuthStateError
    2. Retrieve code_verifier from state record
    3. Delete state record from Redis (one-time use)
    4. Exchange code + code_verifier for access token with provider
    5. Fetch user profile from provider (email, name, provider_user_id)
    6. Upsert user: find by (provider, provider_user_id) OR email
    7. If user created (first OAuth login): set email_verified=true
    8. Issue JWT session (same as login flow steps 6–10)
    9. If guest_token in original state record: migrate guest scans
   10. Return redirect to frontend with session established

6.1 API DESIGN PRINCIPLES
───────────────────────────

  PRINCIPLE 1 — CONSISTENT ENVELOPE
    All API responses use a standard JSON envelope:
    Success:  { "data": {...}, "meta": {...} }
    Error:    { "error": { "code": "...", "message": "...", "details": [...] } }
    The "data" key is always present on success, never on error.
    The "error" key is always present on error, never on success.
    "meta" is optional and used for pagination, timestamps, request_id.

  PRINCIPLE 2 — MEANINGFUL HTTP STATUS CODES
    200 OK          → Successful GET, PATCH
    201 Created     → Successful POST that creates a resource
    202 Accepted    → Async job accepted (scan submission)
    204 No Content  → Successful DELETE with no body
    400 Bad Request → Validation error, malformed request
    401 Unauthorized → Not authenticated (no valid session)
    403 Forbidden   → Authenticated but not authorized for this resource
    404 Not Found   → Resource does not exist OR user not authorized (for security-
                      sensitive resources; return 404 not 403 to avoid leaking
                      existence of resources the user shouldn't know about)
    409 Conflict    → Duplicate resource (email already taken)
    413 Too Large   → File exceeds 10MB
    415 Unsupported Media Type → Invalid file type
    422 Unprocessable Entity → Pydantic validation failure
    429 Too Many Requests → Rate limit exceeded
    500 Internal Server Error → Unexpected backend error
    503 Service Unavailable → Dependency unavailable (DB, Redis, queue)

  PRINCIPLE 3 — VERSIONING
    All API routes are prefixed with /api/v1/. The frontend calls /api/* routes
    (Batch 03 Next.js API layer rewrites /api/* to /api/v1/* at the proxy level).
    This allows backend versioning without frontend changes.

  PRINCIPLE 4 — IDEMPOTENCY WHERE APPLICABLE
    DELETE endpoints are idempotent: deleting an already-deleted resource returns
    204 (not 404). This simplifies frontend retry logic on network failures.
    POST endpoints that create resources are NOT idempotent; duplicate submissions
    create duplicate resources (the frontend must handle deduplication at UI level).

  PRINCIPLE 5 — RATE LIMIT HEADERS
    All responses include rate limit headers for transparency:
      X-RateLimit-Limit: {max_requests}
      X-RateLimit-Remaining: {remaining_requests}
      X-RateLimit-Reset: {unix_timestamp_when_window_resets}
    On 429 responses, add: Retry-After: {seconds_until_reset}

  Bulk delete:
    - scan_ids: array of UUIDs, max 100 items per request

  Pagination (all list endpoints):
    - page: integer ≥ 1, default 1
    - page_size: integer 1–100, default 20
    - Enforced at core/pagination.py

SECTION 7: UPLOAD PIPELINE
================================================================================

7.1 UPLOAD PIPELINE OVERVIEW
──────────────────────────────
The upload pipeline is the most security-sensitive path in the entire system.
A file received from the internet is written to disk, validated, queued for
inference, and the resulting temp file is deleted within 60 seconds. Every
step must be hardened against path traversal, MIME confusion, malicious file
content, oversized uploads, and resource exhaustion.

7.2 UPLOAD PIPELINE STAGES
────────────────────────────

STAGE 1: Nginx Pre-filtering (before FastAPI)
  - client_max_body_size: 11MB (slightly over 10MB to allow for multipart overhead)
  - Nginx returns 413 Request Entity Too Large before FastAPI if exceeded
  - Connection-level rate limiting: limit_req_zone on $binary_remote_addr

STAGE 2: FastAPI Middleware Interception
  Order of middleware execution (innermost to outermost):
    1. RequestID middleware — assigns request_id UUID before anything else
    2. Content-Length middleware — validates Content-Length header ≤ 10MB + overhead
       Reject early (413) if Content-Length exceeds limit (don't read the body)
    3. Rate limit middleware — check upload rate limit BEFORE reading file body
       Guest: 10/hr/IP | Authenticated: 50/day/user
       On limit exceeded: return 429 immediately without reading body
    4. Auth middleware — extract user context from JWT cookie (or guest token)

STAGE 3: Router Layer
  - Accepts multipart/form-data POST to /api/v1/scans/
  - FastAPI streams file to a SpooledTemporaryFile
    (writes to RAM up to 1MB, then spills to /tmp automatically)
  - Reads filename from multipart headers — NEVER trust it as a path component
  - Validates claimed MIME type against allowlist (soft check; hard check is
    magic bytes in stage 4)

STAGE 4: Service Layer — File Receipt and Validation

  Step 4a: Generate a scan-scoped temp directory
    Path: /tmp/voiceguard/{scan_id}/
    scan_id is UUID v4 generated before file write
    This ensures no two scans share a directory; path traversal is impossible
    because the directory name is a UUID we control

  Step 4b: Sanitize filename
    - Extract extension from original filename
    - Validate extension against allowlist: .wav, .mp3, .flac, .ogg, .m4a
    - Build storage filename: audio{extension} (discard original name entirely)
    - Full path: /tmp/voiceguard/{scan_id}/audio{extension}
    - This prevents path traversal, null bytes, Unicode tricks, long filenames

  Step 4c: Stream write to temp path
    - Write from SpooledTemporaryFile to temp path in 64KB chunks
    - Track bytes written; abort and delete if > 10MB encountered mid-stream
      (defense against Content-Length spoofing)
    - After write complete: verify actual file size ≤ 10MB

  Step 4d: Magic bytes validation
    - Open written file in binary mode
    - Read first 16 bytes
    - Check against magic byte signatures:
        WAV:  52 49 46 46 (RIFF header)
        MP3:  49 44 33 (ID3 tag) OR FF FB OR FF F2 OR FF F3 (frame sync)
        FLAC: 66 4C 61 43 (fLaC)
        OGG:  4F 67 67 53 (OggS)
        M4A:  Check bytes 4–7 for 66 74 79 70 (ftyp box)
    - If no match: delete temp directory → raise InvalidFileTypeError(415)
    - Magic bytes MUST match; claimed MIME type is ignored if they conflict

  Step 4e: Duration extraction
    - Read audio file header (do NOT decode entire file) to extract duration
    - Maximum allowed duration: 300 seconds (5 minutes)
    - If duration > 300s: delete temp directory → raise FileTooLongError(400)
    - This prevents excessively long inference jobs from consuming workers

  Step 4f: Database record creation
    - Insert scan record: scan_id, user_id/guest_token, status=PENDING,
      file_path (temp path), original_filename (truncated to 255 chars),
      file_size, claimed_mime_type, created_at
    - Do NOT store file_path in a user-accessible field; it is internal only

  Step 4g: Celery task dispatch
    - Publish to "inference" queue: run_inference_task(scan_id=scan_id)
    - Task payload contains only scan_id; the task retrieves file_path from DB
      (do not pass file_path in task payload — it is an internal path)
    - Record task_id in scan record for debugging

  Step 4h: Response
    - Return 202 Accepted with ScanSubmissionResponse (see Section 6.4)
    - HTTP connection closed; client begins polling

7.3 TEMP FILE LIFECYCLE
────────────────────────

  State: PENDING
    File exists at /tmp/voiceguard/{scan_id}/audio{ext}
    Cleanup: not yet (worker needs it)

  State: PROCESSING
    File exists; inference worker is reading it
    Cleanup: not yet

  State: COMPLETE
    Inference finished; results stored in DB
    Cleanup: IMMEDIATE — delete /tmp/voiceguard/{scan_id}/ recursively
    Cleanup trigger: inference task success handler

  State: FAILED
    Inference failed or was rejected
    Cleanup: IMMEDIATE — delete /tmp/voiceguard/{scan_id}/ recursively
    Cleanup trigger: inference task failure handler

  Failsafe cleanup:
    A Celery Beat periodic task runs every 60 seconds.
    It scans /tmp/voiceguard/ for directories older than 120 seconds.
    Any such directory is deleted regardless of scan state.
    This handles: crashed workers, zombie processes, orphaned uploads.

  Audit logging:
    Every temp file creation and deletion is logged at INFO level with:
    scan_id, file_size, duration_seconds, action (created/deleted), timestamp

7.4 TEMP STORAGE SIZING
─────────────────────────
  Worst case per scan: 10MB audio + Grad-CAM PNG (≤ 2MB) = 12MB
  With 2 inference workers processing simultaneously: 24MB peak
  With 60-second guarantee: files accumulate for at most 60s
  At 10 concurrent uploads (rate limit): 10 × 12MB = 120MB peak
  Recommended /tmp partition size: 1GB (comfortable headroom)
  Monitor with disk usage alert at 70% (/tmp partition)

SECTION 8: AI INFERENCE PIPELINE
================================================================================

8.1 INFERENCE PIPELINE OVERVIEW
─────────────────────────────────
The inference pipeline runs inside a dedicated Celery worker process. It is
completely isolated from the API tier. The API tier submits jobs and polls for
status; it never calls inference functions directly.

The LCNN model (Light CNN) has 699,938 parameters and achieves 7.07% EER on
ASVspoof 2019 LA. Known weakness: A17 neural codec attacks (36.8% EER on that
attack type). This weakness must be surfaced in the UI when confidence is low
and the "uncertain" verdict is returned.

8.2 MODEL LOADING STRATEGY
────────────────────────────

  Loading occurs once at worker process startup, not per-task.

  At worker startup:
    1. Check LCNN model file path from configuration
    2. Verify SHA-256 checksum of model file against expected value from config
       (detect corrupted or tampered model files)
    3. Load model weights into memory
    4. Set model to eval mode (disable training-mode behaviors like dropout)
    5. If CUDA available: move model to GPU; else: remain on CPU
    6. Run a warmup inference pass with a synthetic 1-second silent audio
       to initialize any lazy-loaded components
    7. Log: model_loaded, device (cpu/cuda), warmup_completed, load_time_ms

  If model loading fails:
    - Worker refuses to accept tasks
    - Send alert via configured alerting channel
    - Celery supervisor should restart worker; if repeated failure, page on-call

  Model version tracking:
    - Model version string is stored in config (e.g., "lcnn-v1.0.0-asvspoof2019la")
    - Every inference result stores the model_version used
    - This enables reproducibility auditing and future A/B model comparison

8.3 AUDIO PREPROCESSING PIPELINE
───────────────────────────────────
Before LCNN inference, audio must be converted to the feature representation
the model was trained on. This pipeline runs within the inference Celery task.

  Step 1: Audio Loading
    - Load audio file using librosa or soundfile (not ffmpeg; avoid subprocess)
    - Normalize sample rate: resample to 16000 Hz if different
    - Convert to mono if stereo (average channels)
    - Maximum duration handling: truncate to 5 minutes if somehow past service
      layer validation (defense in depth)

  Step 2: Feature Extraction — Log Power Spectrum (LPS)
    - Apply Short-Time Fourier Transform (STFT)
      - Window: Hamming, 25ms frame length, 10ms frame shift
      - FFT size: 512
    - Compute power spectrum: |STFT|²
    - Apply log compression: log(1 + power_spectrum)
    - Result: 2D spectrogram matrix (frequency bins × time frames)

  Step 3: Normalization
    - Apply per-utterance mean/variance normalization across frequency dimension
    - Clip values to [-5, 5] to prevent outlier features from dominating

  Step 4: Segmentation (for long files)
    - LCNN expects fixed-length input segments
    - Segment audio into overlapping 3-second chunks with 1.5-second hop
    - Each segment becomes an independent inference input
    - Final verdict: aggregate scores across all segments (mean pooling)

  Step 5: Tensor preparation
    - Convert numpy array to torch tensor
    - Add batch and channel dimensions as required by LCNN input shape
    - Move tensor to same device as model (CPU or CUDA)

8.4 LCNN INFERENCE
───────────────────

  Inference execution:
    - Run model forward pass with torch.no_grad() (disable gradient tracking)
    - LCNN outputs: [batch_size, 2] logits (class 0: human, class 1: AI-generated)
    - Apply softmax to logits → probabilities
    - human_score = probability[0], ai_score = probability[1]
    - For multi-segment files: mean human_score and ai_score across all segments
    - confidence = max(human_score, ai_score)

  Verdict determination (backend canonical logic):
    IF confidence ≥ 0.85:
      IF human_score > ai_score: verdict = "human"
      ELSE: verdict = "ai_generated"
    ELIF confidence < 0.65:
      verdict = "uncertain"
    ELSE (0.65 ≤ confidence < 0.85):
      Use dominant score to set verdict; but log as "borderline"

  Timing target: < 5 seconds p95 for files up to 60 seconds
    Longer files (60s–300s): up to 10s acceptable (within overall 10s target
    only for files ≤ 60s; longer files should surface estimated wait time)

8.5 GRAD-CAM VISUALIZATION
────────────────────────────
Grad-CAM generates a frequency heatmap showing which frequency bands the model
weighted most heavily in its decision. This is displayed in the result UI.

  Implementation:
    - Hook into LCNN features[9] (the 9th feature map layer, as specified in
      product architecture Batch 01)
    - Forward pass registers a hook that captures the feature map activations
    - Backward pass (for the predicted class) captures the gradients
    - Grad-CAM weight: global average pool gradients → weights per feature map
    - Weighted combination of feature maps → activation map
    - ReLU the activation map (negative values not meaningful for Grad-CAM)
    - Resize activation map to match spectrogram dimensions
    - Normalize to [0, 1]
    - Apply viridis or jet colormap → RGB heatmap image
    - Overlay heatmap on spectrogram at 50% alpha
    - Encode result as PNG
    - Base64 encode PNG for storage in scan_results.frequency_heatmap

  Storage: Stored as base64 in the scan_results table (not as a file).
  The base64 string is returned directly in the ScanResultResponse.
  For very large heatmaps: if base64 > 500KB, consider storing as a file in
  object storage and returning a signed URL instead (v1: base64 is sufficient)

  If Grad-CAM fails: Log warning, store null in frequency_heatmap, continue.
  Do NOT fail the scan because Grad-CAM failed.

8.6 RESULT STORAGE
────────────────────

  After successful inference, write to scan_results table:
    - scan_id (FK to scans)
    - verdict: "human" | "ai_generated" | "uncertain"
    - confidence: float
    - human_score: float
    - ai_score: float
    - frequency_heatmap: text (base64 PNG, nullable)
    - duration_seconds: float
    - model_version: string
    - inference_time_ms: int (for monitoring)
    - segment_count: int (number of segments processed)
    - created_at: timestamp

  After result stored:
    - Update scans.status = "complete", scans.completed_at = now()
    - Cache result in Redis: key scan_status:{scan_id}, value "complete", TTL 300s
    - Create notification: "Your scan is ready: {verdict}"
    - Delete temp directory: /tmp/voiceguard/{scan_id}/

8.7 INFERENCE TASK ERROR HANDLING
────────────────────────────────────

  Error category 1: File not found at expected path
    - Cause: Cleanup job ran too early; race condition
    - Action: Do NOT retry (file is gone). Update scan status = FAILED.
              Log error with scan_id. Create "scan failed" notification.

  Error category 2: Audio processing error (corrupt file, unsupported codec variant)
    - Cause: File passed magic bytes check but is internally corrupt
    - Action: Do NOT retry. Status = FAILED. Log with file_size and claimed mime.

  Error category 3: Model inference error (CUDA OOM, numeric overflow)
    - Cause: Unexpectedly large or pathological audio
    - Action: Retry once with CPU (fall back from GPU if applicable).
              If second attempt fails: status = FAILED. Log with full traceback.

  Error category 4: Task timeout (inference exceeded 30s hard limit)
    - Cause: Very long audio file, overloaded worker
    - Action: Terminate task. Status = FAILED. Log. Alert if happening repeatedly.

  Error category 5: Worker crash mid-task
    - Cause: OOM kill, hardware fault
    - Celery visibility timeout: 60s. After 60s, task is re-queued.
    - If file still exists: retry inference once.
    - If file gone: same as error category 1.

  Max retries: 1 (for categories 3 and 5). Never retry categories 1 and 2.

SECTION 9: BACKGROUND WORKERS
================================================================================

9.1 WORKER QUEUE ARCHITECTURE
───────────────────────────────

  Two Celery queues with dedicated worker pools:

  QUEUE: inference
    Priority: HIGH
    Concurrency: 1 per worker process (CPU-bound; ML inference)
    Workers: 2 processes (scale by adding processes, not threads)
    Routing: inference tasks ONLY; never share with general tasks

  QUEUE: general
    Priority: NORMAL
    Concurrency: 4 per worker process (IO-bound)
    Workers: 1 process × 4 concurrency (can add processes for scale)
    Routing: email, PDF, notifications, cleanup, webhooks

9.2 CELERY TASK CATALOG
─────────────────────────

INFERENCE TASKS (queue: inference)

  run_inference_task
    Input: scan_id (UUID string)
    Steps:
      1. Load scan record from DB; extract file_path
      2. Verify file exists at file_path; if not → handle error category 1
      3. Update scan status → PROCESSING; cache in Redis
      4. Run full inference pipeline (Section 8)
      5. Store results; update status → COMPLETE
      6. Delete temp directory
      7. Create completion notification
    Timeout: 30 seconds hard limit
    Retries: max 1 (on specific error categories)
    On success: emit inference_completed metric
    On failure: update status → FAILED; send failure notification; clean temp

REPORT TASKS (queue: general)

  generate_pdf_report_task
    Input: scan_id (UUID string), requesting_user_id
    Steps:
      1. Load full scan result from DB
      2. Load user profile (display_name, email)
      3. Render PDF using report module (Section 5)
      4. Return PDF bytes to caller via Celery result backend
    Timeout: 10 seconds
    Retries: 2 (PDF generation is deterministic; retry is safe)
    Note: PDF is NOT stored; generated on demand and streamed to response

EMAIL TASKS (queue: general)

  send_verification_email
    Input: user_id, verification_token
    Steps:
      1. Load user email and display_name from DB
      2. Construct verification URL: {BASE_URL}/auth/verify?token={token}
      3. Send via configured email provider (SMTP or transactional API)
      4. Log delivery attempt
    Timeout: 15 seconds
    Retries: 3 with exponential backoff (email delivery can be slow)

  send_password_reset_email
    Input: user_id, reset_token
    Same pattern as verification email; different template and URL

  send_welcome_email
    Input: user_id
    Triggered after email_verified = true
    Timeout: 15 seconds, Retries: 3

NOTIFICATION TASKS (queue: general)

  create_scan_notification
    Input: user_id, scan_id, verdict
    Creates notification record in DB
    Timeout: 5 seconds, Retries: 3

CLEANUP TASKS (queue: general)

  cleanup_expired_temp_files
    Trigger: Celery Beat, every 60 seconds
    Steps:
      1. List all directories in /tmp/voiceguard/
      2. For each directory: check mtime; if age > 120 seconds, delete
      3. Log count of deleted directories
    Timeout: 30 seconds
    Note: This is the failsafe; normal cleanup happens in run_inference_task

  expire_guest_sessions
    Trigger: Celery Beat, every 1 hour
    Steps:
      1. Query scans with guest_token where created_at < 24 hours ago
         AND status is COMPLETE or FAILED
      2. These scans are no longer accessible by guest (session expired)
      3. Optionally: delete expired guest scan records to control DB growth
    Timeout: 60 seconds

  purge_deleted_accounts
    Trigger: Celery Beat, every 24 hours
    Steps:
      1. Query deleted_accounts where deletion_initiated_at < 30 days ago
      2. For each: call user_service.purge_user(user_id)
         - Delete user record (cascades to scans, notifications, api_keys)
         - Delete scan result records
         - Anonymize audit log entries (replace user_id with deleted_user hash)
    Timeout: 300 seconds

  cleanup_expired_tokens
    Trigger: Celery Beat, every 6 hours
    Steps:
      1. Delete expired refresh_tokens
      2. Delete expired password_reset_tokens
      3. Delete expired email_verification_tokens
      4. Delete expired oauth_states
    Timeout: 60 seconds

9.3 CELERY BEAT SCHEDULE
─────────────────────────
  Task                           Interval     Queue
  ─────────────────────────────────────────────────
  cleanup_expired_temp_files     60 seconds   general
  expire_guest_sessions          1 hour       general
  purge_deleted_accounts         24 hours     general
  cleanup_expired_tokens         6 hours      general

9.4 TASK MONITORING
────────────────────
  - Flower (Celery monitoring UI): deployed at /admin/workers (admin only)
  - Every task emits: task_name, task_id, queue, runtime_ms, status to metrics
  - Failed tasks: emit alert if failure rate > 5% in any 5-minute window
  - Inference queue depth: alert if depth > 20 tasks (workers may be stuck)
  - Worker heartbeat: Celery Beat checks worker heartbeats every 60 seconds

SECTION 10: AUTHENTICATION ARCHITECTURE
================================================================================

10.1 AUTHENTICATION SCHEME OVERVIEW
─────────────────────────────────────
VoiceGuard uses a dual-token JWT scheme with HttpOnly cookies. The access token
is short-lived (15 minutes) and used for API authorization. The refresh token is
long-lived (30 days), stored in a restricted-path cookie, and used only to obtain
new access tokens.

10.2 TOKEN SPECIFICATIONS
───────────────────────────

  ACCESS TOKEN (JWT)
    Algorithm: HS256 (v1) or RS256 (v2 if token verification becomes distributed)
    Payload claims:
      - sub: user_id (UUID string)
      - role: "user" | "admin"
      - email_verified: boolean
      - iat: issued_at (unix timestamp)
      - exp: expires_at (iat + 900 seconds = 15 minutes)
      - jti: JWT ID (UUID, for future revocation index if needed)
    Signature: HMAC-SHA256 with JWT_SECRET from environment
    Cookie settings:
      Name: access_token
      HttpOnly: true
      SameSite: Strict
      Secure: true (HTTPS only)
      Path: /
      Max-Age: 900

  REFRESH TOKEN (opaque random)
    Format: 32 bytes, cryptographically random, hex-encoded (64 chars)
    Storage: SHA-256 hash stored in refresh_tokens table
    Cookie settings:
      Name: refresh_token
      HttpOnly: true
      SameSite: Strict
      Secure: true
      Path: /api/v1/auth/refresh (restricted path — browser only sends on refresh)
      Max-Age: 2592000 (30 days)

  GUEST TOKEN (opaque)
    Format: 32 bytes random, hex-encoded
    Storage: In a non-HttpOnly cookie (needs to be read by JS for guest scan
             association) — OR — passed as a request header X-Guest-Token
    Recommendation: Use a regular (non-HttpOnly) cookie with SameSite=Strict
                    and Secure, named guest_token, Max-Age: 86400 (24 hours)
    Purpose: Associates anonymous scans with a browser session

10.3 JWT VERIFICATION MIDDLEWARE
──────────────────────────────────
Every request passes through auth middleware:

  Step 1: Extract access_token from cookie
  Step 2: If no cookie: set request.state.user = AnonymousUser
  Step 3: Decode JWT header (without verification) to read algorithm
  Step 4: Reject if algorithm is not in allowlist ["HS256"] (alg confusion attack)
  Step 5: Verify signature using JWT_SECRET
  Step 6: Check exp claim; if expired: attempt silent refresh
    - Look for refresh_token cookie
    - If present: call rotate_refresh_token()
    - If refresh succeeds: re-issue cookies, continue with new user context
    - If refresh fails: set request.state.user = AnonymousUser
  Step 7: Verify email_verified == true (for endpoints requiring verified email)
  Step 8: Set request.state.user = AuthenticatedUser(user_id, role, email)

10.4 SILENT TOKEN REFRESH
───────────────────────────
When access token expires and refresh token is valid:
  - Transparent to the frontend; no redirect to login
  - New cookies are set in the response headers of the current request
  - The request that triggered the refresh is processed with the new tokens
  - Frontend receives the response as if the access token was still valid

This means the frontend polling loop (status endpoint every 3s) will
transparently renew tokens without the user noticing.

10.5 API KEY AUTHENTICATION
─────────────────────────────
For programmatic access (developer users with API key plan):

  API Key Format: vg_live_{32_random_bytes_hex} (66 chars total)
  Storage: scrypt hash of full key stored in api_keys table
  Transmission: HTTP header: Authorization: Bearer vg_live_{key}

  API Key middleware:
    1. Check for Authorization: Bearer header
    2. Extract key; validate prefix vg_live_ (or vg_test_ for sandbox)
    3. Hash with scrypt and look up in api_keys table
    4. If found and not revoked: set user context from associated user_id
    5. Check api_keys.rate_limit_tier for this key's rate limits
    6. Proceed as authenticated user

  API keys: shown only once at creation. If lost, must be revoked and recreated.
  API keys do NOT use cookies; they use the Authorization header.

10.6 OAUTH FLOW
────────────────

  Full PKCE flow (per Batch 01 requirement — no implicit flow):

  Step 1 (Frontend → Backend):
    GET /api/v1/auth/oauth/google
    Backend generates: state (32 bytes), code_verifier (32 bytes),
    code_challenge = base64url(SHA-256(code_verifier))
    Stores {state → {code_verifier, provider, timestamp}} in Redis TTL 10min
    Returns: {"auth_url": "https://accounts.google.com/o/oauth2/auth?..."}

  Step 2 (Browser → Provider):
    Browser redirects to auth_url
    Parameters: client_id, redirect_uri, scope, state, code_challenge,
    code_challenge_method=S256, response_type=code

  Step 3 (Provider → Backend):
    Provider redirects to /api/v1/auth/oauth/google/callback?code=X&state=Y
    Backend verifies state matches Redis entry (CSRF protection)
    Backend retrieves code_verifier from Redis
    Backend deletes Redis state entry (one-time use)

  Step 4 (Backend → Provider):
    POST to provider token endpoint with:
    code, redirect_uri, client_id, client_secret, code_verifier, grant_type=authorization_code

  Step 5 (Backend):
    Receive access_token from provider
    Fetch user profile from provider userinfo endpoint
    Upsert user in database
    Issue VoiceGuard JWT session
    Set HttpOnly cookies
    Redirect to frontend: /dashboard (or original destination)

10.7 SESSION MANAGEMENT
─────────────────────────

  Session lifecycle:
    - Created: at login or OAuth callback
    - Active: access token valid (15 min) or refresh token valid (30 days)
    - Expired: refresh token expired or explicitly revoked
    - Revoked: explicit logout; all refresh tokens for user invalidated

  Multiple sessions:
    - A user can have multiple active sessions (different devices/browsers)
    - Each session has its own refresh token
    - Logout on one session does not invalidate other sessions (v1 behavior)
    - "Log out all devices" endpoint revokes all refresh tokens for user_id

  Session storage:
    - Access tokens are stateless JWT (no server-side session store)
    - Refresh tokens are stored in refresh_tokens table
    - guest_token is stateless (stored in cookie only; server trusts it as-is)

10.8 ACCOUNT DELETION AND SESSION INVALIDATION
────────────────────────────────────────────────
  When soft delete is initiated:
    - All refresh tokens for user are revoked immediately
    - Future login attempts: allowed (user can cancel deletion by logging in)
    - JWT claims: check users.deletion_scheduled_at in auth middleware;
      surface deletion warning in user context

  When hard delete (purge) runs after 30 days:
    - User record deleted; cascade deletes all related records
    - Any remaining refresh tokens for this user_id become orphaned (harmless;
      lookup fails; they expire naturally)

SECTION 11: SECURITY ARCHITECTURE
================================================================================

11.1 SECURITY POSTURE
──────────────────────
VoiceGuard operates on the principle that the backend is the last defense. The
frontend performs security UX (blocking UI, validation feedback) but the backend
enforces all security guarantees. Every item in the Batch 01 security requirements
is addressed here with explicit implementation strategy.

11.2 TRANSPORT SECURITY
────────────────────────

  HTTPS enforcement:
    - Nginx: HTTP requests receive 301 redirect to HTTPS equivalent URL
    - HSTS header: Strict-Transport-Security: max-age=31536000; includeSubDomains
    - TLS minimum version: 1.2 (1.3 preferred)
    - Cipher suite: modern-only (AES-GCM, CHACHA20-POLY1305; disable RC4, 3DES)

  Certificate management:
    - Let's Encrypt (auto-renewal via certbot)
    - Certificate expiry monitoring: alert at 30 days, critical at 7 days

11.3 CORS CONFIGURATION
─────────────────────────

  Allowlist (no wildcards):
    - Production: [https://voiceguard.app]
    - Staging: [https://staging.voiceguard.app]
    - Development: [http://localhost:3000]

  Allowed methods: GET, POST, PATCH, DELETE, OPTIONS
  Allowed headers: Content-Type, Authorization, X-Guest-Token, X-Request-ID
  Allow credentials: true (required for cookie-based auth)
  Preflight cache: 600 seconds (Access-Control-Max-Age)

  FastAPI CORS middleware is NOT sufficient alone. Nginx should also be
  configured to handle CORS at the edge for OPTIONS requests.

11.4 CONTENT SECURITY POLICY
──────────────────────────────
Backend API responses include:
  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: microphone=(), camera=(), geolocation=()

  CSP is enforced by the Next.js layer for HTML responses.
  The backend API (JSON responses) also sets:
  Content-Security-Policy: default-src 'none' (API responses should not execute)

11.5 PASSWORD SECURITY
───────────────────────

  Hashing: bcrypt with work factor 12
    - Never store plaintext or weakly-hashed passwords
    - Use bcrypt.checkpw for verification (constant-time; prevents timing attacks)

  Password entropy requirements:
    - Minimum 8 characters
    - At least 1 uppercase letter
    - At least 1 lowercase letter
    - At least 1 digit
    - At least 1 special character from: !@#$%^&*()_+-=[]{}|;:,.<>?
    - Not in top 10,000 common passwords (validate against bundled list)
    - Not the same as the user's email address

  Password change flow:
    - Require current password verification before accepting new password
    - After successful change: revoke all other refresh tokens (force re-login
      on other devices as security measure)
    - Send security notification email: "Your password was changed"

11.6 RATE LIMITING
───────────────────

  Implementation: Redis-based sliding window counter

  Rate limit tiers:
    1. Guest scan submissions: 10 per hour per IP
       Key: rl:scan:guest:{ip_address}:{hour_bucket}
       On exceed: 429 with Retry-After header

    2. Authenticated user scan submissions: 50 per day per user_id
       Key: rl:scan:user:{user_id}:{day_bucket}
       On exceed: 429 with Retry-After header

    3. Auth endpoints (login, register, password reset): 5–10 per hour per IP
       (see route table in Section 6.2 for per-route limits)
       Key: rl:auth:{endpoint}:{ip_address}:{hour_bucket}

    4. API key submissions: determined by api_keys.rate_limit_tier
       Tiers: FREE (50/day), PRO (500/day), ENTERPRISE (custom)

  IP extraction:
    - In production: use X-Forwarded-For header (set by Nginx)
    - Take the leftmost IP in the chain (client IP, not proxy IP)
    - Validate extracted IP is a valid IPv4/IPv6 address
    - Do NOT trust X-Forwarded-For in development (use request.client.host)

  Rate limit counter operations must be atomic:
    MULTI/EXEC or Lua script:
      1. INCR key
      2. If new key: EXPIRE key {window_seconds}
      3. Return current count and TTL

11.7 INPUT VALIDATION
──────────────────────

  All inputs validated before any business logic executes:
    - Pydantic models for all request bodies (enforced at router layer)
    - Query parameter validators for all GET endpoints
    - Path parameter validators: UUIDs validated as UUIDs, not arbitrary strings
    - File upload: magic bytes before any parsing (Section 7)
    - Email: RFC 5322 format + MX record check NOT required for v1 (just format)
    - Strings: max length enforced on all text fields
    - SQL injection: not possible via ORM parameterized queries (never raw SQL)
    - Command injection: no shell subprocess calls with user data

  Null byte protection:
    - Strip null bytes from all string inputs before processing
    - This prevents null byte injection in file paths (defense in depth)

11.8 API KEY SECURITY
──────────────────────

  Key generation:
    - Format: vg_live_{hex(os.urandom(32))}
    - Prefix distinguishes live from test keys (test keys work on sandbox)
    - Generated once; shown to user once; never stored in plaintext

  Key storage:
    - Store: scrypt(key, salt, N=2**14, r=8, p=1) → hash (as specified in Batch 01)
    - scrypt is preferred over bcrypt for high-entropy secrets (API keys)
      because bcrypt truncates at 72 bytes; scrypt does not

  Key verification:
    - Hash incoming key with same scrypt parameters and compare
    - Constant-time comparison to prevent timing attacks

  Key revocation:
    - Set api_keys.revoked = true, revoked_at = now()
    - Rate limit counters for revoked key stop incrementing (key lookup fails)
    - No grace period: revocation is immediate

11.9 AUDIT LOGGING
───────────────────

  Security-relevant events that MUST be audit logged:
    - User registration
    - Login success and failure
    - Password change
    - Email verification
    - OAuth account link
    - Account deletion initiation and cancellation
    - API key creation and revocation
    - Refresh token reuse detection
    - Scan submission (user_id/guest_token, IP, file_size)
    - Admin actions (any admin endpoint call)
    - Rate limit exceeded events

  Audit log record format:
    - event_type: string (from enum)
    - user_id: UUID | null
    - ip_address: string (hashed in logs for GDPR: SHA-256 of IP + salt)
    - user_agent: string (truncated to 512 chars)
    - request_id: UUID
    - timestamp: ISO8601 with milliseconds
    - outcome: "success" | "failure"
    - details: JSON object with event-specific fields

  Audit logs are append-only. The application never deletes audit log records.
  Retention: 2 years (legal requirement baseline). Store in separate audit_logs
  table or ship to external SIEM.

11.10 DEPENDENCY SECURITY
───────────────────────────
  - Pin all Python dependencies with exact versions in requirements.txt
  - Use pip-audit or safety in CI to scan for known CVEs in dependencies
  - Keep PyTorch, librosa, Pillow updated (these have frequent security patches)
  - No dependency should require root access at runtime

11.11 SECRETS MANAGEMENT
──────────────────────────
  All secrets loaded from environment variables. Never in source code.
  Required secrets:
    - DATABASE_URL (PostgreSQL connection string with password)
    - REDIS_URL (Redis connection string with password)
    - JWT_SECRET (minimum 256-bit random string)
    - GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET
    - GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET
    - EMAIL_SMTP_HOST, EMAIL_SMTP_USER, EMAIL_SMTP_PASSWORD
    - SCRYPT_SALT (for API key hashing; static salt per deployment)

  Secret rotation:
    - JWT_SECRET rotation: deploy new secret + 15-minute grace period (existing
      access tokens expire in ≤ 15 minutes; no forced logout required)
    - Database password rotation: update DATABASE_URL; restart API workers
    - OAuth secret rotation: update and restart; no user impact

SECTION 12: LOGGING ARCHITECTURE
================================================================================

12.1 LOGGING PHILOSOPHY
─────────────────────────
All logs are structured JSON. No human-readable log strings in production.
Structured logs are machine-parseable and enable precise log queries without
regex. Every log entry has a minimum set of required fields that enable
correlation across services.

12.2 STANDARD LOG FIELDS
─────────────────────────

  Every log entry MUST include:
    timestamp       ISO8601 with milliseconds (UTC)
    level           DEBUG | INFO | WARNING | ERROR | CRITICAL
    request_id      UUID (assigned by RequestID middleware; propagated to tasks)
    service         "api" | "worker-inference" | "worker-general" | "beat"
    module          Python module name (e.g., "scan.service", "auth.router")
    message         Human-readable description (for debugging)
    environment     "production" | "staging" | "development"

  Request logs additionally include:
    method          HTTP method
    path            URL path (no query params in log; they may contain tokens)
    status_code     HTTP response status
    duration_ms     Request processing time in milliseconds
    user_id         UUID | null (null for anonymous requests)
    ip_address      SHA-256 hash of IP (for GDPR compliance; see Section 11.9)

  Task logs additionally include:
    task_name       Celery task name
    task_id         Celery task UUID
    queue           Queue name
    duration_ms     Task execution time

12.3 LOG LEVELS
─────────────────

  DEBUG:    Detailed diagnostic information. Disabled in production.
            Example: "LCNN forward pass completed, logits=[0.92, 0.08]"

  INFO:     Significant events in normal flow.
            Example: "Scan submitted, status=pending, queue_depth=3"
            Example: "Inference completed, verdict=human, confidence=0.94, duration_ms=2340"
            Example: "User registered, email_verified=false"
            Example: "Temp file deleted, scan_id=..., age_seconds=45"

  WARNING:  Unexpected but recoverable conditions.
            Example: "Grad-CAM generation failed, returning null heatmap"
            Example: "Inference retry 1 of 1 after CUDA error"
            Example: "Rate limit approaching: 8/10 requests used in current window"

  ERROR:    Errors that affect a specific request or task but not the system.
            Example: "Inference task failed after 1 retry, status=FAILED"
            Example: "Database query timeout, operation=list_scans, user_id=..."
            Example: "Email send failed for user_id=..., provider=smtp"

  CRITICAL: System-level failures requiring immediate attention.
            Example: "Database connection pool exhausted"
            Example: "Model file checksum mismatch — possible tampering"
            Example: "Redis connection lost — rate limiting degraded"

12.4 LOG ROUTING
─────────────────

  Development: logs to stdout, human-formatted (using rich or structlog dev mode)
  Staging/Production: structured JSON to stdout → captured by container runtime
    → forwarded to log aggregation (CloudWatch, Datadog, ELK, or equivalent)

  Log aggregation requirements:
    - Full-text search on message field
    - Structured field filtering (level, user_id, request_id)
    - Retention: 30 days active, 90 days cold storage
    - Alert rule support (see Section 13)

12.5 SENSITIVE DATA IN LOGS
─────────────────────────────

  NEVER log:
    - Passwords (even hashed)
    - JWT tokens or refresh tokens
    - Raw API keys
    - File content or audio data
    - Full email addresses in non-audit contexts (use user_id instead)
    - Full IP addresses (use SHA-256 hash)

  MAY log:
    - user_id (UUID, not personal data)
    - scan_id
    - Error messages that do NOT contain user content
    - Performance metrics

  Scrubbing: Implement a log filter that scans for common secret patterns
  (Bearer tokens, password= key in JSON) and replaces with [REDACTED].
  This catches accidental logging of secrets from dependencies.

12.6 REQUEST ID PROPAGATION
─────────────────────────────

  Every inbound request receives a UUID request_id:
    1. Check if X-Request-ID header is present (provided by client or upstream proxy)
    2. If valid UUID format: use it
    3. Otherwise: generate new UUID
    4. Store in request.state.request_id
    5. Include in all logs generated during request
    6. Include in response header: X-Request-ID: {uuid}
    7. When dispatching Celery tasks: pass request_id as task metadata
    8. Workers propagate request_id in all task logs

  This enables end-to-end trace: client receives request_id → can quote it in
  support tickets → ops team can find all related log entries across API and workers.

SECTION 13: OBSERVABILITY & MONITORING
================================================================================

13.1 OBSERVABILITY STRATEGY
─────────────────────────────
Observability is built around three pillars: Logs (Section 12), Metrics, and
Traces. For v1, structured logs and application metrics are the priority.
Distributed tracing (OpenTelemetry) is the v2 add-on. The guiding question for
every metric and alert: "Can an operator diagnose a production incident from
logs and metrics alone?" The answer must be yes.

13.2 APPLICATION METRICS
─────────────────────────

  Metrics format: Prometheus-compatible counters, gauges, and histograms.
  Exposed at: /metrics endpoint (restricted to internal network, not public).

  API METRICS (counters + histograms):
    voiceguard_http_requests_total
      Labels: method, path, status_code
      Type: Counter
      Description: Total HTTP requests, labeled for error rate calculation

    voiceguard_http_request_duration_seconds
      Labels: method, path, status_code
      Type: Histogram
      Buckets: 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0
      Description: Request latency distribution

    voiceguard_http_request_size_bytes
      Labels: method, path
      Type: Histogram
      Description: Request body size (important for upload endpoint)

  SCAN PIPELINE METRICS:
    voiceguard_scans_submitted_total
      Labels: user_type (guest, authenticated)

SECTION 14: ERROR HANDLING ARCHITECTURE
================================================================================

14.1 ERROR HANDLING PHILOSOPHY
────────────────────────────────
Errors are handled at the layer where they can be meaningfully addressed.
Business rule violations are caught in the service layer. Database errors are
caught in the repository layer. HTTP protocol errors are handled by FastAPI
middleware. Unexpected errors are caught globally and returned as structured
500 responses without leaking internal details.

The frontend never sees stack traces. The frontend never sees raw database
error messages. Internal error details go to logs; safe messages go to clients.

14.3 GLOBAL EXCEPTION HANDLER
───────────────────────────────

  FastAPI global exception handler catches all unhandled exceptions:

  For known BaseVoiceGuardError subclasses:
    - Extract HTTP status code from exception class
    - Extract safe user-facing message from exception
    - Return ErrorResponse envelope with error.code and error.message
    - Log at WARNING level (business errors are expected, not alarming)

  For Pydantic ValidationError (from request parsing):
    - HTTP 422
    - Extract field-level errors into error.details array
    - Each detail: { "field": "email", "message": "Invalid email format" }

  For unhandled Python exceptions:
    - HTTP 500
    - Return generic: { "error": { "code": "INTERNAL_ERROR",
      "message": "An unexpected error occurred. Please try again." } }
    - Log at ERROR level with full stack trace and request context
    - Include request_id in response so user can reference it in support

  NEVER expose:
    - Stack traces
    - Database error messages (contain internal query structure)
    - File system paths
    - Internal service names
    - Model weights path or configuration details

────────────────────────────────────

14.5 DATABASE ERROR HANDLING
──────────────────────────────

  All repository functions must handle:

  IntegrityError (unique constraint violation):
    - Catch specifically; map to appropriate ConflictError
    - Example: duplicate email → EmailAlreadyExistsError

  OperationalError (connection lost, timeout):
    - Retry once with exponential backoff (100ms, then 200ms)
    - If second attempt fails: raise DatabaseError
    - Log at ERROR level with query context (not query parameters — they may
      contain sensitive data)

  Timeout:
    - Statement timeout: 30 seconds for all queries
    - If exceeded: log with query identifier (not content); raise DatabaseError

  Connection pool exhausted:
    - Raise DatabaseError immediately (do not queue indefinitely)
    - This is a CRITICAL alert condition (see Section 13.4)

14.6 CELERY TASK ERROR HANDLING
─────────────────────────────────

  All Celery tasks implement:

  On task start:
    - Log: task_started, task_id, task_name, input args (safe fields only)

  On task success:
    - Log: task_completed, duration_ms, output summary
    - Update relevant DB record to reflect completion

  On task failure:
    - Log: task_failed, exception_type, exception_message (not traceback to info;
      traceback to debug/error)
    - Update relevant DB record to FAILED state
    - Do NOT let failures silently disappear

  On task retry:
    - Log: task_retry, retry_count, reason
    - Exponential backoff: countdown = 2 ** retry_number seconds

  Dead letter handling:
    - After max retries exhausted: task lands in dead letter queue
    - Dead letter queue: monitor and alert if it has entries
    - Operator can inspect and manually requeue if appropriate

14.7 PARTIAL FAILURE HANDLING
───────────────────────────────

  Scan with failed Grad-CAM:
    - Store null in frequency_heatmap
    - Scan result is still COMPLETE; verdict is still valid
    - Frontend handles null heatmap gracefully (no visualization shown)

  Scan with failed notification creation:
    - Notification failure does NOT fail the scan
    - Log warning; metric increment; continue

  Bulk delete with some failures:
    - Return success for deleted IDs, errors for failed IDs
    - Response: { "deleted": [...], "failed": [{ "id": "...", "reason": "..." }] }
    - Do NOT wrap entire bulk operation in one transaction
      (partial success is better than all-or-nothing for delete operations)

  Email send failure:
    - Do NOT fail the registration or password reset because email failed
    - User can request resend via dedicated endpoint
    - Log error; alert if persistent email failures

SECTION 16: SCALABILITY STRATEGY
================================================================================

16.1 V1 BASELINE CAPACITY
───────────────────────────

  Target capacity for v1 (single-region, 3-VM topology from Section 3.4):
    - Concurrent API requests: 200
    - Scans per hour: ~100 (constrained by 2 inference workers × 18 scans/hr each)
    - API response latency p95: < 500ms (non-inference endpoints)
    - Inference latency p95: < 5 seconds
    - Storage: PostgreSQL grows at ~1KB per scan (metadata only, no audio)
      At 100 scans/hr: ~2.4MB/day, ~876MB/year (negligible)

  Bottleneck: Inference workers. Every additional inference worker adds ~18
  scans/hour capacity (assuming ~3.3s average inference per scan, plus overhead).

16.2 HORIZONTAL SCALING PATHS
───────────────────────────────

  SCALE PATH 1: Add Inference Workers (primary bottleneck)
    Trigger: Celery inference queue depth consistently > 10
    Action: Deploy additional VMs running only Celery inference workers
    Complexity: LOW — workers are stateless and pre-load the model
    Constraint: Each additional worker needs ~2.8MB RAM for model + ~500MB OS
    Cost: Low (small VMs)

  SCALE PATH 2: Add API Workers (if API tier is CPU-bound)
    Trigger: API VM CPU > 80%, latency degrading
    Action: Add uvicorn workers (increase --workers count) or add API VMs
            behind load balancer
    Complexity: LOW — API workers are stateless (all state in DB/Redis)
    Prerequisite: Ensure DB connection pool is sized for more workers (pgBouncer)

  SCALE PATH 3: Read Replica for PostgreSQL (if query latency degrades)
    Trigger: DB query latency p95 > 1 second
    Action: Add PostgreSQL read replica; route history/stats queries to replica
    Complexity: MEDIUM — requires application-level read/write routing
    Benefit: Eliminates read/write contention on history queries

  SCALE PATH 4: Redis Cluster (if Redis becomes bottleneck)
    Trigger: Redis latency > 10ms or memory pressure
    Action: Migrate to Redis Cluster (3+ nodes)
    Complexity: MEDIUM — client configuration change, key hashing considerations
    Likely never needed for v1 at realistic VoiceGuard scale

  SCALE PATH 5: CDN for Static Assets and Heatmap Images
    Trigger: Bandwidth costs increasing or image delivery latency
    Action: Move base64 heatmaps to object storage (S3/GCS); return signed URLs
    Complexity: MEDIUM — change ScanResultResponse contract

  SCALE PATH 6: Geographic Distribution (v2+)
    Trigger: Users in multiple continents with latency complaints
    Action: Deploy full stack to additional regions with data residency awareness
    Complexity: HIGH — data sovereignty, model deployment, PostgreSQL replication

16.3 CACHING STRATEGY
───────────────────────

  Layer 1: Redis application cache
    - Scan status: cache in Redis after first DB read (TTL: 5s for active,
      300s for terminal)
    - Dashboard stats: cache per user_id (TTL: 60s; acceptable staleness)
    - Notification unread count: cache per user_id (TTL: 30s;
      increment/decrement on events rather than invalidate-and-refetch)
    - Help articles: cache all articles (TTL: 3600s; rarely change)

  Layer 2: HTTP caching headers for API responses
    - GET /api/v1/help/articles: Cache-Control: public, max-age=3600
    - GET /api/v1/scans/{id}/result: Cache-Control: private, max-age=300
      (result is immutable once COMPLETE; safe to cache briefly)
    - All other endpoints: Cache-Control: no-store (auth, mutable data)

  Layer 3: Database query optimization
    Required indexes (specify to DBA; not writing SQL here):
      - users.email (unique index; login query)
      - scans.user_id + created_at (history list queries)
      - scans.guest_token (guest scan lookup)
      - scan_results.scan_id (1:1 join)
      - notifications.user_id + read_at (unread count queries)
      - refresh_tokens.token_hash (auth lookup)
      - api_keys.key_hash (API key auth lookup)

16.4 DATABASE CONNECTION POOLING
──────────────────────────────────

  Without pgBouncer (v1 baseline):
    Per API worker: pool_min=5, pool_max=20
    4 API workers × 20 max connections = 80 max connections to PostgreSQL
    PostgreSQL default max_connections: 100 (adequate for v1)

  With pgBouncer (scale recommendation):
    pgBouncer in transaction pooling mode
    API workers connect to pgBouncer (pool_size=5 per worker)
    pgBouncer manages actual PostgreSQL connections
    Enables 400+ uvicorn workers without exhausting PostgreSQL connections

16.5 STATELESS DESIGN GUARANTEE
─────────────────────────────────
All API workers are fully stateless. There is no in-process state that must be
preserved between requests. This means:
  - Any request can be handled by any API worker
  - Workers can be added/removed without draining (no sticky sessions)
  - Rolling deployments are safe (no session affinity required)
  - Load balancer can use round-robin or least-connections algorithm

The only "sticky" behavior is the HttpOnly cookie — but cookies are verified
against Redis/DB, not stored in the worker process. A cookie issued by Worker A
is valid on Worker B.

17.2 DEPENDENCY INJECTION PATTERN
────────────────────────────────────

  FastAPI's Depends() system is used for:
    - Database session injection into routes (use async context manager)
    - Current user extraction (get_current_user dependency)
    - Rate limit checking (rate_limit dependency)

  Pattern for DB sessions:
    - Session is created at router layer via Depends
    - Session is passed to service layer
    - Service passes session to repository layer
    - Session is committed or rolled back in the router (or via context manager)
    - NEVER create a new session inside a service or repository function

  Pattern for current user:
    - get_current_user(request) → UserContext (authenticated or anonymous)
    - require_authenticated() → calls get_current_user + raises if anonymous
    - require_admin() → calls require_authenticated + raises if role != admin
    - Routes declare their auth dependency explicitly; middleware does NOT
      inject user context automatically (use Depends to be explicit)

17.3 DATABASE MIGRATION STANDARDS
────────────────────────────────────

  Tool: Alembic (with SQLAlchemy async support)

  Rules:
    - Every schema change has a migration file (no manual ALTER TABLE in prod)
    - Migrations are linear (no branches in migration graph)
    - Migrations are reversible (downgrade() must work, not raise NotImplemented)
    - Large table alterations: use `ADD COLUMN ... DEFAULT NULL` pattern
      (adding NOT NULL columns with defaults locks the table)
    - Index creation: use `CREATE INDEX CONCURRENTLY` (non-blocking in PostgreSQL)
    - Never truncate or drop data in a migration without explicit approval

  Migration review checklist:
    - Does this migration lock any table? If yes, flag for maintenance window
    - Is this migration reversible?
    - Does the ORM model match the resulting schema?
    - Are there any data migrations included? (data migrations should be separate
      from schema migrations)

17.4 TESTING STANDARDS
───────────────────────

  Test coverage minimum: 80% for service layer, 70% for repository layer
  Integration tests: Required for all scan pipeline stages

  Test categories:
    1. Unit tests (fast, < 1ms each, no external dependencies):
       - Service layer with mocked repositories
       - Pydantic schema validation
       - Magic bytes validation logic
       - JWT creation/verification
       - Rate limit counter logic

    2. Integration tests (require DB and Redis):
       - Full auth flow (register → verify → login → refresh → logout)
       - Scan submission → inference → result retrieval (with mock LCNN model)
       - Guest scan migration
       - Soft delete and recovery
       - Rate limiting enforcement
       - Bulk operations

    3. Load tests (separate from unit/integration):
       - 50 concurrent scan submissions
       - History pagination under load
       - Rate limit enforcement at scale

    - Dedicated test PostgreSQL database
    - Database is truncated (not dropped/recreated) between test runs (faster)
    - Migrations are run once at test session start

  Mock LCNN for tests:
    - Provide a test fixture that returns a deterministic InferenceResult
    - Never run real model inference in unit or integration tests
    - Test inference module separately with an isolated test suite

────────────────────────────────────────────────────────────────────────────────
Risk:         Compromised deployment could swap the LCNN model file for a
              malicious or incorrect model.
Architecture: SHA-256 checksum of model file verified at worker startup against
              MODEL_CHECKSUM from configuration. Mismatch = CRITICAL alert +
              worker refuses to start.
Status:       RESOLVED

────────────────────────────────────────────────────────────────────────────────
ISSUE 14: Temp storage disk exhaustion
────────────────────────────────────────────────────────────────────────────────
Risk:         High upload volume + inference slowdown could accumulate temp files
              and exhaust disk space.
Architecture: Failsafe cleanup at 120 seconds (regardless of inference status).
              Disk usage alert at 70% and 90%. Max upload 10MB. Rate limit 10/hr
              guest limits worst-case accumulation.
Status:       RESOLVED (Section 7.4 sizing analysis)

ISSUE 15: No blocking sync IO in async FastAPI routes
────────────────────────────────────────────────────────────────────────────────
Risk:         Calling synchronous Python libraries (bcrypt, scrypt, librosa)
              inside async route handlers blocks the event loop.
Architecture: All CPU-bound or blocking operations must run in a thread pool
              using asyncio.run_in_executor() or FastAPI's run_in_threadpool().
              Specific operations requiring threadpool: bcrypt.checkpw,
              scrypt hashing, magic bytes file read.
              LCNN inference runs in Celery worker (separate process; no event
              loop concern).
Status:       REQUIRES ATTENTION — engineering team must enforce this pattern.
              Code review checklist item (Section 17.6).

SECTION 19: RISKS & MITIGATIONS

19.1 RISK REGISTER
────────────────────

────────────────────────────────────────────────────────────────────────────────
RISK 01: LCNN Model Accuracy Degradation in Production
────────────────────────────────────────────────────────────────────────────────
Description:  LCNN achieves 7.07% EER on ASVspoof 2019 LA test set. Real-world
              audio (different recording conditions, new codecs, compressed audio
              from messaging apps) may have significantly higher EER.
Likelihood:   HIGH (this is a known challenge in deepfake detection)
Impact:       HIGH (false verdicts damage user trust and platform credibility)
Mitigation:
  1. Surface confidence score prominently; "uncertain" verdict for borderline cases
  2. Store model_version per scan result to enable retrospective analysis
  3. Implement feedback mechanism where users can flag incorrect verdicts
     (already designed in Batch 01 as the feedback module)
  4. Collect aggregated verdict statistics for monitoring distribution drift
  5. Plan for model update pipeline in v2 (A/B test new model on subset of users)
Residual Risk: MEDIUM

────────────────────────────────────────────────────────────────────────────────
RISK 02: Inference Worker Overload
────────────────────────────────────────────────────────────────────────────────
Description:  During viral traffic spike, inference queue could grow faster than
              workers can process, causing scan wait times to exceed 10 seconds.
Likelihood:   MEDIUM (viral scenarios are unpredictable)
Impact:       MEDIUM (scans still complete; users just wait longer)
Mitigation:
  1. Return estimated_wait_seconds in scan submission response (based on queue depth)
  2. Frontend polls with exponential backoff and displays progress indication
  3. Alert at queue depth > 20 (Section 13.4) to trigger scaling
  4. Horizontal scaling path is defined and low-complexity (Section 16.2)
  5. Rate limiting bounds worst-case queue growth
Residual Risk: LOW

────────────────────────────────────────────────────────────────────────────────
RISK 03: Malicious File Upload Bypass
────────────────────────────────────────────────────────────────────────────────
Description:  Attacker uploads a file that passes magic bytes check but contains
              exploit payload targeting audio parsing libraries.
Likelihood:   LOW-MEDIUM (requires zero-day in librosa/soundfile)
Impact:       HIGH (remote code execution potential)
Mitigation:
  1. Magic bytes validation before any parsing
  2. Audio processing in Celery worker (separate process from API server;
     limits blast radius)
  3. Keep librosa, soundfile, torchaudio pinned and audited
  4. File processing does not have network access (worker network policy)
  5. Duration extraction uses lightweight header parsing, not full decode
  6. Consider running audio processing in a minimal container (v2)
Residual Risk: LOW-MEDIUM

────────────────────────────────────────────────────────────────────────────────
RISK 04: JWT Secret Compromise
────────────────────────────────────────────────────────────────────────────────
Description:  If JWT_SECRET is leaked, attacker can forge JWTs for any user_id
              including admins.
Likelihood:   LOW (secrets in env vars; limited access to production)
Impact:       CRITICAL (full platform compromise)
Mitigation:
  1. JWT_SECRET loaded from secrets manager, not hardcoded
  2. Minimum 256-bit random secret enforced at startup
  3. Secret rotation procedure documented and tested
  4. Access tokens are short-lived (15 min); compromised secret window is limited
  5. Add JTI (JWT ID) claim for future revocation capability if needed
Residual Risk: LOW (with proper secret management)

────────────────────────────────────────────────────────────────────────────────
RISK 05: Database Corruption or Data Loss
────────────────────────────────────────────────────────────────────────────────
Description:  Hardware failure or catastrophic bug could corrupt PostgreSQL data.
Likelihood:   LOW (managed PostgreSQL services have redundancy)
Impact:       HIGH (scan history loss; user account loss)
Mitigation:
  1. Daily automated backups with point-in-time recovery (PITR)
  2. Backup restoration tested quarterly
  3. WAL archiving for PITR enabled
  4. Soft delete (30-day recovery) protects against accidental user deletions
Residual Risk: LOW

────────────────────────────────────────────────────────────────────────────────
RISK 06: Redis Data Loss (Session Invalidation)
────────────────────────────────────────────────────────────────────────────────
Description:  Redis restart or crash clears all session data, rate limit counters,
              and scan status cache. All users are effectively logged out.
Likelihood:   LOW (Redis is usually stable; AOF/RDB persistence reduces risk)
Impact:       MEDIUM (user inconvenience; brief service disruption; not data loss)
Mitigation:
  1. Redis AOF persistence enabled (appendonly yes)
  2. Redis fsync: everysec (acceptable durability for session data)
  3. After Redis restart: users re-login (access token in cookie revalidates via
     refresh token; most users don't notice)
  4. Rate limit counters reset: brief window where rate limits are not enforced.
     This is acceptable (brief window, not a security vulnerability).
  5. Scan status cache: misses fall back to DB query (graceful degradation)
Residual Risk: LOW

────────────────────────────────────────────────────────────────────────────────
RISK 07: Email Deliverability Issues
────────────────────────────────────────────────────────────────────────────────
Description:  Verification emails going to spam, or SMTP provider outage, blocks
              new user registrations (email must be verified before login).
Likelihood:   MEDIUM (email deliverability is notoriously unreliable)
Impact:       MEDIUM (new users blocked; existing users unaffected)
Mitigation:
  1. Use reputable transactional email provider (SendGrid, AWS SES, Postmark)
  2. Implement "resend verification email" endpoint
  3. Email task retries: 3 attempts with exponential backoff
  4. Monitor email bounce rate and delivery rate
  5. SPF, DKIM, DMARC records configured on sending domain
Residual Risk: LOW-MEDIUM

────────────────────────────────────────────────────────────────────────────────
RISK 08: Rate Limit Bypass via IP Spoofing
────────────────────────────────────────────────────────────────────────────────
Description:  Attacker spoofs X-Forwarded-For header to present different IPs
              and bypass IP-based rate limiting.
Likelihood:   MEDIUM (X-Forwarded-For is controllable by the client if Nginx
              is misconfigured or not trusted)
Impact:       MEDIUM (allows unlimited scan submissions from single actor)
Mitigation:
  1. Nginx configured to set X-Forwarded-For from real client IP (overwrite,
     not append, if coming from untrusted upstream)
  2. For authenticated users: rate limiting is by user_id (not IP), making
     IP spoofing irrelevant for the per-day scan limit
  3. Guest rate limiting by IP is inherently easier to bypass; acceptable because
     guest scan results are ephemeral and the product is designed for registered users
  4. Nginx connection-level rate limiting as first defense
Residual Risk: MEDIUM (accepted for v1)

20.2 CRITICAL PATH ITEMS
──────────────────────────

  These items have dependencies that must not be underestimated:

  LCNN Integration (Phase 2):
    The model integration is the highest-risk technical item. Run a spike in
    Week 1 to confirm: model loads correctly, inference returns expected output
    format, Grad-CAM hooks work on the specific LCNN architecture. Do not wait
    until Phase 2 to discover a model integration surprise.

  Magic Bytes Validation (Phase 2):
    Write and test this before writing any other file handling code. It is the
    most security-critical file processing step.

  Blocking Sync IO in Async (Ongoing):
    Establish the asyncio.run_in_executor() pattern for bcrypt and file I/O in
    Phase 1. If not established early, async anti-patterns will proliferate and
    be expensive to fix.

  Celery + Redis local setup (Phase 2):
    Get Docker Compose running with Redis + Celery before writing task code.
    Task development without a working broker wastes time.

20.4 THINGS TO AVOID
──────────────────────

  DO NOT do these things regardless of how convenient they seem:

  1. DO NOT store audio files permanently anywhere. Not even "temporarily in S3."
     The product guarantee is: audio is never stored. Period.

  2. DO NOT call inference functions directly from API routes. The inference must
     go through Celery. This is non-negotiable for latency and scalability.

  3. DO NOT put JWT tokens in the response body for the frontend to store in
     localStorage. HttpOnly cookies only.

  4. DO NOT use wildcard CORS. Even in development, use explicit localhost origin.

  5. DO NOT build the admin panel before Phase 5. It is the lowest priority.
     An engineer spending time on admin views in Phase 2 is stealing time from
     the inference pipeline.

  6. DO NOT skip the magic bytes check because "we validate MIME type." MIME
     types are trivially forged by the client.

  7. DO NOT run the LCNN model in the API server process. It blocks the event
     loop and prevents other requests from being served.

  8. DO NOT commit to WebSockets for scan status in v1. Polling is specified
     in Batch 03 and is sufficient. WebSockets add operational complexity for
     negligible UX improvement at v1 scale.

  9. DO NOT hardcode the model path, model checksum, or any other configuration
     in source code. Everything goes in environment variables.

 10. DO NOT use the same secret values for development and production. Ever.
