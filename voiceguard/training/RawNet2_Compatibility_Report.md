# RawNet2 Compatibility Report

What exactly must change to get a *trained* RawNet2 checkpoint serving through VoiceGuard's real inference pipeline. No changes have been made — this is a classification only, verified by reading `api/inference/adapters/base.py`, `api/inference/adapters/registry.py`, `api/inference/adapters/lcnn_adapter.py`, `api/inference/feature_extraction.py`, `api/inference/model_registry.py`, `api/inference/models.py`, `docker-compose.yml`, both Dockerfiles, and `pyproject.toml`.

## Classification

| Component | Change required | Detail |
|---|---|---|
| Feature extractor | **Small code change** | No raw-waveform extractor is registered (only `("logmel","v1")` and `("logmel64db","v1")` exist in `api/inference/feature_extraction.py`). Needs one new function, e.g. `@register_extractor("raw", "v1")`, returning the already-preprocessed waveform as `ExtractedFeature(name="raw", version="v1", tensor=waveform, ...)` — no new transform logic needed, since the waveform VoiceGuard's serving pipeline already produces (see Phase 3 below) is exactly RawNet2's expected input. The module's own docstring already anticipates this exact case ("Adding MFCC / raw spectral / temporal / embedding extractors later means writing one function..."). |
| Model adapter | **Small code change** | No `RawNet2Adapter` exists (only `LCNNAdapter`, `AudioCNNAdapter` are registered). Needs one new file, `api/inference/adapters/rawnet2_adapter.py`, implementing `ModelAdapter`'s 5 abstract methods (`architecture`, `load_model`, `feature_extractor`, `predict`, `convert_prediction`, `metadata`) — directly mirroring `lcnn_adapter.py`'s ~80 lines. `preprocess()` and `supports_explainability()` can use the base class's defaults (no-op passthrough, `False`) unless explainability for RawNet2 is wanted later. |
| Adapter registration wiring | **Small code change** | One import line added to `_ensure_builtin_adapters_registered()` in `api/inference/adapters/registry.py` (currently imports `audio_cnn_adapter, lcnn_adapter`). |
| Model registry / DB row | **Configuration only** | `register_model_version(db, architecture="RawNet2", name=..., version=..., checkpoint_path=...)` — an existing, already-generic function (explicitly built for "every model other than the bootstrap LCNN" per its own docstring). No schema change: `ModelVersion.architecture` is a plain `String(64)` column, no enum constraint. New rows default to `status="inactive"` — activating requires the separate, deliberate `switch_active_model()` call, so registering never silently changes what's serving. |
| `api.inference.model_loader`, `api.inference.jobs`, `api.inference.confidence`, the API router, the frontend | **No change required** | Verified: none of these import any concrete adapter or branch on architecture name — that's the entire point of the adapter/registry plugin design already in place (`api/inference/adapters/base.py`'s own docstring states this explicitly, and `get_adapter()`/`register_model_version()` are already architecture-agnostic). |
| Docker / dependencies | **No change required** | RawNet2 imports only `torch`, `torch.nn`, `torch.nn.functional`, `numpy` — all already in `requirements.txt` and `api/requirements-ml.txt`, already installed in both `Dockerfile` and `api/Dockerfile.ml`. No new system packages (ffmpeg is already there for the shared audio-loading path, unrelated to RawNet2 itself). |
| Checkpoint mounting | **No change required** | `docker-compose.yml` mounts the entire `./checkpoints:/app/checkpoints:ro` directory — a `checkpoints/rawnet2/best.pt` (or `checkpoints/experiments/rawnet2_.../best.pt`) is automatically visible in the container with no compose edit. |
| Packaging | **No change required** | `pyproject.toml`'s `[tool.setuptools.packages.find]` already includes `src*`, which covers `src.models.rawnet2` the same way it covers `src.models.lcnn`. |
| Database schema / migrations | **No change required** | Confirmed via `api/inference/models.py`: `architecture` is `sa.String(64)`, not an enum — no Alembic migration needed to add a new architecture value. |

## Bottom line

**No large architectural change is required anywhere in VoiceGuard to serve a trained RawNet2 checkpoint.** The plugin-style adapter/registry/extractor design already in this codebase was built for exactly this scenario. The entire integration surface is two small new files (one adapter class, one extractor function) plus one import line and one data-registration call — contingent on a trained checkpoint existing, which it currently does not (see `RawNet2_Readiness_Report.md` §2).
